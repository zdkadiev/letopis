# Engram 2.0 — ключевые сценарии

Актуальное решение: пользователь сохранил прежнее асинхронное индексирование. Apply надёжно фиксирует документы и необходимое служебное состояние, включая задание обновления. Графовый, текстовый и векторный индексы обновляются после этого и публикуются вместе, только после готовности необходимых embeddings. Ошибка обновления сохраняет последний корректный индекс и не откатывает завершённую правку документов. Эти две границы описаны в [модели хранения](Engram_2_Storage_Model_RU.md). Физическая реализация и аварийная проверка ещё предстоят.

Статус: сценарии уточняются последовательно по обсуждению. Основания: [требования](Engram_2_Requirements_RU.md) и [доменная модель](Engram_2_Domain_Model_RU.md). Названия действий ниже описывают поведение и не фиксируют грамматику CLI или JSON-схемы.

## Область изменения документов

Согласовано: Engram записывает изменения только в специально размеченные Markdown-документы корпуса. Существующий файл должен входить в корпус до правки. Запрос на изменение обычного Markdown-документа, исходного кода либо другого внешнего источника отклоняет всю группу без записи файлов. Проверка base_hash не заменяет эту границу. Обычный файл нельзя включить в корпус добавлением разметки через такую правку.

При откате незавершённой разрешённой правки восстанавливаются документы корпуса; откат не расширяет область записи на посторонние документы. Ранее согласованный create по отсутствующему пути создаёт сразу размеченный Markdown-документ после общей проверки. Служебная БД и Git-снимки сохраняют прежние роли.

## Сценарий 1. Поиск знаний по новой задаче

**Участники:** агент и Engram. Агент формулирует поисковый запрос по своей задаче; документы корпуса размечены в согласованном формате.

**Основной поток:**

1. Агент отправляет поисковый запрос через CLI, при необходимости с фильтрами по метаданным.
2. Если корректная версия индекса доступна, Engram выполняет гибридный поиск по согласованной графовой, текстовой и векторной версии.
3. Если корректной версии ещё нет, CLI автоматически запускает построение индекса и ждёт его готовности. До публикации проверяются разметка и целостность метаграфа и вычисляются все необходимые embeddings.
4. После готовности Engram выполняет поиск и возвращает результат в JSON: ссылки с ID элементов, файлами, диапазонами строк проиндексированной версии, ревизиями и пометками устаревания. Содержимое документов и выдержки не возвращаются.
5. Агент самостоятельно читает текущие документы и перепроверяет знания, для которых это требуется.

**Альтернативные потоки:**

- Корректная предыдущая версия существует, но обновление ещё идёт или завершилось ошибкой: поиск продолжает использовать последнюю корректную версию. Ошибка обновления доступна агенту.
- Обновление источника знания изменило его хеш либо указанный фрагмент кода больше не найден: знание по умолчанию остаётся в выдаче с пометкой о необходимости перепроверки и соответствующей причиной.
- Найденный в старом индексе элемент уже удалён из текущего корпуса документов: он исключается из поисковой выдачи.
- Агент отменяет длительный поиск или построение: незавершённый новый индекс не становится активным; последняя корректная версия, если она была, сохраняется.
- Первое построение завершается ошибкой и корректной версии нет: поиск не может обслуживаться по готовому индексу; CLI сообщает об ошибке в JSON.

**Результат:** агент получает адреса релевантных знаний и сведения, необходимые для их самостоятельного чтения и проверки.

**Ограничения:** одна секунда — цель оптимизации, а не отсечка. Первое построение может занимать больше времени; по выбранному правилу поиск ждёт готовности. Постоянное фоновое наблюдение не требуется: изменения обнаруживаются при CLI. Координация одновременных запросов и внутреннее устройство ожидания проектируются далее.

## Сценарий 2. Обход связанных знаний

**Участники:** агент и Engram. Агент выбирает исходное знание и нужные связи для получения дополнительного контекста.

**Согласованный поток:**

1. Агент выбирает режим `relations` для обычных связей, `containment` для включённости или `both` для единого обхода по обоим видам связей, задаёт глубину, лимит результатов и направление обхода: исходящие, входящие либо оба направления. Для обхода обычных связей агент также выбирает их типы.
2. Engram выполняет обход по согласованной корректной версии графового индекса.
3. Агент получает ссылки на связанные знания с метаданными адресации и устаревания и самостоятельно читает текущие документы.

Например, входящий обход по `includes` находит метавершины, непосредственно содержащие исходный элемент. Направление обхода не меняет логическое направление самих рёбер.

В `relations` глубина измеряется числом пройденных обычных рёбер, без `includes`. В `containment` глубина измеряется уровнями включённости; один переход по `includes` соответствует одному уровню. При исходящем обходе включённости глубина 2 охватывает непосредственные элементы и содержимое вложенных метавершин на следующем уровне.

В `both` обычные связи и `includes` могут чередоваться в одном пути. Каждый переход считается одним шагом общей глубины: путь `M —includes→ A —depends_on→ B` достигает `B` при глубине 2.

Агент может опционально включить в `edges` только фактически пройденные рёбра в пределах отдельного лимита: их ID, тип, источник и назначение. В `relations` это обычные связи, в `containment` — `includes`, в `both` — оба вида. Базовые структуры входа и выхода `traverse` согласованы; подробные правила проверки значений ещё будут уточнены.

Рёбра запрашиваются необязательным положительным `edge_limit`. Без него поле `edges` опускается; с ним возвращается массив в пределах лимита, в том числе пустой при отсутствии пройденных рёбер. Отдельный переключатель возврата рёбер не требуется.

Возвращаемые вершины и метавершины ограничиваются одним общим лимитом; опционально возвращаемые рёбра — отдельным лимитом. В `elements` возвращаются только найденные при обходе элементы, каждый один раз. Начальные `element_ids` исключаются из результата и не расходуют лимит.

## Сценарий 3. Подготовка и применение групповой правки

**Участники:** агент и Engram. Агент подготавливает изменения знаний; только CLI применяет их к каноническим документам.

**Согласованная основа потока:**

1. Агент читает актуальные документы и подготавливает изменения Markdown. Для редактирования вершины или метавершины указывает её ID, `base_hash` всего текущего фрагмента и полный новый Markdown-фрагмент с тем же ID. Старый фрагмент заменяется целиком, включая ссылки. Изменение другого элемента в том же файле само по себе конфликта не вызывает; при сохранении чужие изменения сохраняются. Для создания в существующем файле проверяется `base_hash` всего файла. Опционально агент указывает ожидаемые хеши неизменяемых элементов, на которых основана правка.
2. При необходимости агент передаёт JSON правки в `engram apply --check` и получает ошибки и список затрагиваемых файлов и элементов. Канонические документы не изменяются. Для сохранения используется `engram apply` с тем же JSON.
3. Для применения CLI проверяет ожидаемые хеши изменяемых элементов и явно указанного контекста по актуальным документам и валидирует разметку, идентификаторы, ссылки и правила метаграфа. Предыдущая проверка без сохранения не заменяет проверки при применении.
4. При конфликте устаревшая групповая правка отклоняется целиком. Агент перечитывает актуальное состояние и подготавливает новую правку.
5. Корректная правка применяется атомарно; агент получает результат в JSON. Обновление индекса выполняется асинхронно, и новая согласованная версия публикуется только после проверки и готовности необходимых embeddings. Git-коммит остаётся отдельной операцией.

Перенос описания с прежним ID и исправление путей в ссылках агент подготавливает как обычную общую правку. При полном удалении он явно удаляет или переназначает ссылки на элемент. CLI проверяет подготовленные изменения.

Несовпадение любого явно указанного хеша контекста отклоняет всю правку, даже если этот элемент не изменяется операцией. Получение хешей при чтении и обработка повторения и сбоя уточняются далее. Способ защищённого сохранения файлов ещё не выбран.

Для получения актуальных хешей и расположений принят пакетный запрос `inspect` со списком ID и общим Git-снимком. Для одного элемента передаётся список из одного ID. Все возвращённые координаты и хеши относятся к одному завершённому каноническому состоянию.

## Сценарий 4. Потеря ответа и проверка состояния

**Ситуация:** агент не получил ответ apply и не знает, была ли правка сохранена. Бессрочное распознавание завершённых операций по хешу больше не применяется.

**Согласованный поток:**

1. Агент читает актуальные документы и метаданные через inspect. Если после сбоя есть незавершённая запись, Engram сначала завершает восстановление; чтение и новые правки ждут его.
2. Агент сравнивает актуальное состояние с желаемым. Если цель уже достигнута, повторная запись не нужна. Для создания он при необходимости читает затронутые файлы и узнаёт назначенные UUID.
3. Если нужны изменения, агент готовит правку по актуальным base_hash. Новый apply проходит обычные проверки, даже если его JSON и хеш совпадают с прежним запросом.

Возврат исходного успешного ответа и прежней карты tmp-ID/UUID после потери ответа больше не гарантируется. Неизвестный исход не считается неуспехом автоматически; конфликт сам по себе не доказывает успех прежнего вызова. Повторная доставка внутри ещё выполняющегося вызова не должна создавать дополнительное выполнение; конкретный внутренний протокол ещё проектируется.

Хеш SHA-256(JCS(исходный JSON)) остаётся отпечатком содержимого. Новый ID операции, timestamp или поле ID агента этим решением не вводятся. Атомарность и восстановление сохраняются.

## Сценарий 5. Сбой записи и восстановление

**Ситуация:** групповая правка не завершена, а процесс CLI прервался либо компьютер внезапно выключился.

**Требуемый результат:**

- Восстановление откатывает всю незавершённую правку к прежнему состоянию, а не оставляет часть файлов в новом состоянии.
- Данные для отката должны переживать сбой процесса и внезапное выключение компьютера.
- Агент получает информацию об ошибке операции. По дополнительному требованию status показывает, какая атомарная правка не была применена, включая полный откат после сбоя; диагностическая запись переживает очистку записи восстановления. Если восстановление ещё не завершено, нельзя сообщать о полном откате.
- Незавершённая новая версия индекса не заменяет последнюю корректную.

**Порядок запуска:** при следующем вызове CLI восстановление запускается автоматически. Поиск и новые правки ждут его завершения.

**Граница завершения:** После надёжного сохранения всей группы документов финальная транзакция БД сохраняет необходимые служебные изменения и задание индексирования и удаляет запись восстановления. Надёжная фиксация этой транзакции означает завершение правки; отдельное поле состояния в записи восстановления не требуется. Сбой до отправки ответа не откатывает завершённую правку. Если ответ потерян, агент перечитывает актуальные документы и метаданные; первоначальный JSON-результат и карта временных ID не обещаются при отдельном повторном вызове.

После сбоя наличие записи восстановления требует полного отката; после надёжно завершённого отката запись удаляется, а диагностика неприменённой правки сохраняется независимо. Если прервался откат, запись остаётся для следующего восстановления. Физический порядок долговечной записи ещё проектируется; выбранная логическая граница не подтверждает готовность реализации.

Согласовано: восстановитель определяет незавершённую правку по оставшейся записи журнала и восстанавливает её файлы по прежнему Git-снимку. Корректная разметка текущего повреждённого или недописанного файла не является предпосылкой отката. Область восстановления задаётся записью правки, проверенной до начала изменения документов; это не разрешает запись в посторонние файлы. Для существовавшего документа прежнее содержимое восстанавливается целиком, без попытки угадать по текущему тексту, какая часть была записана. Для документа, созданного незавершённой правкой, отсутствие пути в прежнем снимке означает удаление созданного файла.

Для отката выбран служебный Git-снимок состояния перед правкой без создания коммита, включая ещё не закоммиченные изменения. В БД Engram хранится служебная запись восстановления со ссылкой на снимок; её наличие отражает незавершённость правки. Рабочая ветка и подготовленные к коммиту изменения сохраняются. Долговечность данных снимка и записи журнала до изменения канонических файлов и удержание используемых объектов ещё требуют детального проектирования и проверки.

## Сценарий 6. Реиндексирование и публикация

**Участники:** агент и Engram. Обновление запускается явно через CLI либо автоматически после изменений документов, включая Git-изменения.

**Согласованный поток:**

1. Запускается полная перестройка либо выборочное обновление файлов или элементов. Для явного `reindex` агент передаёт `{}` либо списки `paths` и/или `element_ids`; при совместном указании списков обновляется их объединение.
2. Управление документами предоставляет служебный Git-снимок текущего корпуса без создания коммита. По его неизменяемому содержимому индексатор готовит новую версию, проверяя разметку и целостность графа и вычисляя необходимые embeddings. В БД сохраняется ссылка на снимок.
3. До готовности новой версии поиск обслуживается последней корректной версией, если она существует.
4. Новая версия публикуется целиком: графовая, текстовая и векторная проекции становятся доступными согласованно после готовности всех необходимых embeddings.
5. При ошибке или отмене незавершённая версия не публикуется, последняя корректная сохраняется. Состояние, прогресс и ошибки доступны через CLI в JSON.

Явный вызов `reindex` ждёт успешной публикации версии по своему снимку и возвращает `result.revision`; при ошибке возвращается общий JSON-ответ ошибки. Автоматические обновления выполняются асинхронно.

Для отмены связанной с явным вызовом перестройки используется `SIGINT`. Фоновую общую перестройку проекта агент отменяет через `engram reindex --cancel` с входом `{}`: вызов ждёт её остановки и возвращает ревизию сохранённого корректного индекса. Общий рабочий процесс и независимые поисковые запросы продолжают работу.

В запросе состояния `completed` показывает процент выполнения текущего этапа перестройки от 0 до 100. При смене этапа процент относится уже к новому этапу.

Если во время построения поступают новые завершённые правки, готовая согласованная версия публикуется, а эти правки учитываются следующим обновлением. Построение не отменяется и не начинается заново только из-за их появления.

Неудачное вычисление embeddings может повторяться автоматически без новой команды агента с настраиваемым пределом числа попыток. После его исчерпания Engram сообщает об ошибке обновления и сохраняет последний корректный индекс. До готовности всех необходимых embeddings версия не публикуется. Значение предела, задержки и классификация ошибок ещё выбираются.

Ссылка на Git-снимок и состояние задания долговечно сохраняются в БД. Если задание прервано сбоем процесса, после следующего запуска и восстановления документов координатор автоматически повторяет его по тому же снимку, сохраняя использованные попытки и предел ретраев. Новые изменения корпуса обрабатываются следующим обновлением. Явная отмена или исчерпание предела ретраев не считается основанием для автоматического перезапуска по этому правилу.

Git-изменения обнаруживаются, а обновление запускается при вызове CLI. Постоянное фоновое наблюдение не требуется; само обновление остаётся асинхронным. Алгоритм сверки, жизненный цикл выполнения и протокол публикации ещё проектируются.

## Сценарий 7. Git-изменения общей рабочей копии

**Ситуация:** переключение ветки, откат или другая Git-операция изменила Markdown-документы знаний. Используется одна общая рабочая копия.

**Согласованный поток:**

1. При следующем вызове CLI Engram автоматически обнаруживает изменения; постоянное фоновое наблюдение не требуется.
2. Изменившиеся файлы сверяются, проверяются разметка, целостность межэлементных ссылок и отсутствие циклической включённости.
3. Запускается обновление индекса. При наличии последней корректной версии поиск продолжает работать по ней; новый индекс публикуется только после проверки и готовности всех необходимых embeddings.
4. При ошибке обновления сохраняется последняя корректная версия, агент получает диагностику.

Восстановление того же элемента через Git сохраняет его прежний ID. Удалённый из текущего корпуса элемент исключается из поисковой выдачи, даже если остаётся в старом индексе.

**Условие гарантий записи:** Git остаётся внешним инструментом. Его операции, меняющие корпус, не пересекаются с незавершёнными правками CLI и восстановлением. Обратное правило также действует: CLI не сохраняет правки и не восстанавливает файлы во время Git-изменений. Протокол соблюдения этого условия ещё проектируется.

## Сценарий 8. Изменение источника и перепроверка знания

**Участники:** агент и Engram. Знание имеет одну или несколько привязок к источникам с проверенными ревизиями и хешами, а также историю прежних привязок.

**Согласованный поток:**

1. Engram сопоставляет сохранённый и текущий хеши источника. Хешируется указанный фрагмент либо весь документ, если источником указан документ целиком.
2. При несовпадении хешей вычисляется пометка «требует перепроверки»; знание и прежняя привязка сохраняются. Если указанный фрагмент кода удалён, причиной является «источник не найден».
3. Знание остаётся доступным в поиске с явной пометкой. Агент читает актуальный источник и выполняет смысловую проверку.
4. Если знание подтверждено, агент через CLI обновляет проверенную ревизию и хеш источника в том же элементе. Его ID сохраняется; прежние привязки остаются в истории.
5. При дальнейшей проверке актуальности используются текущие подтверждённые привязки; исторические записи не считаются текущими зависимостями.

Противоречащие утверждения представлены отдельными элементами с разными ID и ребром противоречия. Автоматическая смысловая проверка системой не установлена.

Адресация внешних фрагментов, обнаружение изменений источников и обработка временной недоступности уточняются при проектировании контрактов и архитектуры. Эти сценарии фиксируют наблюдаемое поведение, а не готовую реализацию.

## Актуальность ссылок и недоступный источник

Согласовано: результаты `search` и `traverse` содержат один массив `flags` с признаками `stale`, `source_changed` и `source_not_found` вместо отдельных булевых полей и списка причин. Признаки могут сочетаться; без обнаруженных причин список пуст. Агент читает актуальное содержимое по ссылкам и самостоятельно выполняет смысловую перепроверку. `inspect` для известного внешнего источника с сохранёнными ссылками возвращает адрес даже при исчезновении файла: недоступные текущие хеши равны `null`, старые хеши не подставляются.

## Обход недоступного источника и ожидание индекса

Известные недоступные внешние источники сохраняются в графе и возвращаются через `traverse` с `source_not_found` в `flags`. Если индекс ещё описывает существовавший источник, добавляется `stale`; после публикации состояния отсутствия этот признак снимается. Отсутствие такого источника само по себе не блокирует публикацию корректного индекса с готовыми необходимыми embeddings. Новая внешняя привязка по-прежнему требует доступного файла и фрагмента.

Явный `reindex` присоединяется к уже выполняющемуся заданию, только если совпадает согласованный Git-снимок и задание покрывает всю запрошенную область. Вызов ждёт его фактического результата: публикации с `result.revision`, ошибки или отмены. Иначе планируется задание для снимка явного вызова; одного совпадения пути недостаточно.

## Чтение сохранённой идентичности и Git-снимка

`inspect` разрешён по сохранённому ID внешнего источника даже без текущих графовых ссылок. Ответ возвращает актуальные метаданные адресованного источника или `null` для недоступных хешей; чтение не добавляет вершину и рёбра в активный граф. Неизвестный ID по-прежнему вызывает `not_found` для всего пакета.

Поле `snapshot` содержит полный OID объекта Git tree в репозитории проекта. Это неизменяемый снимок файлов без создания коммита; агент читает его стандартными средствами Git по адресу `<tree_oid>:<path>` и передаёт тот же OID в `edit.snapshot`. Формат OID определяется Git-репозиторием и не подменяет SHA-256 содержимого. Состав общего снимка согласован: корпус знаний и нужные источники. Бессрочное удержание средствами Git в первой версии согласовано. Способ построения и долговечная фиксация ещё проектируются. Ревизия источника выбирается по совпадению адресованного содержимого с `HEAD`, иначе используется OID снимка.

## Состав снимка и жизненный цикл индекса

Согласованный общий Git-снимок содержит весь корпус знаний и целые доступные файлы источников, на которые ссылаются текущие знания. Если `inspect` явно запрашивает источник без текущих ссылок, его доступный файл также включается. Пути сохраняются относительно корня репозитория; недоступный файл отсутствует в дереве, его адрес остаётся в реестре. Посторонние файлы проекта и служебная БД в снимок не входят. Ответ `inspect` перечисляет только запрошенные элементы. В первой версии выданные и используемые снимки удерживаются бессрочно средствами Git; Engram сохраняет OID и обеспечивает закрепление через Git-адаптер.

Постоянная история версий индекса в первой версии не хранится: индекс остаётся производным и перестраиваемым. Последний корректный индекс обслуживает запросы до публикации нового; предшествующие опубликованные данные сохраняются только до завершения запросов, закрепивших их, затем освобождаются. Это не задаёт срок хранения Git-снимков документов.

## Ответственность Git за сохранность снимков

В первой версии выданные через `inspect` и используемые для операций, индексирования и истории источников Git-снимки удерживаются бессрочно. За хранение содержимого, Git-объектов и их штатное обслуживание отвечает Git. Engram через Git-адаптер создаёт и закрепляет необходимые снимки служебными Git-ссылками, сохраняет OID и состояние операций; собственное хранение копий текста или управление версиями содержимого вне Git не вводится. Порядок долговечной фиксации объектов, refs и БД ещё требует проектирования и проверки. Постоянная история версий индекса этим решением не создаётся.

## Недоступный снимок и ревизия привязки

Синтаксически допустимый полный OID в `edit.snapshot`, отсутствующий в Git-хранилище проекта, вызывает `not_found` и отклонение всей правки. Неверный формат или существующий объект другого типа вызывают `invalid_request`. Каждый новый вызов проверяет доступность snapshot; прежний успех по совпадению хеша не возвращается.

При первоначальной фиксации или явном подтверждении внешней привязки её ревизией становится полный OID текущего коммита `HEAD`, если адресованный фрагмент побайтно совпадает с тем же путём и диапазоном в этом коммите. Для ссылки на весь файл сравнивается весь файл. При отсутствии совпадения, файла, диапазона или `HEAD` сохраняется OID Git-снимка проверенного содержимого. Коммит выбирается на момент сохранения привязки; реиндексирование не заменяет прежнюю ревизию новым `HEAD`. `filters.source_revisions` точно сравнивает сохранённое значение в той же привязке, что и заданный источник.

## Определение проекта и корпуса

Корень проекта определяется по Git-рабочей копии, содержащей текущий каталог вызова CLI. Вызовы из вложенных папок используют тот же проект; пути запросов, ссылок и результатов остаются относительными корню. Дополнительного поля проекта или параметра корня в первой версии нет. Вне Git-рабочей копии возвращается `not_found`.

Корпус определяется по разметке: файлы `.md` и `.markdown` рабочей копии с маркерами Engram вне блоков кода входят в область проверки и индексирования. Обычные Markdown-файлы без маркеров могут быть внешними источниками. `.git` и служебная директория Engram исключаются. Некорректный маркер вне блока кода вызывает ошибку разметки; файл не исключается молча. Папка корпуса и отдельный список файлов не требуются.

## Поисковое представление и повторное использование векторов

Поиск использует одно детерминированное представление собственного текста вершины или метавершины: служебные блоки Engram и графовые метаданные удаляются, от ссылок остаются подписи, кодовые примеры сохраняются. Содержимое связанных и вложенных элементов не подгружается в этот текст. Он временно используется текстовым индексом и embedding-адаптером; копия текста документа в БД не сохраняется. `base_hash` по-прежнему вычисляется по полному исходному Markdown.

Embedding из доступного корректного индекса повторно используется при совпадении SHA-256 подготовленного поискового текста и идентичности адаптера, версии модели и влияющих на вектор параметров. Изменение текста или конфигурации требует вычисления. Ключ не ограничивается UUID или байтовым хешем исходного Markdown. Постоянный архив прежних векторов не вводится: ненужные данные освобождаются вместе с индексами после завершения читателей. Схема внутренних входа и выхода порта использует `texts` и соответствующий массив `vectors`; размерность задаёт модель.

Бессрочная дедупликация завершённых вызовов apply отменена; после потери ответа агент перечитывает состояние, новый вызов проходит обычные проверки. Хеш правки остаётся отпечатком исходного запроса, а не уникальным ID каждого выполнения. Атомарность, восстановление и история оснований знаний сохраняются. Запись восстановления удаляется после надёжного завершения правки или полного отката; история и диагностика имеют собственные правила хранения.
