## Зачем и что получится

Нужен небольшой продуктовый адаптер в существующем library crate letopis: сохранить неизменяемый набор файлов в Git, удержать его от штатного GC и прочитать прежние байты даже после изменения/удаления live-файла. Снимок — полный OID объекта **tree**, а не commit или SHA-256 содержимого letopis.

TK-8 предоставляет операции нижнего уровня. Будущий прикладной capture собирает весь размеченный корпус и целые доступные адресованные source-файлы, разбирает Markdown, разрешает element_ids и формирует InspectedElement по I-12. Это orchestration, SQL-публикация, flags, source-range сравнение и CLI остаются TK-10/TK-14/TK-21/TK-24. В TK-8 нет обхода всего проекта или автоматического добавления посторонних файлов.

Адаптер получает от вызывающего кода конечный набор root-relative путей и **уже захваченных исходных байтов** файлов. Он сохраняет ровно этот набор, независимо от HEAD и пользовательского index. Согласованность последующих чтений обеспечивается одним неизменяемым tree. Атомарного снимка живой файловой системы во время конкурентной правки не обещается: I-12 прямо допускает такую гонку при capture.

## Архитектура и инженерные решения автора

Продуктовые ограничения определены исходным дизайном. Разделение сервисов, адаптеров и интерфейсов дополнительно подтверждено пользователем 2026-10-22; конкретные имена модулей/типов ниже — инженерное предложение автора.

1. Сохранить один library crate. Объявить небольшой `GitSnapshotPort` на стороне приложения (`src/service/ports/`), реализацию разместить в `src/adapters/git/`. Чистый `src/domain/` не импортирует std::process, filesystem или Git. Использовать существующие RepoPath/TreeOid; не вводить публичный универсальный storage framework, registry или DI-контейнер.
2. Порту нужны три возможности: создать tree из переданных файлов; прочитать полный файл из указанного tree; проверить/удержать существующий tree. Конкретное именование, представление входного набора и разбиение маленьких файлов оставлены плану. Проверка существования/type может быть приватным общим примитивом адаптера.
3. Конструктор конкретного адаптера находит Git-корень из каталога вызова и проверяет версию. Вне рабочей копии — явная ошибка; bare repository не превращается в произвольную рабочую копию. Поддержка нескольких рабочих копий одного проекта не добавляется.
4. Только синхронный `std::process::Command`, argv/stdin; нет shell, async runtime, libgit2/gix или новых runtime-зависимостей. Test-only временные каталоги можно организовать существующим helper либо точно закреплённым dev-dependency, если он понадобится.
5. Для нового tree переданные обычные файлы представлены blob с mode 100644; executable bit для inspect/адресованных байтов не является метаданными контракта. Вложенные каталоги создаются bottom-up через mktree. Пустой набор создаёт пустой tree. Дубли путей и конфликт «файл a / потомок a/b» — ошибка целого входа, а не молчаливое перезаписывание.
6. Переданные пути валидируются до записи: корневые `.git` и `.letopis` и их потомки не включаются в снимок. Адаптер не читает live paths и не следует symlink; границу чтения рабочей копии обеспечивает будущий capture. Исторический blob читается как Git blob, без разыменования symlink в filesystem и без переключения на live file.

## Явное разделение сервисов и адаптеров

Пользователь подтвердил общий принцип: структура проекта модульная, с чёткими границами. У каждого модуля есть одна определённая ответственность и явный публичный контракт; внутренние helper-типы и детали реализации остаются закрытыми. Связи проходят через предусмотренные интерфейсы, без обхода чужого контракта через внутренние файлы/типы. При реализации и ревью проверяются реальные каталоги, видимость типов и направления импортов, а не только соответствие схемы названиям папок.

Пользователь уточнил: Storage, Service, Git, Embedding и остальные ответственности должны быть разделены и связаны интерфейсами; конкретные реализации сервисов и адаптеров — структуры. В Rust интерфейс выражается `trait`, реализация — `struct` с `impl Trait for Struct`. Это относится и к входной границе сервиса, и к выходным портам внешних систем.

Целевая раскладка одного crate (каталоги появляются по мере реализации соответствующих TK, без пустого каркаса всех будущих частей):

```text
src/
  domain/                  # сущности, значения и чистые правила
  service/
    api.rs                 # входные интерфейсы прикладных сервисов
    ports/                 # выходные интерфейсы Storage/Git/Embedding/документов
    documents.rs           # DocumentService, B-2
    indexing.rs            # IndexingService, B-3
    search.rs              # SearchService, B-4
    sources.rs             # SourceValidator, B-5
    state.rs               # StateService, B-6
  adapters/
    storage/               # структуры адаптеров SQLite/FTS/vec1
    git/                   # GitCliAdapter: GitSnapshotPort
    embedding/             # OllamaAdapter/OpenAiCompatibleAdapter: EmbeddingPort
    markdown/              # MarkdownAdapter поверх существующего parser TK-7
    filesystem/            # чтение файлов рабочей копии
  cli/                     # входной адаптер: argv/JSON -> интерфейс сервиса
  lib.rs                   # composition root: сборка и связывание компонентов
  main.rs                  # тонкая точка запуска: сборка из lib.rs + CLI
```

Направление вызова: CLI → интерфейс сервиса → структура сервиса → выходной порт → структура адаптера. Зависимости исходников направлены к домену и интерфейсам: service не импортирует конкретные адаптеры, adapter реализует принадлежащий service порт. Storage, Git и Embedding не вызывают друг друга напрямую. Сервисы получают нужные порты через конструктор; только точка сборки в `lib.rs` знает, какие конкретные структуры подключены. Пользователь явно уточнил место сборки: именно `lib.rs`, а `main.rs` остаётся тонким запуском CLI.

Разделение должно быть физическим: порт Git размещается в `service/ports/git.rs`, конкретный Git-адаптер — в `adapters/git/`; Storage, Embedding, Markdown и filesystem имеют собственные каталоги и файлы реализации по мере соответствующих TK. Бизнес-сценарии располагаются в файлах `service/`, а не в адаптерах или корневом файле. Одни декларации модулей в lib.rs не считаются связыванием.

`lib.rs` содержит небольшую явную сборку через обычные конструкторы: создать конкретные адаптеры, передать их как реализации портов структурам сервисов и вернуть публичную точку входа приложения. Имена функции сборки/возвращаемого типа уточняются в плане; service locator, registry и DI-framework не нужны. Корневой файл знает конкретные типы ради композиции; domain и service сохраняют зависимости только к чистой модели и контрактам. SQL, Git-команды, HTTP и бизнес-алгоритмы остаются в своих модулях.

Порты хранилища разделяются по нуждам сценария и владению write unit/read view, а не становятся одним универсальным интерфейсом со всеми операциями. Общий provider-neutral EmbeddingPort сохраняется для Ollama и совместимого API. Доменные типы не знают о SQL, Git-подпроцессе, HTTP или JSON CLI.

В TK-8 реально добавляются GitSnapshotPort в `service/ports/git.rs` и конкретный GitCliAdapter в `adapters/git/`, вместе с нужными типами результата/ошибок и явной сборкой доступного Git-компонента в `lib.rs`. Интеграционный тест использует эту публичную точку сборки и контракт порта. По мере появления сервисов та же сборка передаёт адаптеры их конструкторам; полнота будущих компонентов не имитируется заглушками. Заглушки будущих сервисов, Storage/Embedding-адаптеров, CLI и переупаковка parser TK-7 ради пустого интерфейса в эту задачу не входят. Их соответствующие задачи должны следовать указанному разделению. Публичный входной trait сервиса добавляется вместе с самим сервисом; отдельный бесполезный forwarding-сервис вокруг трёх Git-операций здесь не вводится.

## Поведение

### Создание дерева

- Каждый blob записывается `git hash-object -w --no-filters --stdin`; byte stream передаётся без UTF-8/EOL/clean-filter преобразований.
- Деревья строятся `git mktree -z` из непосредственных записей mode/type/OID/name с NUL-разделением, без `--missing`. Нельзя использовать пользовательский index, `git add`, `commit`, `checkout` или `reset`.
- Порядок входных файлов не влияет на OID; одинаковые пути/байты дают тот же OID в том же object format. SHA-1 и SHA-256 не сравниваются между собой как одинаковые OID.
- Успешное создание возвращает TreeOid, но ещё не означает удержание. Выдающий inspect обязан вызвать pin до ответа. Незакреплённые объекты после сбоя допустимы и могут быть удалены Git.

### Проверка и чтение

- Принимается только полный lowercase OID (40/64 hex); он должен соответствовать object format конкретного репозитория. Нельзя принимать сокращения, HEAD, ref, tag или выражения ревизий вместо snapshot.
- Корневой объект должен существовать и иметь **точный** type tree. Commit/tag не преобразуется в tree автоматически.
- Чтение использует дерево и root-relative путь. Лист должен быть blob; исходные bytes возвращаются без textconv/filters. Директория не является файлом. Никаких внешних fetch или загрузки отсутствующих объектов.
- Различаются неверный ввод/type (`invalid_request`), корректный отсутствующий корневой объект или путь (`not_found`) и сбой Git/I/O либо обнаруженное повреждение (`internal_error`). Отсутствующий дочерний объект, на который tree уже ссылается, — повреждение, а не отсутствующий пользовательский путь.
- Ошибка subprocess не превращается автоматически в not_found. Структурированный plumbing-ответ, например batch-check missing, используется для проверки отсутствия. Публичная диагностика не копирует произвольный stderr, bytes stdin или содержимое файлов; точное отображение во внешний JSON — TK-11.
- Повторное чтение S1 остаётся S1 после создания S2 или удаления live-файлов. Диапазоны строк вырезает приложение из полного blob, не Git-адаптер.

### Удержание

- Один namespace для inspect и принятых source_snapshot: `refs/letopis/snapshots/<full_oid>`. Происхождение снимка не требует отдельной таблицы, реестра или признака типа ref.
- Pin проверяет существование корневого tree и полноту достижимого tree/blob closure перед первым успешным удержанием. Подходящая plumbing-проверка closure выбирается в плане; полный аудит всех посторонних объектов репозитория на каждом чтении не требуется.
- Ref создаётся/обновляется средствами update-ref с предусловиями и без dereference пользовательской symbolic ref. Уже установленный прямой ref с тем же OID — идемпотентный успех. Чужое значение/symbolic ref в ожидаемом служебном имени или невозможность закрепить ref — явная ошибка; пользовательские refs/HEAD не меняются. Конкурентные повторы одного pin могут завершиться успехом только после проверки того же закреплённого OID; конфликт не замалчивается.
- Ref установлен **до** успешного возврата pin. Выданные снимки и однажды принятые основания не удаляются автоматически; удаления ref, TTL, background GC, snapshots before/after и tree на публикацию не добавляются.
- Вызовы записи задают per-command `core.fsync=all` и `core.fsyncMethod=fsync` по [R-8](../../zkit/letopis/research/R-8-durability-and-search-primitives.md), не переписывая config пользователя. Это настройки hardening, не доказательство физической сохранности. Минимум Git 2.29 относится к функциональной совместимости; отсутствие/различие поддержки этих настроек на старом Git не объявляется доказанной durability.
- TK-8 доказывает штатные object/ref операции, closure и GC-survival. Платформенные file/directory/full-flush барьеры и physical power-loss гарантии требуют отдельного P-3/TK-38; в этом узком результате они остаются неподтверждёнными, как прямо указано X-3/I-12. Старый recovery-row протокол R-8 отменён D-93.

### Запуск Git

Данные идут через stdin либо отдельный argv, имена файлов в tree-протоколах — NUL-delimited. Пути с пробелами, Unicode, ведущим дефисом, двоеточием и shell-метасимволами остаются данными в пределах RepoPath TK-7. Имена с управляющими символами RepoPath уже отвергает; его грамматика здесь не расширяется.

Не наследовать переменные, перенаправляющие Git directory/worktree/index/object store в другой репозиторий; каждую операцию выполнять в обнаруженном корне. Не применять replace refs при чтении явно заданных OID. Не разрешать lazy network fetch. Запись идёт только в object store и служебный refs namespace. Фильтры не запускаются. Эти узкие правила не объявляют Git sandbox или изоляцию от злонамеренного same-UID writer: полный security drill остаётся TK-42.

Git ниже 2.29 отклоняется до операций с объектами. Поддержать обычный version output и vendor suffix Apple Git. Нераспознаваемая версия и невозможность запуска не маскируются как совместимость. Не добавляются общий execution timeout, повторные попытки, фоновые потоки или новый механизм отмены: обработанная отмена во время git-подпроцесса относится к TK-29.

## Приёмка и доказательства

| Критерий | Проверяемое наблюдение |
|---|---|
| Точные bytes и tree без commit | Временный репозиторий с предварительно staged и unstaged изменениями; HEAD/пользовательский index/config/live-файлы byte-for-byte прежние. В snapshot ровно переданный набор, вложенные пути, пустой файл, binary/Unicode/LF/CRLF/без final newline; Git filters/EOL не меняют bytes. Повтор/перестановка входа даёт тот же OID. |
| Чтение неизменяемого снимка | S1 и S2 имеют разные bytes; удаление/правка live-файла не меняет read(S1). Нет fallback на HEAD/live и нет снятия commit/tag в tree. |
| Удержание inspect и source_snapshot | Одинаковый pin применяется к созданному S1 и существующему внешнему tree без пользовательского commit. После закрытия/повторного открытия адаптера refs указывают на точные OID. Повторный pin идемпотентен. |
| GC и closure | Только во временном неиспользуемом репозитории: expire reflogs, GC/prune now и pack-refs. Корень, вложенные trees и blobs обоих закреплённых снимков читаются с исходными bytes; самостоятельный fsck проверяет closure. Негативный контроль без pin теряет заведомо уникальный unreachable снимок; неполное дерево и сбой update-ref не дают успешного удержания. |
| Ошибки | Неверный OID/размер object format/type, отсутствующий tree/path, path collision, tree с потерянным дочерним blob, обнаруженное повреждение и принудительная ошибка Git различаются. Ошибки содержимого/настроек и canary bytes не протекают в публичную диагностику. |
| Процессная граница | Реальные пути с метасимволами не создают sentinel вне Git. Логирующая test fixture проверяет argv/stdin; запрещены shell и пользовательский index. Git-routing env trap и replace-ref fixture не меняют выбранный repository/исторические bytes. |
| Git version/object formats | Version gate отвергает 2.28.x, принимает 2.29.x и Apple suffix. Реальные create/read/pin/GC scenarios проходят и в SHA-1, и в `git init --object-format=sha256` repository. Если реальный Git 2.29 не запускался, минимум обозначается как проверка gate + документированного command subset, а не как запуск на этой версии. |
| Hexagonal и физическая структура | Реальные порт/структура Git-адаптера находятся в отдельных файлах/модулях, trait реализован через impl, подключение доступно из lib.rs. Публичные контракты отделены от приватных деталей, зависимости не обходят границы модулей. Сервисные модули/domain не импортируют конкретный Git-адаптер. Публичный путь сборки используется integration test. Остальные компоненты появляются в своих TK. |
| Регрессии/платформы | Все текущие 30 root tests остаются зелёными; новые meaningful contract/integration tests, fmt/Clippy PASS на macOS ARM64 и Linux glibc ARM64. Зависимости готовятся до Linux `--network none`. x86_64 остаётся TK-43. |

Точные команды/файлы тестов, Linux image и тестовый helper выбираются в плане после согласования. Evidence сохраняется в `docs/zkit/letopis/checks/TK-8/`: исходные hashes/argv/версии и реальные RED/GREEN, итоговый отчёт с ограничениями и независимое ревью. Проверки старых изолированных TK-1…TK-6 не объявляются повторно выполненными автоматически.

## Что сознательно остаётся дальше
