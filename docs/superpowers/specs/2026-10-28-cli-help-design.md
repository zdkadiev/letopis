# CLI `--help` и `--version` (issue #53)

**Дополнение 2026-10-28:** после этого дизайна команда `config` была реализована и пользователь запросил её в help. Текущий help содержит семь публичных команд, включая `config`; прежние исключения `config` и подсчёт шести команд ниже относятся только к исходному объёму issue #53 и заменены этим дополнением. Текущие правила ввода описаны в [X-1](../../zkit/letopis/contracts/X-1-cli.md): терминал даёт пустой запрос, а нетерминальный stdin без первого байта в течение 250 мс тоже считается пустым.

**Состояние:** дизайн согласован с пользователем в диалоге (план «один текстовый help для людей и агентов + help по командам + `--version`» одобрен); пользователь выбрал «как проще»: без отдельной машиночитаемой схемы. Пункты, помеченные **(выбор исполнителя)**, пользователем не обсуждались.

**База:** `main` на `d260348`; ветка `worktree-cli-help-53`, отдельный worktree `.claude/worktrees/cli-help-53`.

## Основания

- [Issue #53](https://github.com/zaurkadiev/letopis/issues/53): `letopis --help` и `--version` сейчас попадают в `_ => invalid_request`, команды нельзя обнаружить из CLI.
- [X-1 CLI](../../zkit/letopis/contracts/X-1-cli.md), [схема X-1](../../zkit/letopis/contracts/schemas/X-1-cli.yaml), [AGENTS.md](../../../AGENTS.md), [skills/letopis/SKILL.md](../../../skills/letopis/SKILL.md).

## Цель и зачем

Человек и агент должны узнать из самого бинарника: какие команды есть, как подаётся вход (JSON-объект в stdin), что приходит в ответ, какие поля у каждой команды. Главный читатель — агент, который один раз вызывает `letopis --help` / `letopis <команда> --help` и по выводу собирает валидный запрос без чтения документации; человеку подходит тот же текст.

## Поведение

Распознаётся ровно три формы argv; всё остальное работает как раньше.

| argv | Вывод в stdout | Exit |
|---|---|---|
| `--help` | общий help | 0 |
| `<команда> --help` | help команды | 0 |
| `--version` | `letopis <версия>` | 0 |

`<команда>` — одна из `check`, `inspect`, `search`, `traverse`, `reindex`, `status`.

- Вывод — обычный текст, не JSON-конверт: help не является результатом команды. Это осознанное исключение из правила X-1 «один JSON в stdout»; оно описывается в X-1.
- Распознавание происходит до `parse_request`: stdin не читается, `locate_environment`/репозиторий/конфигурация/сеть/сервисы не затрагиваются. Работает вне Git-репозитория и при закрытом или пустом stdin.
- Версия и имя — из метаданных пакета (`CARGO_PKG_NAME`, `CARGO_PKG_VERSION`); формат `letopis 0.0.0`.
- Не меняются: ввод команд, JSON-ответы, коды ошибок и exit-коды. Пустой argv, неизвестные флаги, `--help` с лишними аргументами (`--help search`, `search --help x`), `embed --help`, `embed --drain` ведут себя как сегодня (`invalid_request`, exit 1; `embed --drain` — как сегодня).
- Ошибка записи в stdout даёт exit 1 так же, как в `write_response`.
- Argv не в UTF-8: `find_help` возвращает `None`, дальше прежний `invalid_request` из `parse_request` **(выбор исполнителя)**.

## Содержимое

Общий help (до ~80 колонок, без цвета, без определения TTY, на английском, как остальные сообщения CLI):

1. `Usage`: `letopis <command> < request.json`, `letopis <command> --help`, `letopis --version`.
2. Список команд — по строке на команду (`check`, `inspect`, `search`, `traverse`, `reindex`, `status`).
3. Контракт ввода/вывода: вход — один JSON-объект в stdin (`{}` если полей нет), неизвестные поля отклоняются; в stdout — один JSON: `{"ok":true,"result":...}` (при необходимости с необязательным массивом `warnings`, например при сбое запуска фонового embedding) либо `{"ok":false,"error":{"code","message","details"}}`; exit 0 для `ok:true`, 1 иначе; коды ошибок: `invalid_request`, `not_found`, `validation_failed`, `embedding_failed`, `internal_error`, `cancelled`; запускать в Git-репозитории.
4. 2–3 представительных примера вызова в виде `printf '%s\n' '<json>' | letopis <command>`.

Help команды: назначение одной фразой; таблица полей входа (имя, тип, обязательное / значение по умолчанию, смысл, допустимые значения enum); форма `result` успешного ответа; один полный пример. Поля берутся из `SearchInput`/`TraversalInput`/`CheckInput`/`InspectInput` и пустого объекта для `status`/`reindex`. Форматы значений (путь репозитория, адрес элемента `путь` / `путь#якорь` / `путь#Lstart-Lend`, source URI, Git tree OID, типы рёбер, значения `mode`/`direction`) исполнитель сверяет с доменными парсерами (`RepoPath`, `ElementAddress`, `SourceUri`, `TreeOid`, `EdgeType`), а не с памятью.

Не включаются: `embed --drain` (внутренняя, не для агентов, D-94) и `config` (есть в контракте, но не реализована в CLI).

## Реализация

- Новый `src/cli/help.rs`: таблица команд (имя, краткое описание, текст help команды, пример JSON), общий текст, функция `find_help(args: &[OsString]) -> Option<String>`, возвращающая текст для трёх форм выше. Тексты — `const`/`static`; примеры хранятся отдельными константами, чтобы тесты могли подавать их в парсер. Если файл заметно превысит ~400 строк, тексты выносятся в соседний файл модуля.
- `src/cli/output.rs`: `write_text(output, text) -> u8` с тем же write+flush и тем же отображением ошибки записи в exit 1, что у `write_response` (общая запись — один владелец, без дублирования).
- `src/cli/mod.rs`: объявить `help`, реэкспортировать `find_help`/`write_text`.
- `src/lib.rs::run_cli`: первой строкой — если `find_help(&args)` вернул текст, записать его и вернуть код; иначе прежний путь `parse_request → run_request → write_response`. Новых зависимостей, трейтов, сервисов, парсера аргументов (clap) нет: argv-грамматика состоит из трёх форм.
- `Request` и `parse_request` не меняются.
- Код следует AGENTS.md: порядок «вызывающий выше вызываемого», публичные элементы документированы, имена-глаголы, SCREAMING_SNAKE_CASE для констант, Debug на публичных типах, функции до ~40 строк.

## Документация

- X-1 CLI: раздел «Help и version» (три формы, текстовый вывод как исключение из «один JSON», что help не читает stdin и не инициализирует сервисы). Машинная схема `X-1-cli.yaml` не меняется: help не команда со входом/ответом JSON.
- `skills/letopis/SKILL.md`: одна строка — «`letopis --help` / `letopis <command> --help` показывают поля входа» **(выбор исполнителя)**.

## Тесты

Все тесты в Given/When/Then, с мутационной проверкой по AGENTS.md.

1. Unit (`src/cli/help_tests.rs`, подключается как `search_tests`):
   - `find_help` распознаёт ровно три формы и все шесть команд; для `--help search`, `search --help x`, `embed --help`, пустого argv, `--bogus`, `-h`, `-V` возвращает `None`.
   - Пример каждой команды из help, поданный в `parse_request([команда], пример)`, даёт `Ok` — так устаревшее имя поля или пропущенное обязательное поле ломает тест (`deny_unknown_fields` и required-поля играют роль независимого оракула).
   - Общий help упоминает каждую команду из таблицы и не упоминает `embed`/`--drain`; вывод `--version` сравнивается с литералом (`letopis 0.0.0`), а не пересобирается из `env!`; при смене версии пакета литерал обновляется вместе с ней.
2. Интеграция с реальным бинарником (`tests/cli_help.rs`, `CARGO_BIN_EXE_letopis`): запуск в пустом временном каталоге (не Git-репозиторий, без `.letopis`), stdin — открытый pipe, в который ничего не пишется и который не закрывается (процесс обязан завершиться сам, с таймаутом), чистое окружение без конфигурации; для `--help`, `--version`, `<команда> --help` ×6: exit 0, stdout непустой текст, не JSON-конверт, stderr пуст, никаких созданных файлов (в т.ч. `.letopis`) в каталоге.
3. Регрессия существующего поведения: пустой argv, `--bogus`, `--help search`, `status --help` лишнее → JSON `invalid_request`, exit 1 (и `status` без флага по-прежнему читает stdin).

Ограничение: тесты не доказывают «без сети» кроме косвенно (нет кода сети на пути и нет конфигурации); отсутствие нового поля во входе команды, не отражённого в help, тестом не ловится.

## Ручная проверка перед завершением

`cargo build --release` (или `make release`); в пустом каталоге вне Git: `letopis --help`, `letopis --version`, `letopis <каждая команда> --help`, примеры из help через pipe в реальном репозитории; `letopis --bogus` и `letopis` без аргументов; затем `make verify`. Результаты и непрогнанные проверки — в отчёте.

## Цели, не-цели, анти-цели

- **Цели:** критерии issue #53; help достаточен агенту для сборки запроса; тексты не расходятся с парсером.
- **Не-цели:** машиночитаемая схема из `--help`, shell completions, man-страница, подкоманда `help`, цвет, локализация, `-h`/`-V` **(выбор исполнителя; в issue только длинные флаги)**, изменение JSON-контракта, `config`, `embed`.
- **Анти-цели:** help, инициализирующий хоть один сервис или читающий stdin; новая зависимость или парсер аргументов ради трёх форм; text, который тихо расходится с реальным входом.
