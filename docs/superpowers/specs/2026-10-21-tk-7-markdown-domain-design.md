## Зачем и какой результат

TK-1…TK-6 проверяли отдельные риски. TK-7 начинает код продукта: один переиспользуемый разбор превращает байты Markdown в элементы, связи и временный поисковый текст. Будущие индексация, check и embedding drain должны пользоваться теми же правилами, чтобы одинаковые байты не означали разный граф или разные search_hash.

Результат — библиотечный код Rust и воспроизводимые fixtures. Вызов получает проверяемый путь относительно Git-корня и байты одного файла; возвращает отсутствие разметки, целиком валидный результат или диагностики файла. Парсер ничего не записывает, не читает назначения ссылок, не вызывает Git, SQLite, HTTP или модель.

## Принятые ограничения

- Rust 1.95.0, edition 2024. Markdown — `pulldown-cmark`, offset iterator и `ENABLE_HEADING_ATTRIBUTES`; SHA-256 — `sha2`; JSON — `serde`/`serde_json`. Точные версии закрепляются при реализации по D-96.
- Только актуальная разметка X-4; нет совместимости с отменённой грамматикой, UUID, полем kind или закрывающим `<!-- /letopis -->`.
- Нет сериализатора, редактора корпуса, CLI-команд, асинхронного runtime, фоновых потоков, ORM, реестра плагинов или новых конфигурационных полей.
- Существующие proof harnesses остаются изолированными проверками. Их упрощённая разметка не становится grammar продукта.
- Не добавляются лимит размера элемента, усечение, чанкинг, схемы произвольных атрибутов или наследование типов.

## Предлагаемая организация кода

Это инженерный выбор автора для согласования, а не ранее принятое пользователем расположение файлов.

Один корневой library crate `letopis`, без Cargo workspace и без пустого CLI-бинарника. Доменные типы располагаются в `src/domain/`, конкретный Markdown-адаптер — в `src/adapters/markdown/`. Только адаптер зависит от `pulldown-cmark` и формата служебного JSON. В домене нет импортов Git/SQLite/HTTP/CLI/Markdown-парсера, чтения файлов или знания о serde-представлении комментария.

Минимальные предметные значения: проверенный root-relative путь, якорь, ID знания, нормализованный адрес source, включительный диапазон строк, полуоткрытый диапазон байтов, SHA-256, метаданные знания и ребро-тройка. Нельзя создавать заведомо некорректный якорь/адрес/диапазон в обход проверок. Метавершина определяется наличием исходящего includes; отдельного редактируемого или хранимого в разметке kind нет.

Для TK-7 достаточно конкретной чистой функции разбора с типизированным результатом. Придумывать общий trait для единственной реализации, контейнер зависимостей или полный набор будущих портов не нужно. Имена файлов, методов и внутренних диагностик уточняются в плане. Структуры проекции SQL и orchestration нескольких файлов остаются будущим задачам.

## Поведение парсера

### Элементы и границы

1. Файл-элемент начинается служебным комментарием на первой строке. Его ID — путь, диапазон — все исходные байты файла. Других элементов внутри нет.
2. Раздел-элемент — заголовок с явным `{#anchor}` и непосредственно следующая строка с комментарием `<!-- letopis: {...} -->`. ID — `path#anchor`. Начало диапазона — начало строки заголовка; конец — начало следующего настоящего заголовка того же или более высокого уровня либо EOF. Конечный перевод строки и пустые строки входят в диапазон, если они находятся до этой границы.
3. Обычные подзаголовки внутри раздела допустимы. Другой размеченный элемент внутри него — ошибка. Соседние размеченные разделы допустимы; текст вне элементов не индексируется как знание.
4. Контекст определяет CommonMark-парсер: fenced и indented code blocks не объявляют элементы, заголовки, якоря или рёбра. Видимый пример служебного комментария в коде остаётся содержимым примера.
5. Якоря соответствуют `[A-Za-z][A-Za-z0-9_-]*`, уникальны в файле и не имеют форму `L<n>-L<n>`. Проверяются явные якоря настоящих заголовков, включая неразмеченные, чтобы адрес раздела был однозначным.
6. Настоящий служебный комментарий вне допустимой позиции, неверный JSON, метаданные или вложенность дают ошибку файла. Пример маркера внутри code block сам по себе не включает файл в корпус. Обычный неразмеченный Markdown возвращает отдельный результат «не корпус».
7. Входные байты не переписываются. Для разбора нужен UTF-8; некорректное кодирование возвращается диагностикой, без lossy-преобразования.

### Метаданные, байты и время

Метаданные строго соответствуют X-4 schema: обязательный целочисленный `created_at >= 0`, необязательный `source_snapshot` — 40 или 64 строчных hex-символа. Неизвестные поля, включая kind/id, отклоняются. Парсер не назначает текущее время и не обновляет created_at при правке. Историческую неизменность created_at нельзя доказать одним файлом; TK-7 проверяет сохранение переданного значения и отсутствие автоматической подмены.

`hash` — SHA-256 точных байтов диапазона элемента. LF/CRLF, пробелы, Unicode, отсутствие последнего newline, метаданные и адреса ссылок учитываются без нормализации. Диапазоны строк 1-based и включительные; завершающий newline не создаёт фиктивную содержательную строку. Байтовые координаты не являются координатами Unicode-символов. Фикстуры хранят эталонные диапазоны и ожидаемые хеши независимо от результата парсера.

### Связи и адреса

Только inline Markdown-ссылка с корректным title `letopis:type=<type>` внутри знания создаёт ребро. Тип соответствует `[a-z][a-z0-9_]*`; includes и external — системные значения. Обычная ссылка без letopis title остаётся навигацией; malformed letopis title — ошибка файла. Reference-style ссылки не вводят графовые рёбра (MC-1: inline links).

Источник ребра — содержащий элемент; идентичность — `(source, target, type)`. Повторы тройки объединяются; разные типы между теми же узлами сохраняются. Рёбра не получают ID, даты, hash, active-флага или отдельного массива includes. Согласно MC-1, ссылка элемента на самого себя делает файл невалидным и ребром не публикуется.

Внутренняя цель — KnowledgeId: путь `.md`/`.markdown` с допустимым якорем или без него. External указывает на source: root-relative файл целиком либо `#Lstart-Lend`. Пути считаются от Git-корня, а не от расположения документа. Удаляются `.` и внутренние `..`, выход за корень и абсолютный путь отклоняются; регистр сохраняется. Диапазон положительный и включительный, `end >= start`, ведущие нули при нормализации убираются. Пример: `./src/../src/a.rs#L010-L025` → `src/a.rs#L10-L25`. Адрес source не превращается в знание и не загружается по сети.

Парсер выполняет только лексические проверки. Существование цели, полного диапазона в реальном файле, Git tree, разрешение symlink и удержание внутри реального Git-корня проверяются адаптерами/сценариями с доступом к файловой системе. Нельзя объявлять эту безопасность доказанной TK-7. Отсутствующий source_snapshot при external-ссылках не подменяется и не выдумывается: его активная диагностика и признаки перепроверки относятся к интеграции источников.

Висячая внутренняя ссылка допускается как объявленная тройка. Поиск includes-циклов по нескольким элементам/файлам, исключение таких рёбер из обхода и проверки текущего графа — TK-18. Source.created_at вычисляется позднее как минимум created_at всех ссылающихся знаний; один parser файла не имеет полного набора для этого вычисления.

### Поисковый текст

Один детерминированный кодек готовит временный собственный текст элемента для FTS и embeddings: без служебного комментария, якоря и метаданных графовой ссылки; остаются заголовок/обычный текст, подписи ссылок и собственные примеры кода. Назначения и связанные знания не читаются. `search_hash` — SHA-256 UTF-8 этого представления, а не исходного Markdown.

Изменение только метаданных, адреса/типа ссылки или якоря при прежнем содержимом меняет raw hash, но сохраняет search_hash. Изменение собственного текста/подписи/кода меняет search_hash. Перенос по пути меняет ID, но не raw hash неизменных байтов или search_hash.

Точные разделители, отображение остальных конструкций CommonMark и формат публично не обещанного поискового представления — выбор реализации, прямо оставленный строителю контрактом. До кода их нужно закрепить небольшими golden fixtures, включая отсутствие склеивания соседних слов, код и границы блоков; не добавлять второй независимый конвейер для embeddings.

### Результат и ошибки

Успех содержит полный набор элементов, объявленных рёбер и необходимые временные поисковые значения одного файла. Ошибка не выдаёт частично валидную проекцию. Диагностика содержит проверяемую причину и координаты, где они доступны. Решение сохранить последнюю валидную SQL-проекцию принимает будущий publisher (TK-10), а не parser. Конвертация диагностики в общий CLI JSON — TK-11.

## Приёмка и доказательства

- Golden fixtures: файл-элемент, несколько разделов, неразмеченный текст, обычные подзаголовки, EOF/newline, LF/CRLF, Unicode; точные ID, байты, строки, raw SHA-256 и created_at.
- Негативные fixtures: JSON/поля/дата/OID, пустой или запрещённый якорь, дубли, вложенность, orphan-комментарий, неправильный letopis title, self-loop, выход пути за корень, неправильный диапазон и UTF-8. Все ошибки исключают частичную проекцию.
- Code/context fixtures: fenced/indented code с похожей разметкой, ссылки и заголовки в примерах, незакрытый fence; навигационные/reference-style ссылки не создают граф.
- Графовые fixtures: includes, external, дедупликация троек, параллельные типы, root-relative нормализация, разрешённая висячая цель. Проверка kind без поля kind в метаданных.
- Парные fixtures для search_hash: метаданные/адрес/тип/якорь меняют только raw hash; свой текст/подпись/код меняют search_hash; перенос пути сохраняет текстовые хеши.
- Независимые эталоны не вычисляются тестируемым extractor. Проверки должны обнаруживать ошибочный диапазон, нормализацию raw EOL, распознавание маркера в коде и включение служебных метаданных в search text.
- `cargo test`, форматирование и clippy; версии и точные команды появятся в плане после согласования спецификации. Данные фикстур проверяются на macOS и Linux; не заявляется x86_64 или полный системный прогон.
- Evidence в `docs/zkit/letopis/checks/TK-7/`: команды, исходы, привязка к версии/платформе и критериями карточки. Оценки/расписание roadmap не меняются без реального основания. Критерии карточки не отмечаются до проверки реализации.
