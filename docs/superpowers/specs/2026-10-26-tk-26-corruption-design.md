## Цель и согласованная граница

Завершить карточку TK-26: повреждение требуемых Git objects не превращается в
успешную первичную инициализацию; производные cache.db/vectors.db восстанавливаются
из канонических данных после явного удаления повреждённого кэша и полного reindex;
повреждение и недоступность дают безопасную текущую диагностику.

Пользователь разрешил параллельный старт с TK-25 в другой сессии. Сейчас здесь
выполняются спецификация, fixtures и независимые проверки существующих Git/storage
границ. Реализация reindex, detection, CLI reindex и основного publication пути
принадлежит TK-25. Полная приёмка TK-26 остаётся зависимой от готового TK-25.

## Принятые решения

- Обычный Markdown/Git — канон; SQLite — пересоздаваемая проекция. Корпус,
  config.json, Git HEAD/index/user refs и retained source bases не восстанавливаются
  из произвольного содержимого повреждённой БД.
- Синхронный Rust, существующие интерфейсы и адаптеры; никаких новых зависимостей,
  async runtime, repair-команд, recovery.json, фонового наблюдения или хранилища ошибок.
- Подготовительный этап не правит production reindex/detection и файлы другой сессии.
  Не добавляются placeholder интерфейсы или pass-through сервисы на будущее.
- Тяжёлые native/Docker прогоны выполняются по очереди. Сбой Docker/ext4 не выдаётся
  за дефект Letopis либо успешную Linux-проверку; окружение и пределы фиксируются.

## Этап A — независимая работа от текущего main

Добавить воспроизводимые test-owned fixtures и проверки уже существующих публичных
Git/storage capabilities. Каждая проба строит собственный TempDir/TempRepo, сначала
подтверждает здоровый контроль, затем повреждает ровно заданную копию ресурса.

### Git

Проверить SHA-1 и SHA-256, используя фактический OID и Git object path, без
предположения о длине 40 символов. Минимальные случаи:

1. Повреждённый tree object, нужный для запрошенной операции.
2. Повреждённый blob внутри проверяемого tree closure.
3. Валидно упакованные байты другого object по ожидаемому адресу, если этот сценарий
   ещё не покрыт существующими integrity-тестами; oracle — исходные независимые байты.
4. Отсутствующий объект внутри реально требуемого closure: это повреждённая
   связность, а не новый пустой репозиторий; expected outcome проверяется через
   существующий closure verifier.
5. Контроль отсутствующего, но синтаксически корректного OID и неподходящего object
   type по X-3: `not_found`/`invalid_request` не смешиваются с corruption `internal_error`.

Не всякое отсутствие объекта — фатальная ошибка. Отсутствующий авторский
source_snapshot является текущей provenance-проблемой по D-93; отсутствующий
запрошенный OID — not_found. Fail-closed означает запрет ложного успешного результата
при повреждении реально требуемого объекта, а не замену этих контрактов.

Проба не чинит Git автоматически и не создаёт новый basis вместо повреждённого.
После отказа HEAD/index/config/user refs/Markdown остаются прежними; product stderr
не содержит сырого Git payload. Восстановление точных fixture bytes допускается
только как тестовый контроль повторного успешного чтения.

### SQLite

Проверить отдельно cache.db и vectors.db, не называя любой отказ fresh init:

- несуществующий файл: поддерживаемая непубликованная инициализация;
- непустой неверный заголовок/усечённый ранее здоровый файл: безопасный отказ;
- несовместимая user_version или частичная схема: отказ, без DROP/перезаписи;
- недоступный либо unsafe path: отказ, не автоматическое удаление;
- здоровый контроль и повторное открытие новым соединением/процессом.

Не требовать невозможного восстановления истории нулевого SQLite-файла: его байты
не отличают только что созданный файл от прежнего усечённого кэша. В текущем
контракте это непубликованное состояние с последующим initial build, не доказанная
готовая публикация. Не вводить sidecar marker только ради такого различения.
Повреждение непустого файла и несовместимой схемы не должно маскироваться этим случаем.

В подготовительном этапе сохранять здоровый vectors.db при пересоздании только
пустого cache.db на уровне существующего storage open. Это ещё не доказательство
реального CLI reindex/reuse — его проверяет этап B.

Если независимая проба обнаруживает production gap, сохранить точный reproducer и
ожидаемое поведение в отчёте. Не обходить его слабой assertion, blanket ignore или
фиктивным PASS. Пересекающийся с TK-25 production fix откладывается до синхронизации;
падающий default suite не публикуется как законченный подготовительный результат.

## Этап B — после интеграции TK-25

Потребить готовый `Refresher::reindex`/реальный CLI reindex из TK-25, а не писать
второй алгоритм. Перед этапом синхронизировать ветку с принятой ревизией TK-25,
зафиксировать точные зависимости и прогнать затронутые проверки на новом дереве.

Матрица реального CLI:

1. Требуемый повреждённый Git object даёт один безопасный error JSON/exit 1 и не
   продвигает опубликованную ревизию; восстановление fixture подтверждает контроль.
2. Повреждённый cache.db сначала даёт ошибку. После закрытия только test-owned
   процессов/handles операторский сценарий удаляет только этот кэш и его WAL/SHM;
   готовый reindex пересобирает graph/FTS/files из Markdown.
3. При здоровом vectors.db, прежней config identity и прежнем search_hash векторы
   сохраняются побайтно; повторная индексация не вызывает inference для этих текстов.
4. Повреждённый vectors.db даёт ошибку. Явное удаление только его файлов и reindex
   восстанавливают текстовый путь; отсутствующие векторы требуют обычного drain,
   а не фиктивного populated состояния. Здоровый cache/config/Markdown сохраняются.
5. Удалённые cache/vectors проверяются отдельно и вместе; revision/coverage берутся
   из фактического нового состояния, не из прежних потерянных счётчиков.
6. Новый CLI-процесс снова видит сохраняющуюся причину повреждения. Невалидный файл
   при доступной записи имеет текущую files.error, после исправления/публикации она
   исчезает. При недоступном storage ошибка не выдаётся за успешно сохранённую строку.

### Что означает диагностика после restart

Если требуемый Git object либо сама БД остаются повреждёнными/недоступными, каждый
новый вызов снова возвращает безопасный верхнеуровневый `internal_error` с контекстом
отказавшей границы. Это существующая диагностика команды, а не обещание отдельной
строки corruption в `status.problems`: status не может прочитать повреждённую БД.
После устранения причины старое сообщение не сохраняется как история. Для реально
невалидного Markdown при доступной записи по-прежнему используется `files.error`;
инфраструктурный отказ не превращает валидный Markdown в invalid file.

Это уточнение следует из MC-7/D-95 и X-1 observation-only status; нового каталога
публичных error codes, отдельного error store или новой сериализации причины нет.
На этапе A сверяются текущие typed ошибки; production gap в конкретной диагностике
попадает в отчёт и решение по границе владельца, а не маскируется записью в БД.

Удаление выполняет fixture/operator, не продукт по любому пойманному исключению.
Нельзя удалять всю `.letopis` вместе с config.json или живыми чужими locks; нельзя
лечить schema mismatch, permission error и Git corruption автоматическим unlink.
Все разрушительные действия ограничены закрытыми test-owned ресурсами.

«Без потери знаний» означает неизменность канонического Markdown/Git и корректную
повторную проекцию доступных валидных файлов. После удаления единственной
last-valid проекции нельзя обещать восстановление старого содержимого невалидного
текущего файла из отсутствующего SQLite cache: он остаётся диагностируемым invalid
file согласно initial-build политике TK-25. История знаний не изобретается.

## Регрессия публикации MC-2

Переиспользовать существующие controls TK-2/TK-10 и актуальный TK-25 путь:
подготовка, внутри незавершённой cache unit, после commit, освобождение index.lock.
Управлять только собственным child process через явные барьеры/ограниченное ожидание.
После прерывания новый процесс видит прежнюю либо целиком новую публикацию; следующий
refresh заново обнаруживает неопубликованную дельту. Невалидный A не скрывает
валидный B; files и graph/FTS одной публикации не расходятся.

Отмена собственного процесса не означает готовность обработанного cancelled JSON:
его полный контракт остаётся TK-29. Физическая потеря питания и повреждения носителя
остаются TK-38/39; SIGKILL/SQLite rollback не выдаются за такое доказательство.

## Структура и владение файлами

Тесты живут в отдельных responsibility-named integration files и используют
существующие tests/support helpers без изменения их контракта для TK-25. Общий
private corruption helper выделяется только при двух реальных потребителях.
Не держать заранее подготовленные бинарные базы с неизвестным происхождением:
строить их существующими адаптерами и повреждать определённые байты fixture.

Production responsibilities сохраняются: Git object validation — git; confined
file access — filesystem; SQL/schema errors — storage; orchestration — service;
CLI — input/dispatch/serialization; composition — lib.rs. Порты принадлежат service,
сущности domain не получают инфраструктурных зависимостей. Минимальный найденный
fix обсуждается через эту границу, без второго recovery framework.

## Проверка и evidence

- Нормальные независимые oracles, Arrange/Act/Assert, функции около 40/до 60 строк,
  глагольные имена и явные imports, без новых wrapper bundles и лишних generics.
- RED/GREEN и узкие ручные мутации выбранных corruption/error distinctions;
  восстановление исходников после каждого опыта, никаких изменений настоящей БД.
- Для этапа A достаточно существующих API: ожидаемые ошибки и неизменность
  fixture-проекции/канона проверяются отдельно от ещё недоступного reindex.
- `make check` для продуктовых Rust-правок; `make verify` на окончательном коде;
  при storage/native изменениях свежие host/Linux runners с новыми evidence dirs.
  Не повторять тяжёлые кампании без изменения входов/неразрешённого сомнения.
- Отчёт указывает revision/input hashes, ОС/FS, команды/exit codes, классификации
  Git/SQLite, исходы до/после restart, выполненную часть MC-2 и реальные пределы.
- При подготовительном результате TK-26 остаётся in_progress: B/reindex/полная
  приёмка явно pending TK-25. Не закрывать issue и не объявлять G-1/G-2 пройденными.
