## Цель и исходное состояние

Агент определяет структуру каталогов, имена и содержимое файлов. Корень — Git-root,
а не поле config; обнаруживаются .md/.markdown во всех подкаталогах по MC-2.
ID выводится из пути/якоря, в metadata не хранится. Типы отношений агент задаёт
сам в формате [a-z][a-z0-9_]*; includes/external сохраняют системную семантику.
Агент правит обычные Markdown-файлы и вызывает check, чтобы увидеть текущие
ошибки до использования знаний. Команда не редактирует корпус и не исправляет
ссылки автоматически. Переименование меняет ID пути/якоря; старые входящие
ссылки остаются объявлениями и диагностируются до исправления или возврата цели.

В main уже есть Checker, CheckReport, строгий вход paths, handler и JSON renderer.
Production dispatch check пока возвращает operation unavailable. TK-18 даёт
чистый валидатор и GraphDiagnostics, принимающий caller-owned StorageRead.
DocumentRefresher публикует валидные изменения и сохраняет прежнюю валидную
проекцию невалидного файла вместе с текущим files.error. Их правила не дублируем.

## Утверждённое поведение

1. check выполняет существующий refresh ВСЕГО корпуса; paths ограничивает ответ,
   а не публикацию и не множество узлов, нужное для проверки ссылок/циклов.
2. После refresh сервис открывает один закреплённый read view. Файловые ошибки,
   висячие knowledge-ссылки и includes-циклы получает через GraphDiagnostics.
   Empty/missing paths означает весь корпус; повторные пути не дублируют ошибки.
   Непустые paths — точные нормализованные пути файлов от Git-корня, без glob,
   рекурсивного раскрытия каталогов и якорей. Отсутствующий путь сам по себе не
   становится ошибкой: удалённой цели нет, ошибки принадлежат её источникам.
3. Ошибки принадлежат файлу, содержащему неверную разметку/ссылку; фильтр по
   пути цели не переносит на неё ошибки неизменённых источников. Проверка циклов
   до фильтрации сохраняет сведения о цикле, пересекающем выбранную границу.
4. Дополнительно check сообщает проблемы основания: у знания с external-рёбрами
   нет source_snapshot либо указанный source_snapshot отсутствует/не является
   tree/несовместим с форматом репозитория. Различные OID проверяются один раз
   за вызов, затем результат относится к каждому выбранному владельцу.
   Указанные snapshot проверяются и у знаний без external-рёбер, если metadata
   содержит OID. Текущие метаданные берутся из того же read view.
5. Проверка snapshot — синхронное чтение Git, без pin/create_tree/write_blob,
   изменения refs и чтения live source contents. I/O, запрет политики репозитория
   или обнаруженная порча — CommandError, не успешное отсутствие проблемы.
   Полная проверка source bytes/ranges/source_changed и происхождения — TK-21.
6. Все находки возвращаются в одном успешном X-1 ответе
   {"ok":true,"result":{"errors":[...]}} с exit 0, даже если errors непустой.
   Invalid input, инфраструктурный сбой и отмена — один ok:false, exit 1.
   Не меняем envelope/схему и не подменяем findings общей ошибкой команды.
7. Findings имеют безопасные фиксированные сообщения и структурированные
   path/reason/element_id/target по существующим категориям. Порядок стабилен:
   path, reason, element_id, target; одинаковые findings не повторяются.
   Сырые provider/Git/Markdown payload не попадают в публичный JSON.
8. После исправления следующий refresh/check показывает текущий результат,
   без отдельного clear и таблицы активных ошибок. При невалидной новой версии
   файл сохраняет предыдущую валидную проекцию по MC-2; это не ошибка check.
9. Успешная команда использует существующий background runner: векторы не
   ожидаются, возможный drain следует прежним правилам. Тесты check работают
   без настроенного provider, не выполняют платные или реальные HTTP-вызовы.
10. letopis не переписывает Markdown, created_at, якоря или пользовательские
    ссылки. created_at задаёт агент и сохраняет при переносе; проверяем, что
    refresh переносит эти metadata без подмены на время индексации.

## Реализация и варианты

**Предложение автора:** отдельный CheckService в service/check.rs с concrete
struct/impl, реализующий существующий Checker. Зависимости — Refresher, Storage,
GraphDiagnostics и узкий application-owned интерфейс чтения наличия/типа tree.
Точное имя интерфейса и типизированного результата оставлены разработчику;
если существующий Git-интерфейс уже гарантирует read-only probe, переиспользовать
его. Не вызывать pin ради проверки и не вводить новый процесс/базу/registry.
GitCli реализует недостающее чтение через argv, без shell interpolation.

CLI handler остаётся тонким; production constructors и реальное связывание
Checker + background находятся в lib.rs. Общая диагностика пригодна для TK-28;
status, traversal и полноценный provenance service не добавляются.

Альтернативы: проверять граф заново в CLI — дублирование правил и нарушение
границ; использовать pin для проверки tree — лишняя запись refs. Поэтому
предлагается композиция существующих компонентов с read-only Git probe.

Файлы затрагиваются только по ответственности; не дробить одну реализацию на
trivial forwarding файлы. Синхронный Rust, generic dispatch где уместен,
существующие ошибки/конфигурация и текущие зависимости. Соблюдать AGENTS.md:
глагольные имена, документация интерфейсов, функции примерно 40/max60 строк,
Arrange/Act/Assert, без механического переустройства нетронутого кода.

## Проверка результата

- Реальный продуктовый бинарник, настоящий временный Git-репозиторий и storage:
  whole corpus, paths, repeated paths, malformed request, один JSON/exit 0 и 1.
- Несколько невалидных файлов, dangling, includes-цикл; валидные файлы всё равно
  публикуются. Исправление устраняет текущие находки.
- Переименование/удаление файла и якоря: источник не редактируется, его bytes
  неизменны; возврат цели снимает dangling. Directory rename на малом fixture.
- Правка и перенос сохраняют literal created_at; два одновременно запущенных
  refresh/check не теряют правки разных файлов. Использовать детерминированную
  координацию, не гонку с произвольным sleep.
- Ссылки на цели вне paths остаются валидными; cycle crossing paths виден.
- Snapshot: valid tree, absent/wrong-type OID, missing metadata, повторный OID,
  безопасный инфраструктурный failure и отсутствие новых refs от probe.
- Сравнение bytes корпуса до/после, повторный check без новых ошибок/публикаций
  на неизменных входах; cache refresh разрешён и не равен редактированию корпуса.
- Unit tests сервиса проверяют refresh-before-read, общий view, типизированные
  failures, отсутствие частичного success и границы вызовов.
- Выбранные ручные мутации для новых существенных ветвей с восстановлением;
  make check и make verify. Native/platform harness только при реальном изменении
  storage/native stack, не автоматически для композиции над прежним Storage API.
- Воспроизводимый отчёт и receipt с revision/platform/commands/results/limits;
  task card отмечает check отдельно от отложенного status TK-28. Смежный TK-18
  получает ссылку на настоящую CLI-приёмку, без объявления status/traverse готовыми.
