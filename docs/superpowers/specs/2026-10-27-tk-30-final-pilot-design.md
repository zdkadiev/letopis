**Статус:** approved пользователем 2026-10-27. **Дата:** 2026-10-27.
**Разрешено сейчас:** подготовить [план реализации](../plans/2026-10-27-tk-30-final-pilot.md)
в отдельном worktree, ветка `tk-30` от
`origin/main@d260348619c6f4f623f24b907ca5bf41fb14eba9`; без реализации runner,
решения выбранных задач, платных сессий и provider/model preflight.

## 1. Цель и основания

Подготовить воспроизводимый набор из трёх цепочек по три реальные coding-задачи
Letopis и независимые окружения для сравнения одного агента без межсессионной
памяти и с самостоятельно накопленной памятью Letopis. Полный формат —
**3 цепочки × 3 задачи × 2 условия = 18 новых сессий**; подготовка не является
проведением пилота или доказательством пользы памяти.

Источники: [TK-30](../../zkit/letopis/roadmap/epics/EP-5-final-pilot/tasks/TK-30-pilot-setup.md),
[P-1](../../zkit/letopis/pilot/protocol.md), [шаблоны](../../zkit/letopis/pilot/templates/),
[checker](../../../tests/pilot_protocol/README.md),
[NFR-8/FR-36](../../zkit/letopis/requirements.md),
[D-25…D-28/D-33](../../zkit/letopis/decisions.md#D-25),
[архитектура и проверка границ](../../zkit/letopis/architecture.md#program-structure),
[механизмы](../../zkit/letopis/mechanics.md), [X-1](../../zkit/letopis/contracts/X-1-cli.md).
Платные исполнения и анализ принадлежат TK-31/TK-32/TK-33.

## 2. Решения, предложения и зависимости

**Подтверждено пользователем:** отдельный worktree/ветка `tk-30`; подготовка без
платных запусков; новые задачи из открытого backlog; полный формат по карточке.

**Предложения автора, принятые утверждением спецификации:** цепочки C1–C3 ниже,
локальная Python 3.11+ подготовка на основе существующего P-1 без нового
экспериментального протокола или универсальной платформы запуска.

TK-29 выполняется параллельно. Сейчас разрешена предварительная подготовка,
а окончательная фиксация готового продукта, приёмка TK-30 и запуск следующей
фазы зависят от интеграции TK-29 и решения G-2. Наличие этой спецификации не
снимает ограничения TK-16/TK-17 и G-1; D-103 не объявляет эти проверки пройденными.
Дефицит доказательств в матрице G-2 сохраняется как отдельный блокер.

Две ревизии не смешиваются: текущий `d2603486…` — проверенный источник выбора
задач, будущий post-TK-29 commit — кандидат стартовой сборки/кода. После
интеграции повторно проверить, что девять задач ещё не решены ни в источниках,
ни в доступных участнику документах. При совпадении остановить freeze и
пересмотреть выбор до любых наблюдений, с новым prospectively frozen набором.

## 3. Рассмотренные подходы

1. **Новые незавершённые инкременты backlog — выбран пользователем.** Они
   соответствуют реальным потребностям проекта, не требуют удаления готового
   поведения и позволяют проверить перенос знаний между связанными задачами.
2. Повторить TK-17 на старом снимке. Не выбран: задачи check/domain/source-inspect
   уже реализованы; история, соседние ветки и документы содержат готовые ответы.
3. Синтетические упражнения/намеренно сломанный продукт. Не выбран: удобнее для
   oracle, но не выполняет требование трёх реальных цепочек задач Letopis.

Альтернатива ожидать TK-29 до всей подготовки не нужна: подготовительные
документы/фикстуры имеют отдельного владельца. Исполняемые smoke и финальный
freeze полного продукта при этом не переносятся на незавершённую сборку.

## 4. Предварительно выбранные цепочки

Источники backlog проверены read-only 2026-10-27:
[#53](https://github.com/zaurkadiev/letopis/issues/53),
[#43](https://github.com/zaurkadiev/letopis/issues/43),
[#49](https://github.com/zaurkadiev/letopis/issues/49).
В текущем `src/cli/input.rs` flags help/version отсутствуют, `make release`
собирает бинарник, но не реализует описанную ниже поставку, executor выполняет
document requests последовательно. Открытый issue сам по себе не доказывает
незавершённость: окончательный freeze требует повторной проверки исходников и
непроходящего нового критерия на выбранном неизменённом seed.

Каждая цепочка начинается независимо. Код C1 не является входом C2/C3.
Предыдущие результаты внутри одной цепочки продолжаются только в своём условии.
T2/T3 расширяют собственный результат T1/T2, а не получают reference patch.

| ID | Реальный coding-инкремент | Независимый критерий результата |
| --- | --- | --- |
| C1-T1 | `letopis --version` из package metadata | Имя/версия соответствуют зафиксированному Cargo.toml; exit 0 при незакрытом stdin, без репозитория/сети и новых файлов состояния. Обычный JSON-путь сохранён. |
| C1-T2 | Общий `--help` | Называет все команды выбранной post-TK-29 сборки, stdin JSON и конкретные примеры; не читает stdin и не создаёт сервисы. T1 и прежние ошибки argv работают. |
| C1-T3 | Справка `COMMAND --help` для публичных команд | Для каждой команды объясняет фактическую форму входа и ограничения; согласована с общей справкой и X-1. Ошибочные сочетания argv не становятся успешными. |
| C2-T1 | Локальный installable bundle из уже собранного dist-бинарника | Скрипт создаёт в отдельном каталоге один бинарник, полный skill, manifest исходной ревизии/цели/версии и SHA-256 содержимого. Не компилирует заново, не скачивает и не публикует. Неверный/неполный вход отклонён без изменения исходников. |
| C2-T2 | Установка bundle в явно заданный пользовательский prefix | Скрипт проверяет manifest/checksums и кладёт бинарник/skill в документированные пути внутри prefix. Повторная установка того же bundle безопасна; испорченный bundle и целевая коллизия не портят прежнюю установку. Без root и сетевых запросов. |
| C2-T3 | Исполнимая проверка установленной поставки | Использует установленный бинарник и skill вне source tree/target; в одноразовом repo проверяет check → search → inspect → reindex. Диагностирует отсутствующие/повреждённые компоненты; не зависит от новых flags C1. Содержимое оригинальной установки/проектов не меняется. |
| C3-T1 | Две одновременные document embedding операции одного drain | Ограниченные `std` workers с blocking I/O допускают две перекрывающиеся операции на разных hash; ни in-flight, ни буфер текстов/результатов не превышает 2. Один coordinator владеет embed.lock и короткими сериализованными storage writes, HTTP вне транзакций. |
| C3-T2 | Корректность out-of-order результатов и ошибок | Дубли hash не отправляются одновременно, попытка записывается до HTTP; malformed/failure не теряются и не крутятся бесконечно. Изменение/удаление текста или config не допускает принятия устаревшего результата; лимит попыток сохранён. |
| C3-T3 | Сквозная интеграция bounded drain с CLI и жизненным циклом | Настоящий отсоединённый drain выполняет перекрывающиеся requests, второй владелец не проходит, search работает параллельно; смерть drain освобождает lock и сохраняет попытки. Отмена foreground не убивает чужой drain; TK-29 semantics сохраняются. |

Для C1-T3 публичные команды берутся из frozen X-1/сборки, включая config после
TK-29; `embed --drain` получает отдельное явное правило справки до чтения stdin.
Это предлагаемое расширение #53, утверждаемое этой спецификацией, а не уже
реализованная возможность.

Для C2 T1–T3 договор автора: `PREFIX/bin/letopis` и
`PREFIX/share/letopis/skills/letopis/SKILL.md`; переносимые локальные скрипты без
нового product CLI. Manifest описывает фактическую host-цель, не приписывает
проверку четырём платформам. Проверка поведения использует заранее заданные
literal Markdown/source bytes и независимые hashes; отсутствие нового feature
критерия должно подтверждаться отдельно от уже существующих regression checks.

Для C3 фиксированная граница **2**, без нового config-поля, batching или async.
T1/T2 изменяют существующий embedding service и проверяются через уже имеющиеся
`wire_embedder` → `Embedder::drain` с настоящим временным storage и управляемым
локальным HTTP. Это библиотечная граница действующего компонента, не новый
продуктовый API, альтернативный executor или тестовая копия алгоритма.
T3 — отдельная coding-задача на executable integration fixtures, supervision и
исправление обнаруженных границ процесса: она проверяет настоящий binary,
автозапуск и чужие процессы вместо прямого вызова сервиса. Существующая CLI
связка естественно получает изменения T1; повторное искусственное подключение
через новый слой не требуется. Oracle T3 на исходном seed обязательно содержит
новый критерий перекрывающихся HTTP requests, а не только уже зелёные lock checks.
Если T1 заранее реализовал часть T2/T3, это фиксируется по фактическому diff;
оператор не удаляет готовую корректность ради принудительного объёма правок.
Технологический выбор workers/storage sharing и необходимость `Send` остаются
исполнителю при соблюдении hexagonal boundaries. Предложение применимо только
к экспериментальной задаче #49; оно не меняет последовательный дизайн основного
продукта и не обещает speedup. Fake HTTP со ступенчатыми barriers проверяет
перекрытие и пределы независимо от реальной скорости модели. Сравнение throughput
настоящего провайдера/whole-stack RAM из #49 остаётся за его владельцем.

Это **частичные инкременты** #43/#49, не их полная приёмка: нет внешнего релиза,
четырёхцелевой установки, G-3, производственных модельных/RAM-замеров. Патчи
участников не вливаются автоматически и не закрывают issues. Подготовка TK-30
создаёт задания и проверки, но не reference implementation ни одной задачи.

## 5. Одинаковые старты, разные условия

У каждого из шести экземпляров `chain × condition` — независимые Git object
store, workspace и память; `.git` не ссылается на основной checkout и не имеет
remotes/alternates/старых objects. Из общего frozen inventory создаётся свой
одно-коммитный seed. Связь исходного commit с seed и полный список исключений
сохраняются у оператора; seed OID не выдаётся за original main OID.

Две копии одной цепочки побайтово одинаковы по agent-visible исходникам,
документам и тестам. Каждый слот получает новый HOME, CODEX_HOME/agent state
и новый разговор. Переносятся собственные product code/docs предыдущего слота;
raw conversation, compaction, scratch notes и operator feedback не переносятся.
Обычные изменения документации продукта доступны обоим условиям; личные
межсессионные заметки baseline не подменяются файлами в рабочем каталоге.

В memory отдельный корпус пуст в начале **каждой цепочки**, затем сохраняется
только записанное самим участником. Нет корпуса проекта Engram, заметок TK-17,
исходного чата, чужой цепочки или prefilled дизайн-доков в памяти. Участник сам
выбирает структуру Markdown-каталогов и что сохранять. Отсутствие записей/чтений
остаётся результатом; оператор не дополняет память ради успешного сравнения.

Read-only бинарник памяти и skill фиксируются из интегрированного продукта
после TK-29, хранятся отдельно от изменяемого participant source/target и не
подменяются экспериментальной сборкой C3. Полный профиль включает настроенный
embedding provider и query embeddings; FTS-only не объявляется полным пилотом.
Ошибки/деградации записываются, настройки не меняются после начала наблюдений.

## 6. Отсутствие утечек и проверка результата

Операторские prompts будущих задач, acceptance sources, rubric, ожидаемые
ответы, логи другого условия, TK-17 raw evidence, текущий Engram, исходный
repository/.git/другие worktrees и глобальная agent memory недоступны участнику.
Будущие задачи выдаются только в начале соответствующей сессии. Общий доступный
набор docs/tests заранее перечислен и одинаков; требуемые AGENTS.md и design
contracts остаются доступны. Operator-only pilot файлы исключаются явно и
одинаково до вычисления starting_code_sha256.

После слота результат захватывается **до** независимой оценки. Evaluator
получает одноразовую копию: его hidden source/target/logs/cache не монтируются
обратно в participant. Недостаточно вынести только Cargo target: build.rs и
другой код участника может читать oracle и записать его в любую доступную копию.
Следующая сессия получает исходный captured participant state, не evaluation copy.
Проверка inventory до/после evaluator подтверждает отсутствие write-back.

Локальные model-free проверки подготовки должны обнаружить: доступ к canary
оператора/другого условия, ненулевую начальную память, shared Git/target, попытку
toy build.rs записать private marker и несоответствие captured inventory.
Проверяются login-shell PATH для pinned Rust/cargo/rustfmt/git/rg/Python,
запуск установленного memory CLI и готовность локальных fixtures. Это конкретные
проверки границы, не обещание защиты от любого hostile кода.

Каждое новое acceptance поведение имеет независимый oracle, видимые operator
check IDs и негативный контроль. Сборка/тесты участника используют его обычный
target; приватная оценка — свой. Старые готовые решения, product patches и
successful session records не входят ни в image, ни в fixtures. Непроходящий
новый критерий seed отличают от регрессии или поломанного окружения.

## 7. Замораживание и исполнение в последующих задачах

Целевой harness — **Codex CLI `0.164.0`**, тот же тип запуска, что в TK-17.
Локально проверены только `codex --version` и `codex exec --help`; это не
проверка входа в аккаунт/модели. Будущий frozen image закрепляет CLI bytes/digest;
каждый слот использует новый `codex exec --ephemeral --json`, не resume/fork.
Смена harness или недоступность версии требует пересмотра подготовки до freeze,
а не универсального экспортёра. Общая конфигурация отключает внешнюю память и
непредусмотренные agent hooks/plugins/delegation; подключение Letopis и его skill
— единственное различие условий, описанное отдельными instructions.

Источник ledger — сохранённые raw Codex OTLP/HTTP JSON events о запросах и
`response.completed` counters, операторский collector и participant JSONL/exit
metadata. Это тот же механизм, что `tests/early_pilot/{network,evidence}.py`
в закреплённой ревизии TK-17. Request inventory и counters сохраняются раздельно,
со своим scope и correlation; одного итогового footer/равенства числа событий
недостаточно. Retry/error/control completions не отбрасываются. Неустановленная
связь или неполные события означают unknown/incomplete, не zero и не полный ledger.
Embedding usage фиксируется отдельно средствами выбранного provider/tool;
неизвестные counters также остаются null. Новая live telemetry не подтверждена.

До TK-31 фиксируются study_id, 9 prompts, check_ids, agreement_ids/reuse_from,
selection rationale, рубрика research facts, inventory/hash каждого seed,
порядок всех 18 слотов, harness/model/config и версии memory binary/skill,
embedding model/config, tool/network policy и лимиты времени/turns/tokens/retries.
Одинаковый agent/model/config в обоих условиях; auxiliary calls учитываются.
Конкретные model/revision/budget не выдумываются на этапе спецификации: builder
готовит заполняемые manifest поля, оператор фиксирует доступные значения до
freeze. Неизвестная immutable revision остаётся явно неизвестной.

Порядок по существующему P-1: C1 baseline→memory, C2 memory→baseline,
C3 baseline→memory; внутри условия T1→T2→T3. Это не статистическая рандомизация.
Нет одновременного выполнения scored сессий и конкуренции за один provider.
Между цепочками code/corpus не переносится. При failed/incomplete T1/T2
зависимые слоты — not_run; скрытое исправление оператором и selective replay
запрещены. Новый study после пересмотра не заменяет прежние records.

Подготовительный manifest со свободными полями обозначается draft/unready;
его не подают checker как состоявшийся pilot. Для локальной проверки формы
применяется отдельно помеченная demonstration fixture, а не подложные реальные
session logs. Изменять P-1 checker ради удобного verdict или 4-slot mini нельзя.

Будущий явный paid запуск проверяет frozen inputs и отдельное разрешение до
чтения auth/старта agent/provider. Сейчас нет даже платного tool/model probe.
Без credentials можно проверить только локальную инфраструктуру; actual model
identity, access и telemetry остаются непроверенными. Материалы TK-30 не дают
автоматического разрешения на TK-31/TK-32 или дополнительные ретраи.

## 8. Наблюдения и ограничения вывода

Сохраняется P-1 v1: полная корректность, повторные исследования, нарушения
договорённостей и все фактические input/output tokens, включая retries,
compaction/delegation и embedding/auxiliary calls. Cached/reasoning — подмножества,
а не повторное сложение; разные токенизаторы не переводятся в цену. Независимый
request inventory сверяется с usage; неизвестные значения — null, не нули.

Пропуски, failure/not_run, отсутствие использования памяти и неизвестная
семантическая классификация не исключаются из отчёта. Полные traces и workload
rows передаются TK-33; общие source docs доступны обоим условиям. Нет заданного
процента выигрыша, гарантии экономии или статистической/каузальной интерпретации
трёх цепочек. Подготовка не проверяет качество embeddings и G-3/G-4.

Исторический TK-17 изучен по `tk-17@a53ba2cc7fe2803c564d54ac89f777aee61bfd56`:
`docs/zkit/letopis/checks/TK-17/report.md` и `mini-02-preparation.md`,
`tests/early_pilot/`. Эти файлы не присутствуют в текущем main; нельзя ссылаться
на них как на уже доступный runner. При реализации переносить только нужные
общие механизмы после чтения и закрепления их исходной ревизии; не сливать весь
TK-17 или старые ответы/records. Урок evaluator write-back обязателен; старые
результаты/подготовительные proofs не становятся evidence TK-30.

## 9. Артефакты, границы и приёмка подготовки

Предлагаемые владельцы будущих файлов:

- `docs/zkit/letopis/pilot/final/`: prospective selection, prompts, инструкции,
