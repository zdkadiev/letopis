# Issue #108: пакетное чтение исторических источников

Статус: спецификация согласована пользователем целиком в разговоре 2026-11-10.
Изменение границы наблюдения исторических объектов согласовано отдельно ранее
в том же разговоре. План реализации требует отдельного согласования.

Задача: [#108](https://github.com/zdkadiev/letopis/issues/108), подзадача
[#100](https://github.com/zdkadiev/letopis/issues/100).

## Цель и основания

Устранить повторное разрешение Git-пути, чтение, декодирование и проверку одного
исторического файла ради разных диапазонов внутри `observe_sources_batch`.
Нужные границы строк определяются одним проходом по полученным байтам; каждый
уникальный адрес источника хешируется один раз в пределах бюджета.

Сейчас `SnapshotObservations` сохраняет результаты по `(TreeOid, SourceUri)`.
Повтор одинакового диапазона уже использует этот результат; разные диапазоны
одного пути заново вызывают `blob_get_by_tree_oid_and_path` и `select_bytes`.

В локальном синтетическом профиле 10k знаний от 2026-11-10 исторический lookup
занимал 50,3% sampled CPU `check` и 51,5% `status`. Это вложенные CPU scopes,
а не доли wall time и не доказательство ускорения предложенного алгоритма.
Нужен новый сопоставимый baseline; локальные captures в игнорируемой
`.artifacts/profile-20261110-*` не считаются опубликованным evidence.

## Принятое решение о наблюдении

Пользователь согласовал: первое успешно прочитанное и проверенное содержимое
исторического файла используется для всех запланированных диапазонов его группы
`(TreeOid, RepoPath)` внутри одного batch. Повреждение, исчезновение или изменение
Git policy после этого чтения может не обнаружиться при выдаче сохранённого
результата. Следующее фактическое обращение к Git проверяет объект и применимые
политики заново; следующий batch не наследует результаты предыдущего.

Это узкое изменение прежнего решения из
[спецификации #65](2026-11-05-issue-65-refresh-design.md#2026-11-06-native-profiling-continuation):
разные диапазоны больше не требуют независимого физического чтения одного файла
внутри успешно подготовленной группы. Это не атомарный снимок всех Git-объектов
или рабочей копии на всё время команды.

Git-компонент продолжает проверять каждое фактическое чтение. Его raw reader,
проверка целостности объектов, closure audits и сильные операции закрепления
не получают payload cache и не ослабляются. Повторное использование принадлежит
только provenance service. `compare_revision` остаётся вне этой оптимизации.

## Сохраняемые гарантии

- Вход и результат сохраняют порядок `ProvenanceRequest`; источники внутри
  запроса обходятся в существующем порядке `BTreeSet<SourceUri>`.
- Для каждой локальной привязки выполняется отдельный свежий live capture,
  после востребованного исторического результата и до следующей привязки.
- Флаги, причины и типизированные ошибки остаются прежними на стабильном Git.
  Первый востребованный I/O failure сохраняет порядок с учётом явно принятого
  повторного использования успешной исторической группы.
- Планирование не выполняет I/O. Будущие группы, корни и пути заранее не читаются.
  Ошибка Git следующей группы не опережает ошибку текущего live capture.
- Недоступные/невалидные корни не получают новую отрицательную мемоизацию;
  повторное обращение может увидеть восстановление, как сейчас.
- Отсутствие файла не считается успешным чтением группы и не создаёт групповой
  кеш отсутствия. Существующее переиспользование точного `(tree, source)`
  результата `None` остаётся в рамках прежнего ограниченного кеша.
- Отсутствие диапазона в успешно прочитанном blob — результат выбора байтов
  именно этого содержимого. Его можно переиспользовать для этого адреса источника
  вместе с остальными результатами успешной группы.
- HTTP/HTTPS не загружаются; отсутствие basis сохраняет прежнюю диагностику.
- Нет SQL-публикации, новых refs, изменений Markdown, HEAD или реального Git index.
  `nodes.hash` и `search_hash` не подменяют историческое или свежее сравнение.

## Алгоритм

### 1. Ограниченный план без I/O

Просмотреть только переданный batch. Для локальных адресов с объявленным basis
собрать группы по `(TreeOid, RepoPath)` и уникальные адреса источников каждой группы:
целый файл либо включительный диапазон. Разные trees остаются разными группами.
План хранит ссылки на исходные значения, где это позволяет lifetime; не копирует
байты файлов и не строит новый список всего корпуса.

План принимается целиком либо отклоняется целиком до I/O. Если он не помещается
в бюджет, весь вызов использует существующий последовательный алгоритм с его
ограниченным кешем точных исторических результатов. Допустимый вход не
отклоняется и не обрезается. Такое решение исключает переключение одной группы
между разными историческими содержимыми из-за частично заполненного кеша.

### 2. Ленивое чтение успешной группы

Выполнять существующий последовательный обход запросов. Корень проверять в
прежнем месте, сохраняя ограниченное переиспользование доступного root.
При первом востребованном источнике группы:

1. Через существующий Git interface разрешить путь и получить проверенный blob.
2. При ошибке распространить её в прежней классификации. При `NotFound`
   применить прежнее поведение точного адреса; группу не считать подготовленной.
3. При успехе вычислить результаты всех запланированных адресов источников этой группы.
4. Сохранить компактные результаты группы и освободить буфер blob до live capture.

Если файл сначала отсутствовал, а позднее стал доступен, новый ещё не сохранённый
точный адрес может инициировать успешное чтение группы. Ранее сохранённые точные
результаты имеют приоритет: первая успешная группа не переписывает их задним
числом. Это сохраняет существующую семантику отрицательных точных результатов.

После успешной подготовки группы последующие её адреса не выполняют Git I/O.
Другие группы читаются только при собственном первом обращении.

### 3. Границы строк и хеши

Собрать и отсортировать только необходимые границы запрошенных диапазонов строк. Одним проходом
по байтам определить смещения этих границ и доступность полных диапазонов.
Не создавать полный массив каждой строки и отдельные копии фрагментов.

Семантика совпадает с `LocalSource::select_bytes`:

- строки нумеруются с единицы, обе границы включительны;
- LF входит в завершаемую строку; CR сохраняется;
- последняя строка без LF учитывается; завершающий LF не добавляет пустую строку;
- целый пустой файл имеет валидные пустые bytes;
- отсутствующий или неполный диапазон даёт `None`;
- UTF-8 декодирование и нормализация не выполняются.

SHA-256 вычисляется по заимствованному срезу исходного буфера для каждого
уникального валидного адреса источника. Перекрывающиеся разные диапазоны хешируются
отдельно: обычный SHA-256 не позволяет вычитать хеши префиксов. Для B байт файла,
R уникальных диапазонов и H суммарных байт срезов обработка занимает
`O(B + R log R + H)`, не считая Git traversal, decode и integrity verification.

### 4. Свежая текущая привязка

Получить свежие live bytes и текущий SHA-256 через прежний путь каждой привязки.
Сравнить с историческим результатом и сформировать прежние flags/issues.
Кеш текущих файлов не добавляется. Все дополнительные структуры освобождаются
при возврате или ошибке batch; singleton `observe_sources` сохраняет тот же
внешний контракт и отдельное время жизни наблюдения.

## Бюджет и fallback

Предлагаемые инженерные значения, выбранные автором и не отдельные требования
пользователя: сохранить 4096 как верхнюю границу суммы уникальных roots и точных
исторических результатов; ограничить объём адресных строк плана 1 MiB.
Для оценки учитывать все уникальные roots и адреса источников до I/O, а также полные
строки tree/path/адресов, даже если реализация хранит заимствованные ссылки.
Число групп и границ ограничено числом адресов источников; одноразовые вспомогательные
структуры имеют линейный размер относительно принятого плана. Проверки размеров
не должны переполнять счётчики. Новых CLI/config параметров нет.

План заранее резервирует место результатов всех своих адресов источников и roots, чтобы
успешная группа не теряла отдельные хеши при заполнении кеша. Число записей и
размер адресов ограничены независимо: один длинный путь не обходит бюджет.

Буфер одного blob существует только во время подготовки группы. Ограничение
дополнительного кеша не является новым ограничением допустимого размера файла:
полное чтение blob уже существует, его пик RSS измеряется отдельно. Нельзя
удерживать payload нескольких групп или создавать дополнительную полную копию.
Обещание одного успешного чтения относится только к принятым планам; fallback
сохраняет корректность без обещания той же производительности.

## Владение и границы реализации

`ProvenanceService`/его приватное состояние владеют планом и жизненным циклом
результатов в `src/service/provenance.rs`; тесты — в `provenance_test.rs`.
Чистая операция определения диапазонов принадлежит domain рядом с текущей
семантикой выбора байтов, если для неё нужен отдельный API; точную сигнатуру
определяет план. Git остаётся владельцем разрешения пути и проверки объектов.

При реализации обновить batch-документацию `SourceProvenance`, раздел I-4/I-7
и mechanics со ссылкой на принятую новую границу наблюдения. Историческую
спецификацию #65 не переписывать: она описывает гарантию своей реализации.
Не добавлять новые infrastructure-компоненты, runtime, зависимости, схему БД,
кеш между вызовами, дедупликацию по blob OID между разными tree/path или смену
SHA-256. Оптимизация `collect_source_references` и параллелизм — отдельные задачи.

## Проверка корректности и результата

До изменения продукта зафиксировать baseline на текущем исходном коде и
воспроизводимых входах. Тесты и последующее сравнение должны покрывать:

- один tree/path с разными, повторными, вложенными и перекрывающимися диапазонами;
  один исторический успешный blob read и один hash на уникальный валидный адрес источника;
- независимые trees и пути; результат против прежнего алгоритма и независимых
  ожидаемых byte slices, не только сравнение двух новых helper-функций;
- пустой файл, LF, CRLF, отсутствие финального LF, бинарные bytes, целый файл,
  неполные и большие диапазоны без переполнений;
- fresh live capture для каждой привязки, конкурентное редактирование/удаление,
  первая ошибка live до будущей ошибочной исторической группы;
- отсутствие/восстановление root и blob, сохранение точного `None`, недоступный
  диапазон, классификация Git policy, type, corruption и I/O ошибок;
- повреждение/удаление после первого успешного чтения: оставшиеся диапазоны
  используют подготовленный результат, следующий batch читает и проверяет заново;
  прямое повторное Git-чтение и strong closure audit всё ещё обнаруживают повреждение;
- граничный/превышенный entry budget, длинные адреса, fallback, отсутствие частичного
  плана и удержания состояния между вызовами, освобождение при ошибке и отмене.

Счётчики чтений/декодирований и вызовов hashing подтверждают устранение операций;
они не заменяют wall/CPU/RSS. Использовать существующий performance harness либо
изолированное временное instrumentation с сохранением его patch/идентичности;
не добавлять продуктовый observability API ради эксперимента.

На одинаковых 10k/100k входах сравнить повторные диапазоны одного файла и контроль
с уникальными файлами; для доступных сценариев получить минимум три чередующиеся
успешные baseline/candidate пары. Сохранять timeout/error отдельно, не повторять
автоматически тяжёлую неуспешную серию. Указать CPU/platform/build/input hashes,
conditioning, нагрузку общего хоста и ограничения OS cache. Samply captures
получать отдельно от обычных измерений; вложенные CPU scopes не складывать.

Показать оставшуюся стоимость SHA-256 после группировки отдельно от Git и поиска
границ. Проверить поддерживаемое текущей библиотекой ускорение на целевом CPU;
смену алгоритма не включать автоматически. Ускорение признаётся только по замерам
с сохранёнными результатами команд; процент из числа чтений не выводится.

До завершения реализации пройти требуемые проектом Rust-проверки, зафиксировать
evidence и ограничения в отчёте, обновить соответствующие знания Letopis.
Эта спецификация сама по себе не утверждает реализацию, успешные тесты или
производственный выигрыш. После её согласования нужен отдельный план реализации.

Проверка проекта документа 2026-11-10: независимый builder check не выявил
существенных вопросов перед планированием (`nothing important left`). Локальные
ссылки проверены; это проверка документа, не подтверждение реализации.
