## Existing evidence and boundaries

`status` is already an observation-only command. It reports the last published revision, locks, vector backlog/exhaustion and current problems, using one database read view; it does not refresh, launch drain, run inference or modify diagnostics. TK-26 provides prior corruption/recovery and current-invalid-file evidence, including a failure returned as an infrastructure error rather than a fabricated result. TK-27 provides reviewed embedding and retry behavior. Reference these results at their captured revisions; do not relabel them as new runs. Verify the narrower write-failure and combined CLI lifecycle below before marking the two open criteria complete.

No history table, separate `errors` command, error-clearing command, runtime, provider, configuration field, storage schema or new background process is introduced. Preserve the DDD/hexagonal boundaries: status and foreground orchestration remain in services, the CLI dispatches through their interfaces, concrete persistence and process behavior stay in their owners, and `lib.rs` remains the composition root. Make product changes only for a reproduced TK-28 defect.

## Observable behavior

1. **Storage failure while publishing a file diagnostic.** From a known valid published state, make an authored file invalid and deterministically fail the storage operation that would commit its `files.error`, using only a disposable test repository/database. The publishing command returns a safe infrastructure error, not a successful response or a fabricated saved validation error. The old publication and revision remain coherent. A fresh `status` observes the last committed state; it must not report the uncommitted file error as persisted. After removing the injected fault, a new publication stores the real file diagnostic, which survives a fresh process/status call and disappears after the file is fixed and republished. The failure fixture must prove the fault was reached and that its canary is not exposed. Reuse TK-26 corruption/cache-loss evidence for its existing scenarios; do not assume generic database corruption proves this write-path case. SQLite validates the schema on open, so a trigger installed beforehand is rejected too early. If using a trigger, install it in a disposable database only after the tested process has opened and validated storage, synchronize deterministically, and remove it before a fresh CLI status opens the database. A test-controlled Git wrapper or an existing private process checkpoint may provide the barrier; verify the write fault was actually reached. A private service-process fallback and separate CLI error-mapping checks have narrower scope than a product-binary end-to-end test and must be reported as such.
2. **Query failure and recovery.** In a real command lifecycle with matching vectors and unchanged valid config, a failed query embedding leaves successful FTS results with no warning for that query failure. The single `vec.query_error` is safely updated and visible as `query_embedding_failed` in the next `status`, including after a process restart. Repeated failures update the one current record; they do not create an error history. A subsequent successful query embedding clears that record, and a later `status` no longer reports the query problem. Status itself does not call the provider or clear the record. Check input/response canaries never appear in public output or persisted safe diagnostics.
3. **Drain launch failure.** When pending work exists and launching drain fails, the foreground response remains successful and contains the existing safe drain-start warning; the warning is not written as a persistent status problem. In the search case, FTS results remain available. The independent query-failure test controls background work so its no-warning assertion is not confused with an unrelated drain warning. The card's «drain not started» describes the warning; preserve the current contract and safe wording unless evidence demonstrates a mismatch. Force launch failure through an existing injectable process boundary or isolated fixture; report which real CLI, service and process paths the test actually executes. Do not claim a full product-binary scenario from a service-only double.
4. **Current-state semantics.** Preserve already accepted revision/lock/backlog, file/graph/config diagnostics, single pinned database view and safe failure behavior. `status` has no atomic snapshot across the live config file, Git observations and lock probes; do not assert stronger synchronization. Do not claim a previously committed problem disappears merely because an uncommitted attempted update failed.
