# Изменившиеся источники в check и status

[Issue #115](https://github.com/zaurkadiev/letopis/issues/115)

## Цель

Команды `check` и `status` перечисляют элементы знания, у которых изменились адресованные байты источников.

## Подход

Расширить существующее наблюдение provenance. При обнаружении различия тем же сравнением SHA-256 сохранить адрес источника вместе с флагом `SourceChanged`. Адрес добавляется, когда оба набора адресованных байтов доступны и их хэши различаются. Сравнивается один и тот же файл или включительный диапазон строк в объявленном `source_snapshot` и рабочем дереве.

Общий сборщик `CheckObservations` использует эти адреса и существующие `issues` из одного пакетного наблюдения. Сам флаг `SourceChanged` также служит сигналом перепроверки при отсутствующем или недоступном снимке. Адреса подтверждённых различий позволяют сохранить эту семантику в `search` и `traverse` и перечислить в диагностике адреса, для которых установлено различие байтов. Повторное чтение и сравнение источников потребовало бы дополнительных обращений к рабочему дереву и могло бы наблюдать другие байты.

## Согласованное имя поля

Находки проверки знаний выводятся в `result.problems` обеих команд. Для клиентов `check` это переименование `result.errors` в `result.problems`. Ошибка выполнения команды выводится в поле верхнего уровня `error`.

## Диагностика изменившегося источника

Каждая команда возвращает одну запись в `result.problems` на элемент знания с изменившимися источниками. `targets` перечисляет все уникальные изменившиеся адреса этого элемента. Пример ответа `check` для одного элемента приведён ниже. В `status` та же запись находится в `result.problems` рядом с другими текущими проблемами. Команда наблюдает привязки последней опубликованной ревизии и текущие файлы источников.

```json
{
  "ok": true,
  "result": {
    "problems": [
      {
        "code": "validation_failed",
        "message": "knowledge source changed",
        "details": {
          "element_id": "a.md",
          "path": "a.md",
          "targets": ["src/x.rs#L1-L5"],
          "reason": "source_changed"
        }
      }
    ]
  }
}
```

`check` и `status` выводят первые 100 записей в `result.problems`. Лимит общий для всех видов проблем в одном ответе. После отбора по области проверки команда сортирует и устраняет дубли в существующем порядке, затем ограничивает итоговый массив. При отсутствии проблем массив пуст. Все изменившиеся адреса элемента входят в одну запись.

## Поведение команд

- `check.paths` фильтрует `result.problems` по пути файла-владельца. Обновление кэша охватывает весь корпус. Пустой список или отсутствие `paths` запускает полный аудит замыканий снимков по D-105.
- `source_not_found`, `missing_source_snapshot` и `source_snapshot_unavailable` попадают в `result.problems` обеих команд. Если байты одного источника изменились, а другой источник отсутствует, элемент получает две диагностики в одном массиве. `stale` остаётся флагом элемента в командах чтения. `check` и `status` его не перечисляют.
- `check` возвращает код 0 при успешно сформированном отчёте с `ok:true`, в том числе при непустых массивах находок. Ошибка самой команды возвращает код 1 с `ok:false`.

## Проверка

Проверить сбор наблюдений юнит-тестами. В интеграционных тестах проверить сравнение диапазонов и целого файла, уникальные адреса, обе ошибки снимков, отсутствие источника, невалидную разметку, фильтрацию, ремонт привязки, чистый корпус и код выхода. Для одинаковой опубликованной ревизии сверить сигналы изменения в `search` и `traverse`. После зелёных тестов вручную изменить условие, подтвердить падение теста, восстановить код и прогнать `make fmt` и `make verify`. Обновить X-1, справку, руководство операций и issue.
