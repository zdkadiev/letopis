## Назначение

Соединить результаты TK-7…TK-13 в воспроизводимый пользовательский путь: агент
читает исходный код, сохраняет решение и ссылки в обычном Markdown, а следующая
сессия находит это знание настоящим CLI, получает его точный Git-снимок и использует
актуальный embedding. Подготовить минимальный способ загрузки корпуса для TK-15.
Это интеграционная задача; качество реальной модели, RAM и польза памяти здесь
не измеряются.

## Что уже реализовано

Проверено чтением исходников указанной базы; это ещё не приёмка TK-14:

- `src/lib.rs` связывает `DocumentRefresher`, `SearchService`, `InspectionService`,
  `EmbeddingService` и `BackgroundRunnerService` с реальными реализациями границ.
- Search и knowledge inspect обнаруживают и публикуют изменения через refresher.
  Гибридный query embedding уже подключён в TK-12; провайдеры получены из TK-13.
- `src/service/projection.rs` выводит source из external-ссылок, нормализует адреса,
  вычисляет доступные хеши/диапазоны и минимальный created_at, удаляет orphan source.
  Следует проверить достаточность этого пути для начального fixture, не переписывать его.
- `letopis embed --drain` обрабатывает опубликованные тексты последовательно,
  под kernel lock; отдельной очереди сообщений и постоянного процесса нет.
- Knowledge inspect возвращает метаданные и закреплённый Git tree, без текста.
  Полученный tree содержит захваченные файлы знаний; он не считается снимком исходников.
- Полная команда `check` пока недоступна. Полный source/mixed inspect, provenance
  и фильтры источников не реализованы. Нельзя демонстрировать их как готовые.

## Границы

Входит:

1. Сквозной сценарий с реальным product binary, реальными Git/SQLite/Markdown и
   production executor/provider transport. Управляемый HTTP Ollama fixture даёт
   детерминированные vectors без скачивания модели и внешней сети.
2. Начальный переносимый навык `skills/letopis/SKILL.md`: поиск существующего знания,
   сохранение нового решения, ссылки, чтение snapshot, обнаружение проблем и
   честная таблица доступности команд текущего slice.
3. Небольшой фиксированный fixture с знаниями, внутренней связью, source целого
   файла и диапазона строк; его воспроизводимая загрузка через существующий
   foreground CLI refresh, без прямого засевания SQL и без вызова библиотечного
   refresher вместо продуктового CLI. Seed vectors для приёмки запрещены.
4. Исправления только подтверждённых сквозным сценарием дефектов в этих границах.
   Изменение принятого контракта требует отдельного решения.

Не входит: генератор 100k знаний/100k source/500k рёбер (TK-15), RAM-проба (TK-16),
пилот пользы (TK-17), полный check/rename (TK-19), полный source lifecycle и provenance
(TK-20/21), source filters/traverse/mixed inspect (TK-22…24), обработка SIGINT (TK-29),
power-loss drill, поставка пакета (TK-43), новая команда импорта или записи знаний.

## Предлагаемый подход

Использовать существующую сборку и добавить проверяемый пользовательский маршрут,
не строить отдельный integration service. Документы остаются источником истины,
SQLite — пересоздаваемым кэшем. Простая загрузка = разместить файлы fixture в
изолированном Git-репозитории и вызвать search/inspect; корпус letopis не пишет.

Другие рассмотренные варианты: только инструкция не подтверждает интеграцию и
не даёт надёжного входа TK-15; отдельная import-команда/сервис дублирует текущий
refresh и увеличивает API без требования. Выбран первый минимальный путь.

### Маршрут агента

1. Искать уже известное решение. Читатель получает ссылки/строки, затем вызывает
   inspect для выбранных knowledge IDs. Inspect не возвращает содержимое.
2. Читать знания из `git show <snapshot>:<path>` и выделять указанные строки;
   текущие файлы можно читать напрямую, но без гарантии одного общего снимка.
3. Проверить исходник и записать знание обычным файловым редактором. Сохранить
   created_at при правке, использовать путь или явный якорь и корректные inline links.
   Не вкладывать размеченные элементы; includes задаётся ссылками.
4. Для external-ссылки указать root-relative адрес исходника (whole file или
   #Lstart-Lend). Source snapshot добавлять только как существующий tree,
   чьи адресованные bytes действительно проверены. В основном примере исходник
   заранее закоммичен, tree берётся из HEAD; его нельзя путать с inspect snapshot.
   Чтение оснований выполняется Git-командами без изменения пользовательского index.
5. В новом процессе CLI найти сохранённое знание и получить inspect snapshot;
   отдельный запуск `embed --drain` допускается для детерминированного ожидания
   фонового результата. Повторный запуск не пересчитывает уже актуальный текст.
6. Показать проверку новой сессии отдельно: свежий агент получает только навык,
   минимальный контекст fixture и публичный CLI. Зафиксировать действия/результаты;
   отдельный subprocess test сам по себе не называется проверкой агента.

Навык объясняет check и исправление ссылок как предусмотренный контрактом путь,
но явно сообщает, что check недоступен до TK-19 и не выдаёт вымышленный успешный
вывод. Полные source flags/inspect не используются для приёмки текущего slice.

### Источники и загрузка для TK-15

У fixture есть фиксированные входы и ожидаемые knowledge/source/edge counts,
нормализованные ID, source bytes/hashes и created_at. Внешние ссылки размечены
существующей X-4 грамматикой. База строится настоящим CLI из Markdown и source
файлов. Проверки через public Storage read API допустимы только как наблюдение,
не как альтернативный путь загрузки. Цель TK-14 — передать воспроизводимый маршрут
и форму входов, а не реализацию массового генератора или замер производительности.

### Ошибки и согласованность

- Без конфигурации embedding: знание находится FTS и читается через inspect,
  запросов к провайдеру нет.
- При отказе провайдера граф/FTS и corpus сохраняются; число попыток ограничено,
  ошибки безопасны, допустим последующий успешный drain по принятой политике.
- Невалидная правка одного Markdown сохраняет его прежнюю корректную проекцию
  и не блокирует валидные файлы. Inspect текущего невалидного знания может вернуть
  validation_failed; это не повод показывать старый текст как текущий.
- Для подтверждения отсутствия смешанной публикации нужен контролируемый отказ
  или прерывание процесса публикации: проверить rollback и успешный следующий
  refresh. Использовать существующие process/failure harnesses, если они подходят;
  ошибку Markdown нельзя выдавать за проверку падения процесса.
- Старый vector не представляет новый search_hash. Правка знания во время inference
  проверяется на observable результате и совпадении current hash; допустим
  временный orphan vector, который поиск не использует и drain удаляет.
- Повторная загрузка неизменного fixture идемпотентна: нет лишних graph revisions,
  source/edge дублей и повторного document inference.

## Архитектура и стиль

Сохраняются синхронный Rust I/O, один CLI binary и существующие kernel locks;
Tokio/daemon/IPC/новые зависимости не предлагаются. Domain содержит чистые правила,
service оркестрирует через application-owned traits, реализации технологий разделены,
handlers вызывают сервисы, wiring остаётся в lib.rs. При отсутствии продуктового
дефекта production Rust можно не менять. Изменения тестов и fixtures не дают
права обходить эти границы.

Соблюдать текущие Rust style/readability правила AGENTS.md: verb names, явные use,
малые функции, минимальную видимость, независимые ожидаемые значения и Arrange/Act/Assert.
Общие helpers переиспользуются только когда действительно есть несколько потребителей.

| Сбой не смешивает файлы/БД | Невалидный файл + валидный сосед; отдельное rollback/crash доказательство; повторный refresh и неизменность corpus |

| Source projection и загрузка готовы для RAM fixture | Независимые literals counts/IDs/hashes/created_at, production CLI loading, идемпотентный повтор, инструкция передачи TK-15 |
| Соблюдена структура программы | Проверка файлов/trait impl/import direction/lib wiring с названными файлами и evidence либо отсутствие production delta |

Для изменённого Rust обязательны `make check` и `make verify`. Новые проверки
должны заметить конкретную поломку: короткие компилируемые ручные negative controls
с восстановлением исходников, без полного cargo-mutants. Не переиспользовать старые
результаты как подтверждение нового дерева. Root checks не заменяют platform/native
harnesses. Состав host/Linux проверок определяется реальным delta и фиксируется
в плане; полный native stack повторяется только при соответствующих изменениях.

Evidence сохраняется в новом `.artifacts/tk14/` каталоге, отчёт —
`docs/zkit/letopis/checks/TK-14/report.md`; карточка, спецификация и план отражают
фактические результаты и ограничения. Не заявлять RAM, качество реальной модели,
x86, power loss или полный source lifecycle по контролируемому HTTP fixture.
