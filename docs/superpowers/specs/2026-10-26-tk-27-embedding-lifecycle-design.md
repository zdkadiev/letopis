## Behavior

- Configuration identity is SHA-256 of canonical JSON. Reordering keys or changing whitespace preserves identity, vectors and failures; changing any field, including `max_retries`, changes identity. Missing or invalid config cannot wipe existing vector state.
- A valid changed identity triggers a single `BEGIN IMMEDIATE` vector-store transaction that rechecks identity, rebuilds vec1 and clears vector keys and embedding failures while updating identity. A concurrent observer of the same identity must not erase subsequently stored work. A failure during reset rolls back the entire change; a previously pinned read view must remain consistent across reset and rollback.
- Work is derived from current knowledge search hashes without usable vectors and with remaining attempts. Sources are excluded; equal search hashes share a vector. Rebuilding the disposable cache leaves `vectors.db` intact and reuses matching vectors without provider calls, while newly introduced hashes are computed.
- Before each provider call, commit an attempt reservation in `embed_failures`; computing happens outside the write transaction. `max_retries` means additional attempts: zero gives one total and three gives four. Reservation survives process termination and restart, including termination before a response; an exhausted hash does not restart automatically while the same vector-store identity and failure state are retained. Changing identity or deleting vectors.db resets that state. Errors retain safe diagnostics and obey the same finite budget.
- Drain captures config identity. Publication or failure recording checks it within the write transaction. Once the stored identity has changed, a late result for the old identity cannot modify new vector/failure state and the old drain stops, provided no subsequent reset changes the stored identity back. A changed document is guarded by `search_hash`; its old vector must not represent the new text.
- For over-context input, preserve the whole searchable text in FTS and record a safe embedding failure using the ordinary retry budget; no splitting or silent truncation. Ollama native requests send `truncate: false`; compatible providers must meet the existing non-truncation contract. Do not add a universal guessed size limit or claim model-specific guarantees without evidence.
- Verify SIGINT against an actual drain process after an attempt is committed: process termination releases the lock, the attempt remains durable, and subsequent runs respect the remaining budget. Process-level handled cancellation and a `cancelled` JSON response for CLI commands remain TK-29, not this task.

## Concurrent configuration observation: unresolved finding

A process can read config A and pause before reset; the config file then changes to B, and a second process resets storage to B and records a B vector or failure. The first process can later reset storage back to its captured A. This is a code-derived risk, not yet reproduced. The current transaction rechecks stored identity against the captured identity; it does not establish that the file still contains that configuration. The existing MC-3 model checks two observers of the same new identity, not this schedule.

Consequences can include deleting B vectors **and B attempt records**, repeated provider calls or renewed retry budget, and interruption of work using B. It is not enough to describe this solely as recomputing a cache. Existing late-result protection applies when the stored identity is B; it does not prevent an older A reset from changing the stored identity back. What a concurrent search can return must be checked against its captured config and pinned view, not assumed.

First reproduce this schedule deterministically with independent observations of identity, vectors, failure attempts and later behavior. Assess the smallest remedy against the file-editing contract. No universal linearizability with arbitrary external file writes is implied: rereading a freely editable file is not atomic with a database transaction. Do not silently accept lost retry state or change how agents edit config. The remedy and intended guarantee require user review if the finding is confirmed; inability to satisfy an agreed criterion must be reported, not hidden by weakening it. Unexpected conflicts with canonical documents or a required design change similarly return for review.
