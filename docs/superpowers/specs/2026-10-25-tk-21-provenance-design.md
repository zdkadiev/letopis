## 1. Цель и основание

Знание остаётся находимым, когда источник изменился или исчез, но получает
проверяемые признаки необходимости перепроверки. Основание задаёт агент в
Markdown; Letopis не подтверждает знание автоматически при правке текста.

## 2. Утверждённая граница и существующая реализация

Пользователь утвердил: проверка происхождения при индексации и flags существующего
поиска входят в TK-21; поисковые filters остаются TK-22, source в CLI inspect — TK-24.

Переиспользуются без смены смысла:

- TK-8: `GitSnapshots::{read_blob,pin}`, `SnapshotVerifier`, типизированные ошибки,
  raw Git bytes, полный tree OID и существующий `refs/letopis/snapshots/` namespace.
- TK-20: `SourceUri`, `LocalSource::select_bytes`, точные локальные диапазоны,
  `SourceReader` с переданным pinned view; непрозрачные HTTP/HTTPS без fetch.
- `DocumentRefresher`: index.lock, повторное обнаружение изменений, публикация
  по файлу, сохранение последней валидной проекции, атомарный cache commit.
- `CheckService`: текущие snapshot-диагностики, общий graph diagnostics и выбор путей.
- `SearchService`: один pinned StorageRead для ранжирования/метаданных и проверка
  `stale` по текущему знанию; параметры query/limit и формат ссылок сохраняются.

Сейчас refresh не закрепляет основания, search выставляет только `stale`, а check
проверяет наличие/тип root tree, не сравнивая адресованные bytes. Эти пробелы
закрываются здесь. Отдельная таблица истории или сохранённых flags не нужна.

## 3. Канонические данные и редактирование

`source_snapshot` — один необязательный полный tree OID для всех external-связей
знания; external определяется целью Source, а не пользовательским именем типа
ребра. Произвольные типы отношений остаются разрешёнными; `includes` сохраняет
свою существующую системную роль. ID не назначается из метаданных файла.

Обычная правка текста с сохранённым прежним `source_snapshot` сохраняет основание,
даже если источники уже изменились. Только явно записанный агентом новый OID
меняет основание; новый OID всё равно проверяется. Letopis не пишет Markdown,
не подставляет HEAD/inspect snapshot, не наследует скрытое основание только из БД.

Утверждённое уточнение исполнителя: «без нового snapshot» означает, что старое
поле сохраняется в каноническом Markdown. Если агент удалил поле, основание в
каноне отсутствует: external-знание получает диагностику и признак перепроверки.
Восстановление кэша должно воспроизводить тот же результат, без истории SQLite.

## 4. Проверка оснований при публикации

Каждый уникальный OID в эффективных метаданных проверяется и, если доступен,
закрепляется существующим Git API. Это относится и к OID без external-ссылок:
указанный агентом снимок должен оставаться достижимым независимо от равенства bytes.
Одинаковые OID в пределах вызова не требуют повторной полной проверки/закрепления.

Перед успешным cache commit все найденные доступные основания должны быть pinned.
Недоступный root не мешает публикации корректной разметки; отсутствие основания
не делает файл синтаксически невалидным. Ошибка Git I/O, повреждение closure или
отказ публикации ref не маскируются под отсутствие: вызов завершается безопасной
ошибкой, незафиксированная SQL-публикация откатывается. Уже созданный корректный ref
может остаться при последующем rollback: атомарность Git+SQLite не обещается.

Основания сохраняемой последней валидной проекции также не теряют достижимость.
Последующее появление ранее отсутствовавшего tree проверяется и закрепляется при
следующем вызове, даже если Markdown не изменился. Повторная проверка не создаёт
новую SQL revision без публикации и не требует отдельного фонового процесса.
Если для этого требуется pin, координация использует существующий index.lock;
длинная проверка Git не должна расширять время SQLite write transaction без нужды.

Удаление ссылки/знания не удаляет старые Git refs и объекты. Сохранение старых
оснований — существующая политика TK-8/X-3, а не новая history-table или GC.

## 5. Наблюдение локального источника

Сервис получает метаданные знания и его external-привязки из одного переданного
pinned read view. Он сравнивает точные bytes каждого адреса в `source_snapshot`
с текущими bytes из confined FileSystem. Используется один и тот же нормализованный
путь и один и тот же включительный диапазон в обоих состояниях.

Переиспользуется `LocalSource::select_bytes`: без диапазона — весь файл, включая
пустой; с диапазоном — обе границы включены, LF/CRLF и бинарные bytes сохраняются,
неполный диапазон отсутствует целиком. Никакой UTF-8/EOL-нормализации и сравнения
только tree OID/commit OID. Изменение вне адресованного диапазона не меняет основание.

Текущий stored source hash не заменяет чтение Git и не доказывает текущие bytes.
Изменение исходника без изменения Markdown обнаруживается новым наблюдением.
В одном вызове допустимо временное разделение захваченного файла между привязками;
постоянный source cache и хранение текста в SQLite не добавляются. Нет гарантии,
что live-файлы не изменятся после чтения; следующий вызов наблюдает их заново.

HTTP/HTTPS остаются `Unfetched`: не читаются как локальные пути и не скачиваются.
Нельзя объявлять такой URL пропавшим или совпавшим с Git bytes. Доступный root
snapshot закрепляется, но проверка содержимого remote не заявляется.

## 6. Flags и текущая диагностика

Flags вычисляются при чтении, дедуплицируются и не сохраняются как жизненный цикл
в SQLite. Существующий `stale` относится к расхождению самого знания с индексом;
он независим от причин состояния источника. Расширяются `SearchFlag` и formatter
только значениями, уже предусмотренными X-1: `source_changed`, `source_not_found`.
Текст источников, excerpts и новые JSON-поля в выдачу не добавляются.

| Наблюдение | Flags источников | Диагностика check |
| --- | --- | --- |
| Нет external и нет snapshot | пусто | нет |
| Доступное основание, все локальные адресованные bytes равны | пусто | нет |
| Доступные локальные bytes различаются | `source_changed` | отдельная validation error не требуется |
| Текущий локальный файл/полный диапазон отсутствует | `source_not_found` | проблема источника по файлу знания |
| Путь/полный диапазон отсутствует в доступном основании | `source_not_found` | проблема источника по файлу знания |
| External есть, поле snapshot отсутствует | `source_changed` | `missing_source_snapshot` |
| Указанный root отсутствует либо не является допустимым tree | `source_changed` | `source_snapshot_unavailable` |
| Только remote с доступным основанием | пусто, содержимое неизвестно | не выдавать ложный not_found |
| Git corruption / policy / I/O / unsafe filesystem / ref failure | ошибка вызова | безопасная ошибка, не ложные flags |

Утверждённый выбор исполнителя: неизвестное/неуказанное основание отображается
в уже имеющийся `source_changed` как причина перепроверки. Это не утверждение
доказанного изменения bytes; точная причина находится в check. Четвёртый флаг
или новое поле `needs_recheck` не вводится. Если локальный текущий адрес отсутствует
одновременно с неизвестным основанием, обе независимые причины сохраняются.
Неизвестное remote-содержимое само по себе не является доказанным изменением:
пустые flags означают только отсутствие обнаруженной причины, не подтверждение знания.

Check использует общее наблюдение происхождения, сохраняет действующий выбор
owner paths, стабильную сортировку и дедупликацию. Проблема содержит адрес
`file:<путь знания>` средствами существующего formatter и безопасные details
элемента/источника/причины; исходные bytes не раскрываются. Диагностика вычисляется
из текущего состояния; отдельная persisted errors/history-таблица не появляется.
Отсутствие источника или snapshot не удаляет знание, FTS, рёбра или прежнее основание.

## 7. Сравнение ревизий для TK-22

TK-21 даёт общий сервисный примитив сравнения **одной** пары source + revision
с основанием **того же знания**, с типизированным результатом совпадения.
Вход — нормализованный SourceUri и точные tree OID; состояние различается явно:
равные bytes, неравные bytes, недоступный адрес/основание, remote unknown.
Внешнее разрешение Git-ревизий и JSON filters не реализуются раньше TK-22.

Два разных commit/tree C1/C2 с одинаковыми адресованными bytes дают совпадение,
даже если остальные файлы или строки вне диапазона различаются. Не допускается
сопоставить source одной привязки с revision другой. Отсутствующий путь/полный
диапазон в существующем запрошенном tree даёт несовпадение пары. Отсутствующая
явно запрошенная revision — `NotFound`, неверный тип/формат — `InvalidRequest`,
corruption — `InternalError`: неизвестный запрос не превращается в пустой поиск.
Отсутствующее основание знания остаётся состоянием перепроверки, не ошибкой запроса.

## 8. Архитектура и простота

- `domain`: чистые конечные состояния/сравнение значений при необходимости;
  никакого Git/FileSystem/SQL/CLI. Правила выбора bytes переиспользуются из TK-20.
- `service`: небольшой интерфейс происхождения, объявленный/реэкспортированный
  через `service/mod.rs`; concrete struct/impl в отдельном `service/provenance.rs`.
  Refresh, check и search используют общий смысл наблюдения, без трёх алгоритмов.
  Обычное read-наблюдение не закрепляет refs и не публикует данные: pin относится
  к сценарию индексации. Caller владеет refresh и pinned view.
- `git`, `filesystem`, `storage`: существующие реализации нужных интерфейсов;
  адаптеры не вызывают друг друга и не оркестрируют сервисы.
- `cli`: преобразование запроса/ответа; новые flags форматируются здесь,
  проверки происхождения не переезжают в handler.
- `lib.rs`: реальные constructor calls связывают collaborators. `main.rs` тонкий.

Сохраняются synchronous Rust, текущий toolchain и зависимости. Нет Tokio,
нового CLI/process, registry, history/schema migration, постоянного кэша источников,
web loader или нового формата Git refs. Реальные файлы/видимость/trait implementations
и импорты проверяются отдельно от линтеров. Имена, документация, Arrange/Act/Assert,
~40/максимум 60 строк функций и SeaQuery для затронутых обычных запросов — по AGENTS.md.

## 9. Проверки и evidence

Начальный `make check` от чистого base прошёл (2026-10-25, macOS; без продуктовых
изменений). Во время реализации нужны независимые literals/fixtures и отрицательные
случаи, а не ожидаемые значения, вычисленные кодом под тестом:

1. Индексация raw tree, pin и достижимость после Git GC; повторный refresh идемпотентен,
   в том числе после появления прежде отсутствующего root при неизменном Markdown.
2. Equal/changed/current missing/historical missing; LF/CRLF/binary/empty/EOF ranges;
   правка только вне диапазона; несколько причин и несколько источников без дублей.
3. Отсутствующее/неизвестное основание публикуется с диагностикой; wrong-type root,
   foreign OID format, corruption, pin failure и unsafe I/O различаются безопасно.
4. Edit с прежним snapshot, новый snapshot, удалённое поле и пересборка кэша;
   история старых bytes из Git, сохранение знания/FTS при source failures.
5. C1/C2 разные деревья/commits с равными выбранными bytes; другая привязка не даёт
   ложного совпадения; absent requested root — ошибка, absent range — несовпадение.
6. Search отдаёт только существующие X-1 link-поля/flags; `stale` сохраняется;
   source-only правки замечаются; HTTP/HTTPS не вызывают filesystem/network I/O.
7. Общий pinned view сохраняется; read-сервис не refresh/reopen/pin/write; индексная
   ошибка до commit сохраняет старую проекцию; пользовательский HEAD/index не меняются.

Новые meaningful tests проходят ручные точечные controls с восстановлением кода.
После продуктовых изменений — `make check` и перед завершением `make verify`.
Storage/native/build/vendor изменения потребуют соответствующего storage runner;
если их нет, нерелевантный runner не объявляется запущенным. Linux, реальная модель,
платный пилот и ресурсные gates не заявляются без отдельных запусков. Evidence
сохраняется отдельно от исторических TK-8/TK-20 receipts с точными revision/командами.
