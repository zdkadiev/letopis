# Issue 61 Init Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Status:** implemented on branch `issue-61-init` from the approved specification; verification and review evidence are recorded in [the issue 61 report](../../zkit/letopis/checks/issue-61/report.md).

**Goal:** Initialize a Git repository with service schemas and the approved nested configuration, preserving data while embeddings are disabled.

**Architecture:** A service-owned configuration value represents unconfigured, configured-disabled and enabled states. File readers share structural parsing and local provider validation; only enabled settings reach embedding execution. `InitService` owns setup order through filesystem/storage interfaces, `lib.rs` constructs collaborators, and `commands.rs` dispatches the command.

**Tech Stack:** Pinned Rust 1.95.0, existing serde/serde_json/JCS, rustix, rusqlite and synchronous Git/filesystem adapters. No new dependency or database schema.

**Spec:** [approved specification](../specs/2026-10-29-issue-61-init-design.md)

## Global Constraints

- Root contains the required `embedding_model` section; its five required fields are `enabled`, `provider`, `model`, `parameters`, `max_retries`. Reject unknown root/section fields and old flat files; do not auto-migrate.
- Generated defaults: `enabled: false`, `provider: null`, `model: null`, `parameters: {}`, `max_retries: 0`; write indented UTF-8 JSON with a final newline.
- Provider/model are both null or both configured; null values require empty parameters and disabled execution. Validate retained settings locally even when disabled. No validation network calls.
- Disabled embeddings use FTS, never infer/reset/start drain, preserve vectors and retry state, and report zero backlog/failures while hiding stored execution errors. Invalid configuration remains visible.
- Embedding identity is the JCS/SHA-256 of the existing four configured settings (`provider`, `model`, `parameters`, `max_retries`), excluding `enabled` and the root wrapper. This preserves compatibility across migration and enable/disable toggles.
- Git validation precedes writes; existing config validation precedes database creation. Preserve existing files and logical database contents. Retain completed setup after failure; retries finish publication/durability work.
- Application services own sequencing; adapters own I/O; `lib.rs` owns constructor wiring. Keep domain dependency-free; do not add a wrapper that merely bundles constructor arguments.
- Tests use independent expected values, Given/When/Then and meaningful mutation checks. Record restored-code verification and exact limits. Never modify historical evidence to match new behavior.
- Implementation runs through GPT Terra at extra-high reasoning in the isolated task worktree, only after user plan approval. Do not merge, push or update the GitHub issue without authorization.

## Review Focus

- Disabled but configured settings must still fail local provider validation when invalid (Task 1).
- Disable/re-enable must preserve vector identity, vector values and durable retry state, and hide/reveal stored failures correctly (Task 2).
- Invalid config with `enabled:false` must produce a status problem rather than being mistaken for a valid disabled state (Task 2).
- A concurrent config-publication loser must validate the winning file; an invalid winner must prevent init success (Task 4).
- Retrying after file/directory sync failure must complete sync work even if the config or service directory already exists (Tasks 3–4).
