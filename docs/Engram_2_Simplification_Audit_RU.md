# Engram 2.0 — аудит упрощения

Актуальное решение: пользователь сохранил прежнее асинхронное индексирование. Apply надёжно фиксирует документы и необходимое служебное состояние, включая задание обновления. Графовый, текстовый и векторный индексы обновляются после этого и публикуются вместе, только после готовности необходимых embeddings. Ошибка обновления сохраняет последний корректный индекс и не откатывает завершённую правку документов. Эти две границы описаны в [модели хранения](Engram_2_Storage_Model_RU.md). Физическая реализация и аварийная проверка ещё предстоят.

Дата: 12 октября 2026 года. Основания: [требования](Engram_2_Requirements_RU.md), [доменная модель](Engram_2_Domain_Model_RU.md), [сценарии](Engram_2_Scenarios_RU.md), [подсистемы](Engram_2_Subsystems_RU.md), [контракты](Engram_2_Contracts_RU.md) и [модель хранения](Engram_2_Storage_Model_RU.md).

Это проверка проектных решений и согласованности документов. Физический движок, DDL и аварийный протокол ещё не выбраны. Новые поля и команды этим аудитом не принимаются. Проверки ниже не подтверждают работоспособность будущей реализации.

## Применённые исправления

Пользователь принял уникальность UUID среди текущих nodes и edges без проверки истории. Прежнее пожизненное резервирование удалённых UUID заменено этим решением во всех активных описаниях. Отдельная identities и deleted-записи только ради такого резервирования исключены из проекта. Это явное изменение прежней гарантии по решению пользователя, а не доказательство её сохранения без реестра.

В модели хранения сокращены подробные описания непринятых вариантов: отдельной external_nodes, исторического реестра UUID, пометок удаления для него, тройки verified на каждом ребре и независимых source_revision. Вместо конкурирующих схем указаны выбранная модель и оставшиеся вопросы. Сами обязательные функции — история оснований, точная фильтрация по ревизии источника, атомарное восстановление — остаются.

Физическая уникальность UUID должна охватывать обе таблицы и конкурентные создания. Два отдельных первичных ключа сами по себе не обеспечивают межтабличную уникальность. Проверка актуального корпуса обязательна независимо от задержки поискового индекса. Долговечные source без ссылок остаются текущими записями, их UUID заняты.

## Уже выбранная унификация

| Механизм | Минимальное представление | Что сохраняется для агента |
|---|---|---|
| Знания и внешние источники | Одна nodes, kind и uri | Источник доступен по ID, сохраняет идентичность; будущее расширение адресов не требует отдельной таблицы на каждый способ доступа |
| Связи и включённость | Одна edges; includes — системный тип | Обычный и вложенный обход, совместное использование элементов, проверка циклов включения |
| Внутренний фрагмент метавершины | Вычисляется из includes и непосредственного членства концов | Нет второго массива детей, который расходится с рёбрами; метавершина остаётся самостоятельным понятием |
| Редактирование узлов и связей | Замена Markdown-фрагмента по ID; связи заданы ссылками | Нет второго интерфейса записи непосредственно в граф БД |
| Создание ID | tmp:000–tmp:fff внутри apply; UUID генерирует Engram | Создание нескольких элементов и ссылок одним вызовом, без команды предварительного получения ID |
| Проверка правки | apply --check использует подготовку и валидацию apply | Нет отдельного протокола verify; сохранение повторяет проверки актуального состояния |
| Актуальность | Единый flags и существующие коды ошибок | Нет дублирующих булевых признаков и списков причин в ответе |
| История содержимого | Git-объекты и удерживающие ссылки | В БД нет копий Markdown и исходного кода; Git-коммит не создаётся на каждую правку |
| Поисковый текст | Одно детерминированное временное представление для текстового индекса и embeddings | Нет разных правил очистки текста для двух поисковых ветвей |
| Embeddings | Общий порт для индексирования и поиска, сменные адаптеры | Нет отдельного клиентского контракта для каждой модели |
| Выполнение | Один локальный рабочий процесс проекта | Прикладные сервисы не требуют собственного процесса, StateService читает состояние владельцев |
| Обновление индекса | Обнаружение при CLI; полный и выборочный scope одного процесса индексирования | Нет постоянного watcher или отдельного алгоритма публикации для каждого режима |

Объединять индексирование и поиск в один модуль не требуется: они уже разделены по ответственности, но используют общие порты и опубликованное представление. DDD-контекст или прикладной сервис не обязывает создавать отдельные БД, транспорт и развёртывание.

## Различия, которые нельзя удалить без последствий

| Данные или механизм | Зачем нужны | Допустимое упрощение |
|---|---|---|
| ID и hash | ID сохраняет идентичность при изменении текста; hash проверяет прочитанные байты | Не заменять одно другим |
| Хеш элемента и file_hash | Первый допускает независимые правки соседних элементов; второй защищает создание в существующем файле | Не повторять file_hash в каждой строке nodes; способ кэширования ещё не выбран |
| Текущий hash источника и подтверждённое основание знания | Текущий код может быть новее кода, по которому сформировано знание | Старый хеш можно получить из Git; необходимость отдельного постоянного кэша обсуждается |
| Общее основание источников и снимок текущего текста знания | Edit без snapshot меняет текст, сохраняя прежнее основание | Не хранить подтверждение на каждом ребре, но сохранить адрес общего основания; окончательные поля ещё обсуждаются |
| Git tree OID и исходный commit OID | Tree адресует байты; точный фильтр по коммиту требует знать выбранный при подтверждении коммит | Физическая запись происхождения ещё не определена; нельзя восстановить её однозначно по tree |
| Снимок корпуса и версия опубликованного индекса | При одинаковых файлах могут измениться модель и параметры embeddings | Не нужен отдельный публичный ID автоматически; внутреннее представление должно учитывать конфигурацию |
| Поисковые данные и долговечное служебное состояние | Reindex восстанавливает производные данные, но не забытые подтверждения, незавершённое восстановление и UUID источников | Одна БД допустима, жизненные циклы и восстановление различаются |
| Оптимистические предпосылки и короткая защищённая фаза записи | Между проверкой и сохранением может появиться чужая правка | Не удерживать лок во время подготовки агентом; точный протокол сохранения ещё проектируется |
| Журнал операций и Git-снимок отката | Git хранит прежние байты, журнал определяет завершённость и необходимость отката | Один журнал может обслуживать несколько функций, но его удаление до разрешения исхода теряет гарантию восстановления |

Агрегат «метаграф проекта» не требует загрузки всего корпуса в память и одного глобального base_hash для каждой правки. Он задаёт правила целостности. Например, конкурентные добавления includes A→B и B→A должны проверяться против актуального итогового графа, иначе обе локально корректные правки создадут цикл.

## Закрыто: бессрочная дедупликация только по хешу

Ранее были приняты SHA-256 канонического исходного JSON и бессрочный возврат результата идентичного успешного запроса. Ниже сохранён контрпример прежнего правила. После обсуждения пользователь отменил бессрочную дедупликацию: агент перечитывает состояние после потери ответа, а новый вызов проходит обычные проверки. Новый параметр различения намерений не вводится.

Контрпример для одного элемента; ID и его служебная разметка сохраняются, A и B обозначают два варианта полного фрагмента:

| Шаг | Вход apply | Ожидаемое новое действие | Эффект прежней дедупликации |
|---|---|---|---|
| 1 | base_hash = H(A), markdown = B | A→B | Применено; результат сохранён |
| 2 | base_hash = H(B), markdown = A | B→A | Применено; результат сохранён |
| 3 | Полностью тот же JSON, что на шаге 1 | Снова A→B | Возвращён успех шага 1; текст остаётся A |

Упрощённый вход шагов 1 и 3 показывает существующие поля; значения текста и хеша здесь обозначения:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<H(A)>",
      "markdown": "<полный размеченный фрагмент B>"
    }
  ]
}
```

Выход обоих вызовов одинаковый, хотя шаг 3 не меняет документы:

```json
{
  "ok": true,
  "result": {
    "hash": "<один и тот же хеш правки>"
  }
}
```

То же ограничение возникает при create, последующем удалении и новом create с тем же JSON. Хешировать текущие байты корпуса дополнительно недостаточно: после возврата в прежнее состояние они тоже совпадут. Tree OID того же состояния также не различает эти события. Очистка истории или повторное выполнение при расхождении результата изменят уже принятые гарантии дедупликации.

Вопрос закрыт решением пользователя: повтор после потери ответа заменён чтением актуального состояния и подготовкой правки при необходимости. Прежнее правило не требует нового ключа, потому что бессрочный возврат исходного результата больше не является гарантией. Контрпример выше объясняет причину изменения, а не текущую ошибку проекта.

## Согласовано: перечитывание после потери ответа

Пользователь уточнил: повтор относится к работе команды одного агента, а конечное желаемое состояние определяет сам агент. Пример A→B→A относится к бессрочному распознаванию одинакового JSON во всём проекте, а не к выбору конечного значения агентом. Он не обосновывает новый обязательный параметр запроса.

Принято пользователем: каждый новый самостоятельный apply обрабатывается по текущему состоянию, без возврата старого успеха из-за совпадения хеша с исторической записью. Хеш остаётся отпечатком содержимого и возвращается в прежнем формате; разные новые выполнения могут иметь одинаковый хеш. Запись восстановления хранится до надёжного завершения правки или полного отката, после чего удаляется. Диагностика и история оснований имеют собственные правила хранения; физические ключи и аварийный протокол ещё проектируются. Контроль текущего выполнения не заменяется поиском любого совпадающего запроса во всей истории.

Пример входа для повторного отдельного вызова; A — полный старый Markdown-фрагмент, B — полный желаемый фрагмент, включая прежний ID:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<H(A)>",
      "markdown": "<полный размеченный фрагмент B>"
    }
  ]
}
```

Если прежняя команда сохранила B, но агент потерял ответ, этот новый вызов не проходит проверку base_hash. Согласованный выход использует существующий формат ошибки:

```json
{
  "ok": false,
  "error": {
    "code": "conflict",
    "message": "Хеш элемента не совпадает с base_hash",
    "details": {}
  }
}
```

Агент перечитывает актуальный элемент. Если нужное состояние уже достигнуто, повторять запись не требуется; иначе агент готовит правку по новым данным. Если корпус действительно снова содержит A и агент теперь хочет B, тот же вход допустим как новая правка после обычных проверок. Конфликт сам по себе не доказывает, что предыдущая команда была успешной: состояние мог изменить другой агент.

Мотивация: используются уже имеющиеся base_hash, чтение документов и inspect. Не вводятся timestamp, ID агента, новый ключ операции или команда его получения. Новые ID элементов по-прежнему генерирует Engram.

Изменение гарантии принято: после потери ответа новый самостоятельный вызов не обещает вернуть первоначальный успех и прежнюю карту tmp-ID/UUID. Для create агент читает затронутые файлы и узнаёт созданные постоянные ID. Атомарность, полный откат незавершённой записи и сохранение надёжно завершённой правки остаются обязательными. История оснований знаний и правила диагностики не отменяются; устаревший base_hash по-прежнему вызывает конфликт.

## Ограничение: точный фильтр по коммиту источника

Два разных коммита могут содержать одно дерево. Временный Git-репозиторий с обычным коммитом и следующим пустым коммитом дал разные commit OID и одинаковый tree OID. Поэтому общий снимок знания может заменить несколько указателей на содержимое источников, но не всю информацию для filters.source_revisions с точным совпадением ранее сохранённого коммита.

Правило «использовать текущий HEAD при совпадении адресованных байтов, иначе tree OID» также зависит от HEAD на момент подтверждения. Проверенные источники одного знания могут различаться по совпадению с HEAD. Способ сохранения этого происхождения, общих данных подтверждения и истории надо согласовать до DDL. Фильтр не отменён и не подменён поиском по дереву.

## Условия корректности оставшихся механизмов

1. Запрос использует не только одну графовую/векторную проекцию, но и совместимую с ней модель вычисления вектора запроса. Переключение адаптера при сохранённом старом индексе не должно смешивать векторы разных моделей. Уже принятого общего порта достаточно; закрепление конфигурации остаётся внутренней обязанностью.
2. Git-снимок, транзакция БД и замена нескольких файлов не образуют автоматически единую аварийную транзакцию. Необходимы долговечный журнал, точный порядок фиксации и повторяемое восстановление. Снимок отката должен покрывать затронутые разрешённые документы корпуса. Запись в существующий файл без разметки Engram запрещена и отклоняет всю правку. Проверка потери питания предстоит на реализации.
3. Производный текстовый индекс должен удовлетворять запрету на копии документов в БД. Возможный способ — поисковая структура терминов и позиций без хранимого полного текста; конкретный формат и движок не выбраны. Это условие выбора хранилища, а не утверждение о настройках любого готового FTS.
4. Потеря всей БД не равна reindex. Git хранит содержимое, но текущие файлы не содержат всю историю подтверждений, данные незавершённого восстановления и долговечное соответствие URI источников их UUID. Резервное копирование служебного состояния требует отдельного решения.
5. Готовность старого индекса при сбое embedding-провайдера не доказывает возможность гибридного запроса: его вектор ещё нужно получить. Отдельный режим только текстового поиска не согласован. Обработка такой ошибки должна сохранять выбранный контракт.
6. Единый uri допускает разные адресные схемы, но не вводит автоматически сетевое чтение и версионирование веб-страниц. Полностью локальная первая версия сохраняется.
7. Повреждение разметки после внешних Git-изменений может затруднить edit по ID. Сценарий исправления должен быть проверен после выбора грамматики; дополнительная команда прямой файловой записи пока не вводится.

## Документальные противоречия, оставленные для решения

Ранние требования описывают патчи с контекстом, замену старого текста и произвольные вставки. Позже приняты минимальные create/edit/delete, в том числе edit всего фрагмента по ID. Основной контракт edit уже отражает поздний выбор, но общие файловые операции не были явно исключены. Аудит не добавляет их реализацию и не удаляет прежнее требование без сверки; этот вопрос нужно закрыть перед окончательной JSON-схемой.

Описание места сохранения подтверждённого хеша источника в старых разделах не является выбором отдельного поля verified. При общем основании прежние байты читаются из Git. История, точные commit OID и вариант nodes.revision ещё требуют согласованной схемы. Дублирование описаний решения между документами заменять следует ссылками после фиксации этой схемы, чтобы не распространять неоднозначную трактовку.

## Чтение состояния после потери ответа

Отмена бессрочного кэша требует, чтобы агент мог наблюдать эффект правки. Для текста и назначенных UUID он читает затронутые файлы и inspect. Для подтверждения источников, которое может менять только служебное основание при том же Markdown, нужно проверить достаточность выдаваемых метаданных. Текущие текстовые хеши сами по себе не доказывают, что сохранено нужное подтверждённое основание. Точный контракт чтения этих данных следует сверить при выборе полей nodes.revision; новое поле ответа этим аудитом не принимается автоматически.

## Проверка аудита

- Прогнаны две проверки проектных правил: модель дедупликации для A→B→A→B и опыт с двумя коммитами одного дерева во временном Git-репозитории. Пользовательские репозитории не изменялись.
- Первая проверка показала applied/B, applied/A, cached_success/A. Вторая показала different_commits = true и same_tree = true. Это воспроизводимые ограничения описанного протокола и доступной информации, а не тесты Engram 2.0.
- После принятого изменения отдельно проверена модель обычного контроля base_hash без бессрочного кэша: A→B применено; немедленный отдельный повтор даёт conflict и сохраняет B; B→A применено; новое A→B с прежним JSON снова применено. ## Принятое упрощение журнала восстановления

Удаление записи восстановления в финальной транзакции БД означает завершение правки. До первого изменения файлов сохраняются данные полного отката и запись восстановления; после долговечного сохранения всей группы файлов одной транзакцией БД фиксируются необходимые служебные результаты и задание индексирования и удаляется запись. Отдельные состояния pending/committed и отдельная очистка завершённых записей не нужны.

Оставшаяся после сбоя запись требует полного отката, включая случай уже записанных файлов до финальной транзакции. Прерванный откат повторяется; запись удаляется только после надёжного завершения восстановления, а диагностика неприменённой правки сохраняется отдельно. Отсутствие записи не заменяет перечитывание состояния агентом после потери ответа. Индексирование остаётся асинхронным. Это согласованный логический протокол; состав снимка отката, физический порядок сохранения и аварийные проверки ещё проектируются.

## Ограничение записи корпусом

Согласовано: Engram изменяет только специально размеченные Markdown-документы корпуса. Для существующего файла это проверяется до правки; ожидаемый хеш или разметка переданного нового содержимого не дают права изменить обычный документ. Попытка записи вне корпуса отклоняет всю атомарную группу без изменений, включая проверку без сохранения. Новый код ошибки или команда не нужны: используется invalid_request, а ошибки самой разметки сохраняют validation_failed.

Обычные документы и исходный код могут оставаться внешними источниками для чтения и проверки знаний. Журнал и снимок отката не расширяют область записи. Ранее согласованное создание по отсутствующему пути сохраняется и сразу формирует размеченный Markdown-документ; добавление разметки в существующий обычный документ через Engram запрещено.

Согласовано восстановление недописанного файла по оставшейся записи журнала и прежнему Git-снимку. Текущая разметка такого файла не является условием отката; область восстановления ограничена предварительно проверенной правкой. Восстанавливается прежнее содержимое файла целиком либо удаляется файл, созданный незавершённой правкой. Обратный Markdown-патч, отдельное состояние файла и копия текста в БД не требуются. Физический порядок замены файлов и проверка повторного сбоя по-прежнему проектируются.

Согласовано сообщение о неприменённой правке в существующем result.errors: причина и исход атомарной группы, hash, paths и element_ids. Полный патч в БД для этого отчёта не требуется. Сохранение диагностики независимо от очищенной записи восстановления остаётся обязательным; правило её снятия ещё не принято.
