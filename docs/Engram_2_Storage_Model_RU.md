# Engram 2.0 — модель хранения данных

Статус: начало детального проектирования хранения. Согласованные гарантии отделены от предлагаемых записей, ключей и физических механизмов. Согласованы единые `nodes` и `edges`, значение `nodes.kind = source` и общее поле адреса `uri`. Записи источников в `nodes` сохраняют идентичность при реиндексировании. Согласована уникальность UUID среди текущих nodes и edges без проверки истории; отдельное бессрочное резервирование удалённых ID исключено. Имена остальных наборов записей и их устройство обсуждаются. Движок БД, физический DDL и реализация не выбраны.

Основания: [требования](Engram_2_Requirements_RU.md), [доменная модель](Engram_2_Domain_Model_RU.md), [подсистемы](Engram_2_Subsystems_RU.md), [контракты](Engram_2_Contracts_RU.md).

## Полнота проектирования

Количество вопросов не ограничено. По последнему указанию пользователя разбираем один вопрос за раз, с контекстом, входом, выходом и мотивацией новых предложений. Простота механизмов сохраняется, но описание должно включать логическую и физическую модели, ключи, ограничения, индексы доступа, транзакции, публикацию и освобождение данных, восстановление и проверку гарантий. Этот документ пока не является завершённым проектом.

## Согласованное разделение данных

| Группа | Источник истины и место хранения | Жизненный цикл и восстановление |
|---|---|---|
| Канонические знания | Размеченные Markdown-файлы рабочей копии | Правки через CLI; версионирование содержимого в Git |
| Содержимое снимков | Объекты и служебные ссылки Git | Выданные и используемые снимки удерживаются бессрочно средствами Git |
| Графовая проекция | Производные записи в БД | Структура восстанавливается из документов; долговечные ID и адреса источников сохраняются в единой nodes |
| Текстовый индекс | Производная поисковая структура | Перестраивается; копии текста документов в БД не сохраняются |
| Embeddings и векторный индекс | Производные данные в БД/адаптере индекса | Публикуются вместе с корректным графом; конкретная организация хранения не выбрана |
| Идентичность внешних источников | Долговечное служебное состояние БД | Соответствие нормализованного uri и UUID хранится в nodes бессрочно, включая источники без ссылок |
| Подтверждённое основание знания | Долговечное служебное состояние БД и содержимое в Git | Один общий Git-снимок всех источников знания; явное подтверждение и история обязательны. Физические поля и сохранение точных коммитов источников ещё уточняются |
| Выполнение и восстановление | Долговечный журнал БД и OID в Git | Незавершённая правка откатывается после сбоя; надёжно завершённая сохраняется. Запись восстановления удаляется после надёжного завершения правки или полного отката; бессрочный кэш успешных ответов не используется |
| Задания индексирования | Долговечное служебное состояние БД | Снимок, выбранная область, состояние и использованные ретраи; восстановление по тому же снимку |
| Локи и диагностика | Служебное состояние проекта | Локи для короткой фазы сохранения/восстановления; неустранённые ошибки переживают перезапуск |

Перестройка индекса не стирает идентичности источников, подтверждённые основания, историю и данные незавершённого восстановления. Потеря всей служебной БД не равнозначна штатному `reindex`: история и автоматически назначенные UUID внешних вершин не восстанавливаются из одних текущих Markdown-файлов. План резервного копирования и восстановления служебного состояния требует отдельного проектирования.

Предыдущие опубликованные данные индекса сохраняются только для использующих их запросов и освобождаются после их завершения. Подготавливаемый индекс не становится видимым до общей валидации и готовности необходимых embeddings.

## Согласованные правила поисковых данных

Поиск использует одно детерминированное представление собственного текста вершины или метавершины: служебные блоки Engram и графовые метаданные удаляются, от ссылок остаются подписи, кодовые примеры сохраняются. Содержимое связанных и вложенных элементов не подгружается в этот текст. Он временно используется текстовым индексом и embedding-адаптером; копия текста документа в БД не сохраняется. `base_hash` по-прежнему вычисляется по полному исходному Markdown.

Embedding из доступного корректного индекса повторно используется при совпадении SHA-256 подготовленного поискового текста и идентичности адаптера, версии модели и влияющих на вектор параметров. Изменение текста или конфигурации требует вычисления. Ключ не ограничивается UUID или байтовым хешем исходного Markdown. Постоянный архив прежних векторов не вводится: ненужные данные освобождаются вместе с индексами после завершения читателей. Схема внутренних входа и выхода порта использует `texts` и соответствующий массив `vectors`; размерность задаёт модель. Физические записи и ключи ещё проектируются.

## Согласованная уникальность идентификаторов

Статус: принято 12 октября 2026 года. Проверяется уникальность UUID среди текущих nodes и edges, включая долговечные source без ссылок. История удалённых элементов для генерации и проверки UUID не просматривается.

Новый UUIDv4 генерирует Engram. Совпадение с занятым текущим ID требует другого UUID. Дублирующие объявления в каноническом корпусе отклоняются. Проверка не может опираться только на отстающую опубликованную поисковую проекцию; физическая межтабличная уникальность и конкурентный протокол ещё проектируются.

Отдельная identities и deleted-записи только ради резервирования удалённых ID не вводятся. Ранее обсуждавшиеся варианты заменены этим решением. Намеренного переиспользования освобождённых ID генератор не выполняет, но совпадение с забытым историческим UUID не проверяется. Перенос и восстановление той же сущности сохраняют ID. После потери ответа агент узнаёт ID уже сохранённых элементов из документов и актуальных метаданных.

Изменение политики UUID не отменяет историю оснований знаний и соответствие uri/UUID известных источников. Бессрочное хранение результатов для дедупликации отменено отдельным последующим решением. Отсутствие ссылок на source не является удалением его долговечной записи. Данные прежней индексной проекции удерживаются до завершения её читателей, независимо от политики UUID.

Мотивация: устойчивые ссылки и текущая целостность сохраняются без дополнительного исторического реестра и жизненного цикла tombstone. Пожизненное резервирование UUID больше не является гарантией первой версии.

## Согласованная графовая проекция nodes и edges

Статус: сохранение метавершин/includes в доменной модели и представление хранения обычным графом nodes/edges согласованы. Исторический реестр identities не используется; физические ключи и индексы ещё проектируются.

Одна согласованная графовая проекция представляется наборами `nodes` и `edges`. Логическая модель не требует отдельной записи списка детей внутри метавершины. Системное ребро `includes` хранится в том же наборе рёбер; непосредственно включённые элементы выбираются по источнику и типу ребра.

### Логические записи nodes

| Поле | Смысл | Ограничение |
|---|---|---|
| `id` | Постоянный UUID узла | Уникален среди текущих nodes и edges; идентичность источника сохраняется независимо от перестройки и наличия ссылок |
| `kind` | `vertex`, `metavertex` или `source` | Вид хранения; source соответствует обычной вершине источника в домене |
| `uri` | Адрес описания или источника | Для знаний — путь с ID; для файлового источника — путь с необязательным диапазоном; модель допускает веб-адреса, их поведение ещё уточняется |
| `lines` | Начальная и конечная строки | Нумерация от 1, включительно; координаты снимка, для недоступного внешнего источника — его сохранённый адрес |
| `hash` | SHA-256 полного фрагмента | Канонический фрагмент для знаний, адресованный фрагмент/файл для источника; для недоступного внешнего источника допускается `null` |

`file_hash` относится к файлу, а не к независимой сущности: его точное хранение и связь с файловым каталогом ещё проектируются. Это логические записи, а не окончательный физический DDL; пара строк может быть представлена отдельными колонками.

### Логические записи edges

| Поле | Смысл | Ограничение |
|---|---|---|
| `id` | UUID ребра | Уникален среди текущих nodes и edges; исторический реестр UUID не используется |
| `source_id` | UUID источника | Ссылка на запись nodes в той же проекции |
| `target_id` | UUID назначения | Ссылка на запись nodes в той же проекции, отличается от источника |
| `type` | Тип связи | Системные и проектные типы в согласованной грамматике |
| `hash` | SHA-256(JCS({source, markdown})) | Хеш вычисляется из канонической ссылки; полный Markdown в БД не сохраняется |

Для обычных рёбер одна пара может иметь несколько записей, в том числе одного типа. Для `includes` разрешено только одно ребро на упорядоченную пару; его источник — метавершина. Циклическая включённость запрещена. Эти ограничения должны быть проверены доменным валидатором; поддерживаемые физические ограничения БД будут выбраны вместе с движком.

Метавершины разделяют общие элементы посредством разных рёбер `includes`, без копирования записи nodes. Внутренние рёбра фрагмента определяются правилом непосредственного вхождения обоих концов. Физические ключи, привязка к публикуемой проекции, индексы для входящего/исходящего обхода и стратегия обновления проектируются следующим шагом.

Мотивация: агент получает обычные связи и включённость из одной согласованной структуры. Удаление или изменение `includes` не требует синхронизировать отдельный массив членства, а общий элемент остаётся одним узлом.

Вход `engram traverse`; метавершина содержит одну вершину:

```json
{
  "element_ids": [
    "b4655ec0-ddfb-4c13-ab83-dff053dbe399"
  ],
  "mode": "containment",
  "direction": "outgoing",
  "depth": 1,
  "limit": 10,
  "edge_limit": 10
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "elements": [
      {
        "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
        "path": "knowledge/rules.md",
        "lines": [
          1,
          6
        ],
        "revision": "<снимок индекса>",
        "flags": []
      }
    ],
    "edges": [
      {
        "id": "064f2964-77cc-41f0-87ac-d280c0ec59a7",
        "type": "includes",
        "source": "b4655ec0-ddfb-4c13-ab83-dff053dbe399",
        "target": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c"
      }
    ]
  }
}
```

## Отклонено: отдельная external_nodes

Первоначальная отдельная таблица адресов источников заменена согласованной единой nodes с kind = source и uri. Её гарантия устойчивого соответствия адреса и UUID сохраняется; отдельная структура и дублирующее описание её полей удалены из актуального проекта.

## Согласованная единая nodes для знаний и источников

Статус: пользователь принял единую nodes, kind = source и uri. Отдельная external_nodes заменена этим решением. Отдельный исторический реестр UUID не используется; проверяется уникальность текущих nodes и edges.

Пользователь предложил хранить источники в общей nodes с дополнительным видом узла или признаком, учитывая будущие ссылки на веб-страницы. Различный жизненный цикл идентичности и поисковых данных требует правил сохранения, но сам по себе не требует отдельной таблицы источников. В текущем проекте приняты единые логические записи nodes.

Хранимый kind расширен значением source. Он обозначает обычную вершину внешнего источника в доменной модели, а не новую разновидность метаграфового элемента. В Markdown корпуса по-прежнему разрешены только vertex и metavertex; вершины источников создаёт Engram при разрешении external-ссылок. Источник и метавершина одновременно не требуются текущей моделью, поэтому отдельный признак происхождения пока не предлагается.

| Поле | Согласованный смысл | Ограничение |
|---|---|---|
| id | Постоянный UUID узла | Для источника сохраняется независимо от наличия ссылок и перестройки индекса |
| kind | vertex, metavertex или source | Вид записи хранения; source отображается на обычную вершину домена |
| uri | Адрес канонического описания либо источника | Используется вместо узкого path в хранении; для знаний — путь с ID фрагмента, для источника — путь с диапазоном или веб-адрес |

Производные hash и координаты фрагмента сохраняют свой смысл, но не составляют долговечную идентичность источника. Для source нормализованный uri должен однозначно определять UUID в рамках проекта; это условная уникальность по kind = source, а не требование уникальности любого адреса всех видов узлов. Стратегия физического ограничения проектируется вместе с движком БД. Изменение содержимого источника не меняет его UUID; другой адрес обозначает другой источник. Основание подтверждения относится к конкретному знанию: согласован один общий снимок всех его источников. История обязательна, её схема ещё не выбрана.

Вход — ссылки в Markdown знания. Веб-ссылка иллюстрирует расширяемость адресной модели и пока не является принятым сценарием первой версии:

```markdown
[Реализация](src/storage.go#L10-L25 "engram:id=tmp:001;type=external")
[Документация](https://example.org/docs#storage "engram:id=tmp:002;type=external")
```

Результат разрешения — логические записи nodes; это иллюстрация хранения, а не новые поля публичного ответа apply:

```json
[
  {
    "id": "91e1798a-d1f4-43ba-817b-ad93c9c5ea86",
    "kind": "source",
    "uri": "src/storage.go#L10-L25"
  },
  {
    "id": "d047c32e-c620-4a91-a956-a697d71f3b77",
    "kind": "source",
    "uri": "https://example.org/docs#storage"
  }
]
```

Для собственного знания uri может иметь вид knowledge/rules.md#08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c; вид записи остаётся vertex или metavertex. ID связывает узлы и рёбра, адрес задаёт место чтения. Перенос знания меняет его адрес, сохраняя ID.

Основное условие единой таблицы: reindex не должен очищать соответствия ID и адресов источников, записанные в nodes. Известные источники без текущих ссылок сохраняются для inspect и последующего повторного использования ID. Они не становятся самостоятельными результатами поиска знаний. Наличие строки в nodes не заменяет проверку принадлежности согласованной поисковой проекции. Обновление индексных полей должно сохранять принятую атомарную публикацию и закрепление запросов за одной версией; физический способ обеспечения этих гарантий ещё не выбран.

URI-reference позволяет одинаковым адресным полем представить относительный путь и абсолютный веб-адрес. При этом нормализация и разрешение зависят от адресной схемы; файловые правила нельзя автоматически переносить на URL. Основание: [RFC 3986, относительные ссылки и нормализация](https://www.rfc-editor.org/rfc/rfc3986). Согласованная нормализация локальных адресов остаётся в силе. Правила веб-адресов, чтения страниц, фиксации их содержимого и перепроверки ещё не обсуждены; универсальное поле не включает автоматически сетевые операции в полностью локальную первую версию.

Мотивация: код и веб-документация представлены теми же узлами и рёбрами, агент использует обычные ссылки, а хранение не требует отдельного набора записей для каждого способа доступа к источнику. Одно значение kind = source также позволяет отличить доступные для редактирования знания от источников при валидации операций.

## Согласованная нормализация ключа адреса

Статус: пользователь принял нормализацию компонентов пути и номеров строк, сохранение регистра имени и неизменность исходного Markdown. Особенности кодирования адресов и альтернативных путей через символьные ссылки ещё требуют детализации.

Адрес нормализуется только для разрешения и сравнения источников: компоненты `.` удаляются, внутренние `..` сворачиваются без выхода из корня; номера строк записываются десятичными числами без ведущих нулей. Диапазон должен быть положительным и упорядоченным. Регистр имени сохраняется; дополнительная нормализация Unicode не вводится. Согласованные проверки выхода из корня через символьные ссылки сохраняются. Объединение различных адресов по физическому расположению файла этим решением не определяется.

Внутренний вход:

```json
{
  "uri": "./src/../src/storage.go#L010-L025"
}
```

Выход:

```json
{
  "uri": "src/storage.go#L10-L25"
}
```

Вход и выход показывают адрес после разбора Markdown-ссылки. Эти правила не вводят новые поля CLI и не меняют исходный Markdown: хеш фрагмента по-прежнему учитывает его точные байты. Каноническое кодирование специальных символов адреса относится к общей грамматике ссылок и не предполагает изменения имён файлов. Нормализация не исправляет недоступный файл или некорректный диапазон; такие случаи обрабатываются согласованными правилами валидации и перепроверки.

Мотивация: эквивалентные написания одного адреса не создают несколько внешних вершин. При этом агент сохраняет свой Markdown, а Engram не смешивает разные имена файлов или разные адресованные фрагменты.

## Предложение 3. Хеш файла по запросу

Статус: предварительно принято хеширование всего файла, SHA-256 точных байтов. Пользователь оставил возможность пересмотра после отдельного этапа выбора разметки. Способ постоянного хранения или вычисления file_hash по запросу этим ответом не выбран; ниже сохраняется предложение вычисления по запросу.

Предлагается пока не вводить отдельную таблицу files и не повторять file_hash во всех узлах одного файла. Для inspect хеш файла вычисляется по точным байтам общего Git-снимка, один раз на уникальный файл в рамках вызова. Для проверки base_hash при записи вычисляется хеш согласованного текущего состояния файла; прежний индекс не используется как доказательство совпадения. Хеш фрагмента в графовой проекции остаётся отдельным значением. Код и Markdown в БД не копируются.

Вход engram inspect:

```json
{
  "element_ids": ["08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c"]
}
```

Выход соответствует принятому контракту; file_hash получен из файла в выданном снимке:

```json
{
  "ok": true,
  "result": {
    "snapshot": "<Git tree OID>",
    "elements": {
      "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c": {
        "path": "knowledge/rules.md",
        "lines": [1, 6],
        "hash": "<SHA-256 полного фрагмента>",
        "file_hash": "<SHA-256 всего файла>"
      }
    }
  }
}
```

Если несколько запрошенных элементов расположены в одном файле, рассчитанный file_hash используется для каждого ответа. Этот временный результат не вводит постоянный кэш. Для недоступного известного файлового источника сохраняются согласованные null-значения. Предложение не распространяет файловые хеши на будущие веб-источники.

Мотивация: агент получает необходимые base_hash без дополнительного набора записей и синхронизации дубликатов. Цена — чтение и хеширование файла при соответствующем вызове; постоянный кэш можно обосновать позднее измерениями. Выбор механизма обнаружения изменений всего корпуса остаётся отдельным вопросом и этим решением не задаётся.

### Уточнение: хеш файла из хешей элементов

Пользователь предложил вычислять file_hash из хешей элементов. Такой составной хеш возможен, но не равен принятому SHA-256 байтов файла. Если использовать только хеши размеченных фрагментов, изменение заголовка, комментария, пробелов или другого содержимого вне этих фрагментов не изменит результат. Состав и порядок элементов также должны учитываться; нельзя брать хеш неупорядоченного множества. Полное покрытие каждого байта файла размеченными элементами ранее не требовалось.

Для полного контроля файла составной вариант должен учитывать и промежутки между элементами, что вводит дополнительную схему разбиения и хеширования. Во всех вариантах для проверки новой правки нужны актуальные данные: старые хеши из индекса не доказывают неизменность рабочей копии. Выигрыш составного варианта не установлен измерениями; при чтении и подготовке изменённого файла SHA-256 его байтов можно вычислять в том же проходе.

Пользователь предварительно выбрал хеширование всего файла. Условие покрывает любые его байты, включая содержимое вне описаний элементов. Разметка ещё не выбрана и проектируется отдельным этапом; после этого file_hash может быть пересмотрен явным решением. Составной хеш элементов сейчас не принят. Отказ от постоянного кэша file_hash остаётся предложением, а не следствием выбранного покрытия.

## Основание знаний и ревизии

Согласован один общий Git-снимок всех источников знания. Предложения хранить тройку verified.hash/revision/snapshot либо независимую source_revision на каждом external-ребре не приняты; их подробные схемы исключены из актуального проекта. Нельзя одновременно считать эти варианты выбранными и применять общее основание знания.

Содержимое прежнего источника доступно в Git по общему снимку и uri. Хеш можно вычислить по этому содержимому; необходимость постоянного кэша ещё не доказана. История подтверждений и точная фильтрация по сохранённым commit OID остаются требованиями. Один tree OID не определяет исходный commit OID; место хранения информации для такого фильтра ещё требует решения.

### Обсуждаемый вариант: revision у знаний и источников

Статус: принято одно общее Git-состояние для всех источников одного знания. Пользователь предложил revision одновременно у узла знания и узла источника; точный смысл поля и правила обновления ещё обсуждаются. Отдельные ревизии у рёбер не приняты.

Одно поле nodes.revision можно использовать для Git-адресации состояния собственного содержимого знаний и файловых источников. Но это само по себе не определяет, по какой версии источника агент сформировал или подтвердил конкретное знание. Git-снимок собственного описания и основание зависимостей совпадают только при определённых правилах формирования и обновления.

Минимальное направление обсуждения: revision знания указывает на общий Git-снимок его основания, включающий все адресованные источники; revision source-узла указывает на доступное состояние самого источника. Тогда прежний источник можно прочитать по URI из снимка знания. Пример: знание A относится к S1, источник уже изменён в S2; знание Б сформировано по S2. У знаний сохраняются разные снимки, источник остаётся одним узлом. Условие общего основания всех источников одного знания принято. Использование nodes.revision как указателя на основание и отказ от полей у рёбер ещё требуют согласования смысла и обновления поля.

До выбора схемы остаются детали физического сохранения общего основания, история его изменений и сохранение точных коммитов источников для принятых фильтров. Обычная правка без snapshot сохраняет основание; добавление или замена источника требует snapshot; явная перепроверка через edit с snapshot подтверждает все источники вместе. Из произвольного tree OID нельзя однозначно восстановить исходный commit OID. Ревизия текущей опубликованной проекции также не должна автоматически считаться подтверждением источников агентом.

Сохранение прежнего основания при edit без snapshot согласовано ниже; обязательность snapshot при добавлении или замене источника также согласована. История привязок по указанию пользователя пока не обсуждается. Предыдущее описание независимого обновления отдельных привязок заменено этими правилами общего основания знания.

### Согласовано: обычная правка сохраняет основание источников

Статус: пользователь подтвердил сохранение прежнего основания при edit без snapshot. Правило применяется к обычной правке с прежними источниками; добавление или замена источника требует snapshot по следующему согласованному правилу.

В обсуждаемой модели revision знания обозначает последний подтверждённый общий снимок его источников. Если edit меняет только Markdown и не передаёт snapshot, при неизменном наборе источников этот указатель сохраняется. Edit с snapshot после проверок обновляет основание всех источников знания целиком. Автоматическое реиндексирование не подтверждает новое основание.

Смысл поля требует явного различения: revision знания в этом варианте не обязательно указывает на последний текст самого знания. Актуальный Markdown читается по уже существующему snapshot ответа inspect либо снимку опубликованного индекса; его актуальное состояние проверяется собственным hash. У source-узла revision адресует состояние самого источника. Роли поля для знаний и источников различаются и должны быть явно описаны в окончательной схеме.

Сценарий: основание знания — S1; код изменился и доступен в S2. Агент исправляет формулировку знания, сохраняя ссылки, без подтверждения источников. Вход apply:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш исходного фрагмента>",
      "markdown": "<полный новый Markdown-фрагмент с прежними source-ссылками>"
    }
  ]
}
```

Публичный выход остаётся согласованным:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

После сохранения текущий Markdown доступен в новом Git-снимке, а обсуждаемое служебное основание знания остаётся прежним:

```json
{
  "id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
  "revision": "<снимок S1>"
}
```

Мотивация: обычная правка формулировки не превращается в подтверждение изменившегося кода. Пометки о необходимости перепроверки сохраняют смысл. Правки с добавлением, удалением или переназначением external-ссылок требуют отдельного решения и данным предложением не покрываются. Возможность выбирать по прежней ревизии исходного коммита также остаётся открытой деталью общей модели.

### Согласовано: новый источник требует общего snapshot

Статус: пользователь подтвердил обязательность snapshot при добавлении или замене источника. У знания одно общее основание; независимая новая привязка к другой версии не создаётся.

Snapshot обязателен у edit, который добавляет новый адрес источника или заменяет адрес прежнего. Агент подтверждает знание по всем конечным источникам одного снимка. Engram проверяет доступность каждого адресованного фрагмента в снимке и соответствие его текущим байтам, затем меняет общее основание целиком. Изменение только подписи ссылки или иной графовой разметки без изменения адресов источников нового snapshot не требует. Удаление источника само по себе не добавляет новой зависимости и при edit без snapshot сохраняет основание остальных источников.

Сценарий: знание раньше ссылалось на src/storage.go, агент добавляет src/cache.go. Снимок S2 содержит оба файловых источника в состоянии, по которому агент подтверждает подготовленный текст. Вход apply:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш исходного элемента>",
      "markdown": "<!-- engram: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"vertex\"} -->\nОписание хранилища и кэша.\n[Хранилище](src/storage.go#L10-L25 \"engram:id=064f2964-77cc-41f0-87ac-d280c0ec59a7;type=external\")\n[Кэш](src/cache.go \"engram:id=tmp:001;type=external\")\n<!-- /engram -->\n",
      "snapshot": "<Git tree OID S2>"
    }
  ]
}
```

Выход при успешных проверках соответствует действующему apply:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>",
    "ids": {
      "tmp:001": "07bd2df0-a311-479e-b21b-cd2728daf852"
    }
  }
}
```

Согласованные временные ID заменяются Engram; новые команды не вводятся. В рассматриваемой модели общее revision знания становится S2, а не отдельной версией только для нового ребра. Без snapshot в таком сценарии возвращается invalid_request с объяснением необходимости общего основания, без применения изменений.

Уточнение действующего проектного контракта: edit.snapshot принимает полный OID любого доступного tree в Git-хранилище текущего репозитория, а не только выданные Engram снимки. not_found относится к отсутствию самого объекта в Git. Требование регистрации снимка в отдельном реестре ранее не принималось и не вводится. Способ получения согласованного снимка с новыми незакоммиченными источниками должен быть описан в окончательном рабочем сценарии; обязательный коммит для этого не требуется выбранной моделью Git-объектов.

Мотивация: после правки у всего знания остаётся одно объяснимое основание. Engram не объединяет незаметно старую проверку одного источника и новую проверку другого. Прежний сценарий добавления новой привязки без snapshot заменён этим решением.

## История оснований: схема пока не выбрана

История прежних подтверждённых оснований и адресов источников обязательна. Пользователь отложил выбор её хранения. После принятого удаления завершённых записей восстановления они не могут быть единственным хранилищем обязательной истории. Совместное физическое размещение допускается, но история и временные записи восстановления имеют разные сроки жизни; отдельная физическая таблица этим правилом не устанавливается.

Ранее обсуждавшийся source_changes с независимой ревизией каждого ребра не принят и должен быть пересмотрен с учётом общего основания знания. История должна сохранять прежний снимок знания и возможность восстановить адреса источников; одно текущее поле revision и сохранённый UUID этого не обеспечивают.

Удаление исторического реестра UUID не удаляет эту историю. Git хранит содержимое, Engram — необходимые связи и состояние. Конкретные записи, ключи, порядок фиксации, восстановление после Git-отката и резервное копирование ещё проектируются.

## Согласовано: область изменения канонических документов

Engram изменяет только специально размеченные Markdown-документы корпуса. При существующем пути принадлежность корпусу определяется по исходному каноническому состоянию: разметка Engram должна присутствовать до правки. Обычные документы без разметки, исходный код и другие внешние источники доступны для чтения по прежним правилам, но не являются целями записи Engram. Переданный base_hash и разметка нового содержимого не разрешают изменение существующего файла вне корпуса.

Нарушение этой границы отклоняет всю атомарную группу без изменения документов; тот же контроль действует при проверке без сохранения. Снимок для отката относится к разрешённым изменениям корпуса, а не создаёт право записи вне него. Ранее согласованное создание нового файла через create сохраняется: по отсутствующему пути создаётся сразу размеченный Markdown-документ после общей проверки. Служебные записи БД и удерживаемые Git-снимки сохраняют ранее согласованные роли; это ограничение области изменения пользовательских файлов.

## Согласовано: две транзакционные границы

Статус: пользователь сохранил прежнее асинхронное индексирование. Рассмотренная единая синхронная транзакция файлов с опубликованным поисковым индексом не выбрана. Граф остаётся производной структурой, восстанавливаемой из Markdown. Следующие две границы имеют разные условия завершения и восстановления.

### Запись документов через apply

Одна логическая транзакция фиксирует всю группу файлов и необходимое служебное состояние управления документами: назначенные идентичности, подтверждённые основания и их историю, а также долговечное задание индексирования со ссылкой на согласованный Git-снимок. Содержимое документов находится в файлах и Git; текст не копируется в БД.

До изменения канонических файлов должна быть надёжно сохранена запись восстановления и данные полного отката. Оптимистические предпосылки и целостность проверяются по актуальному состоянию перед сохранением. После надёжной фиксации документов и необходимого служебного состояния apply возвращает успех с hash и, при создании, ids. Он не ждёт вычисления embeddings и публикации индекса.

Сбой до этой границы требует полного отката файлов и относящихся к записи служебных изменений. Надёжно завершённая правка сохраняется при потере ответа; агент перечитывает состояние. Запись восстановления удаляется после надёжного завершения либо полного отката, а диагностика неприменённой правки сохраняется по согласованным правилам.

Это общая гарантия файлов и метаданных, а не свойство одной транзакции БД автоматически. Точный порядок сохранения Git-объектов, файлов, каталогов, записи восстановления и служебных данных ещё проектируется и требует аварийной проверки. Согласовано: удаление записи восстановления в финальной транзакции БД означает завершение правки. Эта транзакция сохраняет необходимое служебное состояние и задание индексирования; отдельное поле состояния завершения в записи восстановления не вводится.

### Асинхронное обновление графа и поисковых индексов

Индексатор читает неизменяемый согласованный Git-снимок завершённого корпуса. Обновлённые графовая, текстовая и векторная проекции подготавливаются как непубликуемые данные. Все необходимые embeddings должны быть готовы до публикации.

Готовая версия публикуется целиком. Каждый запрос закрепляет одну опубликованную версию до завершения; новые запросы после публикации получают новую версию. Предыдущие данные освобождаются после завершения их читателей. Завершённые правки, появившиеся во время сборки, учитываются следующим обновлением; само их появление не отменяет уже выполняющуюся сборку.

Ошибка или отмена обновления не публикует незавершённую версию, сохраняет последний корректный индекс и не откатывает завершённую правку документов. Status показывает ошибку индексирования отдельно от неприменённой правки. Ограниченные ретраи embeddings, восстановление задания по тому же снимку и явный reindex с ожиданием публикации сохраняются по прежним правилам.

Для чтения операций Engram требуется согласованное представление документов и метаданных; произвольное чтение нескольких файлов рабочей копии во время их замены само по себе не даёт общей атомарности чтения. Точный протокол чтения и фиксации ещё выбирается. Реализация не объявляется готовой или проверенной.

## Согласовано: срок жизни записи восстановления

Запись восстановления существует только для незавершённой правки. Она надёжно сохраняется до первого изменения канонических файлов и удаляется либо в финальной транзакции успешной записи, либо после надёжно завершённого полного отката. Бессрочная дедупликация завершённых вызовов отменена; первоначальный JSON-ответ не требуется хранить для отдельного повторного вызова.

Очистка не удаляет историю оснований, идентичности источников, необходимые задания индексирования, диагностику и удерживаемые Git-снимки. Эти данные имеют собственные правила хранения; запись восстановления не должна оставаться их единственным владельцем. После полного отката сведения о неприменённой правке сохраняются независимо от удаляемой записи.

Упрощённый логический вид незавершённой записи ниже не определяет полный физический набор полей или первичный ключ. Хеш является отпечатком содержимого правки, а не уникальным идентификатором всех выполнений. Snapshot здесь адресует состояние до правки; состав снимка ещё уточняется.

```json
{
  "hash": "<хеш содержимого правки>",
  "snapshot": "<Git tree OID состояния до правки>",
  "paths": ["knowledge/design.md"]
}
```

После надёжного завершения или полного отката запись отсутствует:

```json
null
```

## Согласовано: удаление записи как маркер завершения

Статус: принято пользователем. Наличие записи восстановления означает незавершённую правку. Отдельные состояния pending/committed и отдельная очистка завершённых записей не вводятся; прежнее предложение двух состояний заменено этим решением. Внешние вход и выход apply не меняются.

Логический порядок:

1. Надёжно сохранить Git-снимок состояния до правки и запись восстановления в БД до изменения канонических файлов.
2. Сохранить всю группу файлов и обеспечить долговечность записанного содержимого и необходимых изменений каталогов.
3. Одной финальной транзакцией БД сохранить необходимые служебные изменения управления документами, включая подтверждённые основания и историю, назначенные идентичности и долговечное задание индексирования, и удалить запись восстановления.
4. После надёжной фиксации этой транзакции вернуть успех. Индексирование выполняется асинхронно по согласованному снимку завершённого корпуса.

Совпадение файлов с желаемым содержимым само по себе не означает завершения. Сбой после сохранения файлов, но до надёжной фиксации финальной транзакции оставляет запись восстановления: требуется полный откат. Сбой после финальной транзакции не откатывает правку, даже если агент не получил ответ. После потери ответа агент перечитывает актуальные документы и метаданные.

| Вход восстановителя после сбоя | Действие и результат |
|---|---|
| Запись восстановления существует | Откатить всю группу по сохранённому снимку; надёжно завершить восстановление, сохранить диагностику неприменённой правки и удалить запись |
| Записи нет | По этой записи восстанавливать нечего; отсутствие записи само по себе не сообщает агенту, был ли прежний вызов успешен или уже откатан |

Согласовано: восстановитель определяет незавершённую правку по оставшейся записи журнала и восстанавливает её файлы по прежнему Git-снимку. Корректная разметка текущего повреждённого или недописанного файла не является предпосылкой отката. Область восстановления задаётся записью правки, проверенной до начала изменения документов; это не разрешает запись в посторонние файлы. Для существовавшего документа прежнее содержимое восстанавливается целиком, без попытки угадать по текущему тексту, какая часть была записана. Для документа, созданного незавершённой правкой, отсутствие пути в прежнем снимке означает удаление созданного файла.

Если прервался сам откат, запись остаётся; следующий запуск повторяет восстановление. Ошибка отката также сохраняет запись и диагностику, а поиск и новые правки ждут завершения восстановления. Удаление после отката не происходит до надёжного восстановления всех затронутых файлов.

Мотивация: финальная транзакция одновременно фиксирует служебные результаты и удаляет маркер незавершённости. Дополнительное поле состояния и отдельная очистка после успеха не требуются. Логическая граница принята; физический порядок долговечной записи Git-объектов и refs, файлов и каталогов, настройки БД и аварийные проверки после потери питания ещё проектируются. Состав снимка отката и физический ключ записи ещё не выбраны. Этот дизайн не подтверждает готовность реализации.

## Согласовано: диагностика неприменённых правок

Сообщение о неприменённой атомарной правке хранится независимо от записи восстановления и попадает в существующий result.errors команды status. Согласован общий формат code, message, details: message объясняет причину и исход всей группы, details содержит hash правки, paths файлов и element_ids элементов. Хеш остаётся отпечатком содержимого, а не уникальным ID всех выполнений. Код ошибки выбирается из существующего каталога по фактической причине.

Диагностика переживает очистку записи восстановления и перезапуск. Полный Markdown-патч или исходный JSON-запрос не требуется хранить в БД только ради этого сообщения. Ошибка индексирования после завершения apply остаётся отдельным событием и не означает отката документов. Успешный откат также не доказывает исполнения исходного намерения агента и сам не очищает сообщение о неприменённой правке.

Публичные вход и выход приведены в контракте status. Физические ключи и записи диагностики, отображение ещё не назначенных ID и условие удаления сообщений ещё проектируются; новые внешние поля этим решением не вводятся.

## Согласовано: основа очереди заданий индексирования

Статус: пользователь принял основу очереди — таблицу в служебной БД, одного исполнителя и обработку в порядке постановки. Ниже приведён логический каркас записи для дальнейшей детализации. Это внутреннее хранение проекта, а не новый формат CLI. Движок, DDL, окончательный набор полей и оставшиеся правила ещё проектируются.

Принята одна таблица indexing_jobs, которая сама представляет очередь. Один исполнитель координатора индексирования берёт задания в порядке постановки. Поиск и обработка CLI остаются отдельными действиями того же рабочего процесса. Выполняющееся задание использует свой неизменяемый Git-снимок; поступившие правки создают задания для следующих снимков и не перезапускают текущую сборку.

### Каркас записи

| Поле | Назначение |
|---|---|
| seq | Внутренний номер, назначаемый Engram; ключ записи и порядок постановки. Во внешний CLI не добавляется |
| snapshot | Git tree OID входного снимка; содержимое файлов остаётся в Git |
| paths | Выбранные файлы, как в reindex |
| element_ids | Выбранные элементы, как в reindex; непустые селекторы объединяются, пустые равнозначны отсутствию |
| state | Предлагаемые состояния queued, running, done, failed, cancelled |
| retries | Число уже использованных повторных попыток после ошибки embeddings; перезапуск не обнуляет счётчик |

При отсутствии непустых paths и element_ids требуется полная перестройка по ранее принятому правилу. Текст патча и документы не входят в запись. Отдельные поля полного режима, времени постановки и публичного ID задания этим каркасом не задаются.

Пример содержимого очереди: первое задание выполняется по снимку S1, второе ждёт обработки более позднего S2. Ниже показан логический массив строк таблицы, не ответ status:

```json
[
  {
    "seq": 1,
    "snapshot": "<Git tree OID S1>",
    "paths": ["knowledge/design.md"],
    "element_ids": [],
    "state": "running",
    "retries": 1
  },
  {
    "seq": 2,
    "snapshot": "<Git tree OID S2>",
    "paths": ["knowledge/rules.md"],
    "element_ids": [],
    "state": "queued",
    "retries": 0
  }
]
```

### Вход и результат обработки

После успешного apply задание становится долговечным вместе с необходимым служебным состоянием записи. Apply возвращает прежние hash/ids, не ожидая выполнения очереди. Явный reindex ставит необходимую работу и ждёт готовой опубликованной версии. Если уже выполняющееся задание имеет тот же снимок и покрывает выбранную область, reindex присоединяется к нему по ранее принятому правилу; отдельная работа не запускается.

Исполнитель берёт queued, сохраняет переход в running и выполняет индексирование. После проверки и готовности необходимых embeddings публикуется вся версия. Ошибка либо отмена не публикует частичный индекс. Предлагаемые терминальные состояния фиксируют итог задания; срок хранения завершённых строк и передача результата ожидающим вызовам ещё проектируются. Срок удаления записи восстановления документов автоматически на эти строки не переносится.

При перезапуске прерванное сбоем running возобновляется по тому же снимку с сохранением использованных ретраев. Failed с исчерпанным пределом и cancelled не возобновляются автоматически по правилу восстановления. Автосверка файлов также должна учитывать такие исходы, чтобы не создавать заново ту же остановленную работу на каждом обращении; точный механизм ещё выбирается. Явный новый reindex сохраняет свою роль отдельного запроса.

### Что ещё нужно определить

- Какие данные фиксируют конфигурацию embedding-адаптера и предел ретраев, чтобы восстановление задания не подменяло их текущими настройками.
- Как задание закрепляет необходимые подтверждённые основания знаний и их историю вместе со своим Git-снимком: одних байтов файлов для всей служебной семантики недостаточно.
- Как следующая публикация учитывает изменения, которые не попали в индекс из-за предыдущего неудачного или отменённого задания. Нельзя потерять эти изменения, обработав только paths последней правки.
- Как задаётся фактическая область выборочного построения, объединяются ещё не начатые автоматические задания и сохраняются гарантии явного reindex. Снимок выполняющегося задания не заменяется более новым.
- Физические ключи и индексы выборки, атомарное получение задания, отмена, прогресс status, очистка терминальных записей и проверка аварийных переходов.

Мотивация: существующая служебная БД хранит очередь и восстановление, а один исполнитель упрощает порядок публикаций и управление памятью. Монотонный номер объединяет ключ и порядок, селекторы повторяют CLI, файлы не копируются. Это основа для детального проектирования, не завершённая реализация очереди.

## Последовательность дальнейшего детального проектирования

1. Единые nodes/edges, сохранение идентичности источников и физическая уникальность текущих UUID.
2. Каталог файлов и координат, актуальные и подтверждённые хеши, история привязок источников.
3. Журнал восстановления: состав данных полного отката и физический порядок долговечной фиксации; наличие записи и её удаление в финальной транзакции как маркер завершения согласованы. Диагностика и история имеют отдельные правила.
4. Задания, используемая конфигурация, локи, диагностика и восстановление владельца.
5. Текстовый и векторный индексы, совместимость модели и данные embeddings.
6. Публикация, закрепление читателями, удаление ненужных производных данных.
7. Выбор движка, физические схемы и индексы доступа, транзакционные границы портов, миграции схемы и резервное копирование служебного состояния.
8. Проверка инвариантов, аварийных сценариев и ресурсных ограничений на прототипе.

Порядок может уточняться при обнаружении зависимости или противоречия; количество вопросов не ограничено.

## Открытые вопросы согласованности для аудита

- Вопрос бессрочной дедупликации закрыт: она отменена, после потери ответа агент перечитывает состояние. Хеш исходного JSON остаётся отпечатком содержимого, а не уникальным ключом каждого нового выполнения. Срок жизни записи восстановления согласован: удаление после надёжного завершения правки или полного отката. Удаление записи восстановления в финальной транзакции БД принято как маркер завершения без отдельного поля состояния. Физический аварийный протокол ещё проектируется.
- Для отката требуется сохранить прежнее содержимое всех затронутых размеченных Markdown-документов корпуса. Изменение существующего неразмеченного файла не допускается: весь запрос отклоняется до записи. Точный состав снимка восстановления ещё уточняется; откат не разрешает запись в посторонние документы. Ранее согласованный create по отсутствующему пути создаёт сразу размеченный документ после общей проверки.
- Точный порядок Git-объектов, служебных refs, файла журнала БД, замен файлов и результата операции должен выдерживать потерю питания. Одно применение Git или транзакции БД не описывает весь протокол.
- Проверенные основания, соответствия uri/UUID источников и данные восстановления требуют сохранного служебного состояния. Для полной потери БД ещё не определены резервное копирование и восстановление.
- Старая графовая проекция не является достаточным основанием для проверки новой записи: документы и источники могли измениться после её публикации. Нужен точный контракт доступа к текущему каноническому состоянию.

Эти пункты фиксируют незавершённые вопросы проекта, а не обнаруженные дефекты реализованного Engram 2.0.

## Метаграф и обычный граф: анализ представления

Статус: пользователь подтвердил сохранение метавершин и includes в доменной модели и обычный граф nodes/edges в хранении. Исторический реестр идентификаторов не используется; движок и физический DDL не выбраны.

Текущая модель Engram содержит вершины, метавершины и направленные бинарные рёбра; метарёбра исключены. По этим определениям она точно представляется типизированным направленным мультиграфом: вершины и метавершины — узлы с `kind`, а включённость — системное ребро `includes`. Для метавершины непосредственный состав определяется исходящими includes; внутренние рёбра выбираются по непосредственному вхождению обоих концов. Отдельного физического примитива вложенного графа для этого не требуется.

Обычная модель property graph предоставляет узлы, их свойства и типы связей; представление составных сущностей через связи описано в [официальных понятиях Neo4j](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/). Это подтверждение возможностей представления, а не выбор Neo4j для Engram. Точная представимость нашей модели — вывод из её собственных согласованных правил.

Дополнительная польза метавершин относится к предметной семантике: составное понятие имеет собственные ID и описание; агент может сначала прочитать его, затем раскрыть нужные части; общий элемент включается в несколько контекстов без копирования. Связь с компонентом в целом имеет отдельный смысл от связи с отдельным его решением. Эти возможности сохраняются в обычном графе, если у него есть те же узлы-группы, связи includes и правила обхода.

Стоимость этой семантики — проверка разрешённых источников includes, уникальности включения пары и отсутствия циклов, различение непосредственного и транзитивного состава. Она не доказывает повышение recall или экономию токенов и не заменяет проверку актуальности знаний. Сокращение лишнего контекста следует измерять на задачах агентов.

Согласовано: составные сущности и включённость сохраняются в доменной модели, хранение использует обычную графовую проекцию. Специализированный метаграфовый движок не обоснован текущими требованиями. При отказе от использования составных сущностей их предметную семантику следует пересмотреть отдельным решением пользователя.
