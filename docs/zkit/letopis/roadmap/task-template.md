# Стандарт описания эпика и задачи — zkit 0.2.6

Roadmap задаёт порядок, эпики, диапазоны оценок, зависимости и недельный ресурс. Подробные задания находятся в `roadmap/epics/EP-n-<slug>/tasks/TK-n-<slug>.md`; описание каждого эпика — в соседнем `epic.md`. Имена сохраняют точный ID из таблицы, без дополнения нулём: TK-1, а не TK-01. Каждый файл задачи содержит одно полное задание.

Все 45 задач детализируются сразу и распределяются по неделям по [D-86](../decisions.md#D-86). Эпики — контейнеры: их часы равны сумме задач и повторно не планируются. [D-88](../decisions.md#D-88) уточняет прежний формат D-87; новый tracker, assignee, story points и продуктовые параметры не вводятся.

## Эпик

Шапка: ID/название, фаза, best/expected/worst, внешние зависимости. Разделы:

- **Цель:** единый результат и основание в требованиях/рисках.
- **Границы:** In, Out с владельцами исключённой работы, интерфейсы результата.
- **Задачи:** ссылка на каждую карточку, конкретный результат и причина разделения. Порядок определяется зависимостями.
- **Приёмка:** выполнены дочерние критерии с evidence; gate фазы проверяется при переходе фазы, а не создаёт цикл с соседним эпиком.
- **Оценка и риски:** сумма карточек и общие условия, без дополнительных часов контейнера.

## Шаблон карточки

```markdown
# TK-N — Проверяемый результат

> **Статус:** planned
> **Эпик:** [EP-N](../epic.md)
> **Фаза:** PH-N
> **Оценка, ч:** best / expected / worst (best / expected / worst)
> **План:** неделя N — X ч; неделя N+1 — Y ч
> **Зависимости:** ссылки на карточки TK из roadmap или —

## 1. Цель
Что получит потребитель и почему это нужно сейчас.

## 2. Контекст и входные данные
Документы и ID требований/контрактов/механизмов/drills/решений; входной gate.

## 3. Что сделать
Конкретные действия по логическим границам, включая собственные проверки.

## 4. Ожидаемый результат
Артефакт, который передаётся потребителю; реализация, отчёт или поставка.

## 5. Критерии приёмки
- [ ] Наблюдаемое условие, которое может не выполниться.
- [ ] Отрицательный/аварийный случай, когда применим.

## 6. Как проверить
Вход → действие → ожидаемый исход → фактическое evidence.
Точные команды указываются после создания соответствующих targets.

## 7. Границы
- **Входит:** собственная работа.
- **Не входит:** смежная работа и конкретные TK/EP, которые ею владеют.
- **Интерфейсы — вход:** результаты названных зависимостей.
- **Интерфейсы — выход:** передаваемый результат и названные потребители.

## 8. Риски и примечания
Причины best/expected/worst: готовые входы, оплаченный expected объём,
конкретная неопределённость worst и действие при её реализации.

## 9. Отчёт о выполнении
До начала: задача не выполнялась, evidence отсутствует.
После: изменённые файлы, фактические проверки, evidence, блокеры/отклонения.
```

## Согласованность и завершение

Шапка и ссылки соответствуют таблице roadmap. Полные критерии находятся только в карточке; `Acceptance` строки таблицы ссылается на них. Зависимости означают готовые результаты, а не обязательную повторную реализацию. Общая часть имеет одного владельца; повторная регрессия не считается вторым владельцем реализации.

Проверка `python3 roadmap/schedule.py --check` сверяет таблицу, эпики, пути, сумму часов без удвоения, недели, шапки, разделы, входы/выходы и конечную задачу. Отдельно применяется checker установленного zkit 0.2.6. Эти проверки не доказывают смысл текста границ и не заменяют независимое ревью.

Допустимые статусы: planned/in_progress/blocked/done. Done возможен только после всех критериев и фактического отчёта; карточки не отмечаются выполненными заранее. Неуспешный gate или выход за оценённый объём требует блокера и пересчёта плана. TK-45 объявляет готовность конкретной сборки только после полной приёмки.
