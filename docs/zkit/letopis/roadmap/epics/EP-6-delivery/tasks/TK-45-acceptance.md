1. Собрать evidence всех зависимостей и gates по конкретной сборке.
2. Проверить матрицу Must/C и результаты NFR-3/NFR-8 с решениями по отклонениям.

## 4. Ожидаемый результат

Приёмочный отчёт конкретной сборки: «v1 готова» только при выполненных критериях.

Передать пользователю готовую поставку v1 и приёмочный отчёт вместе с версиями/входами и воспроизводимым способом проверки. Конкретные пути изменённых файлов фиксируются в отчёте после выполнения.

## 5. Критерии приёмки

- [ ] Приёмочный отчёт по конкретной сборке подтверждает все Must и C, закрытые G-0…G-4, schema/integration/platform/offline/concurrency/recovery/restore evidence и поставленный навык, включая evidence обнаружения Git-правок C-8.
- [ ] NFR-3/NFR-8 имеют результаты и явное решение по отклонениям.
- [ ] Resource-math/contracts и инструкции обновлены по фактам, нет открытого блокирующего дефекта.
- [ ] Только при выполнении критериев фиксируется «v1 готова»; иначе задача остаётся незавершённой и описан блокер.

- [ ] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 7. Границы

- **Входит:** Приёмочный отчёт конкретной сборки: «v1 готова» только при выполненных критериях. Работа и собственные проверки перечислены в разделе 3.
- **Не входит:** Системные измерения — EP-4, поставка/инструкции — [TK-43](TK-43-delivery.md)/[TK-44](TK-44-operations.md). Неизвестный дефект не становится неоценённой работой внутри приёмки.
- **Интерфейсы — вход:** [TK-43](TK-43-delivery.md): Воспроизводимая локальная поставка v1 для macOS и Linux с install smoke evidence; [TK-44](TK-44-operations.md): Готовый coding-agent skill и проверенная эксплуатационная документация поставки; [TK-42](../../EP-4-system-validation/tasks/TK-42-exhaustion.md): Exhaustion/trust-boundary отчёт DR-7/DR-8 и решение о допуске поставки; [TK-33](../../EP-5-final-pilot/tasks/TK-33-pilot-analysis.md): Сравнительный отчёт P-1 и входные данные P-2.7 для ресурсной проверки
- **Интерфейсы — выход:** Пользователь получает приёмочный отчёт и поставку v1 только при выполненных критериях TK-45.

## 8. Риски и примечания

**Основание оценки 2 / 4 / 8 ч:** best — все evidence уже полны и соответствуют одной сборке; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — нужно сверить расхождения evidence или вернуть задачу владельцу дефекта; при блокере readiness не объявляется. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Нужно сверить расхождения evidence или вернуть задачу владельцу дефекта; при блокере readiness не объявляется. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
