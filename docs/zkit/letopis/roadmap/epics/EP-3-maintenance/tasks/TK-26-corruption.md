# TK-26 — Проверить corruption и fail-closed восстановления

> **Статус:** planned

## 1. Цель

После рабочего save/recovery TK-10 нужно проверить отказ при повреждении его durable входов. Результат: corruption/fail-closed ветви и регрессии диагностики; обязательный порядок MC-2 уже реализован до раннего пилота.

## 3. Что сделать

1. На готовом протоколе TK-10 добавить fixtures missing/corrupt journal, source registry и Git objects; отличать повреждение от штатной первой инициализации.
2. Завершить fail-closed ветви и устойчивую диагностику; при невозможности установить durable исход не запускать обслуживание и не создавать пустую БД.
3. Прогнать сохранённую MC-2 матрицу как регрессию, включая uncertain COMMIT и повторный recovery; не создавать второй save/recovery путь.

## 4. Ожидаемый результат

Проверенные corruption/fail-closed ветви существующего recovery и долговечная диагностика.

## 5. Критерии приёмки

- [ ] Отсутствующий/повреждённый журнал, registry или требуемый Git object дают предусмотренный fail-closed, а не fresh init.
- [ ] Неустановленный durable исход блокирует обслуживание; исходные данные не заменяются пустым состоянием.
- [ ] Ошибка отката сохранена после restart, когда durable диагностика возможна.
- [ ] MC-2 regression подтверждает уже реализованные в TK-10 fsync ordering, uncertain COMMIT и repeated recovery без ослабления гарантий.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 7. Границы

- **Входит:** Проверенные corruption/fail-closed ветви существующего recovery и долговечная диагностика. Работа и собственные проверки перечислены в разделе 3.
- **Не входит:** Durable порядок, fsync и uncertain COMMIT уже полностью принадлежат [TK-10](../../EP-1-thin-slice/tasks/TK-10-save-recovery.md); физические доказательства — [TK-38](../../EP-4-system-validation/tasks/TK-38-power-loss.md); storage API — [TK-9](../../EP-1-thin-slice/tasks/TK-9-storage.md).
- **Интерфейсы — вход:** [TK-25](TK-25-reindexing.md): Координатор reindex и Git detection без фонового watcher; [TK-10](../../EP-1-thin-slice/tasks/TK-10-save-recovery.md): Production save/recovery путь атомарной группы изменений с optimistic conflict checks
- **Интерфейсы — выход:** Результат раздела 4 и воспроизводимые проверки получают [TK-27](TK-27-embedding-lifecycle.md), [TK-28](TK-28-diagnostics.md), [TK-30](../../EP-5-final-pilot/tasks/TK-30-pilot-setup.md), [TK-38](../../EP-4-system-validation/tasks/TK-38-power-loss.md), [TK-39](../../EP-4-system-validation/tasks/TK-39-corruption-drill.md).

## 8. Риски и примечания

**Основание оценки 4 / 8 / 16 ч:** best — готовый recovery TK-10 принимает corruption fixtures без перепроектирования; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — надёжное различение повреждённого registry/journal и пустой БД, повторный сбой восстановления. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Надёжное различение повреждённого registry/journal и пустой БД, повторный сбой восстановления. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
