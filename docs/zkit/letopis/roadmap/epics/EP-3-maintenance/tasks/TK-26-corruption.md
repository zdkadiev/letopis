## 3. Что сделать

1. Добавить fixtures повреждённых/отсутствующих Git objects, отдельно повреждённого/удалённого SQLite-кэша и vectors.db; отличать повреждение кэша от первой инициализации.
2. Git — fail-closed с диагностикой; кэш и vectors.db — удалить и пересобрать reindex (D-91, D-92).
3. Прогнать матрицу прерываний MC-2 из TK-2/TK-10 как регрессию.

## 4. Ожидаемый результат

Проверенные ветви повреждений: fail-closed для Git, пересборка для кэша и vectors.db (D-93).

## 5. Критерии приёмки

- [x] Повреждённый требуемый Git object даёт fail-closed, а не fresh init.
- [ ] Повреждённый или удалённый кэш/vectors.db пересобирается reindex без потери знаний; векторы неизменных текстов сохраняются, если vectors.db цел.
- [x] Диагностика повреждения видна после restart, когда запись возможна.
- [ ] Регрессия MC-2 подтверждает публикацию по файлу и повторное обнаружение после прерывания.

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 7. Границы

- **Входит:** Проверенные ветви повреждений: fail-closed для Git, пересборка для кэша и vectors.db. Работа и собственные проверки перечислены в разделе 3.

## 8. Риски и примечания

**Основание оценки 3 / 6 / 12 ч (пересчёт 2026-10-20):** после D-91/D-93 нет recovery.json: повреждённый кэш или vectors.db удаляется и пересобирается; best — готовая публикация TK-10 принимает corruption fixtures без перепроектирования; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — надёжное различение повреждённого Git и пустого кэша. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Надёжное различение повреждённого Git и пустого кэша. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
