## 3. Что сделать

1. Завершить seq replacement, полную config replacement и сброс несовместимых vectors/jobs.
2. Сохранять attempts до вычисления и bounded retry budget через restart.
3. Проверить failed, cancel и слишком длинный текст с сохранённым FTS без усечения.

## 4. Ожидаемый результат

Полный lifecycle embedding jobs/config и ограниченные ретраи.

## 5. Критерии приёмки

- [ ] Каждая замена получает новый seq.
- [ ] config replace атомарно очищает несовместимые vectors/jobs, reserve attempts переживает restart, max_retries=дополнительные попытки, failed не оживает сам.
- [ ] Длинный текст остаётся в FTS с ошибкой без усечения.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 8. Риски и примечания

**Основание оценки 4 / 8 / 16 ч:** best — seq CAS из TK-13 и vec1 proof TK-3 пригодны для полного lifecycle; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — гонки config replacement, retries после restart и недопустимый по длине текст. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Гонки config replacement, retries после restart и недопустимый по длине текст. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
