## 3. Что сделать

1. Завершить [условный сброс MC-3](../../../../mechanics.md#mc-3--embeddings-работа-из-данных-и-попытки) при смене `.letopis/config.json`: каноническая identity, защита устаревшего наблюдения и сохранение уже совпавшей конфигурации; поздние результаты и ошибки проверяют identity. Сохранить reuse векторов по search_hash после удаления кэша (D-92, D-95).
2. Резервировать attempts в embed_failures до вычисления и держать bounded retry budget через restart.
3. Проверить исчерпанные попытки, SIGINT и слишком длинный текст с сохранённым FTS без усечения.

## 4. Ожидаемый результат

Полный lifecycle config и embeddings с ограниченными ретраями (D-95).

## 5. Критерии приёмки

- [x] Смена config.json очищает vectors.db и embed_failures, поздний результат прежней конфигурации отбрасывается; правка только пробелов или порядка ключей не сбрасывает векторы.
- [x] После удаления кэша считаются только тексты без вектора; attempts переживают restart, max_retries = дополнительные попытки, исчерпанный текст не возобновляется сам.
- [x] Длинный текст остаётся в FTS с ошибкой без усечения.

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 8. Риски и примечания

**Основание оценки 3 / 6 / 12 ч (пересчёт 2026-10-20):** после D-95 нет замены заданий и config --set: сброс по отпечатку config.json, попытки в embed_failures; best — пропуск по search_hash из TK-13 и vec1 proof TK-3 пригодны для полного lifecycle; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — гонки смены config с drain, retries после restart и недопустимый по длине текст. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Гонки смены config с drain, retries после restart и недопустимый по длине текст. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
