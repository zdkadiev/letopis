## 1. Цель

Нужно довести принятые контракты и инварианты до полного v1 scope, сохранив общий путь сохранения/чтения. Конкретный результат этой задачи: полный reindex и Git detection без фонового watcher.

## 3. Что сделать

1. Реализовать первичное построение и полный reindex: index.lock удерживается всё время, граф и FTS строятся заново одной unit (D-95).
2. Обнаруживать внешнюю Git-смену при CLI-вызове через обычное обнаружение изменений.
3. Проверить последний корректный индекс при invalid corpus, SIGINT во время reindex и завершение без ожидания vectors.

Обнаружение изменений и reindex используют один путь публикации (I-2/MC-2); обычная правка не превращается в полный reindex; выборочного reindex нет.

## 4. Ожидаемый результат

Полный reindex и Git detection без фонового watcher (D-95).

## 5. Критерии приёмки

- [ ] Первый вызов строит graph/FTS и ждёт; полный reindex не ждёт vectors.
- [ ] Внешняя Git-смена замечается при вызове без watcher.
- [ ] SIGINT или ошибка во время reindex оставляют прежний кэш; reindex не меняет подтверждённое основание.
- [ ] Reindex с невалидным A и валидным B публикует B, сохраняет прежнюю проекцию A с ошибкой в строке files; detection не пропускает B.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 7. Границы

- **Входит:** Полный reindex и Git detection без фонового watcher. Работа и собственные проверки перечислены в разделе 3.
- **Не входит:** Полный embedding lifecycle — [TK-27](TK-27-embedding-lifecycle.md); отмена/CLI waiter integration — [TK-29](TK-29-cancellation.md); watcher в v1 не добавляется.
- **Интерфейсы — вход:** [TK-24](../../EP-2-knowledge/tasks/TK-24-inspect.md): Полный batch inspect и рабочий навык чтения/записи перед G-2; [TK-10](../../EP-1-thin-slice/tasks/TK-10-change-detection.md): Production путь обнаружения изменений и публикации по файлу; [TK-13](../../EP-1-thin-slice/tasks/TK-13-embeddings.md): Базовый embedding runtime и drain по текстам без вектора

## 8. Риски и примечания

**Основание оценки 3 / 6 / 12 ч (пересчёт 2026-10-20):** после D-95 только полный reindex под блокировкой: нет выборочного, reindex_state и предусловий; best — готовые snapshot/projection/validator порты дают один согласованный вход; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — сдвиг координат, обнаружение Git-смены и длительность полного reindex под блокировкой. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Сдвиг координат, обнаружение Git-смены и длительность полного reindex под блокировкой. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
