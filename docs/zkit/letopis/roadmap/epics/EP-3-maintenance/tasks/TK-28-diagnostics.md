## 1. Цель

Нужно довести принятые контракты и инварианты до полного v1 scope, сохранив общий путь сохранения/чтения. Конкретный результат этой задачи: status с текущими проблемами, выведенными из данных.

## 3. Что сделать

1. Собрать status: revision, занятость блокировок с PID, число текстов без вектора и исчерпавших попытки, текущие проблемы.
2. Выводить проблемы из данных (D-95): ошибки файлов из files, висячие ссылки и циклы — запросом, embed_failures, валидность config.json.
3. Проверить restart, удаление кэша и невозможность записать ошибку файла при storage failure.

Истории сообщений, active/completed и errors --clear нет; команда errors входит в status.

## 4. Ожидаемый результат

Status с текущими проблемами, выведенными из данных (D-95).

## 5. Критерии приёмки

- [x] Status даёт revision, блокировки с PID, отставание векторов, исчерпанные попытки и текущие проблемы.
- [x] Ошибка файла видна, пока файл невалиден, и исчезает после публикации исправленного файла; висячие ссылки и циклы появляются и исчезают вместе с причиной без пересчёта при публикации.
- [x] storage failure не выдаётся за сохранённую ошибку.
- [x] Последняя ошибка query embedding из TK-22 хранится одной строкой vec.query_error и видна в status.problems до успешного запроса, без предупреждения в ответе search (D-62); сбой запуска drain — предупреждение «drain not started» в ответе и не сохраняется; FTS-only выдача остаётся успешной.

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 8. Риски и примечания

**Основание оценки 4 / 6 / 10 ч (пересчёт 2026-10-20):** после D-95 нет истории ошибок, active/owner и errors --clear: status выводит текущие проблемы; best — владельцы уже поставляют files.error, embed_failures и query_error; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — полнота выводимой диагностики и I/O отказ при записи files.error. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Полнота выводимой диагностики и I/O отказ при записи files.error. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.

## 9. Отчёт о выполнении

2026-10-26: реализован строгий observation-only `status` с пятью полями X-1,
одним опциональным опубликованным read view, конфигурацией, query/exhaustion,
graph/source проблемами и best-effort busy-lock PID. Реальный lifecycle подтверждает
отмеченный критерий текущих file/graph проблем. [Общий отчёт](../../../../checks/TK-18-19-status/report.md)
содержит точные команды, host PASS, квалифицированный Linux ARM64 functional PASS и
сохранённые standard-overlay/tmpfs3GiB failures.

Финальное whole-branch review не нашло Critical/Important замечаний; два test-style
замечания исправлены в `6f8e181`, scoped re-review APPROVED без новых замечаний.
Синхронизация с main и упрощение `StatusService` в `ad81a8c` проверены, а текущая
архитектурная приёмка и поставленные status fields отмечены.

Задача остаётся `in_progress`: критерий storage failure требует TK-26-specific
acceptance, а составной query/drain/FTS lifecycle критерий — TK-27-specific acceptance.
Они не выводятся из component tests и этим отчётом не закрываются. Qualified Linux
PASS не доказывает overlay health, persistence/power-loss, resource/minimum-hardware
или x86_64 acceptance.

2026-10-27: два оставшихся критерия закрыты acceptance-тестами на `tk-28`
(ревизия проверки `faaecda`, host macOS/Darwin arm64), продуктовый Rust-код не
изменён. storage failure: production-process сценарий
`uncommitted_file_diagnostic_is_absent_from_status_until_republished` (`2d14922`)
доказывает, что поздний storage-отказ не публикует staged `files.error`, старая
публикация остаётся coherent, а свежий `status` не выдаёт несохранённую ошибку;
после снятия fault повторная публикация сохраняет реальный diagnostic, он исчезает
после исправления файла. Query/drain lifecycle: real product CLI сценарии
`query_failure_is_visible_in_status_until_a_successful_query` (`84c9d03`) и
`drain_start_failure_warns_without_persisting_and_keeps_fts` (`277528b`) подтверждают
одну строку `vec.query_error` (замена, не история), видимость в `status` после
отдельных процессов, сброс успешным запросом, отсутствие предупреждения в ответе
search и transient «cannot start background embedding drain» без сохранения;
FTS-only выдача успешна. Мутационные контроли выполнены; плановая мутация commit
guard дала PASS — guard избыточен относительно распространения ошибки оператора
(record), это задокументировано как defense-in-depth; compound-мутация
(проглатывание ошибки + отключённый guard) детектирована тестом. `make check` и
`make verify` — `ok`; полный root suite 796 passed / 0 failed / 5 ignored.
Повторно использованы evidence TK-26 (`8bc4fca`) и TK-27 (`14d1e47`, ревью
`02b9736`) без переклеймивания. Точный [отчёт](../../../../checks/TK-28-status-acceptance/report.md).
Границы: x86_64, физический power-loss (TK-38), resource/minimum-hardware
(TK-36/G-1/TK-17) и качество реальной модели не проверялись; G-2 закрывается
в TK-29. Storage-failure сценарий использует production-composition в реальном
child-процессе, не полный product binary.
