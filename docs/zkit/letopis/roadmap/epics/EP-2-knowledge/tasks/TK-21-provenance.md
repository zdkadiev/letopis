# TK-21 — Завершить source_snapshot и проверку происхождения

> **Статус:** planned
> **Эпик:** [EP-2](../epic.md)
> **Фаза:** PH-2
> **Оценка, ч:** 4 / 8 / 16 (best / expected / worst)

> **Зависимости:** [TK-8](../../EP-1-thin-slice/tasks/TK-8-git-snapshots.md), [TK-20](TK-20-source-identity.md)


## 1. Цель

Нужно довести принятые контракты и инварианты до полного v1 scope, сохранив общий путь сохранения/чтения. Конкретный результат этой задачи: проверка происхождения и оснований знания с корректными freshness flags.

## 3. Что сделать

1. При индексации проверять существование source_snapshot и равенство адресованных bytes: несовпадение — флаг source_changed, отсутствующий снимок — диагностика file:<путь> и флаг; найденный снимок закрепляется ref (D-93).
2. Сохранять прежнее основание edit без snapshot и обновлять его только явно.
3. Проверить changed/not_found, C1/C2 с одинаковыми bytes и чтение истории из Git.

## 4. Ожидаемый результат

Проверка происхождения и оснований знания с корректными freshness flags.

## 5. Критерии приёмки

- [ ] При индексации существующий снимок закреплён ref, несовпадение bytes даёт source_changed, отсутствующий снимок — диагностику без отказа индексации.
- [ ] edit без snapshot сохраняет основание.
- [ ] Changed/not_found ставят flags.
- [ ] C1/C2 с одинаковым адресованным содержимым равны для фильтра, история остаётся в Git.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 7. Границы

- **Входит:** Проверка происхождения и оснований знания с корректными freshness flags. Работа и собственные проверки перечислены в разделе 3.
- **Не входит:** Git чтение/удержание — [TK-8](../../EP-1-thin-slice/tasks/TK-8-git-snapshots.md); source identity — [TK-20](TK-20-source-identity.md); поисковые filters — [TK-22](TK-22-filters.md).
- **Интерфейсы — вход:** [TK-8](../../EP-1-thin-slice/tasks/TK-8-git-snapshots.md): Git adapter со снимками, служебными refs и тестами сохранности объектов; [TK-20](TK-20-source-identity.md): Source identity по нормализованному URI, выводимая из ссылок (D-91), и корректные metadata доступности
- **Интерфейсы — выход:** Результат раздела 4 и воспроизводимые проверки получают [TK-22](TK-22-filters.md), [TK-23](TK-23-traversal.md), [TK-24](TK-24-inspect.md), [TK-39](../../EP-4-system-validation/tasks/TK-39-corruption-drill.md).

## 8. Риски и примечания

**Основание оценки 4 / 8 / 16 ч:** best — Git port и source identity уже возвращают нужные адресованные байты; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — сравнение разных trees с одинаковыми bytes, исчезнувшие источники и сохранение прежнего основания. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Сравнение разных trees с одинаковыми bytes, исчезнувшие источники и сохранение прежнего основания. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
