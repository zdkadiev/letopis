## 3. Что сделать

1. Завершить разбор файл-элементов и раздел-элементов с якорями, уникальность якорей и запрет вложенности; kind выводится: метавершина — элемент с исходящими includes (D-95).
2. Находить запросом в check/status висячие ссылки, петли и includes-циклы через файлы; traverse берёт только рёбра с существующей целью и не заходит повторно в посещённые узлы.
3. Проверить, что ошибка одного файла не блокирует остальные и check не меняет файлы.

## 4. Ожидаемый результат

Полный доменный валидатор графа с ошибками по файлу (D-95).

## 5. Критерии приёмки

- [x] ID path и path#anchor стабильны при вставке строк; дубль якоря и вложенный элемент — ошибка файла.
- [x] Висячая ссылка, петля и косвенный includes-цикл видны в check/status, пока причина существует; появление цели убирает проблему без правки файла-источника; traverse не зацикливается и не возвращает несуществующие цели.
- [x] check не меняет файлы — реальный binary/lifecycle проверен в [TK-19](../../../../checks/TK-19/report.md).

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

**Основание оценки 4 / 8 / 12 ч:** best — готовые fixtures и предыдущие задачи переиспользуются; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — стоимость запроса висячих ссылок и циклов на целевом графе. **Риск и действие:** Стоимость запроса висячих ссылок и циклов на целевом графе. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план.
