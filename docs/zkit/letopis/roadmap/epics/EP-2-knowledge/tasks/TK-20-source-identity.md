## 1. Цель

Нужно довести принятые контракты и инварианты до полного v1 scope, сохранив общий путь сохранения/чтения. Конкретный результат этой задачи: долговечный реестр source identity и корректные metadata доступности.

## 3. Что сделать

1. Нормализовать source URI целого файла и диапазона строк.
2. Сохранить устойчивые source UUID/created_at и чтение source без текущих ссылок.
3. Проверить missing hash=null/flags и адреса URL без добавления web fetch.

## 4. Ожидаемый результат

Долговечный реестр source identity и корректные metadata доступности.

## 5. Критерии приёмки

- [ ] Нормализованный URI целого файла/lines имеет один durable source UUID/created_at.
- [ ] source без текущих ссылок инспектируется, недоступный hash=null и flags корректны.
- [ ] Удалённый URL остаётся адресом без web fetch.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 7. Границы

- **Входит:** Долговечный реестр source identity и корректные metadata доступности. Работа и собственные проверки перечислены в разделе 3.
- **Не входит:** Синтаксис URI — [TK-7](../../EP-1-thin-slice/tasks/TK-7-markdown.md); проверка source_snapshot/bytes — [TK-21](TK-21-provenance.md); web fetch не входит в v1.
- **Интерфейсы — вход:** [TK-18](TK-18-graph-validation.md): Полный доменный валидатор графа и atomic validation failures; [TK-19](TK-19-mutations.md): Полные CRUD/перенос и optimistic conflict semantics согласованного CLI; [TK-9](../../EP-1-thin-slice/tasks/TK-9-storage.md): Начальная схема SQLite и storage adapters для всех согласованных сущностей
- **Интерфейсы — выход:** Результат раздела 4 и воспроизводимые проверки получают [TK-21](TK-21-provenance.md), [TK-22](TK-22-filters.md), [TK-23](TK-23-traversal.md), [TK-24](TK-24-inspect.md).

## 8. Риски и примечания

**Основание оценки 4 / 8 / 12 ч:** best — SQL source identity из TK-9 и URI codec из TK-7 переиспользуются; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — нормализация whole-file/line URI и сохранность identity без текущих ссылок. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Нормализация whole-file/line URI и сохранность identity без текущих ссылок. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
