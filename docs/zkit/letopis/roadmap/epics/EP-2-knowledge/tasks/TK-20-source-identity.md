## 3. Что сделать

1. Нормализовать source URI целого файла и диапазона строк.
2. ID source = нормализованный URI; created_at = минимальный created_at текущих external-ссылок; source без ссылок удаляется из графа (D-91).
3. Проверить missing hash=null/flags и адреса URL без добавления web fetch.

**Утверждённая граница TK-20 (2026-10-25):** общий source-сервис и типизированная доступность реализуются здесь; source в CLI inspect — TK-24, историческое сравнение — TK-21. HTTP/HTTPS URL хранится как непрозрачный адрес с исходными query/fragment, без нормализации файлового пути и fetch. При обновлении требуется явная пересборка производного cache.db; автоматической миграции старых URL нет. Markdown, Git, vectors.db, config и lock-файлы сохраняются.

## 4. Ожидаемый результат

Source identity по нормализованному URI, выводимая из ссылок (D-91), и корректные metadata доступности.

## 5. Критерии приёмки

- [x] Нормализованный URI целого файла/lines — единственный ID source; после удаления кэша и reindex ID и created_at source совпадают с прежними.
- [x] адрес source без текущих ссылок даёт not_found; у source со ссылками и недоступными bytes hash=null и flags корректны.
- [x] Удалённый URL остаётся адресом без web fetch.

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 8. Риски и примечания

**Основание оценки 3 / 6 / 10 ч (пересчёт 2026-10-20):** после D-91 нет реестра source: ID и created_at выводятся из ссылок; best — SQL source identity из TK-9 и URI codec из TK-7 переиспользуются; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — нормализация whole-file/line URI и сохранность identity без текущих ссылок. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Нормализация whole-file/line URI и сохранность identity без текущих ссылок. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
