## 3. Что сделать

1. Завершить прикладной сервис и команду check по корпусу и путям, подключив CLI-границу TK-11. Проверить реальный вызов продуктового бинарника после refresh; контрактный test double TK-11 не заменяет эту приёмку.
2. Проверить удаление и переименование файла/якоря: висячие ссылки видны в check/status до исправления.
3. Проверить сохранность created_at при правке и переименовании и параллельные правки разных файлов.

Полная проверка корпуса и обработка удалений/переименований согласованного CLI (D-93/D-94).

## 5. Критерии приёмки

- [x] Реальный вызов продуктового CLI check через прикладной сервис после refresh возвращает все ошибки файлов и висячие ссылки по X-1 без изменения файлов; проверены весь корпус, paths и исправление текущих ошибок. Один JSON stdout и exit 0/1 проверены на этом настоящем пути, а не только с test double.
- [x] После переименования или удаления файла/якоря входящие ссылки из неизменённых файлов видны в check как висячие; после исправления или возвращения цели проблема исчезает без правки файла-источника и без пересчёта при публикации (D-95).
- [x] Тот же результат доступен через status — потребитель [TK-28](../../EP-3-maintenance/tasks/TK-28-diagnostics.md); полное завершение TK-28 этой приёмкой не подтверждается.
- [x] created_at сохраняется при правке и переименовании; параллельные правки разных файлов публикуются обе.

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 8. Риски и примечания

**Основание оценки 3 / 6 / 10 ч (пересчёт 2026-10-20):** после D-93 нет apply/batch мутаций, tmp-ID и base_hash: только check, удаления и переименования; best — готовые fixtures и предыдущие задачи переиспользуются; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — большие переименования каталогов и их стоимость при следующем обнаружении. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Большие переименования каталогов и их стоимость при следующем обнаружении. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
