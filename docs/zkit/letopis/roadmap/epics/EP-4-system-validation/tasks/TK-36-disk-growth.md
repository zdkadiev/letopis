## 3. Что сделать

1. Построить репрезентативную трассу правок на основе фактического профиля.
2. Учесть sources/refs/objects/embed_failures/WAL и пиковое место до/во время/после pack.
3. Обосновать годовую экстраполяцию диапазоном, не переносить коэффициент маленькой пробы автоматически.

## 4. Ожидаемый результат

Обоснованная оценка годового диска и стоимости штатного Git обслуживания.

## 5. Критерии приёмки

- [ ] Репрезентативная трасса правок учитывает whole-file sources, retained refs/objects, embed_failures, WAL и временное место до/во время/после Git pack.
- [ ] Экстраполяция на год имеет диапазон и основания.
- [ ] Сутки pack остаются расчётным условием, не новым таймером.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

- **Не входит:** Генератор входов — [TK-15](../../EP-7-early-validation/tasks/TK-15-target-corpus.md); измерение RAM/latency — [TK-34](TK-34-mixed-memory.md)/[TK-35](TK-35-search-latency.md); backup/restore — [TK-40](TK-40-restore.md); таймер Git pack не создаётся.

**Основание оценки 4 / 8 / 12 ч:** best — реальный профиль TK-33 и штатный pack дают устойчивую трассу; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — разброс object retention, whole-file delta и пикового WAL/temp пространства. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Разброс object retention, whole-file delta и пикового WAL/temp пространства. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
