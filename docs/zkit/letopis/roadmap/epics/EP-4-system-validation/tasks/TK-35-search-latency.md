## 1. Цель

Предварительные модели и отдельные пробы не подтверждают реализацию: здесь нужны фактические результаты полного профиля и отказов. Конкретный результат этой задачи: latency отчёт полного поиска и решение по NFR-3 без обрезания результата по времени.

## 3. Что сделать

1. Измерить warmed search целиком: query embedding, filters, ранжирование и CLI.
2. Измерить cold startup отдельно и сохранить распределения задержек.
3. Оценить секундную Should-цель; подтверждённый узкий дефект исправить и перепроверить в пределах задачи.

Прогретый полный semantic/hybrid run начинать с 100k current vectors и успешным query embedding; подтвердить фактическое vector participation и coverage/config/search_hash. FTS fallback/backlog измерять и маркировать отдельно.

## 4. Ожидаемый результат

Latency отчёт полного поиска и решение по NFR-3 без обрезания результата по времени.

## 5. Критерии приёмки

- [ ] Полный warmed search с query embedding/filters/CLI и cold startup измерены отдельно, распределение задержек сохранено.
- [ ] Секундная Should-цель оценена, результат не обрезан.
- [ ] Только подтверждённый недостаток получает узкое исправление и повторную проверку в пределах задачи.

- [ ] Основной latency verdict использует populated 100k current vectors и реальный hybrid путь; FTS-only fallback, failed embeddings либо неполное покрытие не заменяют его. Cold startup и backlog результаты помечены отдельно.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 7. Границы

- **Входит:** Latency отчёт полного поиска и решение по NFR-3 без обрезания результата по времени. Работа и собственные проверки перечислены в разделе 3.
- **Не входит:** RAM — [TK-34](TK-34-mixed-memory.md); queue throughput — [TK-37](TK-37-queue-drill.md); пересмотр архитектуры только по gate, не предварительная оптимизация.
- **Интерфейсы — вход:** [TK-34](TK-34-mixed-memory.md): Полная проверка NFR-2/NFR-4/NFR-7 с реальной mixed-client нагрузкой; [TK-22](../../EP-2-knowledge/tasks/TK-22-filters.md): Полные поисковые фильтры и проверенная деградация query embedding
- **Интерфейсы — выход:** Результат раздела 4 и воспроизводимые проверки получают [TK-42](TK-42-exhaustion.md), [TK-43](../../EP-6-delivery/tasks/TK-43-delivery.md).

## 8. Риски и примечания

**Основание оценки 4 / 8 / 12 ч:** best — полный поиск измеряется готовым runner и узких дефектов нет; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — выявленный локальный дефект или шум cold/warm требуют повторной ограниченной проверки. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Выявленный локальный дефект или шум cold/warm требуют повторной ограниченной проверки. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
