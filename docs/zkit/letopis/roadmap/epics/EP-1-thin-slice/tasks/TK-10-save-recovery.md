## 1. Цель

Сквозной путь должен соединить реальные адаптеры; ранние RAM и usefulness результаты нужны до расширения полного функционала. Конкретный результат этой задачи: production save/recovery путь атомарной группы изменений с optimistic conflict checks.

## 3. Что сделать

1. Соединить prepare/validate, проверку текущих хешей и одну защищённую фазу сохранения.
2. До recovery row надёжно сохранить before/after/source Git closure и refs; после byte-splices синхронизировать файлы и directory entries, включая каталоги, с платформенными барьерами MC-2.
3. Одной финальной SQLite unit сохранить graph/FTS/source metadata/revision/jobs и удалить recovery/lock. Успех выдавать только после подтверждённого durable commit.
4. Подключить полный повторяемый rollback и startup recovery; uncertain COMMIT разрешать повторным открытием SQLite и проверкой журнала, при неопределимом исходе блокировать обслуживание. Перенести crash cases TK-2 в production integration checks.

## 4. Ожидаемый результат

Production save/recovery путь атомарной группы изменений с optimistic conflict checks.

## 5. Критерии приёмки

- [ ] Production apply валидирует текущий base_hash, сохраняет recovery row до файловых splice и синхронно фиксирует graph/FTS/jobs с удалением журнала.
- [ ] Ошибка откатывает группу, startup recovery предшествует обслуживанию.
- [ ] Git objects/refs надёжны до recovery row; file/directory sync выполнен до финального commit по MC-2, включая macOS flush.
- [ ] Uncertain COMMIT разрешается чтением recovery row после reopening SQLite; неизвестный исход блокирует обслуживание, успех не откатывается из-за потери ответа.
- [ ] Повторный crash во время rollback оставляет recovery доступным для следующего восстановления.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 8. Риски и примечания

**Основание оценки 5 / 8 / 14 ч:** best — протокол и crash oracle из TK-2 без изменений переносятся на адаптеры TK-8/TK-9; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — интеграция durable Git/file/directory барьеров и разрешение uncertain COMMIT. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Интеграция durable Git/file/directory барьеров и разрешение uncertain COMMIT. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
