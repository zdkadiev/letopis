## 1. Цель

Сквозной путь должен соединить реальные адаптеры; ранние RAM и usefulness результаты нужны до расширения полного функционала. Конкретный результат этой задачи: базовый search/inspect с согласованными ссылками и гибридным ранжированием.

## 3. Что сделать

1. Закреплять SQLite read view на время search/traverse (inspect читает Git-снимок I-12).
2. Реализовать FTS и согласованное объединение с vector-каналом, сортировку и ссылки.
3. Проверить отсутствие текста в выдаче, metadata/flags и FTS-only fallback.
4. Подключить реальный базовый inspect к CLI-границе из TK-11 и проверить настоящий вызов бинарника: refresh до ответа, один сохранённый Git tree snapshot, актуальные metadata/lines/hash, отсутствие raw text и корректные ошибки. Успех контрактного test double из TK-11 не считается этой приёмкой; полный batch/source scope остаётся TK-24.
5. По решению пользователя 2026-10-23 подключить уже завершённую TK-13 для настоящего query embedding в CLI search. Для изолированной проверки rank/read view использовать подготовленные векторы; для интеграции — существующих HTTP-провайдеров с управляемыми ответами. Новая реализация provider не создаётся; сквозной сценарий новой сессии агента остаётся TK-14.

## 4. Ожидаемый результат

Базовый search/inspect с согласованными ссылками и гибридным ранжированием.

## 5. Критерии приёмки

- [ ] Search читает один SQLite snapshot, объединяет FTS/vector по принятому rank и возвращает только URI/ID/lines/revision/flags.
- [ ] Без config/vector/query embedding работает FTS.
- [ ] Реальный CLI search вызывает готовый query embedding из TK-13 с согласованной identity/размерностью; управляемый HTTP-сбой даёт обычный FTS success без query warning, безопасная ошибка хранится в singleton query_error (D-62).
- [ ] Реальный базовый inspect проходит вызов продуктового CLI через прикладной сервис и Git snapshot; ответ соответствует X-1 и не возвращает raw text. Ошибки входа/отсутствующего ID и refresh до ответа проверены на реальном пути; полный batch/source scope остаётся TK-24.

- [ ] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 7. Границы

- **Входит:** Реальная CLI-приёмка базового inspect, перенесённая из TK-11 по решению пользователя 2026-10-22; базовый search/inspect с согласованными ссылками и гибридным ранжированием. Работа и собственные проверки перечислены в разделе 3.
- **Не входит:** Повторная реализация provider/executor из [TK-13](TK-13-embeddings.md); сквозной сценарий новой сессии агента — [TK-14](TK-14-thin-slice.md); полные filters — [TK-22](../../EP-2-knowledge/tasks/TK-22-filters.md); batch inspect — [TK-24](../../EP-2-knowledge/tasks/TK-24-inspect.md).
- **Интерфейсы — вход:** [TK-9](TK-9-storage.md): Начальная схема SQLite и storage adapters для всех согласованных сущностей; [TK-11](TK-11-cli-runtime.md): Рабочий CLI без постоянного процесса, с блокировками и запуском drain
- **Интерфейсы — выход:** Результат раздела 4 и воспроизводимые проверки получают [TK-14](TK-14-thin-slice.md), [TK-22](../../EP-2-knowledge/tasks/TK-22-filters.md), [TK-23](../../EP-2-knowledge/tasks/TK-23-traversal.md).

## 8. Риски и примечания

**Основание оценки 5 / 8 / 14 ч:** best — rank/read-view проверяются подготовленными векторами и контрактным embedding-портом; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — совместимость read view FTS/vec1 и fallback при недоступном query-векторе. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Совместимость read view FTS/vec1 и fallback при недоступном query-векторе. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.

## 9. Отчёт о выполнении

Спецификация утверждена, независимый builder check завершён; план готовится к review. Продуктовый код пока не менялся; критерии продуктовой приёмки не отмечены. [Проверка дизайна](../../../../checks/TK-12/design-review-2026-10-23.md) отделена от будущего отчёта реализации.

**Уточнение планирования 2026-10-22:** пользователь утвердил разделение с TK-11: та поставляет CLI/runtime и контрактную проверку границы, а TK-12 владеет реальным алгоритмом базового inspect и его вызовом через продуктовый бинарник. Зависимость TK-12 → TK-11 сохраняется; встречной зависимости TK-11 → TK-12 для завершения транспортной части нет. Это перенос ответственности за evidence, а не выполненная приёмка или изменение конечного X-1.

При препятствии поставить `blocked` и указать причину, следующий шаг и затронутые зависимости.
