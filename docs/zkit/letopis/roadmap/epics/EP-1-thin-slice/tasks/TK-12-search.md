## 1. Цель

Сквозной путь должен соединить реальные адаптеры; ранние RAM и usefulness результаты нужны до расширения полного функционала. Конкретный результат этой задачи: базовый search/inspect с согласованными ссылками и гибридным ранжированием.

## 3. Что сделать

1. Закреплять SQLite read view на время search/traverse (inspect читает Git-снимок I-12).
2. Реализовать FTS и согласованное объединение с vector-каналом, сортировку и ссылки.
3. Проверить отсутствие текста в выдаче, metadata/flags и FTS-only fallback.
4. Для изолированной приёмки использовать подготовленные векторы и контрактный embedding-порт; живой provider подключается в TK-13/TK-14, новая реализация provider здесь не создаётся.

## 4. Ожидаемый результат

Базовый search/inspect с согласованными ссылками и гибридным ранжированием.

## 5. Критерии приёмки

- [ ] Search читает один SQLite snapshot, объединяет FTS/vector по принятому rank и возвращает только URI/ID/lines/revision/flags.
- [ ] Без config/vector/query embedding работает FTS.
- [ ] inspection не возвращает raw text.

- [ ] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 7. Границы

- **Входит:** Базовый search/inspect с согласованными ссылками и гибридным ранжированием. Работа и собственные проверки перечислены в разделе 3.

## 8. Риски и примечания

**Основание оценки 5 / 8 / 14 ч:** best — rank/read-view проверяются подготовленными векторами и контрактным embedding-портом; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — совместимость read view FTS/vec1 и fallback при недоступном query-векторе. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Совместимость read view FTS/vec1 и fallback при недоступном query-векторе. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
