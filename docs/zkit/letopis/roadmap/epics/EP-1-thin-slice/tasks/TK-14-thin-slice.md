Сквозной путь должен соединить реальные адаптеры; ранние RAM и usefulness результаты нужны до расширения полного функционала. Конкретный результат этой задачи: первый работающий сквозной slice и минимальная инструкция coding-агенту.

## 3. Что сделать

1. Соединить реальные адаптеры в единый путь CLI→Markdown/Git→graph/FTS→drain. Готовое подключение query embedding в CLI search приходит из TK-12 по решению пользователя 2026-10-23; повторно реализовывать его здесь не нужно.
2. В новой сессии сохранить знание/ссылку, найти и инспектировать его, дождаться актуального vector.
3. Подготовить начальный навык и минимальную source projection/загрузку для целевого RAM-корпуса.

## 4. Ожидаемый результат

Первый работающий сквозной slice и минимальная инструкция coding-агенту.

## 5. Критерии приёмки

- [x] Агент новой сессии записывает знание и ссылку в файл; следующий вызов реального CLI находит изменение, даёт FTS-результат/inspect и актуальный embedding.
- [x] Сбой не смешивает файлы/БД.
- [x] Навык объясняет этот путь.
- [x] Базовая source projection и загрузка корпуса готовы для RAM-пробы.

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.
