## 1. Цель

Сквозной путь должен соединить реальные адаптеры; ранние RAM и usefulness результаты нужны до расширения полного функционала. Конкретный результат этой задачи: production путь обнаружения изменений и публикации по файлу.

## 3. Что сделать

1. Реализовать обнаружение изменённых файлов: кандидаты из `git ls-files -z --cached --others --exclude-standard` (D-97), таблица files со строкой у каждого кандидата, stat-префильтр, хеш изменённых и racy файлов.
2. Публиковать изменённые файлы под index.lock одной SQLite unit: проекции валидных файлов, все объявленные рёбра, files-строки с текстом ошибки невалидного файла, счётчик revision.
3. Невалидный файл сохраняет прежнюю проекцию; висячие ссылки и циклы не пересчитываются при публикации, их находит запрос (D-95); повторное обнаружение под блокировкой (MC-2).
4. Перенести сценарии прерывания TK-2 в production integration checks.

При отсутствии прежней публикации строить полную проекцию.

## 4. Ожидаемый результат

Production путь обнаружения изменений и публикации по файлу (D-95).

## 5. Критерии приёмки

- [ ] Каждый вызов search/traverse/inspect/check видит валидные правки, сделанные до него (FR-13).
- [ ] Невалидный файл сохраняет прежнюю проекцию, его ошибка хранится в строке files и видна в status/check; остальные файлы публикуются (FR-6).
- [ ] Прерывание публикации не оставляет смешанного кэша; files-строки меняются только в unit публикации.
- [ ] Неразмеченный `.md` получает строку files без узлов и при следующем вызове не читается; файл в `.gitignore` не сканируется; добавление разметки в такой файл публикует его знания (D-97).
- [ ] Пустая дельта не берёт index.lock; обычная правка индексирует только изменённые файлы; Git tree на публикацию не пишется (D-95).

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 8. Риски и примечания

**Основание оценки 6 / 8 / 14 ч (пересчёт 2026-10-20):** после D-95 нет пересчёта активности рёбер и tree на публикацию; best — готовые fixtures и предыдущие задачи переиспользуются; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — стоимость stat-префильтра и корректность racy-хеширования на больших каталогах. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Стоимость stat-префильтра и корректность racy-хеширования на больших каталогах. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
