## 1. Цель

Сквозной путь должен соединить реальные адаптеры; ранние RAM и usefulness результаты нужны до расширения полного функционала. Конкретный результат этой задачи: production путь обнаружения изменений и публикации по файлу.

## 3. Что сделать

1. Реализовать обнаружение изменённых файлов: кандидаты из `git ls-files -z --cached --others --exclude-standard` (D-97), таблица files со строкой у каждого кандидата, stat-префильтр, хеш изменённых и racy файлов.
2. Публиковать изменённые файлы под index.lock одной SQLite unit: проекции валидных файлов, все объявленные рёбра, files-строки с текстом ошибки невалидного файла, счётчик revision.
3. Невалидный файл сохраняет прежнюю проекцию; висячие ссылки и циклы не пересчитываются при публикации, их находит запрос (D-95); повторное обнаружение под блокировкой (MC-2).
4. Перенести сценарии прерывания TK-2 в production integration checks.

При отсутствии прежней публикации строить полную проекцию.

## 4. Ожидаемый результат

Production путь обнаружения изменений и публикации по файлу (D-95).

## 5. Критерии приёмки

В этой задаче критерии проверены на production-сервисе `Documents::refresh` и независимом чтении кэша. Подключение search/traverse/inspect/check/status и отображение ошибок в CLI остаётся TK-11/TK-14 согласно одобренной спецификации; выполнение этих команд здесь не заявляется.

- [x] Каждый вызов search/traverse/inspect/check видит валидные правки, сделанные до него (FR-13).
- [x] Невалидный файл сохраняет прежнюю проекцию, его ошибка хранится в строке files и видна в status/check; остальные файлы публикуются (FR-6).
- [x] Прерывание публикации не оставляет смешанного кэша; files-строки меняются только в unit публикации.
- [x] Неразмеченный `.md` получает строку files без узлов и при следующем вызове не читается; untracked-файл в `.gitignore` не сканируется (tracked-файлы остаются кандидатами по точной команде D-97); добавление разметки в такой файл публикует его знания (D-97).
- [x] Пустая дельта не берёт index.lock; обычная правка индексирует только изменённые файлы; Git tree на публикацию не пишется (D-95).

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 8. Риски и примечания

**Основание оценки 6 / 8 / 14 ч (пересчёт 2026-10-20):** после D-95 нет пересчёта активности рёбер и tree на публикацию; best — готовые fixtures и предыдущие задачи переиспользуются; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — стоимость stat-префильтра и корректность racy-хеширования на больших каталогах. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Стоимость stat-префильтра и корректность racy-хеширования на больших каталогах. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.

## 9. Отчёт о выполнении

Реализованы синхронные Git-кандидаты и безопасное чтение файлов, stat/hash/racy обнаружение изменений, повторная проверка под kernel flock и публикация FileRow/графа/FTS одной SQLite unit. Невалидный файл сохраняет последнюю валидную проекцию, source metadata согласуются по итоговому графу. `lib.rs` связывает реальные реализации с сервисом; никаких Git tree или embedding-вызовов на публикацию нет.

[Отчёт приёмки](../../../../checks/TK-10/report.md) содержит команды, исходные хэши, проверенные границы архитектуры и отображение критериев на проверки. Первичные evidence `2378731`/`8e29067` сохранены отдельно. Финальные исходники `15fcc19`; по 172 Rust-теста и 9 Python-тестов на macOS ARM64 и source-built Linux ARM64, fmt/compiler/Clippy/strict Rustdoc/schema/native/copied executable PASS. Десять SIGKILL checkpoints, реальная конкуренция, WAL, поздняя StorageError и проверенные отрицательные контроли публикации и исправлений, каждый привязан к своей версии исходников; 86 общих хэшей платформ совпадают. Все четыре task-review одобрены, открытых замечаний нет. Финальное whole-branch review выявило гонку открытия при активном writer и неточность описания зависимости; исправления прошли новые прогоны обеих платформ и ждут scoped re-review. Готовая схема проверяется чтением; создание схемы перепроверяется под SQLite ownership, readiness/ownership шаги ограничены пятью секундами каждый, без общего CLI deadline и повторов обычной записи. Отдельно воспроизведена и покрыта гонка macOS `openat(O_CREAT|O_NOFOLLOW)`: один reopen без CREATE сохраняет защитные флаги. Merge/push/GitHub issue не выполнялись.

Ограничения: CLI подключается позже; live corpus не является атомарным снимком, racy window равен одной секунде. Не доказана атомарная защита SQLite pathname lookup от враждебной конкурентной замены предков каталога. SIGKILL между операциями не доказывает физическую потерю питания. x86_64, ресурсы/качество моделей и несвязанные исторические harness не запускались.
