## 1. Цель

Сквозной путь должен соединить реальные адаптеры; ранние RAM и usefulness результаты нужны до расширения полного функционала. Конкретный результат этой задачи: рабочий CLI без постоянного процесса, с блокировками и запуском drain.

## 3. Что сделать

1. Реализовать процесс на вызов: разбор argv/stdin, общий JSON envelope, exit codes.
2. Подключить flock index.lock/embed.lock и отсоединённый запуск `letopis embed --drain`.
3. Подключить check/inspect к прикладным портам; проверить неизвестные поля и exit codes.

## 4. Ожидаемый результат

Рабочий CLI без постоянного процесса, с блокировками и запуском drain (D-93/D-94).

## 5. Критерии приёмки

- [ ] check/inspect проходят реальный вызов CLI; drain запускается, когда есть тексты без вектора, и завершается, когда их не осталось (D-95).
- [ ] Один JSON stdout, exit 0/1, unknown fields reject.
- [ ] Повтор вызова после потери ответа идемпотентен; letopis не меняет корпус.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 7. Границы

- **Входит:** Рабочий CLI без постоянного процесса, с блокировками и запуском drain. Работа и собственные проверки перечислены в разделе 3.
- **Не входит:** Предметные read-алгоритмы — [TK-12](TK-12-search.md)/[TK-24](../../EP-2-knowledge/tasks/TK-24-inspect.md); полный cancel/waiter lifecycle — [TK-29](../../EP-3-maintenance/tasks/TK-29-cancellation.md); runtime proof уже в [TK-4](../../EP-8-proofs/tasks/TK-4-runtime-harness.md).
- **Интерфейсы — вход:** [TK-4](../../EP-8-proofs/tasks/TK-4-runtime-harness.md): Проверенная координация процессов: одна публикация, один drain, отмена SIGINT с negative fixtures; [TK-9](TK-9-storage.md): Начальная схема SQLite и storage adapters для всех согласованных сущностей; [TK-10](TK-10-change-detection.md): Production путь обнаружения изменений и публикации по файлу
- **Интерфейсы — выход:** Результат раздела 4 и воспроизводимые проверки получают [TK-12](TK-12-search.md), [TK-14](TK-14-thin-slice.md), [TK-29](../../EP-3-maintenance/tasks/TK-29-cancellation.md).

## 8. Риски и примечания

**Основание оценки 4 / 6 / 10 ч (пересчёт 2026-10-20):** после D-94 нет worker и IPC-протокола: процесс на вызов с общим JSON envelope; best — готовые fixtures и предыдущие задачи переиспользуются; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — отсоединённый запуск drain и обработка сигналов на обеих ОС. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Отсоединённый запуск drain и обработка сигналов на обеих ОС. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
