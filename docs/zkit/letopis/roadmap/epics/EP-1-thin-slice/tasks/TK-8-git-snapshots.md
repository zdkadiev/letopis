## 1. Цель

Сквозной путь должен соединить реальные адаптеры; ранние RAM и usefulness результаты нужны до расширения полного функционала. Конкретный результат этой задачи: git adapter со снимками, служебными refs и тестами сохранности объектов.

## 3. Что сделать

1. Реализовать порт создания/чтения tree snapshots без пользовательского commit.
2. Добавить удержание служебными refs выданных inspect-снимков и найденных source_snapshot и чтение адресованных байтов; tree на публикацию не пишется (D-95).
3. Проверить object closure, повторное чтение и сохранность принятых snapshots после GC.
4. Вызывать `git` подпроцессом с argv/stdin без shell (D-96); при `git --version` ниже 2.29 отказывать явной ошибкой; проверить на фикстуре SHA-256-репозитория.

## 4. Ожидаемый результат

Git adapter со снимками, служебными refs и тестами сохранности объектов (D-95).

## 5. Критерии приёмки

- [x] Git adapter создаёт согласованные tree snapshots без пользовательского commit, читает заданные bytes и удерживает inspect-снимки и source_snapshot служебными refs; снимков before/after и tree на публикацию нет (D-93, D-95).
- [x] GC не теряет принятые основания и выданные inspect-снимки.
- [x] Git ниже 2.29 даёт явную ошибку; аргументы не проходят через shell; SHA-256-репозиторий читается и удерживается так же, как SHA-1 (D-96).

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 8. Риски и примечания

**Основание оценки 4 / 5 / 10 ч (пересчёт 2026-10-20):** после D-95 нет tree и refs на каждую публикацию; проверка версии Git и фикстура SHA-256 по D-96 укладываются в прежний диапазон (пересчёт 2026-10-21 не нужен); best — Git tree/ref операции из TK-2 непосредственно переиспользуются; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — долговечность object closure и refs при GC и различия платформенных flush барьеров. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Долговечность object closure и refs при GC и различия платформенных flush барьеров. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.

## 9. Отчёт о выполнении
