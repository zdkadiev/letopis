## 1. Цель

Сквозной путь должен соединить реальные адаптеры; ранние RAM и usefulness результаты нужны до расширения полного функционала. Конкретный результат этой задачи: воспроизводимый target-scale fixture: 100k знаний, assumed 100k source и 500k рёбер.

## 3. Что сделать

1. Сгенерировать изолированные Markdown/источники целевого масштаба по ресурсным допущениям.
2. Проверить counts, валидные ссылки/includes и раскладку файлов.
3. Загрузить корпус через production путь slice, сохранить seed/входы и способ воспроизведения.

Подготовить/воспроизвести состояния backlog и populated по resource-math/D-90. Зафиксировать выбранную модель/конфигурацию, реальные A-2 byte statistics, knowledge/current-vector/queued/failed counts. Получение всех vectors проходит production executor; срок готовности не задаётся.

## 4. Ожидаемый результат

Воспроизводимый target-scale fixture: 100k знаний, assumed 100k source и 500k рёбер.

## 5. Критерии приёмки

- [x] Генератор test Markdown даёт 100k знаний, assumed 100k source и 500k рёбер с валидной разметкой, includes без циклов и профилем 10–50 элементов/файл.
- [x] Полная загрузка проходит через slice, а не обход production путей.

- [x] Payload соответствует выбранному A-2 сценарию; записаны точные UTF-8 byte sum/mean/min/max и seed, короткие заглушки не подменяют размер при том же node count.
- [x] Для populated доступны 100 000 current vectors знаний выбранной конфигурации/search_hash; source исключены. Backlog описан отдельно. Неполное покрытие фиксируется как not assessed populated, queued=0 само по себе не критерий.

- [x] Соблюдены [структура программы и границы модулей](../../../../architecture.md#program-structure); в отчёте названы проверенные границы/файлы и evidence либо обосновано отсутствие изменений продуктового Rust-кода.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка:** выполнить [общий порядок проверки структуры](../../../../architecture.md#program-structure-review) для изменяемых компонентов и зафиксировать результат в отчёте; область без изменений продуктового Rust-кода указать явно.

## 8. Риски и примечания

**Основание оценки 4 / 8 / 16 ч:** best — фиксированный seed и готовый загрузчик TK-14 дают валидный корпус; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — раскладка 100k знаний/100k sources/500k edges и массовая загрузка через реальный путь. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Раскладка 100k знаний/100k sources/500k edges и массовая загрузка через реальный путь. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
