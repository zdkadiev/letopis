## 1. Цель

До основного build нужно проверить рискованные примитивы на узком воспроизводимом сценарии и получить основание для G-0. Конкретный результат этой задачи: матрица crash cuts с точным oracle и воспроизводимый harness save/recovery.

## 3. Что сделать

1. В harness связать before tree, recovery row, файловый splice и финальную SQL-транзакцию по MC-2.
2. Добавить точки прерывания до/после durable шагов, неопределённого COMMIT и потери ответа.
3. После каждого прерывания перезапустить recovery и сравнить все файлы/БД с ожидаемым before или after.

Проверить repair apply после внешних invalid A + valid changed B, включая создание/удаление других файлов: publication delta берётся от опубликованной revision, rollback касается только request paths.

## 4. Ожидаемый результат

Матрица crash cuts с точным oracle и воспроизводимый harness save/recovery.

## 5. Критерии приёмки

- [ ] На каждой process-crash границе до финальной фиксации восстановлен полный before, после неё сохранён полный after, включая потерю ответа и повторный recovery.
- [ ] Uncertain COMMIT разрешается reopening SQLite и наличием recovery row.
- [ ] Это не физический power-loss drill.

- [ ] Repair apply(A) публикует весь outstanding delta A/B/созданий/удалений; crash/rollback сохраняет внешние изменения вне request paths и прежнюю DB revision.

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

## 8. Риски и примечания

**Основание оценки 8 / 16 / 32 ч:** best — готовый build TK-1 и повторно используемые fixtures; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — нестабильная инъекция process crash и воспроизведение неопределённого COMMIT. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Нестабильная инъекция process crash и воспроизведение неопределённого COMMIT. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
