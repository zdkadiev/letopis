## 3. Что сделать

1. Реализовать минимальные вызовы Ollama и OpenAI-совместимого embedding API в harness.
2. Подать malformed/неполные vectors, молчащий endpoint, ошибки и отмену.
3. Проверить deadline, локальный режим и безопасную диагностику без response body/секретов.
4. Клиент — блокирующий `ureq` 3 (D-96): `max_redirects(0)`, прокси из окружения игнорируются, таймаут попытки 60 s, TLS rustls + `rustls-platform-verifier`; без tokio и `reqwest`.

## 4. Ожидаемый результат

Boundary harness двух API с воспроизводимыми негативными transport-сценариями.

## 5. Критерии приёмки

- [x] Harness Ollama и OpenAI-совместимого API проверяет форму vectors, silent endpoint, deadline/cancel и безопасные ошибки без ключа/response body.
- [x] local mode не использует внешний endpoint.
- [x] Redirect не выполняется, `HTTPS_PROXY`/`HTTP_PROXY` не меняют маршрут, сертификат проверяется системным хранилищем; дерево зависимостей не содержит tokio (D-96).

## 6. Как проверить

1. Выполнить сценарии из разделов «Что сделать» и «Критерии приёмки» на подготовленных входах; для изменения кода запустить соответствующие unit/integration/contract checks созданной реализации.
2. Для каждого критерия записать команду или последовательность действий, ожидаемый исход и фактический результат; сверить отрицательные/аварийные случаи, прямо перечисленные в критериях.
3. Приложить минимальные воспроизводимые evidence: версию сборки, платформу/конфигурацию, версию Ollama (проверенная в R-4 — 0.40.6; минимум не гарантируется, D-96), входы и результаты. Ещё не существующие CLI/test targets не объявлять запущенными; точные команды появятся вместе с реализацией.

**Архитектурная проверка при последующих изменениях:** соблюдать [общие правила структуры](../../../../architecture.md#program-structure-review) в затронутом продуктовом коде и отразить проверку в новом отчёте. Эта ссылка не означает повторную проверку исторической реализации.

## 8. Риски и примечания

**Основание оценки 4 / 8 / 16 ч (сверено 2026-10-21):** настройки клиента D-96 (ureq без redirect и прокси окружения, системный TLS) — конфигурация готовой библиотеки и укладываются в прежний диапазон; best — transport fixtures и доступный Ollama подходят выбранному контракту; expected включает работу раздела 3, собственные проверки и передачу результата; неопределённость worst — отмена молчащего endpoint, некорректные ответы и безопасная обработка ошибок двух API. Это инженерный диапазон, не измеренная скорость.

**Риск и действие:** Отмена молчащего endpoint, некорректные ответы и безопасная обработка ошибок двух API. Зафиксировать воспроизводимый failing case и ограничить исправление указанной границей; если требуется смена принятого дизайна или работа выходит за worst — поставить blocked, вернуть решение на соответствующий gate и пересчитать план. Ожидание оборудования/весов не маскировать рабочими часами.
