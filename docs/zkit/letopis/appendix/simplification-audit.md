# letopis — аудит упрощения

Актуальное решение: файлы, граф и FTS обновляются при применении правки; задания на embeddings сохраняются в той же финальной транзакции SQLite. Вычисление векторов выполняется через долговечную очередь и может отставать. Без актуального embedding поиск использует FTS; устаревший вектор не представляет новый текст. Status показывает число заданий на embeddings. Общий протокол фиксации файлов и БД требует журнала восстановления; физическая реализация и аварийная проверка ещё предстоят. Подробности описаны в [модели хранения](../mechanics/storage-model.md).

Дата: 12 октября 2026 года. Основания: [требования](../requirements.md), [доменная модель](domain-model.md), [сценарии](scenarios.md), [подсистемы](../architecture.md), [контракты](../contracts.md) и [модель хранения](../mechanics/storage-model.md).

Это проверка проектных решений и согласованности документов. Выбраны Rust, rusqlite, единая SQLite-БД, FTS5 contentless-delete и vec1. Профиль WAL + FULL и fullfsync на macOS согласован; физический DDL, остальные настройки и аварийный протокол ещё проектируются. Новые поля и команды этим аудитом не принимаются. Проверки ниже не подтверждают работоспособность будущей реализации.

## Применённые исправления

YAGNI и KISS приняты как критерии дальнейшего проектирования: у каждого нового механизма должна быть необходимость в текущих требованиях, а способ реализации выбирается простейший достаточный. Оптимизации требуют измерений. Эти принципы сохраняют обязательные гарантии целостности и восстановления.

Пользователь исключил предварительную оптимизацию. Предложение бинарного хранения UUID отклонено; в SQLite используется TEXT с тем же каноническим строковым UUID, что в Markdown и JSON. Дополнительные оптимизации скорости, памяти и размера хранения требуют измерений и конкретного узкого места. Необходимые механизмы целостности и восстановления определяются согласованными гарантиями.

Пользователь принял уникальность UUID среди текущих nodes и edges без проверки истории. Прежнее пожизненное резервирование удалённых UUID заменено этим решением во всех активных описаниях. Отдельная identities и deleted-записи только ради такого резервирования исключены из проекта. Это явное изменение прежней гарантии по решению пользователя, а не доказательство её сохранения без реестра.

Для nodes приняты row_id INTEGER PRIMARY KEY AUTOINCREMENT и id TEXT NOT NULL UNIQUE. Один внутренний числовой ключ связывает узел с FTS5 и vec1 без отдельной таблицы соответствий. Принят UPSERT nodes по id с сохранением row_id; обновление узла не удаляет строку и связанные задания embeddings. INSERT OR REPLACE для создания нового seq в очереди сохраняется. Для kind = source принят частичный уникальный индекс nodes_source_uri по нормализованному uri; отдельная таблица соответствия адресов источников не вводится. AUTOINCREMENT относится к внутренним номерам SQLite и не вводит исторический реестр UUID; политика уникальности текущих nodes и edges сохраняется. Для nodes.hash принят CHECK (hash IS NOT NULL OR kind = 'source'): у знаний хеш обязателен, для недоступного source допустим NULL без удаления узла. Для всех видов nodes принят uri TEXT NOT NULL: отсутствие содержимого источника сохраняет его адрес. Для edges.id принят TEXT NOT NULL PRIMARY KEY; отдельная явная колонка row_id для edges не вводится, межтабличная уникальность UUID остаётся проверкой общего валидатора. Для edges.hash принят TEXT NOT NULL: недоступность внешнего содержимого сохраняет вычислимый хеш ссылки. Для edges.type принят TEXT NOT NULL; справочник типов и регистрация проектных имён не вводятся. Принят UPSERT edges по id, как для nodes: существующая связь обновляется с сохранением UUID, отдельный механизм замены не вводится. Согласованная грамматика и правила системных includes и external проверяются общим доменным валидатором. Принято сводное определение edges из пяти обязательных TEXT-полей и created_at INTEGER NOT NULL, с первичным ключом по id, внешними ключами обоих концов без каскадного удаления, CHECK разных концов и частичным уникальным индексом edges_includes. Оно объединяет уже выбранные правила; порядок обновления группы записей обсуждается отдельно. В nodes и edges принято created_at INTEGER NOT NULL: Unix timestamp в секундах. letopis автоматически назначает метку, у размеченных элементов одно значение сохраняется в Markdown и БД, у внешних source — только в БД. Первоначальное время сохраняется при редактировании, переносе и реиндексировании; отдельные поля часового пояса и формата не вводятся.

В модели хранения сокращены подробные описания непринятых вариантов: отдельной external_nodes, исторического реестра UUID, пометок удаления для него, тройки verified на каждом ребре и независимых source_revision. Вместо конкурирующих схем указаны выбранная модель и оставшиеся вопросы. Сами обязательные функции — история оснований, фильтрация по совпадению содержимого источника в Git-ревизии, атомарное восстановление — остаются.

Физическая уникальность UUID должна охватывать обе таблицы и конкурентные создания. Два отдельных первичных ключа сами по себе не обеспечивают межтабличную уникальность. Проверка актуального корпуса обязательна независимо от задержки поискового индекса. Долговечные source без ссылок остаются текущими записями, их UUID заняты.

## Различия, которые нельзя удалить без последствий

| Данные или механизм | Зачем нужны | Допустимое упрощение |
|---|---|---|
| ID и hash | ID сохраняет идентичность при изменении текста; hash проверяет прочитанные байты | Не заменять одно другим |
| Хеш элемента и file_hash | Первый допускает независимые правки соседних элементов; второй защищает создание в существующем файле | Не повторять file_hash в каждой строке nodes; способ кэширования ещё не выбран |
| Текущий hash источника и подтверждённое основание знания | Текущий код может быть новее кода, по которому сформировано знание | Старый хеш можно получить из Git; необходимость отдельного постоянного кэша обсуждается |
| Общее основание источников и снимок текущего текста знания | Edit без snapshot меняет текст, сохраняя прежнее основание | Source_snapshot TEXT: отсутствие основания — NULL в nodes и опущенное поле в Markdown; у source NULL; история читается по известным Git-снимкам без учёта в БД |
| Git tree OID и исходный commit OID | Фильтр сравнивает адресованные байты в запрошенной ревизии и source_snapshot знания | Отдельный OID коммита не хранится; поиск по C2 находит знание из C1 при совпадении содержимого источника |
| Снимок корпуса и версия опубликованного индекса | При одинаковых файлах могут измениться модель и параметры embeddings | Не нужен отдельный публичный ID автоматически; внутреннее представление должно учитывать конфигурацию |
| Поисковые данные и долговечное служебное состояние | Reindex восстанавливает производные данные, но не забытые подтверждения, незавершённое восстановление и UUID источников | Одна БД допустима, жизненные циклы и восстановление различаются |
| Оптимистические предпосылки и короткая защищённая фаза записи | Между проверкой и сохранением может появиться чужая правка | Не удерживать лок во время подготовки агентом; точный протокол сохранения ещё проектируется |
| Журнал операций и Git-снимок отката | Git хранит прежние байты, журнал определяет завершённость и необходимость отката | Один журнал может обслуживать несколько функций, но его удаление до разрешения исхода теряет гарантию восстановления |

Агрегат «метаграф проекта» не требует загрузки всего корпуса в память и одного глобального base_hash для каждой правки. Он задаёт правила целостности. Например, конкурентные добавления includes A→B и B→A должны проверяться против актуального итогового графа, иначе обе локально корректные правки создадут цикл.

## Закрыто: бессрочная дедупликация только по хешу

Ранее были приняты SHA-256 канонического исходного JSON и бессрочный возврат результата идентичного успешного запроса. Ниже сохранён контрпример прежнего правила. После обсуждения пользователь отменил бессрочную дедупликацию: агент перечитывает состояние после потери ответа, а новый вызов проходит обычные проверки. Новый параметр различения намерений не вводится.

Контрпример для одного элемента; ID и его служебная разметка сохраняются, A и B обозначают два варианта полного фрагмента:

| Шаг | Вход apply | Ожидаемое новое действие | Эффект прежней дедупликации |
|---|---|---|---|
| 1 | base_hash = H(A), markdown = B | A→B | Применено; результат сохранён |
| 2 | base_hash = H(B), markdown = A | B→A | Применено; результат сохранён |
| 3 | Полностью тот же JSON, что на шаге 1 | Снова A→B | Возвращён успех шага 1; текст остаётся A |

Упрощённый вход шагов 1 и 3 показывает существующие поля; значения текста и хеша здесь обозначения:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<H(A)>",
      "markdown": "<полный размеченный фрагмент B>"
    }
  ]
}
```

Выход обоих вызовов одинаковый, хотя шаг 3 не меняет документы:

```json
{
  "ok": true,
  "result": {
    "hash": "<один и тот же хеш правки>"
  }
}
```

То же ограничение возникает при create, последующем удалении и новом create с тем же JSON. Хешировать текущие байты корпуса дополнительно недостаточно: после возврата в прежнее состояние они тоже совпадут. Tree OID того же состояния также не различает эти события. Очистка истории или повторное выполнение при расхождении результата изменят уже принятые гарантии дедупликации.

Вопрос закрыт решением пользователя: повтор после потери ответа заменён чтением актуального состояния и подготовкой правки при необходимости. Прежнее правило не требует нового ключа, потому что бессрочный возврат исходного результата больше не является гарантией. Контрпример выше объясняет причину изменения, а не текущую ошибку проекта.

## Согласовано: перечитывание после потери ответа

Пользователь уточнил: повтор относится к работе команды одного агента, а конечное желаемое состояние определяет сам агент. Пример A→B→A относится к бессрочному распознаванию одинакового JSON во всём проекте, а не к выбору конечного значения агентом. Он не обосновывает новый обязательный параметр запроса.

Принято пользователем: каждый новый самостоятельный apply обрабатывается по текущему состоянию, без возврата старого успеха из-за совпадения хеша с исторической записью. Хеш остаётся отпечатком содержимого и возвращается в прежнем формате; разные новые выполнения могут иметь одинаковый хеш. Запись восстановления хранится до надёжного завершения правки или полного отката, после чего удаляется. Диагностика хранится по своим правилам; прежние основания читаются по известным Git-снимкам без отдельного учёта истории в БД. Физические ключи служебных записей и аварийный протокол ещё проектируются. Контроль текущего выполнения не заменяется поиском любого совпадающего запроса во всей истории.

Пример входа для повторного отдельного вызова; A — полный старый Markdown-фрагмент, B — полный желаемый фрагмент, включая прежний ID:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<H(A)>",
      "markdown": "<полный размеченный фрагмент B>"
    }
  ]
}
```

Если прежняя команда сохранила B, но агент потерял ответ, этот новый вызов не проходит проверку base_hash. Согласованный выход использует существующий формат ошибки:

```json
{
  "ok": false,
  "error": {
    "code": "conflict",
    "message": "Хеш элемента не совпадает с base_hash",
    "details": {}
  }
}
```

Агент перечитывает актуальный элемент. Если нужное состояние уже достигнуто, повторять запись не требуется; иначе агент готовит правку по новым данным. Если корпус действительно снова содержит A и агент теперь хочет B, тот же вход допустим как новая правка после обычных проверок. Конфликт сам по себе не доказывает, что предыдущая команда была успешной: состояние мог изменить другой агент.

Мотивация: используются уже имеющиеся base_hash, чтение документов и inspect. Не вводятся timestamp, ID агента, новый ключ операции или команда его получения. Новые ID элементов по-прежнему генерирует letopis.

Изменение гарантии принято: после потери ответа новый самостоятельный вызов не обещает вернуть первоначальный успех и прежнюю карту tmp-ID/UUID. Для create агент читает затронутые файлы и узнаёт созданные постоянные ID. Атомарность, полный откат незавершённой записи и сохранение надёжно завершённой правки остаются обязательными. История оснований знаний и правила диагностики не отменяются; устаревший base_hash по-прежнему вызывает конфликт.

## Согласовано: фильтр по содержимому источника в Git-ревизии

Два коммита могут содержать одно дерево, а при разных деревьях адресованный источник также может остаться неизменным. Пользователь выбрал совпадение содержимого: filters.source_revisions с C2 находит знание, основанное на C1, если байты адресованного источника одинаковы. Это явно заменяет прежнюю семантику точного совпадения отдельно сохранённой ревизии.

Отдельный OID коммита знания или привязки не хранится. letopis сравнивает адресованный файл или диапазон из source_snapshot знания с тем же адресом в запрошенной Git-ревизии. При filters.sources сравнение относится к той же привязке. Правило выбора HEAD при совпадении и tree OID в остальных случаях отменено. История читается по известным Git-снимкам; новая таблица происхождения или истории для фильтра не требуется.

Полные байты файлов источников хранятся в Git; в БД остаются согласованные адреса, хеши и метаданные графа. Решение не вводит копии текста или постоянный кэш прежних хешей в БД. Отсутствие хотя бы одной явно запрошенной Git-ревизии даёт not_found всего поиска с OID в error.details.revision, включая запросы с другими доступными ревизиями. Отсутствие файла или диапазона внутри существующей запрошенной ревизии означает несовпадение только этой пары источника и ревизии; поиск продолжает проверять остальные пары и возвращает успешный пустой результат при отсутствии совпадений. Детали сбоев чтения необходимых Git-объектов ещё требуют уточнения.

## Условия корректности оставшихся механизмов

1. Запрос использует не только одну графовую/векторную проекцию, но и совместимую с ней модель вычисления вектора запроса. Переключение адаптера при сохранённом старом индексе не должно смешивать векторы разных моделей. Согласована отдельная таблица embedding_config служебной SQLite-БД с одной активной конфигурацией проекта; запрос закрепляет её вместе с индексом и сохраняет совместимый адаптер до завершения. Смена одной транзакцией обновляет метаданные, очищает прежние векторы и заменяет очередь с новыми seq по снимку опубликованного графа/FTS. Общий порт сохраняется как texts → vectors; пользователь решил пока не добавлять purpose. Принят базовый DDL embedding_config и отдельная колонка provider, обозначающая поставщика модели или обслуживающую её платформу. Для project приняты id = 1 и revision — Git tree OID снимка опубликованных графа и FTS, NULL до первой публикации. Сохранение embeddings эту ревизию не меняет. Согласовано отсутствие project_id в embedding_config: принадлежность единственному проекту задаёт общая БД, а ревизия и настройки читаются в одной транзакции SQLite. Колонка adapter исключена: реализация порта выбирается в Rust по provider. Для parameters принят CHECK корректности JSON-объекта; SQL не задаёт перечень ключей конкретного провайдера; конкретные параметры адаптеров и операции vec1 ещё проектируются.
2. Git-снимок, транзакция БД и замена нескольких файлов не образуют автоматически единую аварийную транзакцию. Необходимы долговечный журнал, точный порядок фиксации и повторяемое восстановление. Снимок отката должен покрывать затронутые разрешённые документы корпуса. Запись в существующий файл без разметки letopis запрещена и отклоняет всю правку. Проверка потери питания предстоит на реализации.
3. Производный текстовый индекс должен удовлетворять запрету на копии документов в БД. Выбран FTS5 в режиме contentless-delete: он хранит поисковую структуру без полной копии текста. Окончательные ключи, обслуживание и совместная публикация ещё проектируются; само решение не подтверждает качество или скорость поиска.
4. Потеря всей БД не равна reindex. Git хранит содержимое, но текущие файлы не содержат всю историю подтверждений, данные незавершённого восстановления и долговечное соответствие URI источников их UUID. Резервное копирование служебного состояния требует отдельного решения.
5. Готовность старого индекса при сбое embedding-провайдера не доказывает возможность гибридного запроса: его вектор ещё нужно получить. Отдельный режим только текстового поиска не согласован. Обработка такой ошибки должна сохранять выбранный контракт.
6. Единый uri допускает разные адресные схемы, но не вводит автоматически сетевое чтение и версионирование веб-страниц. Полностью локальная первая версия сохраняется.
7. Повреждение разметки после внешних Git-изменений может затруднить edit по ID. Сценарий исправления должен быть проверен после выбора грамматики; дополнительная команда прямой файловой записи пока не вводится.

## Закрыто: общие файловые патчи первой версии

2026-10-18: пользователь выбрал только create/edit/delete размеченных элементов, [D-30](../decisions.md#D-30). Общие патчи с контекстом, точная замена текста и произвольные файловые вставки исключены из v1. Edit передаёт полный новый фрагмент по ID/base_hash; рёбра меняются через ссылки в нём. Create добавляет новые элементы в конец файла, перенос сохраняет прежний ID через delete + create и исправление ссылок агентом. Ранее оставленное противоречие закрыто; окончательная JSON-схема ещё не завершена.

Описание места сохранения подтверждённого хеша источника в старых разделах не является выбором отдельного поля verified. При общем основании прежние байты читаются из Git. Текущий указатель принят как source_snapshot в Markdown знания и проекции nodes. Принято source_snapshot TEXT с NULL для неустановленного основания и для source; в Markdown неустановленное поле опускается. Edit без snapshot сохраняет прежний снимок при удалении ссылок. История читается по известным Git-снимкам без отдельного учёта в БД. Фильтр по ревизии сравнивает содержимое источника через Git, отдельный OID коммита не хранится. Дублирование описаний решения между документами заменять следует ссылками после фиксации этой схемы, чтобы не распространять неоднозначную трактовку.

## Чтение состояния после потери ответа

Отмена бессрочного кэша требует, чтобы агент мог наблюдать эффект правки. Для текста и назначенных UUID он читает затронутые файлы и inspect. Подтверждение нового основания записывает source_snapshot в канонический Markdown и меняет полный hash узла. Агент читает сохранённые метаданные документа и сверяет их со снимком inspect; для наблюдения текущего основания отдельное поле ответа не требуется. Для чтения истории прежних оснований достаточно известных Git-снимков; отдельный учёт истории в БД и поиск истории по ID через CLI не вводятся. Для фильтра по Git-ревизии согласовано сравнение содержимого источника без отдельного хранения OID коммита.

## Проверка аудита

- Прогнаны две проверки проектных правил: модель дедупликации для A→B→A→B и опыт с двумя коммитами одного дерева во временном Git-репозитории. Пользовательские репозитории не изменялись.
- Первая проверка показала applied/B, applied/A, cached_success/A. Вторая показала different_commits = true и same_tree = true. Это воспроизводимые ограничения описанного протокола и доступной информации, а не тесты letopis.
- После принятого изменения отдельно проверена модель обычного контроля base_hash без бессрочного кэша: A→B применено; немедленный отдельный повтор даёт conflict и сохраняет B; B→A применено; новое A→B с прежним JSON снова применено. Последовательность: applied/B, conflict/B, applied/A, applied/B. Это проверка логики соглашения, а не работающей реализации.
- Проверка семи документов прошла: 137 JSON-блоков корректно разбираются, Markdown-ограждения закрыты, 48 локальных ссылок ведут к существующим файлам. Проверяемые устаревшие формулировки запрета повторной выдачи UUID и зависимости от identities.category отсутствуют. Грамматика примеров ссылок внутри inline-кода не проверяется как ссылка на реальный локальный файл. Состав сообщения status о неприменённой правке согласован: code, message, details с hash и paths. Согласовано снятие сообщений о завершённых неуспешных правках через letopis errors --clear по всему проекту, с сохранением активных ошибок.
- Производительность, качество поиска, потребление 4 ГБ памяти, восстановление после потери питания и физические ограничения БД пока не проверены. Дальнейшее проектирование хранения должно уточнить физическую схему SQLite, ключи и индексы, публикацию, жизненный цикл читателей, журнал, аварийный протокол и резервное копирование.

## Принятое упрощение журнала восстановления

Удаление записи восстановления в финальной транзакции БД означает завершение правки. До первого изменения файлов сохраняются данные полного отката и запись восстановления; после долговечного сохранения группы файлов одной транзакцией фиксируются необходимые служебные результаты, граф, FTS, ревизия корпуса и задания на embeddings и удаляется запись. Отдельные состояния pending/committed и отдельная очистка завершённых записей не нужны. Готовность всех embeddings не является условием успешного apply или поиска.

Оставшаяся после сбоя запись требует полного отката, включая случай уже записанных файлов до финальной транзакции. Прерванный откат повторяется; запись удаляется только после надёжного завершения восстановления, а диагностика неприменённой правки сохраняется отдельно. Отсутствие записи не заменяет перечитывание состояния агентом после потери ответа. Индексирование остаётся асинхронным. Это согласованный логический протокол; состав снимка отката, физический порядок сохранения и аварийные проверки ещё проектируются.

## Ограничение записи корпусом

Согласовано: letopis изменяет только специально размеченные Markdown-документы корпуса. Для существующего файла это проверяется до правки; ожидаемый хеш или разметка переданного нового содержимого не дают права изменить обычный документ. Попытка записи вне корпуса отклоняет всю атомарную группу без изменений, включая проверку без сохранения. Новый код ошибки или команда не нужны: используется invalid_request, а ошибки самой разметки сохраняют validation_failed.

Обычные документы и исходный код могут оставаться внешними источниками для чтения и проверки знаний. Журнал и снимок отката не расширяют область записи. Ранее согласованное создание по отсутствующему пути сохраняется и сразу формирует размеченный Markdown-документ; добавление разметки в существующий обычный документ через letopis запрещено.

Согласовано восстановление недописанного файла по оставшейся записи журнала и прежнему Git-снимку. Текущая разметка такого файла не является условием отката; область восстановления ограничена предварительно проверенной правкой. Восстанавливается прежнее содержимое файла целиком либо удаляется файл, созданный незавершённой правкой. Обратный Markdown-патч, отдельное состояние файла и копия текста в БД не требуются. Физический порядок замены файлов и проверка повторного сбоя по-прежнему проектируются.

Согласовано сообщение о неприменённой правке в существующем result.errors: причина и исход атомарной группы, hash и paths. Element_ids исключён из записи восстановления и диагностики отката; откат использует Git-снимок и пути файлов. Полный патч в БД для этого отчёта не требуется. Сохранение диагностики независимо от очищенной записи восстановления остаётся обязательным; сообщения о завершённых неуспешных правках явно снимаются letopis errors --clear по всему проекту, а активные ошибки сохраняются.

Принято: просмотр и очистка диагностики выполняются отдельной командой errors; действие очистки задаётся флагом --clear. Команда использует тот же набор сообщений, что result.errors у status, и возвращает оставшийся список. Очищаются все сообщения о завершённых неуспешных правках проекта, без нового поля clear_errors или списка хешей. Активные ошибки сохраняются до устранения соответствующей проблемы. Status остаётся командой чтения.

Принято: SQLite является единой служебной БД первой версии для графа, embeddings и необходимого служебного состояния. Согласован профиль WAL с synchronous=FULL, fullfsync на macOS и SQLite 3.51.3 или новее. Выбраны Rust, драйвер rusqlite, FTS5 contentless-delete для текстового поиска и нативный vec1 для векторного поиска. Окончательная физическая схема и режим vec1 ещё проектируются; профиль SQLite не заменяет прикладной журнал отката документов. Документы и прежние байты остаются в Markdown и Git.

Согласовано: FTS5 contentless-delete обслуживает текстовую часть гибридного поиска в единой SQLite-БД. Хранится поисковая структура без полной копии текста документов; исходный текст остаётся в Markdown и Git. Rowid связывается с ID узла внутренним механизмом; публичные результаты search сохраняют ссылки. Векторным расширением выбран vec1; его режим и окончательная схема публикации ещё проектируются. Выбор Rust и rusqlite не добавляет новых команд, полей CLI или отдельного хранилища.


## Очередь embeddings и удаление обработанной работы

Согласованы одна строка embedding_jobs на вершину или метавершину и UNIQUE(node_id). Каждая новая работа, включая замену для того же узла, получает новый seq. Исполнитель читает задание, вычисляет embedding вне транзакции БД и в новой короткой транзакции записи проверяет существование исходного seq перед сохранением вектора и удалением строки; отмена удаляет исходную строку. Старое вычисление не затрагивает заменившую его работу. Согласован seq INTEGER PRIMARY KEY AUTOINCREMENT: SQLite назначает номера новым заданиям и не переиспользует номера надёжно сохранённых удалённых строк. Отдельный прикладной счётчик не требуется. Согласован INSERT OR REPLACE для постановки: приложение передаёт данные новой работы, не указывая seq; UNIQUE(node_id) заменяет прежнюю строку того же узла, а AUTOINCREMENT назначает новый номер. Для CLI-правки постановка входит в финальную транзакцию apply. Готовый применимый вектор и удаление обработанной строки фиксируются одной транзакцией SQLite; отдельное состояние успешного завершения и история выполненных заданий не хранятся. При пропуске устаревшего элемента удаляется только прежняя сохранившаяся строка; завершение старого вычисления не затрагивает новую работу.

Согласовано: после исчерпания ретраев строка сохраняется с state = failed и пропускается исполнителем, в том числе после перезапуска. Новая работа того же узла заменяет её через INSERT OR REPLACE; удаление узла удаляет строку через ON DELETE CASCADE. Диагностика сохраняется в errors, а строка failed не входит в status.result.embedding_jobs. Согласовано: отменённая строка удаляется по исходному seq, диагностика сохраняется в errors в той же транзакции. Отдельное состояние cancelled в очереди не вводится; удалённая работа не восстанавливается после перезапуска. Результат ожидающего reindex при замене заданий ещё уточняется. Согласованы только queued и failed в embedding_jobs.state. Queued включает ожидание, текущее вычисление и ожидание разрешённого ретрая; единственный исполнитель хранит сведения о текущем выполнении в памяти рабочего процесса. После сбоя сохранившаяся queued-строка доступна для повторной обработки по своему снимку и счётчику; отдельный переход running → queued не требуется. Очередь не хранит тексты документов: используются адреса и неизменяемые Git-снимки.
