# X-4 — Размеченные Markdown-файлы
> x-boundary: X-4 · x-direction: published · x-status: draft
> x-serves: FR-3, FR-4, FR-5, FR-6, FR-10, FR-11, FR-17, FR-18, FR-19, FR-35, C-3 · x-limits: []

## Layout
[JSON Schema метаданных](schemas/X-4-metadata.yaml) проверяет JSON открывающего маркера; это не парсер всего Markdown. Каждый элемент занимает один непрерывный неперекрывающийся фрагмент одного UTF-8 файла .md/.markdown. В файле могут быть несколько независимых элементов без общего корня. Физическое соседство/вложение файлов не означает includes.

```text
fragment = opening-marker newline markdown-body closing-marker
opening-marker = "<!-- letopis: " JSON-object " -->"
closing-marker = "<!-- /letopis -->"
node-metadata = {id, kind, created_at [, source_snapshot]}
graph-title = "letopis:id=" ID ";type=" TYPE ";created_at=" UNIX_SECONDS
TYPE = [a-z][a-z0-9_]*
```

Пробелы внутри JSON/порядок ключей определяются JSON; служебные маркеры располагаются на отдельных строках. Внутри fenced/indented code blocks примеры маркеров не объявляют элемент. Перекрытие и вложение размеченных описаний недопустимы; содержимое — обычный Markdown. Хеш всего канонического фрагмента включает его маркеры и реальные переводы строк, без EOL-нормализации.

В канонических метаданных id — UUIDv4, kind — vertex либо metavertex, created_at — назначенный letopis Unix timestamp в секундах; source_snapshot — опциональный tree OID. Types/атрибутные схемы/наследование не вводятся. В новых элементах/рёбрах агент объявляет tmp:000–tmp:fff и может не передавать created_at. letopis подставляет ID и время, включая ссылки; это меняет сохраняемый Markdown, но hash операции остаётся хешем исходного JCS. При edit/переносе исходные ID и created_at сохраняются; переданная попытка подменить immutable-метаданные отклоняется валидатором. Пропущенная автоматически поддерживаемая метка восстанавливается из текущей сущности, а не получает новое время.

Внутренняя графовая ссылка:
```markdown
[Зависимость](knowledge/other.md#521eb6f0-bd63-4d44-9aaf-c2d9be2bb5e4 "letopis:id=064f2964-77cc-41f0-87ac-d280c0ec59a7;type=depends_on;created_at=1792285200")
```
Ссылка на источник:
```markdown
[Код](src/storage.rs#L10-L25 "letopis:id=064f2964-77cc-41f0-87ac-d280c0ec59a7;type=external;created_at=1792285200")
```
Временная новая ссылка может не содержать created_at. Для external допустим также файл целиком без #Lx-Ly. Источник ребра — размеченная вершина/метавершина, содержащая ссылку; направление — от неё к назначению. Без корректного зарезервированного letopis title обычная навигационная Markdown-ссылка не создаёт графовую сущность. Некорректный letopis title не игнорируется как обычная ссылка. Reference-style/прочие обычные Markdown-ссылки не расширяют принятую inline-грамматику графа.

Пути всегда относительно Git-корня, внутренние назначения явно содержат стабильный ID. Includes — системный тип от метавершины к вершине/метавершине, без повторов упорядоченной пары и циклов. Петли запрещены, обычные циклы и параллельные рёбра разрешены. Полное удаление требует исправить все ссылки в той же атомарной правке; перенос подготавливает агент через delete/create/edit ссылок с прежними ID. External создаёт/находит зарегистрированный source по нормализованному адресу, не делает код размеченным документом. Интернет-ссылки не означают поддержку скачивания веб-источников.

## Timing and limits
2026-10-19: уточнена область гарантии чтения по D-77; грамматика и поля метаданных не меняются.

Согласованное чтение нескольких документов выполняется по одному неизменяемому Git-снимку (существующий snapshot из inspect), [D-77](../decisions.md#D-77). Обычные чтения живых Markdown-файлов разрешены, но могут пересекать применение правки и не получают межфайловой гарантии. Search/traverse сохраняют собственный согласованный снимок SQLite; он не распространяется автоматически на последующее чтение файлов. Протокол reader locks не вводится; физическая замена файлов не выбирается как обязательный способ применения правки.

Содержимое и метаданные знаний самодостаточны в Markdown/Git; граф/FTS и векторы производны. Не добавляется лимит длины Markdown-элемента: если модель не принимает текст, знание/FTS сохраняются с диагностикой, без усечения/дробления, D-61. 4096 tmp-имён — согласованное пространство новых объявлений одной правки, не новая квота файлов. Новые source получают created_at в служебной БД; их содержимое не копируется в SQLite.

Create с external-ссылками содержит source_snapshot в метаданных каждого знания. Edit без operation.snapshot сохраняет прежнее основание; явная перепроверка задаёт snapshot операции, подтверждая все итоговые external-привязки. Прямое изменение основания только в Markdown без протокола перепроверки не обходит проверки. Неверный/отсутствующий Git-снимок и несовпадение bytes обрабатываются по X-1/X-3. Изменение источника/пропажа диапазона не удаляют старое знание.

## Errors
Невалидные JSON/маркеры, ID/тип/ссылка, повтор ID, петля, includes-цикл, неразрешённая внутренняя цель — validation_failed всей правки. Недопустимый путь операции — invalid_request; выход графовой ссылки за Git-корень — validation_failed. Атомарность означает согласованный результат всей правки, полный откат при незавершённости и согласованную фиксацию графа/FTS; она не обещает единого состояния для независимых чтений живых файлов во время применения изменений. Ни одна JSON Schema сама не доказывает includes DAG или ссылочную целостность: это обязательные application проверки по итоговому метаграфу.

При чтении файла источника строки нумеруются от 1, диапазон включительный, без диапазона хешируется весь файл. End>=start и существование полного диапазона проверяются приложением. Правила точного хеша файла/фрагмента и SHA-256(JCS({source,markdown})) ребра сохранены в [подробном контракте](../contracts.md).
