# X-4 — Размеченные Markdown-файлы
> x-boundary: X-4 · x-direction: published · x-status: draft
> x-serves: FR-3, FR-4, FR-5, FR-6, FR-11, FR-17, FR-18, FR-19, FR-35, C-3 · x-limits: []

## Layout
2026-10-20, [D-93](../decisions.md#D-93): агенты правят эти файлы напрямую; letopis только читает и проверяет их. ID знания — путь или путь#якорь, UUID нет; рёбра без ID и даты.

[JSON Schema метаданных](schemas/X-4-metadata.yaml) проверяет JSON служебного комментария; это не парсер всего Markdown. Markdown разбирает `pulldown-cmark` (байтовые диапазоны через offset iterator, `{#anchor}` через heading attributes), только чтение, сериализатора нет (D-96). Файл входит в корпус, если содержит хотя бы один служебный комментарий letopis.

```text
file-element    = metadata-line newline markdown-body            ; ID = path
section-element = heading " {#" ANCHOR "}" newline metadata-line newline markdown-body
                                                                  ; ID = path "#" ANCHOR
metadata-line   = "<!-- letopis: " JSON-object " -->"
metadata        = {created_at [, source_snapshot]}
ANCHOR          = [A-Za-z][A-Za-z0-9_-]*, не вида L<n>-L<n>, уникален в файле
graph-title     = "letopis:type=" TYPE ";path=" ADDRESS
TYPE            = [a-z][a-z0-9_]*
ADDRESS         = весь оставшийся непустой title
```

Корпус — файлы `.md`/`.markdown` из `git ls-files --cached --others --exclude-standard` (с учётом `.gitignore`), содержащие разметку letopis; файлы без разметки просто не дают элементов (D-97). Уточнение issue #84: Git-адаптер исключает конечные симлинки по текущему состоянию рабочей копии; чтение дополнительно допускает только обычные файлы и не следует симлинкам. Удалённые tracked-пути сохраняются кандидатами до проверки отсутствия.

Файл-элемент: служебный комментарий — первая строка файла, элемент — весь файл, других элементов в файле нет. Раздел-элемент: заголовок с явным якорем и сразу следующий служебный комментарий; раздел продолжается до следующего заголовка того же или более высокого уровня либо до конца файла. Вложенные элементы (раздел-элемент внутри другого раздела-элемента или внутри файла-элемента) недопустимы; включённость выражается только ссылками includes. Текст файла вне элементов знанием не является. Внутри fenced/indented code blocks примеры заголовков и комментариев не объявляют элемент. Хеш элемента — SHA-256 точных байтов его диапазона (от заголовка либо первой строки до конца раздела), без EOL-нормализации.

Метаданные пишет агент: created_at — Unix seconds, назначается при создании и сохраняется при правке, переносе и переименовании; source_snapshot — необязательный полный tree OID основания. Вид элемента не пишется: метавершина — элемент с исходящими includes, остальные знания — вершины ([D-95](../decisions.md#D-95)). Types/атрибутные схемы/наследование не вводятся.

Пример раздела-элемента в `knowledge/decisions.md`:
```markdown
## Используем WAL {#sqlite-wal}
<!-- letopis: {"created_at":1792285200,"source_snapshot":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"} -->
SQLite работает в режиме WAL, см. [код](../src/storage.rs#L10-L25 "letopis:type=external;path=src/storage.rs#L10-L25")
и [роль кэша](#viewer-cache "letopis:type=depends_on;path=knowledge/decisions.md#cache-role").
```
ID этого элемента — `knowledge/decisions.md#sqlite-wal`. Ссылка на файл-элемент — `[текст](x.md "letopis:type=depends_on;path=knowledge/x.md")`.

Ребро = (элемент, содержащий ссылку; цель; тип); повтор той же тройки — одно ребро. Только inline-ссылка с title `letopis:type=TYPE;path=ADDRESS` внутри элемента объявляет ребро; изображения и reference-style ссылки его не создают. Title без префикса `letopis:` — обычная навигация; некорректный letopis title — ошибка файла. `path` обязателен, прежний title без него не поддерживается. Цель внутренней ссылки — ID знания (путь или путь#якорь); цель external — нормализованный адрес source (файл целиком или #Lx-Ly), который не является элементом корпуса. Includes — системный тип от метавершины к вершине/метавершине, без циклов. Петли запрещены, обычные циклы и параллельные рёбра разных типов разрешены. Каноническая цель берётся исключительно из `path` и для локального адреса всегда относительна Git-корню; обычный Markdown destination относителен содержащему документу. Удаление или переименование цели оставляет висячие ссылки, которые check и status показывают до исправления. Интернет-ссылки не означают скачивания веб-источников.

## Title и локальный путь навигации — issue #69, 2026-10-31

[D-106](../decisions.md#D-106): грамматика применяется к декодированному title
из `pulldown-cmark`. Ключи строчные и в указанном порядке, без пробелов у
разделителя. `target` не является псевдонимом; пропущенный/пустой `path`, неверный
TYPE, лишнее поле до `path` или иной порядок дают `InvalidLinkTitle`.
`path` — терминальное поле: после `;path=` весь остаток принадлежит адресу,
включая `;`, `=`, пробелы и проценты, если их допускает прежняя доменная грамматика.
Это не карта параметров. Добавленные после адреса настройки становятся частью
адреса. После Markdown escaping/entities нет дополнительного unescape, trim,
percent decode или смены регистра title. Неверный адрес даёт `InvalidTarget`.

Например, из `letopis/cache/key.md`:

```markdown
[код](../../src/cache%20key.rs#viewer "letopis:type=external;path=src/cache key.rs#L2-L4")
[знание](invalidation.md#viewer "letopis:type=related_to;path=letopis/cache/invalidation.md#expiry")
[URL](https://Host/a "letopis:type=external;path=https://Host/a?x=1;path=literal#part")
```

Локальный файл canonical `path` сравнивается с destination чисто лексически,
без файловой системы, Git, сети, проверки существования и Markdown viewer:

1. Отбросить первый буквальный `#` и весь fragment destination до декодирования.
   Fragment не разбирается и не сравнивается с якорем/диапазоном `path`.
2. Допустить относительный локальный путь; отвергнуть абсолютный `/`, network path
   `//`, URI scheme перед первым `/`, буквальные `?`, backslash и controls.
   Для имени с `?` используется `%3F`, для `:` в первом компоненте — префикс `./`.
3. Декодировать percent escapes destination ровно один раз как UTF-8; отвергнуть
   неверные escapes/UTF-8, controls, backslash и encoded `/`. В title `%20`
   остаётся буквальным `%20`; пробел в имени пишется пробелом. Буквальный `%`
   в destination пишется `%25`.
4. Пустой destination означает содержащий документ; прочие пути соединяются с
   его каталогом. Нормализовать `.`, `..`, повторные `/`, не выходя за Git-корень;
   пустой результат/выход за корень отвергается. Symlink/case aliases не разрешаются.
5. Сравнить файл с локальной частью canonical `path`, без якоря/диапазона,
   сохраняя регистр и Unicode spelling. Различие/отказ выше — `LinkPathMismatch`.

Совпадающий отсутствующий файл проходит эту проверку; отдельные dangling/source
проверки сохраняются. HTTP/HTTPS source в `path` непрозрачен и полностью исключён
из локального сравнения: destination не обязан быть эквивалентным URL, fetch нет.
Доменные правила якоря/диапазона `path` по-прежнему действуют, но fragment
destination может быть любым. Letopis не обещает совместимость с viewer.

`LinkPathMismatch` имеет фиксированный текст
`Markdown link path does not match letopis path` и reason `link_path_mismatch`.
Успешная публикация refresh/reindex сохраняет ошибку в существующем `files.error`
в той же транзакции: прежняя валидная проекция остаётся, свежий кэш не получает
частичных элементов/рёбер невалидного файла. Остальные файлы публикуются.
`check` и `status.result.problems` показывают `validation_failed` с `details.path`
содержащего файла и этим reason; конфликтующие адреса не выводятся. Существующий
байтовый диапазон parser diagnostic сохраняется, отдельного persisted range нет.
`status` только читает последнюю публикацию: новая ошибка видна после refresh,
правка автора сама её не очищает, следующий успешный refresh/reindex очищает.
При SQL failure остаётся прежнее состояние, команда сообщает ошибку публикации.

Изменение только title/destination меняет exact hash элемента, но при прежних
видимом тексте/подписи сохраняет search text/search_hash и reuse вектора.
Переезд документа требует правки относительных destinations и входящих связей;
неизменённый canonical `path` продолжает адресовать прежнюю цель.

## Обновление корпуса и кэша

Сначала дождаться завершения старых команд/drain, установить новый бинарник,
мигрировать каждый marked title и локальный destination, затем выполнить
`reindex` с `{}` и `check` с `{}`. Только явный reindex принудительно переосмысляет
неизменённые файлы. `status` кэш не обновляет. Не удалять БД, векторы, lock-файлы,
Git или авторские документы; не смешивать версии бинарника на одном кэше.
Fallback, legacy mode, автоматического rewrite/migration/parser-version нет.
Reindex сохраняет last-valid проекции невалидных файлов, поэтому один успешный
reindex не доказывает миграцию: markup findings должны быть устранены, а прочие
provenance findings — отдельно рассмотрены. См. [порядок обновления](../../../development.md#issue-69-обязательный-path-и-явный-reindex).

## Timing and limits
2026-10-19: уточнена область гарантии чтения по D-77; грамматика и поля метаданных не меняются.

Согласованное чтение нескольких документов выполняется по одному неизменяемому Git-снимку (существующий snapshot из inspect), [D-77](../decisions.md#D-77). Обычные чтения живых Markdown-файлов разрешены, но могут пересекать правку агента и не получают межфайловой гарантии. Search/traverse сохраняют собственный согласованный снимок SQLite; он не распространяется автоматически на последующее чтение файлов. Протокол reader locks не вводится; letopis не пишет корпус (D-93).

Содержимое и метаданные знаний самодостаточны в Markdown/Git; граф/FTS и векторы производны. Не добавляется лимит длины Markdown-элемента: если модель не принимает текст, знание/FTS сохраняются с диагностикой, без усечения/дробления, D-61. Created_at source вычисляется из его external-ссылок и воспроизводится reindex; содержимое source не копируется в SQLite, D-91.

Знание с external-ссылками содержит source_snapshot в метаданных; его пишет агент после проверки источников. Правка без изменения source_snapshot сохраняет прежнее основание; перепроверка — запись нового snapshot. Отсутствующий или неизвестный снимок даёт активную диагностику и признак перепроверки, несовпадение адресованных байтов с текущими — source_changed ([D-93](../decisions.md#D-93)). Изменение источника/пропажа диапазона не удаляют старое знание.

## Errors
Ошибки проверяются командой check и при индексации, по файлу ([D-93](../decisions.md#D-93)): невалидный JSON/метаданные, дубль якоря, вложенные элементы, некорректный letopis title — validation_failed файла; файл сохраняет в индексе прежнюю валидную проекцию. Висячая внутренняя ссылка и includes, замыкающее цикл, сохраняются как рёбра, но traverse и фильтры их не обходят; check и status показывают проблему, пока её не исправят (D-95). Петля (ссылка элемента на себя) ребром не становится. Выход ссылки за Git-корень — validation_failed. letopis не пишет в эти файлы, поэтому многофайловой атомарности нет: незавершённая агентом группа правок видна как висячие ссылки. Ни одна JSON Schema сама не доказывает includes DAG или ссылочную целостность: это обязательные application-проверки по итоговому графу.

При чтении файла источника строки нумеруются от 1, диапазон включительный, без диапазона хешируется весь файл. End>=start и существование полного диапазона проверяются приложением. Правила точного хеша файла/фрагмента сохранены в [подробном контракте](../contracts.md); у ребра хеша нет (D-93).

## Уточнение TK-20 — 2026-10-25

[Утверждённая спецификация](../../../superpowers/specs/2026-10-25-tk-20-source-identity-design.md)
разделяет локальный нормализованный путь/диапазон и непрозрачный абсолютный
HTTP/HTTPS адрес. Для URL исходное написание, query и fragment сохраняются;
`#L1-L2` внутри URL — непрозрачный fragment, не локальный диапазон. Разные написания
URL — разные ID; fetch и локальное чтение для URL не выполняются, bytes/hash неизвестны.
Неверный authority и управляющие символы отклоняются, а не превращаются в путь.

Локальный адрес отклоняется, если после нормализации `.`/`..` и слешей путь
начинается с `http:` или `https:` без учёта регистра: например `./https:notes`,
`dir/../HTTP:notes`, `./https://Host/a`, в том числе с диапазоном строк. Такой
адрес не превращается в URL: его сохранённый ID иначе менял бы классификацию
при повторном чтении. Принятый ID повторно разбирается с тем же адресом и типом.
Корневой файл с таким префиксом нужно переименовать или поместить в однозначный
каталог (`docs/https:notes`). Грамматика RepoPath/KnowledgeId и исходное написание
настоящих абсолютных HTTP/HTTPS URL не меняются. Неверная external-ссылка следует
обычной политике invalid-file: прежняя валидная проекция сохраняется, а в свежий
кэш некорректный source/edge не попадает; исправление ссылки не требует пересборки.

Source существует по эффективным external-ссылкам; `created_at` — минимум
авторских `created_at` ссылающихся знаний. Невалидный Markdown сохраняет прежнюю
валидную проекцию и ссылки до исправления или удаления файла. Исчезновение bytes
не удаляет знание/source, удаление последней эффективной ссылки удаляет source
в той же публикации. При upgrade TK-20 канонические Markdown не меняются; старый
производный cache.db требует [явной пересборки](../../../development.md#tk-20-явная-пересборка-кэша-при-обновлении).
