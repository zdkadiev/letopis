# X-4 — Размеченные Markdown-файлы
> x-boundary: X-4 · x-direction: published · x-status: draft
> x-serves: FR-3, FR-4, FR-5, FR-6, FR-11, FR-17, FR-18, FR-19, FR-35, C-3 · x-limits: []

## Layout
2026-10-20, [D-93](../decisions.md#D-93): агенты правят эти файлы напрямую; letopis только читает и проверяет их. ID знания — путь или путь#якорь, UUID нет; рёбра без ID и даты.

[JSON Schema метаданных](schemas/X-4-metadata.yaml) проверяет JSON служебного комментария; это не парсер всего Markdown. Файл входит в корпус, если содержит хотя бы один служебный комментарий letopis.

```text
file-element    = metadata-line newline markdown-body            ; ID = path
section-element = heading " {#" ANCHOR "}" newline metadata-line newline markdown-body
                                                                  ; ID = path "#" ANCHOR
metadata-line   = "<!-- letopis: " JSON-object " -->"
metadata        = {created_at [, source_snapshot]}
ANCHOR          = [A-Za-z][A-Za-z0-9_-]*, не вида L<n>-L<n>, уникален в файле
graph-title     = "letopis:type=" TYPE
TYPE            = [a-z][a-z0-9_]*
```

Файл-элемент: служебный комментарий — первая строка файла, элемент — весь файл, других элементов в файле нет. Раздел-элемент: заголовок с явным якорем и сразу следующий служебный комментарий; раздел продолжается до следующего заголовка того же или более высокого уровня либо до конца файла. Вложенные элементы (раздел-элемент внутри другого раздела-элемента или внутри файла-элемента) недопустимы; включённость выражается только ссылками includes. Текст файла вне элементов знанием не является. Внутри fenced/indented code blocks примеры заголовков и комментариев не объявляют элемент. Хеш элемента — SHA-256 точных байтов его диапазона (от заголовка либо первой строки до конца раздела), без EOL-нормализации.

Метаданные пишет агент: created_at — Unix seconds, назначается при создании и сохраняется при правке, переносе и переименовании; source_snapshot — необязательный полный tree OID основания. Вид элемента не пишется: метавершина — элемент с исходящими includes, остальные знания — вершины ([D-95](../decisions.md#D-95)). Types/атрибутные схемы/наследование не вводятся.

Пример раздела-элемента в `knowledge/decisions.md`:
```markdown
## Используем WAL {#sqlite-wal}
<!-- letopis: {"created_at":1792285200,"source_snapshot":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"} -->
SQLite работает в режиме WAL, см. [код](src/storage.rs#L10-L25 "letopis:type=external")
и [роль кэша](knowledge/decisions.md#cache-role "letopis:type=depends_on").
```
ID этого элемента — `knowledge/decisions.md#sqlite-wal`. Ссылка на файл-элемент — `[текст](knowledge/x.md "letopis:type=depends_on")`.

Ребро = (элемент, содержащий ссылку; цель; тип); повтор той же тройки — одно ребро. Ссылка без корректного title `letopis:type=…` — обычная навигационная ссылка, не ребро; некорректный letopis title — ошибка check. Reference-style ссылки грамматику графа не расширяют. Цель внутренней ссылки — ID знания (путь или путь#якорь); цель external — нормализованный адрес source (файл целиком или #Lx-Ly), который не является элементом корпуса. Includes — системный тип от метавершины к вершине/метавершине, без циклов. Петли запрещены, обычные циклы и параллельные рёбра разных типов разрешены. Пути всегда относительно Git-корня. Удаление или переименование цели оставляет висячие ссылки, которые check и status показывают до исправления. Интернет-ссылки не означают скачивания веб-источников.

## Timing and limits
2026-10-19: уточнена область гарантии чтения по D-77; грамматика и поля метаданных не меняются.

Согласованное чтение нескольких документов выполняется по одному неизменяемому Git-снимку (существующий snapshot из inspect), [D-77](../decisions.md#D-77). Обычные чтения живых Markdown-файлов разрешены, но могут пересекать применение правки и не получают межфайловой гарантии. Search/traverse сохраняют собственный согласованный снимок SQLite; он не распространяется автоматически на последующее чтение файлов. Протокол reader locks не вводится; физическая замена файлов не выбирается как обязательный способ применения правки.

Содержимое и метаданные знаний самодостаточны в Markdown/Git; граф/FTS и векторы производны. Не добавляется лимит длины Markdown-элемента: если модель не принимает текст, знание/FTS сохраняются с диагностикой, без усечения/дробления, D-61. Created_at source вычисляется из его external-ссылок и воспроизводится reindex; содержимое source не копируется в SQLite, D-91.

Знание с external-ссылками содержит source_snapshot в метаданных; его пишет агент после проверки источников. Правка без изменения source_snapshot сохраняет прежнее основание; перепроверка — запись нового snapshot. Отсутствующий или неизвестный снимок даёт активную диагностику и признак перепроверки, несовпадение адресованных байтов с текущими — source_changed ([D-93](../decisions.md#D-93)). Изменение источника/пропажа диапазона не удаляют старое знание.

## Errors
Ошибки проверяются командой check и при индексации, по файлу ([D-93](../decisions.md#D-93)): невалидный JSON/метаданные, дубль якоря, вложенные элементы, некорректный letopis title — validation_failed файла; файл сохраняет в индексе прежнюю валидную проекцию. Висячая внутренняя ссылка — диагностика, ребро не публикуется. Петля и includes, замыкающее цикл, не публикуются, диагностика активна. Выход ссылки за Git-корень — validation_failed. letopis не пишет в эти файлы, поэтому многофайловой атомарности нет: незавершённая агентом группа правок видна как висячие ссылки. Ни одна JSON Schema сама не доказывает includes DAG или ссылочную целостность: это обязательные application-проверки по итоговому графу.

При чтении файла источника строки нумеруются от 1, диапазон включительный, без диапазона хешируется весь файл. End>=start и существование полного диапазона проверяются приложением. Правила точного хеша файла/фрагмента и SHA-256(JCS({source,markdown})) ребра сохранены в [подробном контракте](../contracts.md).
