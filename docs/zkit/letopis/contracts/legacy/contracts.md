# letopis — контракты

Статус: поэтапное проектирование. Здесь фиксируются согласованные решения внешнего CLI и будущих внутренних портов. Точные имена команд, полей и схемы JSON ещё определяются.

Основания: [требования](../../requirements.md), [доменная модель](../../appendix/domain-model.md), [сценарии](../../appendix/scenarios.md), [подсистемы](../../architecture.md).

## Согласованные границы записи и индексирования

Согласовано: apply возвращает успех после надёжной фиксации группы файлов и финальной транзакции SQLite с необходимым служебным состоянием, графом, FTS, ревизией корпуса и заданиями на embeddings. Вычисление векторов через очередь не входит в ожидание apply; входы CLI и поля hash/ids остаются прежними.

Отставание embeddings допустимо. Без актуального вектора поиск использует FTS; прежний несовместимый вектор не представляет новый текст. Готовности всех embeddings перед публикацией графа и FTS больше не требуется. Status показывает число заданий на embeddings и различает неприменённую правку и ошибку вычисления векторов. Протоколы фиксации, восстановления и публикации описаны в [модели хранения](../../mechanics/storage-model.md).

## Корень адресации

Все пути локальных файлов в CLI и локальных ссылках Markdown задаются относительно единого корня репозитория — корня общей рабочей копии, где лежат его файлы. Они не зависят от текущего каталога вызова CLI и расположения файла-источника. Например, ссылка `knowledge/new.md#ID` адресует один и тот же элемент из любого документа корпуса. Корень определяется по Git-рабочей копии, содержащей каталог вызова CLI; команды работают из её вложенных папок. Отдельное поле корня в каждой ссылке не вводится.

Пути операций над документами и назначения графовых ссылок должны после разрешения оставаться внутри корня репозитория. Абсолютные пути и выход наружу через `..` или символические ссылки отклоняются. Недопустимый путь операции вызывает `invalid_request`, недопустимое назначение внутри графовой ссылки — `validation_failed`. Ограничение не меняет трактовку обычных внешних URL в тексте и пока не задаёт адресацию источников происхождения.

## Контекст запроса применения

Агент получает актуальные метаданные и читает содержимое, подготавливает изменение и передаёт один JSON-запрос через stdin. letopis проверяет ожидаемое состояние, подготавливает операции в указанном порядке, валидирует итоговый метаграф и атомарно сохраняет файлы, граф, FTS и необходимые служебные данные с заданиями на embeddings. После финальной фиксации возвращается хеш правки; только вычисление embeddings выполняется позднее.

Запрос содержит изменения и ожидаемые хеши состояния, на котором они основаны. Для редактирования согласованы ID вершины или метавершины и ожидаемый хеш всего её Markdown-фрагмента. В согласованных записях `create` и `edit` базовый хеш помещается непосредственно в запись операции. Представление дополнительных проверок неизменяемых зависимостей ещё определяется; отдельные карты `files` и `elements` не утверждены.

Каждый контракт описывается с расположенными рядом входом и выходом и обоснованием пользы для агента. Согласованное поведение и утверждённые схемы отмечаются отдельно от предложений. Общий формат ошибок приведён в разделе JSON-ответов; точные схемы ещё не определённых команд не придумываются.

## Контракт edit

Статус: поведение и приведённые JSON-структуры входа и успешного выхода согласованы. Грамматика канонической разметки ещё определяется.

### Поведение

Вершина или метавершина представлена размеченным фрагментом Markdown-файла. Ребро представлено Markdown-ссылкой внутри описания источника. Агент должен иметь возможность точечно изменять эти фрагменты и ссылки. Отдельные операции установки произвольных атрибутов вершины из предлагаемого контракта убраны; необходимые метаданные остаются в канонической разметке.

Ранее согласованные структурированные изменения уточняются как изменения канонических элементов и их разметки. Согласовано: редактирование указывает ID вершины или метавершины и заменяет её полный Markdown-фрагмент, включая ссылки. Текст других элементов не изменяется. Новый фрагмент сохраняет ID редактируемого элемента. Это решение уточняет ранее рассмотренные способы точечных замен текста.

Подтверждено после уточнения: ID элемента и хеш его текущего состояния — отдельные значения. ID сохраняет идентичность элемента при редактировании. Ребро меняется через редактирование ссылки в тексте вершины или метавершины; отдельный контракт редактирования ребра по его ID не утверждён.

Согласовано: проверяется хеш всего Markdown-фрагмента вершины или метавершины, включая ссылки. Изменение ссылки меняет хеш её источника; хеш назначения от этого не меняется. Прежнее правило независимости хеша источника от обычных рёбер заменено этим правилом. Отдельный дополнительный хеш фрагмента не вводится. Защищённое сохранение учитывает актуальное содержимое остальных элементов файла и не перезаписывает их.

### Вход

Согласована запись с полями `type: "edit"`, `element_id`, `base_hash` исходного фрагмента и `markdown` — полным новым фрагментом с тем же ID. Необязательный `snapshot` явно подтверждает перепроверку источников по указанному снимку; без него прежние подтверждения сохраняются. Полный контракт перепроверки приведён ниже. Путь определяется по актуальному расположению элемента. Значения в примере являются заполнителями.

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "<ID вершины или метавершины>",
      "base_hash": "<хеш прочитанного Markdown-фрагмента>",
      "markdown": "<полный новый Markdown-фрагмент с тем же ID>"
    }
  ]
}
```

### Выход

Согласованный успешный ответ без создания новых ID:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

Если новый Markdown вводит новые рёбра с временными ID, применяется общий механизм замены ID, а `result` дополнительно содержит `ids` — карту временных ID постоянным. ID самой редактируемой вершины или метавершины остаётся прежним. При ошибке используется общий JSON-формат ошибки; вся атомарная правка отклоняется.

## Контракт delete

Статус: правило полного удаления, запись `delete` и приведённый успешный ответ согласованы.

### Вход

Согласована запись с полями `type: "delete"`, `element_id` и `base_hash` всего исходного Markdown-фрагмента вершины или метавершины.

```json
{
  "operations": [
    {
      "type": "delete",
      "element_id": "<ID вершины или метавершины>",
      "base_hash": "<хеш текущего Markdown-фрагмента>"
    }
  ]
}
```

### Выход

Согласованный успешный ответ запроса, содержащего только удаление:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

При несовпадении хеша или нарушении целостности возвращается общий JSON-ответ ошибки и отклоняется вся атомарная правка. Если в том же запросе есть создание с временными ID, успешный результат также содержит общую карту `ids` согласно контракту создания.

### Правила применения

Агент явно удаляет или переназначает все входящие ссылки на удаляемый элемент в том же запросе; оставшиеся ссылки дают ошибку. Ссылки внутри удалённого фрагмента исчезают вместе с ним. Включённые элементы метавершины сохраняют свои отдельные канонические описания. Ребро удаляется изменением ссылки через `edit` его источника. letopis проверяет уникальность UUID среди текущих nodes и edges, включая известные source без ссылок; история удалённых элементов для этой проверки не используется. Новые UUIDv4 генерирует letopis, без намеренного повторного назначения освобождённых ID. Перенос и восстановление той же сущности сохраняют её ID. Потеря ответа не изменяет ID сохранённых элементов; агент узнаёт их из актуальных файлов и метаданных.

## Внешний интерфейс

Единственный внешний интерфейс первой версии — CLI. Результаты и ошибки выдаются в JSON. CLI является входным адаптером и передаёт запросы прикладным сервисам одного локального рабочего процесса на проект.

## Единый формат JSON-ответов

Согласована одинаковая структура ответа для всех команд:

- Успех: `ok` имеет значение `true`, поле `result` содержит результат команды.
- Ошибка: `ok` имеет значение `false`, поле `error` содержит машинный код `code`, пояснение `message` и детали `details`.

Агент использует код ошибки для выбора действия: например, конфликт требует перечитать данные и подготовить правку заново, ошибка разметки — исправить подготовленное изменение. Пояснение и детали описывают конкретную причину.

Оставшиеся схемы содержимого `result`, структура деталей отдельных ошибок и обязательность ещё не согласованных вложенных полей проектируются далее. Каталог ошибок и коды завершения процесса согласованы ниже. Ошибка фонового обновления индекса не превращает успешный поиск по последнему корректному индексу в ошибку запроса; сведения об обновлении отражаются в соответствующем результате и состоянии.

### Канал ответа и код завершения

Согласованы два общих правила CLI:

1. Каждый завершённый вызов возвращает ровно один JSON-объект в `stdout`, включая ответы об ошибках и обработанной отмене. Прогресс получается через `status`. Агент разбирает весь ответ как один JSON без выделения результата из потока сообщений.
2. При штатном завершении с JSON-ответом процесс возвращает код `0` для `ok: true` и `1` для `ok: false`, включая обработанную отмену с `error.code: cancelled`. Причина определяется полем `error.code`; дополнительных числовых кодов для видов ошибки не предлагается. Агент использует код процесса для определения успеха, а JSON — для выбора следующего действия.

Пример входа `letopis search` через стандартный ввод:

```json
{
  "query": "Как сохраняются знания?",
  "limit": 10
}
```

Пример успешного ответа в `stdout`, когда совпадений нет; код завершения — `0`:

```json
{
  "ok": true,
  "result": []
}
```

При принятой отмене через `SIGINT` ответ в `stdout` использует согласованный формат; код завершения — `1`:

```json
{
  "ok": false,
  "error": {
    "code": "cancelled",
    "message": "Запрос отменён",
    "details": {}
  }
}
```

Канал ответа и коды завершения согласованы.

### Проверка входа и каталог ошибок

Согласованы два решения:

1. Неизвестные поля в JSON-запросе CLI отклоняются с `invalid_request`, с указанием поля в `error.details.field`. Это правило относится к фиксированной структуре входа команды и вложенным полям её JSON; значения пользовательских типов рёбер продолжают определяться проектом по согласованной модели. При отклонении атомарной правки ни одна операция не применяется. Агент получает явную диагностику опечатки вместо выполнения запроса с пропущенным условием.
2. Для первой версии используется следующий набор кодов. Детали конкретной ошибки остаются в `message` и `details`, а числовой код завершения для всех ответов `ok: false` равен `1`.

| Код | Значение и действие агента |
|---|---|
| `invalid_request` | Исправить JSON, поля или значения запроса. |
| `not_found` | Запрошенный файл или элемент отсутствует; проверить адресацию и текущее состояние. |
| `conflict` | Нарушена предпосылка записи, например `base_hash` или отсутствие пути; перечитать актуальное состояние и подготовить правку заново. |
| `validation_failed` | Разметка или итоговый метаграф нарушают правила; исправить подготовленное содержимое. |
| `embedding_failed` | Вычисление embeddings завершилось ошибкой после предусмотренных попыток; проверить адаптер и условия вычисления. |
| `internal_error` | Прочий сбой исполнения, включая файловые операции, Git или БД; получить диагностику и проверить состояние. |
| `cancelled` | Работа отменена; дальнейшее действие определяется намерением агента. |

Такой каталог даёт агенту ветвление по способу исправления, сохраняя общий формат ответа. Конкретный отсутствующий источник существующего знания продолжает обрабатываться принятым флагом `source_not_found`, а отсутствие совпадений поиска — успешным пустым результатом.

Пример входа `letopis search` с опечаткой в поле фильтров:

```json
{
  "query": "Как сохраняются знания?",
  "limit": 10,
  "filtres": {
    "needs_recheck": true
  }
}
```

Выход в `stdout`, код завершения `1`:

```json
{
  "ok": false,
  "error": {
    "code": "invalid_request",
    "message": "Неизвестное поле filtres",
    "details": {
      "field": "filtres"
    }
  }
}
```

Проверка неизвестных полей и приведённый каталог согласованы.

### Списки выбора

Согласованы два правила:

1. Пустой список в `filters.sources` или `filters.source_revisions` равнозначен отсутствию поля: ограничение по этому фильтру не применяется. Для непустых списков сохраняется согласованное правило совпадения хотя бы одного значения. Агент использует одинаковое поведение для пустого и отсутствующего списка.
2. Повторяющиеся значения в списках выбора обрабатываются один раз. Это относится к `element_ids` в `inspect`, `traverse`, `reindex`, к `paths` в `reindex`, к `edge_types` и списковым фильтрам поиска. Для внутреннего списка выбора сохраняется порядок первого появления значения. Список изменяющих `operations` сохраняет согласованный порядок и не сокращается этим правилом. Агент может объединять известные ID из нескольких результатов без отдельного удаления повторов.

Пример входа `letopis search` с пустым фильтром, равнозначным отсутствию `filters.sources`:

```json
{
  "query": "Как сохраняются знания?",
  "limit": 10,
  "filters": {
    "sources": []
  }
}
```

Пример выхода при наличии подходящего знания:

```json
{
  "ok": true,
  "result": [
    {
      "element_id": "node-a",
      "path": "knowledge/design.md",
      "lines": [
        10,
        25
      ],
      "revision": "<проиндексированная ревизия>",
      "flags": []
    }
  ]
}
```

Пример входа `letopis inspect` с повторяющимся ID:

```json
{
  "element_ids": ["node-a", "node-a"]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "snapshot": "<ссылка на общий Git-снимок>",
    "elements": {
      "node-a": {
        "path": "knowledge/design.md",
        "lines": [10, 25],
        "hash": "<хеш элемента>",
        "file_hash": "<хеш файла>"
      }
    }
  }
}
```

Оба правила списков согласованы. Пустые списки обязательных начальных ID и селекторов `reindex` здесь не определяются.

### Успешное применение правки

Согласован результат применения: result.hash содержит вычисленный letopis хеш исходного запроса, отпечаток его содержимого. При создании result.ids содержит соответствие временных ID постоянным; без создания возвращается только hash. ok: true означает надёжную фиксацию всех документов и необходимого служебного состояния. Хеш не является уникальным ID отдельного выполнения; успешные ответы не хранятся бессрочно ради дедупликации.

Для успешного ответа создания согласован объект `result` с полями `hash` (хеш исходной правки) и `ids` (карта временный ID → постоянный ID).

После успешного apply граф и FTS уже опубликованы, новая правка доступна текстовому поиску. Только embeddings могут ещё вычисляться; их очередь и ошибки доступны через status. После потери ответа агент перечитывает документы и актуальные метаданные; отдельный новый вызов проходит обычные проверки.

## Передача атомарной правки

Согласовано: одна атомарная правка передаётся одним JSON-запросом через стандартный ввод CLI. Запрос охватывает весь набор изменений, включая многофайловую правку.

Согласованные составляющие запроса:

- Ожидаемые хеши элементов, на которых основано изменение, и при необходимости явно заданных неизменяемых зависимостей.
- Весь набор структурированных изменений метаграфа и/или правок Markdown.

Хеш патча вычисляет letopis по содержимому всей атомарной правки, включая пути, упорядоченные изменения и ожидаемые хеши. Отдельный `operation_id` в запросе и предварительная выдача ID операции не требуются. Timestamp и дополнительные параметры для различения операций не вводятся. Одинаковый полный запрос имеет тот же отпечаток содержимого, но новый самостоятельный вызов не считается завершённым только из-за совпадения хеша. Изменение содержимого запроса даёт другой хеш. Согласовано SHA-256 канонического JSON по JCS; оформление JSON и порядок ключей объектов не меняют хеш.

Согласовано сочетание структурированных операций и Markdown-правок в одном атомарном запросе.

### Неизменяемый контекст

Согласована необязательная карта `base_hashes`: постоянный ID элемента → хеш его исходного состояния. Она проверяет элементы, на которых основана правка, даже если она их не меняет. Эти предпосылки, как и `base_hash` изменяемых элементов, проверяются по актуальным каноническим документам перед сохранением; несовпадение отклоняет всю правку с `conflict`. Карта входит в исходный запрос и в вычисление хеша всей правки. Отдельная команда проверки контекста не требуется.

Вход `letopis apply`:

```json
{
  "base_hashes": {
    "node-rule": "<хеш знания, на котором основана правка>"
  },
  "operations": [
    {
      "type": "edit",
      "element_id": "node-a",
      "base_hash": "<хеш исходного node-a>",
      "markdown": "<полный новый размеченный фрагмент node-a>"
    }
  ]
}
```

Успешный выход:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

Агент передаёт для неизменяемого знания только ID и хеш, полученные через `inspect`; текст этого знания не требуется. Имя и структура карты согласованы.

### Перенос существующего элемента

Согласовано выражать перенос с сохранением ID через `delete` старого описания, `create` описания в целевом файле и `edit` затронутых ссылок в одном запросе. В `create` разрешены постоянные ID существующих переносимых элементов, только если прежние описания удаляются тем же запросом. При сохранении учитывается итоговое состояние всей правки: сохраняются идентичность и история переносимого элемента и его рёбер. Новые сущности по-прежнему используют временные ID, заменяемые letopis; постоянные ID ранее окончательно удалённых элементов этим правилом повторно не выделяются.

Вход `letopis apply`; целевой файл в этом примере существует:

```json
{
  "operations": [
    {
      "type": "delete",
      "element_id": "node-a",
      "base_hash": "<хеш исходного node-a>"
    },
    {
      "type": "create",
      "path": "knowledge/archive.md",
      "base_hash": "<хеш целевого файла>",
      "markdown": "<размеченный фрагмент с прежним ID node-a>"
    },
    {
      "type": "edit",
      "element_id": "node-ref",
      "base_hash": "<хеш исходного node-ref>",
      "markdown": "<полный фрагмент node-ref с исправленной ссылкой knowledge/archive.md#node-a>"
    }
  ]
}
```

Успешный выход, если новых сущностей нет:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

Если целевого файла нет, для его `create` опускается `base_hash` по уже согласованному правилу. Все затронутые пути в графовых ссылках, включая относительные исходящие ссылки, подготавливает агент; итоговая целостность проверяется перед атомарным сохранением. Это позволяет выполнить перенос уже имеющимися операциями, без отдельной команды. Правило использования прежних ID в `create` при переносе согласовано.

### Алгоритм хеширования и канонизация JSON

Согласованы два решения:

1. Хеши содержимого файлов и полных канонических Markdown-фрагментов вершин и метавершин вычисляются SHA-256 по точным байтам. Пробелы, переводы строк и служебная разметка учитываются без нормализации. Представление результата — 64 строчных шестнадцатеричных символа без префикса. Хеш состояния остаётся производным значением; он не записывается внутрь собственного хешируемого фрагмента. Байтовое содержимое служебного Git-снимка должно соответствовать каноническим файлам, чтобы хеш из `inspect` относился к содержимому, которое агент читает. Для ребра согласовано SHA-256(JCS({source, markdown})), описанное далее.
2. Хеш правки вычисляется SHA-256 по каноническому JSON всего исходного запроса по [JCS, RFC 8785](https://www.rfc-editor.org/rfc/rfc8785), до замены временных ID. Оформление JSON и порядок свойств объектов не влияют на результат; порядок массивов и значения строк сохраняются. В частности, порядок `operations` и содержимое `markdown` остаются значимыми. Другое оформление того же JSON даёт тот же хеш; это не подменяет проверки нового самостоятельного вызова. Предложение не приравнивает различные структуры запроса с одинаковым эффектом.

Вход `letopis inspect` для первого решения:

```json
{
  "element_ids": ["node-a"]
}
```

Пример выхода с обозначениями формата хешей:

```json
{
  "ok": true,
  "result": {
    "snapshot": "<общий Git-снимок>",
    "elements": {
      "node-a": {
        "path": "knowledge/design.md",
        "lines": [10, 25],
        "hash": "<64 строчных hex-символа>",
        "file_hash": "<64 строчных hex-символа>"
      }
    }
  }
}
```

Вход `letopis apply` для второго решения, два оформления одного запроса:

```json
{
  "operations": [
    {
      "type": "delete",
      "element_id": "node-a",
      "base_hash": "<исходный хеш node-a>"
    }
  ]
}
```

```json
{"operations":[{"base_hash":"<исходный хеш node-a>","element_id":"node-a","type":"delete"}]}
```

Успешный выход для обоих оформлений:

```json
{
  "ok": true,
  "result": {
    "hash": "<один и тот же хеш правки, 64 строчных hex-символа>"
  }
}
```

Точные байты дают агенту однозначную предпосылку записи; канонизация JSON позволяет повторить запрос после потери ответа без сохранения прежних отступов и порядка ключей. Оба решения согласованы. Вход для хеширования правки должен соответствовать JCS, включая запрет повторяющихся ключей JSON-объекта; нарушение формата запроса возвращает `invalid_request`.

### Хеш ребра и формат постоянного ID

Согласованы два решения:

1. Собственный хеш ребра вычисляется SHA-256 канонического JSON по JCS с двумя полями: `source` — постоянный ID вершины или метавершины-источника и `markdown` — точное исходное представление Markdown-ссылки, включая её текст, адрес и `title` с ID и типом ребра. Источник определяется по содержащему ссылку фрагменту. Хеш учитывает смену источника даже при неизменном тексте ссылки и не зависит от остального текста исходной вершины или содержимого целевой вершины. Объект используется при вычислении; сохранение текста ссылки в БД этим решением не вводится.
2. Постоянные ID вершин, метавершин и рёбер генерируются letopis как UUIDv4 в канонической строковой записи со строчными hex-символами и дефисами. Временные ID сохраняют префикс `tmp:`. UUIDv4 описан в [RFC 9562, раздел 5.4](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.4). Проверяется уникальность среди текущих nodes и edges, без проверки истории удалённых ID. Карта ID возвращается текущим успешным вызовом; её автоматический возврат при отдельном повторе после потери ответа не гарантируется. Формат ID не кодирует структурный вид, путь или содержимое элемента.

Для первого предложения `letopis inspect` получает:

```json
{
  "element_ids": ["edge-a"]
}
```

Выход с собственным хешем ребра:

```json
{
  "ok": true,
  "result": {
    "snapshot": "<общий Git-снимок>",
    "elements": {
      "edge-a": {
        "path": "knowledge/design.md",
        "lines": [18, 18],
        "hash": "<SHA-256 JCS-объекта source и markdown>",
        "file_hash": "<хеш файла>"
      }
    }
  }
}
```

Обозначения `edge-a` и `node-a` в примерах служат читаемыми заменителями постоянных ID. Агент может проверять конкретную связь через `base_hashes`, независимо от изменений остального текста исходной вершины.

Для второго предложения вход `letopis apply`; файл в примере отсутствует:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/new.md",
      "markdown": "<размеченный фрагмент с временным ID tmp:000>"
    }
  ]
}
```

Пример успешного выхода:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>",
    "ids": {
      "tmp:000": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c"
    }
  }
}
```

Агент продолжает использовать временные имена при подготовке и получает готовые постоянные ID в результате одной правки; собственная генерация и отдельная команда выделения ID не требуются. Состав хеша ребра и формат UUIDv4 согласованы.

### Временные ID и границы Markdown-фрагмента

Статус: согласованы временные ID `tmp:000`–`tmp:fff` и границы фрагмента в HTML-комментариях с JSON-метаданными `id`, `kind`.

1. Формат временного ID — `tmp:` и ровно три строчных hex-символа: `tmp:000`–`tmp:fff`, шаблон `^tmp:[0-9a-f]{3}$`. Это 4096 различных имён для новых вершин, метавершин и рёбер вместе в одном атомарном запросе. Агент может выбирать их последовательно. Объявления должны быть уникальны в запросе; ссылки на одно объявление могут повторяться. В следующем запросе эти имена снова доступны. Отдельного числового поля или команды выделения временных ID нет.

Вход `letopis apply`; файл отсутствует:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/new.md",
      "markdown": "<размеченный фрагмент с временным ID tmp:000>"
    }
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>",
    "ids": {
      "tmp:000": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c"
    }
  }
}
```

2. Фрагмент ограничивается отдельными служебными HTML-комментариями: открывающий `<!-- letopis: {JSON} -->` канонического фрагмента содержит `id`, `kind`, назначенный letopis `created_at` и, при установленном основании, `source_snapshot`; закрывающий — `<!-- /letopis -->`. `kind` принимает `vertex` или `metavertex`. Между ними находится обычный Markdown. Границы входят в хеш всего фрагмента. Вложение и перекрытие таких описаний запрещены согласно доменной модели. Служебные маркеры распознаются в контексте Markdown, а примеры внутри кодовых блоков остаются текстом. Файловое и текстовое расположение фрагментов не создаёт графовую включённость; она по-прежнему определяется ссылками `includes`. Остальные поля метаданных будут уточнены отдельно. Префикс letopis: согласован как маркер служебной разметки, а не корневой ключ JSON: метаданные остаются плоским объектом без обёртки letopis.

Согласовано автоматическое назначение времени создания самим letopis. Агент передаёт новые элементы без даты. letopis подготавливает метку и сохраняет её вместе с новыми элементами в успешной атомарной правке; размеченные элементы получают одно значение в Markdown и БД, новые внешние источники — только в БД. Редактирование и перенос существующего элемента сохраняют его первоначальное время. Принято created_at: Unix timestamp в целых секундах с 1970-01-01 00:00:00 UTC. В JSON-маркере канонического узла это число; в title ребра — created_at=SECONDS. В nodes и edges используется created_at INTEGER NOT NULL. Вход create без даты остаётся допустимым: letopis добавляет метку при сохранении. Конкретная диагностика попытки изменить служебную метку при edit ещё уточняется.

Для основания знания принято source_snapshot в JSON-метаданных канонического Markdown; nodes хранит его проекцию. Значение — общий Git tree OID всех источников этого знания. Существующий edit.snapshot после проверок задаёт новое значение; при edit без snapshot прежний source_snapshot сохраняется. letopis сохраняет метаданные атомарно с документами и БД. Полный хеш фрагмента включает source_snapshot, поэтому смена основания защищается base_hash. Новые команды и отдельный параметр edit.source_snapshot не вводятся. У знания без установленного основания поле source_snapshot отсутствует в Markdown, а в БД используется NULL; у внешнего source также NULL. Если ссылки удалены, edit без snapshot сохраняет прежнее основание. При create агент передаёт первый source_snapshot в JSON-метаданных фрагмента внутри существующего поля create.markdown. letopis проверяет снимок и адресуемые источники, разрешает временные ID, назначает created_at и сохраняет основание атомарно с новым элементом. Если новый элемент содержит external-ссылки, отсутствие source_snapshot отклоняет всю правку. Несколько элементов одной записи create могут иметь разные основания: каждый source_snapshot относится ко всем источникам своего знания. Отдельный параметр create.snapshot и новая команда не вводятся. Первый source_snapshot агент получает средствами Git по инструкции для навыка ниже. Команда letopis snapshot не вводится. Перед записью обязательны проверка существования объекта и его точного типа tree.

Вход `letopis apply`; файл отсутствует:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/new.md",
      "markdown": "<!-- letopis: {\"id\":\"tmp:000\",\"kind\":\"vertex\"} -->\n# Решение\nТекст знания.\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>",
    "ids": {
      "tmp:000": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c"
    }
  }
}
```

Трёхзначное временное имя даёт агенту короткое и однозначное обозначение. Явные границы позволяют ему заменить один целый фрагмент и позволяют letopis определить источник ссылок в файле с несколькими элементами. Содержимое и метаданные остаются вместе в Markdown. Формат временных имён и данная разметка согласованы.

### Графовые ссылки

Смысловые метки `types` не вводятся. Согласован корень адресации: пути всех локальных ссылок считаются от корня репозитория, независимо от расположения файла-источника. Собственный ID и тип ребра по-прежнему хранятся в `title`.

Согласована точная inline-грамматика: `[Описание](knowledge/file.md#ID "letopis:id=EDGE_ID;type=TYPE;created_at=SECONDS")`. Это каноническая форма; при создании нового ребра вход может не содержать автоматически назначаемую метку. Целевой ID, ID ребра и тип обязательны; временные ID допустимы внутри создающей правки и заменяются letopis в соответствующих полях. Тип ребра имеет форму `[a-z][a-z0-9_]*`. Для включённости используется системный `includes`, источник которого — метавершина. Описание остаётся текстом Markdown-ссылки. Дополнительное кодирование имени типа не требуется. Трактовка ссылок без графовых метаданных согласована ниже.

Вход `letopis apply`; новый файл содержит два независимых описания, связанных включённостью:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/new.md",
      "markdown": "<!-- letopis: {\"id\":\"tmp:000\",\"kind\":\"metavertex\"} -->\n# Архитектура\n[Ограничение](knowledge/new.md#tmp:001 \"letopis:id=tmp:002;type=includes\")\n<!-- /letopis -->\n\n<!-- letopis: {\"id\":\"tmp:001\",\"kind\":\"vertex\"} -->\n# Ограничение\nОдин проект.\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>",
    "ids": {
      "tmp:000": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "tmp:001": "521eb6f0-bd63-4d44-9aaf-c2d9be2bb5e4",
      "tmp:002": "064f2964-77cc-41f0-87ac-d280c0ec59a7"
    }
  }
}
```

Одна атомарная правка создаёт метавершину, вершину и ребро, возвращая все три соответствия. Агент строит связь средствами Markdown и существующим механизмом временных ID; дополнительных команд графа не требуется. Общий корень позволяет использовать одинаковый адрес назначения в любых файлах.

#### Графовые ссылки и внешние источники

По последнему уточнению пользователя файловый источник знания тоже представлен обычной вершиной графа; ссылка на него образует ребро. Для таких ссылок согласован системный тип `external` в существующей грамматике `title`; назначение адресуется файлом и фрагментом. Это заменяет прежнее исключение источников из графа. Некорректные метаданные графовой ссылки по-прежнему вызывают ошибку проверки. Трактовка остальных навигационных Markdown-ссылок не определяет автоматически происхождение знания.

#### Грамматика типа ребра и границы путей

Следующие два решения согласованы.

1. Поле `title` графовой ссылки в каноническом документе имеет форму `letopis:id=ID;type=TYPE;created_at=SECONDS`. Для новой ссылки во входе создания метка может отсутствовать; letopis назначает её автоматически. Тип ребра — непустое имя по шаблону `[a-z][a-z0-9_]*`, например `depends_on`, `contradicts`, `includes`. Имена задаёт проект, без отдельной регистрации и схем. Произвольный текст описания остаётся в подписи ссылки. Дополнительное кодирование имени типа не требуется. Мотивация: агент использует короткие машинные имена; парсеру не требуется отдельный механизм экранирования типа, смысл связи выражается её описанием.

Вход `letopis apply --check`; создаваемый файл отсутствует, целевая вершина уже существует:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/new.md",
      "markdown": "<!-- letopis: {\"id\":\"tmp:000\",\"kind\":\"vertex\"} -->\n[Зависимость](knowledge/base.md#08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c \"letopis:id=tmp:001;type=depends_on\")\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "paths": ["knowledge/new.md"],
    "element_ids": ["tmp:000", "tmp:001"]
  }
}
```

Список содержит новую вершину и её новое ребро. Существующая цель не изменяется. Ошибка грамматики графовой ссылки использует согласованный код `validation_failed`.

2. Пути операций над документами и назначения графовых ссылок должны быть относительными корню репозитория и после разрешения оставаться внутри него. Абсолютные пути и выход наружу через `..` или символические ссылки отклоняются. Это не вводит ограничений на обычные внешние URL в тексте и не определяет адресацию источников происхождения. Мотивация: изменяемые документы и графовые цели остаются в общей рабочей копии и могут входить в согласованный Git-снимок; агент не зависит от абсолютных путей конкретного компьютера.

Вход `letopis apply`:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "../outside.md",
      "markdown": "<!-- letopis: {\"id\":\"tmp:000\",\"kind\":\"vertex\"} -->\nТекст знания.\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход; правка не применяется:

```json
{
  "ok": false,
  "error": {
    "code": "invalid_request",
    "message": "Путь выходит за корень репозитория",
    "details": {
      "field": "operations[0].path"
    }
  }
}
```

Недопустимый путь в поле операции вызывает `invalid_request`; недопустимое назначение внутри графовой Markdown-ссылки вызывает `validation_failed` при проверке разметки. В обоих случаях отклоняется вся атомарная правка.

### Пустая правка и повторное редактирование

Следующие два решения согласованы.

1. Поле `operations` обязательно и должно содержать хотя бы одну операцию. Пустой список отклоняется с `invalid_request`. Мотивация: агент сразу получает диагностику, если при подготовке запроса потерял изменения; дополнительный результат для пустой правки не требуется.

Вход `letopis apply`:

```json
{
  "operations": []
}
```

Выход:

```json
{
  "ok": false,
  "error": {
    "code": "invalid_request",
    "message": "operations должен содержать хотя бы одну операцию",
    "details": {
      "field": "operations"
    }
  }
}
```

2. В одном атомарном запросе разрешается не более одной операции `edit` для каждого ID. Агент передаёт один окончательный Markdown-фрагмент. Повторный `edit` того же элемента отклоняет весь запрос с `invalid_request`, без применения первого изменения. Правило не запрещает согласованный перенос через `delete` + `create` с прежним ID и не дедуплицирует операции автоматически. Мотивация: одна полная замена выражает конечное состояние и сокращает объём запроса; агенту и проверяющему проще сопоставить результат с единственным исходным `base_hash`.

Вход `letopis apply`:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш исходного фрагмента>",
      "markdown": "<!-- letopis: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"vertex\"} -->\nПервая редакция.\n<!-- /letopis -->\n"
    },
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш исходного фрагмента>",
      "markdown": "<!-- letopis: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"vertex\"} -->\nОкончательная редакция.\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход:

```json
{
  "ok": false,
  "error": {
    "code": "invalid_request",
    "message": "Один элемент нельзя редактировать дважды в одном запросе",
    "details": {
      "field": "operations[1].element_id"
    }
  }
}
```

### Область записи

Согласовано: letopis изменяет только специально размеченные Markdown-документы корпуса. Для существующего пути принадлежность корпусу проверяется по исходному каноническому состоянию до применения операций: файл должен иметь расширение .md или .markdown и разметку letopis. Внешние источники, обычные Markdown-документы без разметки и остальные файлы не являются целями записи через apply. Наличие base_hash или разметки в переданном новом содержимом не разрешает изменение существующего файла вне корпуса.

Попытка записи вне этой области отклоняет всю атомарную правку до изменения файлов. Используется существующий код invalid_request; новый код или команда не вводятся. Неполная либо некорректная разметка letopis по-прежнему вызывает validation_failed при проверке разметки, а не молчаливое исключение документа из корпуса. Общая проверка действует и для apply --check. Служебные записи БД и Git-снимки остаются внутренними механизмами по ранее согласованной архитектуре; ограничение относится к изменению содержимого пользовательских документов и источников.

Выход для попытки изменить существующий README.md без разметки letopis:

```json
{
  "ok": false,
  "error": {
    "code": "invalid_request",
    "message": "Изменять можно только размеченные Markdown-документы корпуса letopis",
    "details": {
      "path": "README.md"
    }
  }
}
```

Мотивация: агент получает явную границу инструмента; запрос на изменение обычного документа не расширяет корпус и не затрагивает другие операции группы. Ранее согласованный create для отсутствующего пути сохраняется: новый файл создаётся сразу как размеченный Markdown-документ letopis после общей проверки. Изменение существующего неразмеченного файла при создании элемента запрещено.

### Порядок обработки

Операции create/edit/delete выполняются в указанном порядке на временном состоянии документов. Следующая операция видит результат предыдущей: например, после создания элемента можно добавить ссылку на него. Edit заменяет полный Markdown-фрагмент по ID; рёбра меняются через ссылки внутри фрагмента. Общие файловые операции сопоставления старого текста и контекста в v1 не предоставляются, [D-30](../../decisions.md#D-30).

Поле `operations` обязательно и непусто. Для одного ID допускается не более одного `edit` в запросе. Это не отменяет порядок разных операций и согласованный перенос через `delete` + `create` с прежним ID.

Ожидаемые хеши относятся к исходному каноническому состоянию, а не к промежуточному результату собственных операций запроса. Сохраняется требование проверки актуального состояния перед защищённым сохранением, чтобы подготовка не обходила оптимистический контроль конкурентных изменений.

Оптимистическая проверка хешей не заменяется блокировкой файла на время работы агента. Агенты могут читать и подготавливать правки параллельно. На этапе сохранения требуется согласовать финальную проверку предпосылок и запись, чтобы другая операция не изменила проверенное состояние между ними. Это внутренняя защита фиксации; конкретный механизм и его область ещё проектируются, отдельная блокировка файла на всё время создания не согласована.

Перед сохранением проверяется целостность итогового состояния целиком. Промежуточные состояния не записываются в канонические файлы и не публикуются в индексе. Ошибка любой операции или итоговой проверки отклоняет всю правку. Стратегия загрузки данных, координация подготовки и сохранения и точные диагностические поля ещё проектируются.

### Хеш существующего файла при create

Create добавляет размеченные элементы в конец указанного документа. Если файл существует, base_hash относится ко всему исходному файлу и проверяется перед сохранением; несовпадение отклоняет всю атомарную правку. Для нового файла путь должен быть свободен, base_hash опускается. Это ранее согласованная предпосылка создания, [D-5](../../decisions.md#D-5), сохранённая при уточнении [D-30](../../decisions.md#D-30).

Для edit по ID проверяется хеш Markdown-фрагмента, включая ссылки; хеш всего файла не добавляется как новая предпосылка редактирования. Изменение другого элемента само по себе не меняет base_hash редактируемого фрагмента. Для последовательных create одного запроса файловый base_hash относится к исходному каноническому состоянию. Хеш файла — SHA-256 точных байтов.

## Контракт create

Статус: структура входа, успешного выхода и основные правила создания согласованы. Грамматика Markdown ещё определяется.

### Вход

Контракт создания сейчас уточняется. У нового элемента нет предыдущего состояния, поэтому `base_hash` самого нового элемента не передаётся. Это не отменяет проверки актуальности существующего файла, если создание изменяет его, проверки уникальности выданного letopis ID и целостности итогового метаграфа. Существующий файл назначения обязан быть размеченным Markdown-документом корпуса до правки; create не используется для превращения обычного существующего файла в документ letopis.

Согласована запись создания в списке `operations`: `type: "create"`, путь `path`, разметка нового элемента `markdown` и `base_hash` исходного файла, если файл существует. Временный ID содержится в разметке и не дублируется отдельным полем операции. Для нового файла `base_hash` опускается. Эта структура принята; грамматика разметки ещё определяется.

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/design.md",
      "base_hash": "<хеш существующего файла>",
      "markdown": "<разметка новых элементов tmp:000 и tmp:001>"
    }
  ]
}
```

### Выход

Согласованный успешный ответ:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>",
    "ids": {
      "tmp:000": "<постоянный ID первого элемента>",
      "tmp:001": "<постоянный ID второго элемента>"
    }
  }
}
```

`hash` относится ко всему исходному атомарному запросу, `ids` содержит соответствие временных ID постоянным. При ошибке используется общий JSON-формат ошибки; изменения не сохраняются частично. Новый вызов с тем же JSON заново проверяет условия создания и актуальные хеши. Если прежняя правка уже создала элементы, агент узнаёт их ID из файлов и метаданных.

При переносе существующего элемента через `delete` и `create` в одном запросе сохранение прежнего постоянного ID допускается по согласованному правилу переноса. Если новых сущностей нет, `result.ids` не добавляется: возвращается только хеш правки.

### Правила применения

Для создания в новом файле поле `base_hash` опускается согласно согласованному условию отсутствия файла. Грамматика Markdown и временного ID ещё выбирается; значения в примере являются заполнителями.

Согласовано: поле `markdown` одной записи `create` может содержать несколько новых размеченных вершин или метавершин со ссылками между ними. Все они добавляются в один указанный файл; путь и хеш файла указываются один раз. Каждый элемент сохраняет собственный ID и отдельный непрерывный Markdown-фрагмент согласно доменной модели.

Согласовано: подготовленный размеченный Markdown нового элемента добавляется в конец указанного файла. Если файл отсутствует, он создаётся с этим содержимым в той же атомарной правке. Параметр позиции для операции создания не нужен. Агент использует временные ID, которые letopis заменяет постоянными при применении. Точная схема запроса и синтаксис временных ID ещё определяются.

Согласовано: при создании в существующем файле агент передаёт `base_hash` всего этого файла. Перед сохранением он сравнивается с актуальным хешем; если файл изменился, вся атомарная правка отклоняется. Хеш относится к исходному каноническому состоянию, как и остальные предпосылки запроса. Добавление к изменившемуся файлу без проверки переданного хеша не принято. Это оптимистический контроль файла; резервирование на всё время работы агента не вводится.

### Создание нового файла

Согласовано: новый файл создаётся только при условии, что указанный путь не занят. Вместо ожидаемого хеша существующего содержимого применяется предпосылка отсутствия файла. Если путь занят, вся атомарная правка отклоняется как конфликт; существующий файл не перезаписывается.

Например, из двух конкурентных операций создания по одному пути первая может завершиться успешно, а вторая должна получить конфликт. Корректность разметки нового содержимого и целостность итогового метаграфа проверяются вместе со всей правкой.

Каждый новый вызов заново проверяет отсутствие файла либо base_hash существующего файла. Если предыдущий create уже изменил корпус, новый самостоятельный вызов может вернуть conflict; старый успех по хешу не возвращается. Формат create и условия base_hash согласованы выше.

Согласовано: отсутствие поля `base_hash` в операции создания элемента означает, что исходный файл по указанному пути должен отсутствовать. Если путь уже занят, вся правка отклоняется как конфликт. Условие отсутствия относится к исходному каноническому состоянию, как и остальные предпосылки запроса; собственные изменения промежуточного состояния не меняют его смысл.

## Генерация идентификаторов

Единственный генератор постоянных ID новых вершин, метавершин и рёбер — letopis. Агент задаёт временные ID в запросе создания и в разметке новых элементов, а также использует их в графовых ссылках того же атомарного запроса. Временные ID действуют в пределах одного запроса и не становятся каноническими идентификаторами.

Для обозначения временных ID согласован формат `tmp:[0-9a-f]{3}`, например `tmp:000` и `tmp:001`. Он используется в разметке элементов и графовых ссылках того же запроса и позволяет отличать временные ID от постоянных без дополнительной карты объявлений в JSON. В одном запросе доступны 4096 имён для новых элементов всех видов вместе.

letopis сопоставляет временные ID постоянным и заменяет их в полях адресации, разметке элементов и графовых ссылках до сохранения итогового состояния. Обычный текст не подвергается общей строковой замене. Неоднозначные объявления и неразрешённые ссылки отклоняются при общей проверке. Синтаксис объявления и ссылки на временный ID ещё проектируется. Отдельная команда предварительной выдачи ID для создания не требуется.

letopis проверяет уникальность UUID среди текущих nodes и edges, включая известные source без ссылок; история удалённых элементов для этой проверки не используется. Новые UUIDv4 генерирует letopis, без намеренного повторного назначения освобождённых ID. Перенос и восстановление той же сущности сохраняют её ID. Потеря ответа не изменяет ID сохранённых элементов; агент узнаёт их из актуальных файлов и метаданных. Хеш правки вычисляется по исходному полному запросу с временными ID до их замены. После потери ответа агент перечитывает сохранённые элементы. Хеш полного исходного патча является отпечатком содержимого, не уникальным ID каждого выполнения; отдельная команда выдачи ID операции не нужна.

Согласовано: успешный ответ создания возвращает хеш правки и соответствие временных ID постоянным в result.hash и result.ids. Бессрочное хранение этого ответа для отдельного повторного вызова не требуется; после потери ответа агент читает документы и узнаёт созданные ID.

Сохраняется различие между созданием нового элемента и восстановлением той же сущности либо переносом её канонического описания с прежним ID. История удалённых ID не проверяется; постоянный формат UUIDv4 и временный формат tmp:[0-9a-f]{3} уже согласованы. Хеш содержимого правки и стабильные ID элементов выполняют разные роли.

## Необязательная проверка без сохранения

Статус: согласованы `letopis apply` для применения правки, `letopis apply --check` для необязательной проверки с тем же JSON-запросом и успешный результат проверки с `paths` и `element_ids`. Общий каталог ошибок согласован; детали ошибок проверки ещё уточняются.

### Вход

Согласовано: предварительная проверка остаётся необязательным режимом общего сценария применения и использует тот же JSON-запрос. По окончательному выбору пользователя используется `letopis apply --check`; для обычного применения — `letopis apply` с тем же JSON через стандартный ввод. Оба режима используют общий путь подготовки и проверки в «Редакторе знаний». Новое поле в теле запроса не требуется. Например:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "node-a",
      "base_hash": "<хеш исходного фрагмента>",
      "markdown": "<полный новый размеченный фрагмент node-a>"
    }
  ]
}
```

### Выход

Режим возвращает ошибки и список затрагиваемых файлов и элементов в JSON, не сохраняет каноническую правку. После проверки агент может применить тот же запрос; хеши и условия перед сохранением проверяются заново. Проверка не связывает хеш патча с сохранённым результатом применения.

Согласован успешный результат со списками `paths` и `element_ids`:

```json
{
  "ok": true,
  "result": {
    "paths": ["knowledge/design.md"],
    "element_ids": ["node-a"]
  }
}
```

Списки описывают файлы и элементы, которые подготовленная правка создаёт, изменяет или удаляет, без повторов. Для новых элементов используются временные ID из запроса; проверка не резервирует постоянные ID. Успешный результат согласован. При ошибке используется общий формат `ok: false` с `error.code`, `error.message` и `error.details`; помещение списков `paths` и `element_ids` в `error.details` пока остаётся предложением.

Пример ответа при несовпадении `base_hash` с согласованным кодом `conflict`:

```json
{
  "ok": false,
  "error": {
    "code": "conflict",
    "message": "Элемент node-a изменился после чтения",
    "details": {
      "paths": ["knowledge/design.md"],
      "element_ids": ["node-a"]
    }
  }
}
```

### Правила применения

Проверка не применяет изменения, не выделяет постоянные ID и не регистрирует выполнение как успешное сохранение. Хеш запроса не требует резервирования. Последующее apply заново проверяет актуальное состояние.

Обычное применение всегда выполняет необходимые проверки. Отдельная предварительная проверка не является обязательным шагом и не гарантирует последующий успех при конкурентных изменениях. Выбор вызовов `letopis apply` и `letopis apply --check` и успешный результат проверки согласованы; детали ошибок ещё уточняются. Отдельный дополнительный сценарий подготовки не требуется.

### Польза для агента

Одна команда `apply` принимает подготовленную атомарную правку; флаг `--check` выбирает проверку без сохранения. Агент проверяет уже подготовленный запрос и затем передаёт его для применения без изменения JSON. Списки показывают область изменений, а общий формат ошибок позволяет использовать ту же обработку диагностики, что при сохранении. Дополнительная команда подготовки правки не требуется.

Оба вида правок обслуживает единый «Редактор знаний». Правила контроля конфликтов, целостности, атомарного сохранения и восстановления общие. Каждый новый самостоятельный вызов применяет их к актуальному состоянию; старый успешный ответ по хешу не возвращается.

Поддерживаемые create/edit/delete изменяют канонические Markdown-файлы: размеченные фрагменты вершин и метавершин и ссылки внутри них, задающие рёбра. До сохранения подготовленное состояние проверяется по правилам агрегата. После сохранения индексирование получает Git-снимок корпуса и обновляет производную графовую структуру и поисковые проекции в БД. Адресация элемента не является отдельным путём прямой записи в опубликованный граф БД.

Передача текста в запросе необходима для применения правки и не означает сохранение копии текста в БД letopis. Каноническое содержимое остаётся в Markdown; служебные снимки для отката и индексирования сохраняются в Git без создания коммита. БД хранит структуру графа, embeddings, локи и согласованные служебные данные.

## Исследованные форматы текстовых правок

2026-10-18: по [D-30](../../decisions.md#D-30) эти форматы не входят в v1. Действующий контракт записи ограничен create/edit/delete размеченных элементов; edit передаёт полный новый фрагмент. Создание элементов в конце документа остаётся частью create, перенос — delete + create с прежним ID и исправлением ссылок агентом.

Согласовано точное и однозначное сопоставление старого текста для замены и контекста патча: требуется ровно одно место совпадения. Формат позиции ещё определяется в схеме запроса.

Добавление внутри файла также может выражаться патчем с существующим контекстом и только добавляемыми строками либо точной заменой якорного фрагмента на тот же фрагмент с новым текстом. Для этих форм сохраняется правило точного и единственного совпадения.

Конкретная грамматика патча и схема JSON ещё проектируются. Выбор патчей с контекстом не устанавливает автоматически формат V4A или unified diff. Общие требования контроля хешей, валидации разметки, целостности графа и атомарности сохраняются для обоих форматов.

## Контракт inspect

Статус: имя команды, пакетный вход и выход с общим Git-снимком согласованы. Пакетная схема заменяет ранее принятую одиночную; отдельной команды для одного элемента нет.

### Вход

Согласован список `element_ids`. Для одного элемента передаётся список из одного ID. Запрос получает актуальные метаданные по известным ID без поиска.

```json
{
  "element_ids": ["node-a", "node-b"]
}
```

### Выход

Все результаты относятся к одному неизменяемому Git-снимку. Ссылка на снимок возвращается один раз, а метаданные адресуются ключами-ID в карте `elements`.

```json
{
  "ok": true,
  "result": {
    "snapshot": "<ссылка на общий Git-снимок>",
    "elements": {
      "node-a": {
        "path": "knowledge/design.md",
        "lines": [10, 25],
        "hash": "<хеш первого элемента>",
        "file_hash": "<хеш файла>"
      },
      "node-b": {
        "path": "knowledge/design.md",
        "lines": [27, 40],
        "hash": "<хеш второго элемента>",
        "file_hash": "<хеш файла>"
      }
    }
  }
}
```

Если любой запрошенный ID отсутствует, возвращается общий JSON-ответ ошибки. `lines` — пара начальной и конечной строк включительно, с нумерацией от 1, по общему снимку. Для внешнего источника, адресованного как файл целиком без диапазона, `lines` опускается; `path` указывает весь файл. Для размеченных знаний и источников с заданным диапазоном обе границы возвращаются. `hash` используется как `base_hash` для `edit` или `delete`, а `file_hash` — как `base_hash` для `create` в существующем файле. Сам текст знания в ответе не возвращается. Значения в примере являются заполнителями.

Для известной внешней вершины с сохранёнными ссылками отсутствие файла не вызывает `not_found`: адрес и диапазон сохраняются, а актуальные `hash` и `file_hash` равны `null`. Если файл существует, но диапазон недоступен, только `hash` равен `null`, а `file_hash` содержит актуальный хеш файла. Строки в таком ответе обозначают адресованный диапазон, а не существующее содержимое. Отсутствие запрошенного ID по-прежнему вызывает `not_found` для всего пакета. Старые хеши не выдаются за актуальные.

### Правила чтения

Все метаданные соответствуют одному завершённому каноническому состоянию на момент получения Git-снимка. Они не берутся без проверки из устаревшего поискового индекса. Согласовано: `file_hash` вычисляется по точным байтам всего файла в этом снимке один раз на уникальный файл в рамках `inspect`; постоянный кэш `file_hash` в БД не используется. Агент читает содержимое по ссылке на снимок средствами Git. Последующие изменения рабочей копии могут вызвать конфликт при применении подготовленной правки согласно проверкам `base_hash`.

Для чтения используется общий механизм служебных Git-снимков без создания коммита. `snapshot` содержит полный OID объекта Git tree. Агент читает файл по форме `<tree_oid>:<path>`. Создание и повторное использование снимка ещё проектируются. В первой версии выданные и используемые снимки удерживаются бессрочно средствами Git.

## Внешние вершины и ссылки на источники

Согласовано: файловые источники знаний тоже представлены в графе обычными вершинами. Ссылка знания на такой источник образует направленное ребро. Файл источника остаётся вне размеченного корпуса знаний; добавление вершины не означает необходимость размечать или переписывать исходный код. Отдельный массив `sources` в JSON-метаданных элемента не вводится. Адрес файла и диапазон строк находятся в самой Markdown-ссылке.

«Внешний» здесь означает источник вне корпуса знаний; это может быть файл `src/storage.go` внутри корня того же репозитория. Адресация источников за пределами локального репозитория ещё уточняется.

Текущее подтверждённое основание знания хранится в source_snapshot его канонического Markdown и проекции nodes. Актуальные хеши источников находятся в nodes. История подтверждений читается по известным Git-снимкам без отдельного учёта в БД. Там же хранятся граф, его структура, embeddings, локи, идентификаторы и другое согласованное служебное состояние. Текст документов и источников в БД не копируется; необходимое прежнее содержимое остаётся в Git-снимках. По направлению пользователя БД размещается в скрытой служебной директории проекта; `.letopis/` — предлагаемое имя, движком единой служебной БД выбран SQLite, точные файлы и параметры хранения ещё выбираются.

Реиндексирование не заменяет проверенное состояние актуальным содержимым автоматически. Служебное состояние происхождения не восстанавливается из одних текущих ссылок; его сохранность требуется отдельно от пересоздания поисковых проекций. Первоначальная привязка сохраняется при добавлении нового `external`, явная перепроверка подтверждается операцией `edit` с необязательным `snapshot` в `apply`. Регистрация и восстановление стабильных ID внешних вершин и детали снимков ещё проектируются.

### Тип внешней ссылки и границы внешней вершины

Следующие два решения согласованы.

1. Для ссылки на внешний источник используется системный тип ребра `external` и существующий формат `title`: `[код](src/storage.go#L10-L25 "letopis:id=ID;type=external;created_at=SECONDS")`. Путь задаётся от корня репозитория, диапазон — в адресе ссылки. Тип `external` указывает, что назначение разрешается как внешний источник, а не как размеченный элемент корпуса со стабильным ID в адресе. letopis сам регистрирует обычную внешнюю вершину и выдаёт ей постоянный ID. Код не размечается. ID самого ребра по-прежнему задаётся временным ID и заменяется letopis при создании. Это новое исключение из адресации внутренних графовых ссылок по ID цели; дополнительного поля `target_id` в ссылке не предлагается. Мотивация: один формат Markdown-ссылок обслуживает внутренние рёбра, включённость и внешние источники, без новой JSON-схемы создания источника.

Вход `letopis apply`; файл знания новый:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/storage.md",
      "markdown": "<!-- letopis: {\"id\":\"tmp:000\",\"kind\":\"vertex\",\"source_snapshot\":\"<Git tree OID источников>\"} -->\nОписание основано на [коде](src/storage.go#L10-L25 \"letopis:id=tmp:001;type=external\").\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>",
    "ids": {
      "tmp:000": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "tmp:001": "064f2964-77cc-41f0-87ac-d280c0ec59a7"
    }
  }
}
```

Карта `ids` сопоставляет переданные агентом временные ID постоянным. ID автоматически зарегистрированной внешней вершины можно получить при обходе графа. Конкретная регистрация внешней идентичности ещё проектируется; отдельной команды создания такой вершины не предлагается.

2. Внешняя вершина представляет адресованный источник: файл целиком либо конкретный фрагмент. Для локальных источников один и тот же нормализованный путь и диапазон обозначают одну общую внешнюю вершину независимо от числа ссылающихся знаний. Разные диапазоны одного файла обозначают разные вершины; отсутствие диапазона обозначает файл целиком. Проверенная ревизия не является частью идентичности вершины и сохраняется в привязке конкретного знания, поскольку разные знания могут быть проверены по разным состояниям одного источника. ID внешних вершин генерирует только letopis. Мотивация: обход сразу возвращает точный фрагмент в существующем формате ссылок; не нужны новые поля диапазона в результате ребра. Область неперекрытия канонических описаний относится к размеченным элементам корпуса, а не к адресуемым фрагментам внешнего источника.

Исходное знание имеет две ссылки `external`: на строки 10–25 и 40–60 файла `src/storage.go`. Вход `letopis traverse` после готовности индекса:

```json
{
  "element_ids": [
    "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c"
  ],
  "mode": "relations",
  "direction": "outgoing",
  "edge_types": [
    "external"
  ],
  "depth": 1,
  "limit": 5
}
```

Пример выхода:

```json
{
  "ok": true,
  "result": {
    "elements": [
      {
        "element_id": "521eb6f0-bd63-4d44-9aaf-c2d9be2bb5e4",
        "path": "src/storage.go",
        "lines": [
          10,
          25
        ],
        "revision": "<снимок индексирования источника>",
        "flags": []
      },
      {
        "element_id": "15d9fca9-3997-464d-86f0-5e8c9ad76c21",
        "path": "src/storage.go",
        "lines": [
          40,
          60
        ],
        "revision": "<снимок индексирования источника>",
        "flags": []
      }
    ]
  }
}
```

Согласованный формат ссылок обхода распространяется на внешние вершины: `path` указывает файл источника, а `revision` — снимок его проиндексированного состояния. При заданном диапазоне `lines` содержит обе границы; для источника, адресованного как файл целиком, `lines` опускается. В ссылках используется общий массив `flags`. Доступная внешняя вершина получает `stale`, если её фрагмент отличается от проиндексированного; причины перепроверки относятся к знаниям, связанным с источником. В примере адресованный источник актуален и список флагов пуст. Недоступная внешняя вершина остаётся в графе и возвращается в обходе с `source_not_found`; до публикации состояния отсутствия также возвращается `stale`. В первой версии внешние вершины доступны через `inspect` и `traverse`, без собственного текстового или векторного индексирования. `apply` не изменяет внешние файлы; перенос внешнего адреса ещё уточняется. После удаления всех графовых ссылок источник исключается из следующей проекции, но его соответствие адреса и диапазона UUID и история сохраняются бессрочно; повторная ссылка использует прежний ID.

## Доступ к внешним источникам и область поиска

Следующие два решения согласованы.

1. В первой версии внешние вершины доступны для чтения метаданных через `inspect` и для обхода через `traverse`; операции `edit` и `delete` в `apply` разрешены только для размеченных элементов корпуса знаний. Чтобы убрать или изменить связь с источником, агент редактирует Markdown знания. Сам код или иной внешний документ изменяется его обычными средствами редактирования; letopis обнаруживает изменения и проверяет актуальность привязок. Это граница возможностей редактора знаний, а не разграничение прав между агентами. Мотивация: один контракт замены размеченного Markdown не распространяется на произвольные файлы кода, форматы которых letopis не редактирует; агент использует привычные инструменты для исходного кода.

Вход `letopis apply`; ID принадлежит зарегистрированной внешней вершине:

```json
{
  "operations": [
    {
      "type": "delete",
      "element_id": "521eb6f0-bd63-4d44-9aaf-c2d9be2bb5e4",
      "base_hash": "<хеш внешнего фрагмента>"
    }
  ]
}
```

Выход; правка целиком отклонена:

```json
{
  "ok": false,
  "error": {
    "code": "invalid_request",
    "message": "Внешняя вершина не изменяется через apply",
    "details": {
      "field": "operations[0].element_id"
    }
  }
}
```

Удаление внешнего файла этим запросом не выполняется. Правила сохранения записей о внешней идентичности после удаления последней входящей ссылки, а также переименования источника ещё уточняются.

2. В первой версии `search` возвращает только размеченные вершины и метавершины корпуса знаний. Внешние вершины присутствуют в графе и доступны через `traverse` и `inspect`, но их собственное содержимое не участвует в текстовом и векторном поиске; embeddings для них автоматически не вычисляются. Графовые отношения с внешними вершинами сохраняются, а фильтры происхождения работают для знаний, ссылающихся на источники. Нового параметра области поиска не вводится. Мотивация: меньше вычисляемых embeddings и объём индекса при ограниченной памяти; агент получает знания через гибридный поиск и переходит к источникам по графу.

В графе есть знание `knowledge/storage.md` и его внешний источник `src/storage.go#L10-L25`. Вход `letopis search`:

```json
{
  "query": "Поведение хранилища",
  "limit": 5
}
```

Пример выхода:

```json
{
  "ok": true,
  "result": [
    {
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "path": "knowledge/storage.md",
      "lines": [
        1,
        3
      ],
      "revision": "<снимок индекса>",
      "flags": []
    }
  ]
}
```

Сам внешний фрагмент не возвращается как отдельный поисковый результат. Его ссылка доступна при обходе external. Граф и FTS доступны после проверки без ожидания всех embeddings; отсутствие актуальных векторов допускает поиск через FTS. Поисковая область согласована; показатели памяти и времени ответа требуют измерений.

## Первоначальная фиксация источника

Первоначальная фиксация нового источника согласована. Последующая явная перепроверка подтверждается через `edit` с необязательным `snapshot`; контракт приведён ниже.

1. При успешном создании знания с external-ссылками letopis использует общий source_snapshot из JSON-метаданных его Markdown. Агент заранее получает Git tree OID источников и читает их по этому снимку. letopis проверяет существование объекта и тип tree до записи, а также доступность адресованных файлов и фрагментов по правилам новой привязки. Без диапазона адресуется весь файл. Общее основание сохраняется в каноническом знании и nodes в одной границе с графом, FTS и заданиями на embeddings; разные знания могут иметь разные основания для одного общего source. Смысловую обоснованность обеспечивает агент. Обычное редактирование с сохранением внешнего назначения и без snapshot не заменяет подтверждённую основу. Если источник или диапазон недоступны для новой привязки, вся правка отклоняется с validation_failed. Мотивация: отставание embeddings не меняет основание знания, а канонический Markdown сохраняет ссылку на проверяемое содержимое.

Вход `letopis apply`; файл знания новый, источник доступен:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/storage.md",
      "markdown": "<!-- letopis: {\"id\":\"tmp:000\",\"kind\":\"vertex\",\"source_snapshot\":\"<Git tree OID источников>\"} -->\nОписание основано на [коде](src/storage.go#L10-L25 \"letopis:id=tmp:001;type=external\").\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>",
    "ids": {
      "tmp:000": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "tmp:001": "064f2964-77cc-41f0-87ac-d280c0ec59a7"
    }
  }
}
```

letopis сохраняет общее основание в source_snapshot канонического знания и проекции nodes вместе с успешной операцией; отдельные поля источника в ответе не вводятся. Хеш содержимого правки по-прежнему вычисляется по исходному JSON; по нему не извлекается бессрочный результат завершённого вызова.

## Недоступный источник при создании и редактировании

Следующие два решения согласованы.

1. Новое ребро `external` или переназначение существующего ребра на другой внешний адрес допускается, только если источник и указанный фрагмент доступны для фиксации исходного состояния. Отсутствующий файл или неадресуемый диапазон вызывает `validation_failed` и отклонение всей правки. Проверка относится к новой привязке знания, даже если внешняя вершина ранее уже регистрировалась для других знаний. Мотивация: новая привязка получает реальную ревизию и хеш источника, а агент сразу видит неверный путь или диапазон. Повтор после устранения внешней причины разрешён, если прежняя попытка не оставила изменений либо полностью откатилась, как описано ниже.

Вход `letopis apply`; файл знания новый. Указанный Git tree существует и содержит src/missing.go со строками 10–25, но src/missing.go сейчас отсутствует в рабочей копии:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/new.md",
      "markdown": "<!-- letopis: {\"id\":\"tmp:000\",\"kind\":\"vertex\",\"source_snapshot\":\"<Git tree OID источников>\"} -->\nОсновано на [коде](src/missing.go#L10-L25 \"letopis:id=tmp:001;type=external\").\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход; файл знания не создаётся:

```json
{
  "ok": false,
  "error": {
    "code": "validation_failed",
    "message": "Невозможно зафиксировать источник: файл не найден",
    "details": {
      "path": "src/missing.go"
    }
  }
}
```

2. Обычный `edit` существующего знания допускается, даже если его прежний источник изменился или исчез. Для сохранённых рёбер `external` с теми же ID и назначениями letopis сохраняет прежние подтверждённые привязки и историю. Редактирование без `snapshot` не подтверждает перепроверку; пометка необходимости перепроверки сохраняется по текущему состоянию источника. Все обычные проверки хеша знания и целостности графа продолжают действовать. Исчезновение внешнего файла не удаляет автоматически его зарегистрированную вершину и не превращает сохранённое ребро в ссылку на отсутствующий ID. Мотивация: агент может уточнять знание, фиксировать обнаруженную проблему или исправлять связи при недоступном источнике, без автоматического подтверждения нового состояния.

Вход `letopis apply`; источник существовал при сохранении исходной привязки, но теперь `src/storage.go` отсутствует. ID и назначение сохранённого ребра не меняются:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш исходного знания>",
      "markdown": "<!-- letopis: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"vertex\"} -->\nУточнённое описание поведения хранилища.\n[Исходный код](src/storage.go#L10-L25 \"letopis:id=064f2964-77cc-41f0-87ac-d280c0ec59a7;type=external\").\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

При последующем поиске знание по-прежнему имеет `source_not_found` в `flags`, пока причина не устранена. Это не добавляет новых полей успешного ответа `apply`. Если правка добавляет другую привязку, к ней применяется проверка нового источника из первого решения. Корректный индекс может публиковаться с сохранёнными недоступными внешними источниками; их отсутствие само по себе не нарушает целостность графа. Для `inspect` согласованы недоступные хеши со значением `null`.

## Повтор неуспешной правки

Повтор полностью откатанной неуспешной правки согласован.

1. После потери ответа агент перечитывает состояние. После неуспешной попытки без изменений или полного отката он может подготовить новый вызов, в том числе с тем же JSON, если его предпосылки актуальны. Каждый новый вызов заново проверяет хеши, snapshot и целостность. При неопределённом исходе сначала завершается восстановление; уже надёжно завершённая правка не откатывается. Прежние ошибки сохраняются по правилам диагностики. Бессрочного возврата исходного успеха нет. Мотивация: используются существующие чтение и контроль конфликтов; не нужны внешний ID попытки, timestamp или регистрация повтора. Автоматический ретрай правок этим решением не вводится.

Ранее такой же запрос получил validation_failed, поскольку src/missing.go отсутствовал в рабочей копии. Указанный в запросе Git tree всё время содержал этот источник. Файл теперь восстановлен из того же снимка и содержит строки 10–25 с теми же байтами; файл знания ещё отсутствует. Вход letopis apply — прежний JSON:

```json
{
  "operations": [
    {
      "type": "create",
      "path": "knowledge/new.md",
      "markdown": "<!-- letopis: {\"id\":\"tmp:000\",\"kind\":\"vertex\",\"source_snapshot\":\"<Git tree OID источников>\"} -->\nОсновано на [коде](src/missing.go#L10-L25 \"letopis:id=tmp:001;type=external\").\n<!-- /letopis -->\n"
    }
  ]
}
```

Пример успешного выхода новой попытки:

```json
{
  "ok": true,
  "result": {
    "hash": "<тот же хеш исходного JSON>",
    "ids": {
      "tmp:000": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "tmp:001": "064f2964-77cc-41f0-87ac-d280c0ec59a7"
    }
  }
}
```

После этого новый идентичный create заново проверяет исходные условия и при занятом пути без base_hash возвращает conflict. Агент читает созданный файл и узнаёт постоянные ID. Хеш одинакового исходного JSON остаётся прежним, но не обозначает одну бессрочно дедуплицируемую операцию. Внутренние записи выполнения и их срок хранения ещё проектируются.

## Перепроверка через edit

Согласовано: набор операций остаётся `create`, `edit`, `delete`. Для явного подтверждения перепроверки в `edit` используется необязательный `snapshot`.

Поле `snapshot` входит в исходный JSON-запрос и его JCS-хеш. Без `snapshot` редактирование сохраняет прежние подтверждённые состояния источников. Наличие `snapshot` означает явное утверждение агента, что подготовленное знание проверено по источникам этого снимка. letopis проверяет `base_hash` исходного знания и совпадение текущих источников с адресованным состоянием в снимке. Изменение знания или любого источника отклоняет всю правку с `conflict`. При успехе Markdown и подтверждённые привязки обновляются атомарно, прежние подтверждения остаются в истории. Подтверждаются все ссылки `external` в подготовленном конечном фрагменте; их источники должны быть доступны в указанном снимке. Если текст знания остался верным, агент передаёт тот же полный фрагмент. Поле `markdown` остаётся обязательным.

Мотивация: меньше типов операций и одна атомарная запись. Компромисс: полный Markdown повторно передаётся даже при неизменившемся тексте. Снимок нужен для адресации действительно проверенной версии и участия её в хеше запроса; обычное редактирование без этого намерения не снимает пометку перепроверки. Автоматическое обновление проверенной основы при любом `edit` не предлагается.

Вход `letopis apply`; текст знания после смысловой проверки остался прежним:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш знания>",
      "markdown": "<!-- letopis: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"vertex\"} -->\nОписание поведения хранилища.\n[Исходный код](src/storage.go#L10-L25 \"letopis:id=064f2964-77cc-41f0-87ac-d280c0ec59a7;type=external\").\n<!-- /letopis -->\n",
      "snapshot": "<снимок перепроверенных источников>"
    }
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

Каждый новый самостоятельный вызов проходит проверки актуального состояния и snapshot. Снимок входит в хеш содержимого правки, но совпадение хеша не возвращает старый успешный результат. Создание и долговечная фиксация снимков ещё проектируются. Бессрочное удержание средствами Git и правило ревизии источника согласованы. Это проектируемый контракт, а не подтверждение реализации.

## Контракт search

Статус: базовые вход и выход, имя `search`, гибридный режим и ссылки вместо текста согласованы. Поля фильтров и их семантика уточняются последовательно.

### Вход

Согласованы обязательные `query` и `limit`, а также необязательный объект `filters` с полями `needs_recheck`, `sources` и `source_revisions`. Смысловые метки знаний и `filters.types` исключены по последнему уточнению пользователя.

```json
{
  "query": "Как устроено сохранение знаний?",
  "limit": 10,
  "filters": {
    "needs_recheck": true
  }
}
```

### Фильтр needs_recheck

Для состояния знания согласован необязательный булевый фильтр `filters.needs_recheck`: `true` выбирает знания, у которых `flags` содержит `source_changed` или `source_not_found`; `false` выбирает знания без обоих признаков. Отсутствие поля не ограничивает выборку. `stale` сам по себе не означает изменение источников. Значение `false` не утверждает смысловую достоверность знания. Дополнительный фильтр флагов не вводится.

```json
{
  "filters": {
    "needs_recheck": true
  }
}
```

Пример показывает только объект фильтров; обязательные `query` и `limit` остаются в полном запросе `search`.

### Фильтр sources

Для источников происхождения согласован необязательный `filters.sources` — список адресов исходных документов или файлов кода. Элемент подходит, если хотя бы одна его текущая привязка происхождения относится к указанному источнику. Для привязки к фрагменту проверяется адрес его исходного документа. Исторические привязки не используются как текущие зависимости.

```json
{
  "filters": {
    "sources": ["src/storage.go", "docs/architecture.md"]
  }
}
```

Согласованы точное совпадение адресов источников и правило «хотя бы один источник». При отсутствии поля фильтр не ограничивает источники. Фильтр касается текущих привязок происхождения знания.

### Фильтр source_revisions

Согласовано новое назначение фильтра: сопоставление содержимого источников знания с указанными Git-ревизиями. Это заменяет прежнее точное сравнение сохранённого OID ревизии. Поле revision поисковой ссылки по-прежнему обозначает проиндексированное состояние документов знаний.

filters.source_revisions остаётся необязательным списком Git-ревизий: OID коммитов либо tree для незакоммиченного состояния. Для текущей привязки знания к источнику letopis читает по одному адресу содержимое из source_snapshot знания и из запрошенной ревизии. Для ссылки с диапазоном сравниваются точные байты этого диапазона, для ссылки на файл целиком — весь файл. Фильтр выполнен, если содержимое совпало хотя бы для одной запрошенной ревизии и одной текущей привязки.

При совместном filters.sources адрес и проверка содержимого должны относиться к одной привязке. Отсутствующий либо пустой список не ограничивает поиск. Отдельный OID исходного коммита для происхождения знания не сохраняется. Текст источников остаётся в Git, БД хранит адреса, хеши, структуру графа и source_snapshot знания; постоянный кэш подтверждённых хешей этим решением не вводится.

```json
{
  "filters": {
    "sources": [
      "src/storage.go"
    ],
    "source_revisions": [
      "<коммит исходного кода>"
    ]
  }
}
```

Пример: знание создано по содержимому src/storage.go в C1, затем C2 меняет только README. Поиск с source_revisions C2 возвращает знание, поскольку адресованный источник совпадает с сохранённым основанием. Равенство полных деревьев не требуется; изменение за пределами адресованного диапазона не мешает совпадению. Для полного search сохраняются обязательные query и limit, формат результата не меняется.

Проверка актуальности относительно рабочей копии и вычисление flags остаются отдельными: совпадение с C2 само по себе не подтверждает перепроверку знания по текущему коду. Для отсутствующей явно запрошенной Git-ревизии согласован not_found всего поиска; правило и пример приведены ниже. Отсутствие файла или диапазона в существующей запрошенной ревизии означает несовпадение пары источника и ревизии; правило приведено ниже. Сбои чтения необходимых Git-объектов ещё требуют уточнения.

### Недоступная ревизия в source_revisions

Согласовано: если хотя бы один синтаксически допустимый OID из filters.source_revisions отсутствует в Git текущего проекта, весь search возвращает not_found. Наличие других доступных ревизий или совпадающих знаний не превращает такой запрос в успешный. error.details.revision содержит отсутствующий OID. Доступность явно запрошенных ревизий проверяется независимо от наличия кандидатов поиска; частичный результат либо успешный пустой результат вместо этой ошибки не возвращается.

Вход letopis search; первый OID существует, второй отсутствует:

```json
{
  "query": "срок действия сессии",
  "limit": 5,
  "filters": {
    "source_revisions": [
      "<существующий OID>",
      "<отсутствующий OID>"
    ]
  }
}
```

Выход:

```json
{
  "ok": false,
  "error": {
    "code": "not_found",
    "message": "Git-ревизия не найдена",
    "details": {
      "revision": "<отсутствующий OID>"
    }
  }
}
```

Мотивация: агент отличает ошибку выбора или доступности ревизии от отсутствия подходящих знаний и может исправить запрос либо получить необходимые Git-объекты. Используются прежний формат ошибки и код завершения 1. Для отсутствия файла или диапазона внутри существующей запрошенной ревизии применяется правило несовпадения ниже. Детали сбоев чтения необходимых Git-объектов уточняются отдельно.

### Источник отсутствует в существующей запрошенной ревизии

Согласовано: если запрошенная Git-ревизия существует, но адресованного файла или полного указанного диапазона строк в ней нет, эта пара «текущая привязка источника — запрошенная ревизия» не совпадает с фильтром source_revisions. Это не ошибка всего поиска. Другие привязки и ревизии продолжают проверяться по прежнему правилу «хотя бы одно»; при filters.sources адрес и сравнение по ревизии относятся к одной привязке.

Вход letopis search; C2 существует, но src/auth.rs появился позже:

```json
{
  "query": "срок действия сессии",
  "limit": 5,
  "filters": {
    "sources": [
      "src/auth.rs"
    ],
    "source_revisions": [
      "<C2>"
    ]
  }
}
```

Выход при отсутствии других совпадений:

```json
{
  "ok": true,
  "result": []
}
```

То же правило действует, если файл существует, но адресованный диапазон строк в нём отсутствует. Сравнение не подменяется чтением укороченного диапазона. Существование самой запрошенной ревизии по-прежнему обязательно: отсутствие её OID даёт not_found всего запроса.

Мотивация: отсутствие источника в более раннем или другом состоянии репозитория является нормальным результатом фильтрации. Правило касается содержимого существующей запрошенной ревизии; ошибки исполнения Git и повреждение объектов не считаются обычным несовпадением. Детали поведения при невозможности прочитать необходимые Git-объекты, включая сохранённое основание знания, ещё уточняются.

### Сочетание фильтров

Согласовано объединение всех заданных полей `filters` по правилу И: элемент должен удовлетворять каждому из них. Внутри списков `sources` и `source_revisions` действует правило «хотя бы одно». Адрес источника и его ревизия при совместном указании проверяются в одной привязке. Например, `sources: ["src/storage.go"]` вместе с `needs_recheck: true` выберет знания из указанного источника, требующие перепроверки. Дополнительный параметр режима сочетания не нужен.

### Выход

Согласован массив ссылок в порядке релевантности:

```json
{
  "ok": true,
  "result": [
    {
      "element_id": "node-a",
      "path": "knowledge/design.md",
      "lines": [
        10,
        25
      ],
      "revision": "<ревизия, по которой построен индекс>",
      "flags": []
    }
  ]
}
```

`path` ведёт к текущему каноническому документу, а `lines` и `revision` относятся к проиндексированной версии. Обязательный массив `flags` передаёт признаки актуальности и причины перепроверки, описанные ниже. Признаки могут сочетаться; при отсутствии обнаруженных проблем возвращается `flags: []`. При отсутствии совпадений возвращается `ok: true` и пустой массив `result`.

### Признаки актуальности

Вход `search` сохраняется. Согласован единый обязательный массив `flags` вместо отдельных булевых полей и списка причин. `stale` означает изменение самого адресованного элемента после индексации; `source_changed` — изменение хотя бы одного источника знания относительно подтверждённого состояния; `source_not_found` — недоступность хотя бы одного источника или его фрагмента. Список не содержит повторов и позволяет передать несколько признаков одновременно. Пустой список означает отсутствие обнаруженных причин, а не доказанную истинность знания. Пример фрагмента поискового результата:

```json
{
  "flags": [
    "source_changed",
    "source_not_found"
  ]
}
```

Имя поля, списковая форма и значения причин согласованы. Для агента причина определяет следующий шаг: сравнить изменившийся источник с сохранённым знанием либо найти отсутствующий источник и уточнить привязку. Такая диагностика направляет перепроверку на конкретную проблему.

Поиск выполняется на одной транзакции чтения SQLite до завершения запроса. Он использует FTS и доступные актуальные embeddings; отсутствие векторов не блокирует FTS. Удалённые элементы исключаются; знания, требующие перепроверки, остаются с пометкой. Если корректных графа и FTS ещё нет, CLI автоматически строит их и ждёт проверки и публикации, но не всех embeddings. Текст документов и выдержки в ответ не включаются. Детальное объединение результатов при неполном векторном покрытии ещё проектируется; внешний контракт search не меняется.

## Контракт traverse

Статус: базовые структуры входа и выхода `traverse` согласованы. Приняты три режима — `relations`, `containment` и `both`, состав возвращаемых элементов и рёбер, управление направлением, типами связей, глубиной и отдельными лимитами. Подробные правила проверки значений ещё будут уточнены.

`relations` выполняет обход обычных связей; глубина считает пройденные рёбра без `includes`. `containment` выполняет обход включённости через `includes`; глубина считает уровни включённости. Один переход по `includes` соответствует одному уровню. Эти режимы не смешивают обычные связи с включённостью.

Согласован третий режим `both`: единый обход по обычным связям и `includes`, с возможностью чередовать их в одном пути. Сохраняется один `depth`: каждый переход по любому из этих рёбер считается одним шагом. Например, путь `M —includes→ A —depends_on→ B` достигает `B` при глубине 2.

Во входе меняется только значение `mode`; новые поля не требуются. `direction` задаёт направление обхода, а `edge_types` ограничивает обычные связи; `includes` в режиме `both` разрешён независимо от этого фильтра. `mode: both` объединяет виды связей, тогда как `direction: both` разрешает идти по исходящим и входящим рёбрам. Выход имеет общий формат `elements` и опционального `edges` с пройденными рёбрами. Такой режим позволяет агенту одним запросом получить вложенные знания и связанный с ними контекст без объединения нескольких ответов вручную.

### Вход

Список `element_ids` задаёт начальные вершины или метавершины. Для одного начального элемента передаётся список из одного ID. Поле `mode` выбирает режим: `relations`, `containment` или `both`. `direction` принимает `outgoing`, `incoming` или `both`: для включённости это переход к содержимому, к содержащим метавершинам или в обе стороны. `edge_types` применяется к обычным связям в `relations` и `both`; отсутствие поля означает все обычные типы. Для `containment` тип проходимых рёбер уже определён режимом — `includes`. `depth` имеет согласованный смысл для выбранного режима; `limit` ограничивает вершины и метавершины вместе. При заданном положительном `edge_limit` возвращаются также рёбра в пределах отдельного лимита. Дополнительный переключатель возврата рёбер не требуется.

`element_ids`, `mode`, `direction`, `depth` и `limit` обязательны; `edge_types` и `edge_limit` необязательны. Вход и выход согласованы как одна базовая структура; подробные правила проверки значений ещё будут уточнены.

```json
{
  "element_ids": ["node-a"],
  "mode": "both",
  "direction": "outgoing",
  "edge_types": ["depends_on"],
  "depth": 2,
  "limit": 10,
  "edge_limit": 20
}
```

### Выход

Объект `result` содержит массив ссылок `elements` в том же формате, что `search`. Если запрошены рёбра, добавляется массив `edges` с ID, типом и концами связи.

```json
{
  "ok": true,
  "result": {
    "elements": [
      {
        "element_id": "node-b",
        "path": "knowledge/design.md",
        "lines": [
          27,
          40
        ],
        "revision": "<проиндексированная ревизия>",
        "flags": []
      }
    ],
    "edges": [
      {
        "element_id": "edge-a",
        "type": "depends_on",
        "source": "node-a",
        "target": "node-b"
      }
    ]
  }
}
```

Согласовано не повторять начальные `element_ids` в `elements`: возвращаются ссылки только на найденные при обходе элементы, с общим лимитом `limit` для вершин и метавершин. Повторно достигнутые элементы возвращаются один раз. Для агента такой результат сохраняет лимит для дополнительного контекста и сокращает повторение уже известных исходных элементов. Согласовано опускать поле `edges` при отсутствии `edge_limit`; при заданном положительном `edge_limit` возвращается `edges` в пределах этого лимита, включая пустой массив при отсутствии пройденных рёбер. Поле `edge_limit` одновременно запрашивает рёбра и ограничивает их число, поэтому отдельный переключатель возврата не требуется. Каждая ссылка содержит согласованный массив `flags`. Обход выполняется на одной опубликованной версии индекса; направление обхода не меняет направление самих рёбер.

Согласовано единое правило выхода: в `edges` возвращаются только фактически пройденные рёбра с учётом отдельного лимита. В `relations` это обычные связи, в `containment` — `includes`, в `both` — оба вида. Для получения обычных связей внутри раскрываемого контекста агент выбирает `both`. Доменное определение внутренних рёбер метавершины по непосредственному вхождению обоих концов сохраняется.

### Польза для агента

Режим явно выражает цель агента: найти связанные знания, раскрыть включённые элементы или совместить оба обхода. Один параметр глубины сохраняет простой запрос. Список ID совпадает по форме с `inspect`, а лимиты помогают контролировать объём последующего чтения. Опциональные рёбра объясняют, как знания связаны между собой. Формат ссылок совпадает с `search`, поэтому агент использует один способ обработки найденных знаний. Базовые структуры входа и выхода согласованы.

## Контракт reindex

Статус: согласованы вход, выход и ожидание завершения явного вызова `reindex`. Доступны полная и выборочная перестройка.

### Вход

Вход — один JSON-объект. Без селекторов выполняется полная перестройка:

```json
{}
```

Для выборочного реиндексирования задаются пути файлов:

```json
{
  "paths": ["knowledge/design.md"]
}
```

Либо ID элементов:

```json
{
  "element_ids": ["node-a", "node-b"]
}
```

При совместном указании `paths` и `element_ids` обновляется объединение выбранных файлов и элементов. Если уже выполняющееся задание использует тот же Git-снимок и покрывает всю запрошенную область, вызов ждёт его результата вместо повторной перестройки. Отдельное поле выбора полного режима не требуется. Индексирование читает согласованный служебный Git-снимок корпуса; выборочный режим сохраняет обязательную проверку целостности всего метаграфа перед публикацией.

#### Пустые селекторы

Согласовано считать пустой список `paths` или `element_ids` равнозначным отсутствию этого селектора. Если после этого непустых селекторов не осталось, выполняется полная перестройка. Если один список непустой, он задаёт выборку. Новые поля и команды не требуются.

Вход `letopis reindex`, равнозначный `{}`:

```json
{
  "paths": [],
  "element_ids": []
}
```

Выход после завершения полной перестройки:

```json
{
  "ok": true,
  "result": {
    "revision": "<ревизия опубликованного индекса>"
  }
}
```

Агент передаёт автоматически собранные списки с единым правилом пустых значений; оба пустых списка означают полный режим. Это правило согласовано.

### Выход

Явный `reindex` ожидает успешной публикации версии, построенной по полученному снимку, и возвращает её ревизию:

```json
{
  "ok": true,
  "result": {
    "revision": "<ревизия опубликованного индекса>"
  }
}
```

Этот результат означает завершение перестройки по её снимку; новые завершённые правки учитываются следующим обновлением по ранее согласованному правилу. При ошибке возвращается общий JSON-формат ошибки, последняя корректная версия сохраняется. Отмена также сохраняет последний корректный индекс; используются согласованные `SIGINT` и `reindex --cancel`. Правки apply публикуют граф/FTS синхронно по [D-7](../../decisions.md#D-7); обнаруженные внешние изменения проходят проверку и согласованную публикацию. В фоне вычисляются embeddings. Отдельный внешний ID задания не требуется.

### Польза для агента

Явный вызов возвращает готовый результат, поэтому агент может продолжить работу без дополнительных запросов состояния для ожидания этой перестройки. Файлы и ID уже известны агенту из результатов поиска и `inspect`; отдельная подготовительная команда не нужна. Базовые структуры входа и выхода согласованы.

Уточнение хранения: одна строка embedding_jobs относится к одному элементу и ограничена UNIQUE(node_id). По [D-71](../../decisions.md#D-71) reindex ждёт публикацию графа/FTS и постановку необходимых поэлементных заданий, но не их вычисление. Замена заданий и проверка seq относятся к фоновой работе; группа не превращается в отдельную строку очереди.

## Контракт status

Статус: согласованы вход `{}` и выход с полями `revision`, `reindex`, `embedding_jobs`, `locks`, `errors`. При отсутствии опубликованного индекса `revision` равен `null`, при отсутствии задания `reindex` равен `null`; отсутствие локов и ошибок представляется пустыми списками. Также согласованы поле `completed` в процентах текущего этапа, запись лока с `hash`, `paths`, `element_ids`, общий формат записей ошибок и их сохранение до устранения соответствующей проблемы, включая перезапуски. Набор этапов и представление неизвестного процента ещё уточняются. Согласовано поле embedding_jobs и правило подсчёта активных заданий, приведённое ниже.

### Вход

Согласован `letopis status` с пустым JSON-объектом через стандартный ввод:

```json
{}
```

### Выход

Согласован общий JSON-ответ со сводным состоянием проекта:

```json
{
  "ok": true,
  "result": {
    "revision": "<ревизия опубликованного индекса>",
    "reindex": {
      "stage": "graph",
      "completed": 60
    },
    "embedding_jobs": 1,
    "locks": [
      {
        "hash": "<хеш правки>",
        "paths": ["knowledge/design.md"],
        "element_ids": ["node-a"]
      }
    ],
    "errors": []
  }
}
```

`revision` обозначает последнюю опубликованную версию, как в результате `reindex`; при отсутствии готового индекса значение равно `null`. `reindex` описывает текущее задание; если оно отсутствует, значение равно `null`. `stage` обозначает текущий этап. Согласовано возвращать `completed` как процент выполнения текущего этапа от 0 до 100, без отдельного поля `total`. Например, `completed: 60` означает выполнение 60% этапа `graph`. Если процент определить нельзя, предлагается `completed: null`. При переходе к следующему этапу процент относится уже к нему. Набор этапов ещё уточняется.

`locks` и `errors` — списки сведений о текущих локах и диагностике; пустой список означает отсутствие соответствующих записей. Ошибки фонового индексирования передаются в `result.errors` при успешном получении состояния, не превращая сам запрос состояния в ошибку. Ошибка выполнения `status` использует общий формат `ok: false` и `error`. Общий формат записей ошибок и правила удержания диагностики согласованы ниже; новые внешние ID заданий не требуются.

Для одной записи `locks` согласованы `hash` — уже введённый хеш правки, владеющей локом, `paths` — файлы, охваченные локом, и `element_ids` — соответствующие элементы. Запись отражает действующую служебную координацию сохранения или восстановления; механизм реализации локов ещё выбирается. Основанием обнаружения конфликта остаётся сверка `base_hash` с текущим состоянием. Агент подготавливает правку оптимистично, а защищённая фаза сохранения остаётся короткой. Новые внешние идентификаторы и параметры агента для этой структуры не требуются. Такой формат показывает область занятости и связывает её с уже существующим идентификатором правки.

Согласованы два решения:

1. Запись в `errors` использует общий формат `code`, `message`, `details`, уже введённый для ошибок команд. Детали содержат адреса проблемных элементов и файлов, когда они известны. Агент использует одну обработку диагностики для ответа команды и сводки состояния.
2. В `errors` сохраняются текущие неустранённые ошибки подсистем, включая неудачное индексирование или восстановление. Чтение `status` и перезапуск процесса их не сбрасывают. Запись снимается только после успешного выполнения работы, устраняющей соответствующую проблему; успешное действие другой подсистемы её не снимает. Это позволяет агенту получить диагностику, даже если ошибка возникла между его вызовами. Сообщения о завершённых неуспешных правках сохраняются отдельно от записи восстановления до явной очистки через letopis errors --clear. Бессрочный кэш успешных ответов не вводится.

Пример входа `letopis status`:

```json
{}
```

Пример выхода после неудачной перестройки с согласованным кодом `embedding_failed`:

```json
{
  "ok": true,
  "result": {
    "revision": "<ревизия последнего корректного индекса>",
    "reindex": null,
    "embedding_jobs": 0,
    "locks": [],
    "errors": [
      {
        "code": "embedding_failed",
        "message": "Не удалось вычислить embedding для node-a",
        "details": {
          "element_ids": ["node-a"]
        }
      }
    ]
  }
}
```

Оба решения и общий каталог кодов ошибок согласованы.

### Польза для агента

Один запрос даёт сведения для решения, доступен ли индекс, идёт ли обновление и нужна ли реакция на локи или ошибки. Формат ревизии совпадает с `reindex`. Процент в `completed` позволяет агенту читать прогресс без вычисления отношения двух счётчиков; `stage` показывает, к какой работе он относится. Базовые вход и выход согласованы; набор этапов и представление неизвестного процента уточняются отдельно.

### Согласовано: число заданий на embeddings в status

Статус: поле embedding_jobs и правило подсчёта согласованы пользователем. Одно поле result.embedding_jobs содержит число заданий, ожидающих выполнения, выполняющихся или ожидающих очередного разрешённого ретрая. Это число заданий, а не элементов или готовых векторов. Завершённые, отменённые и исчерпавшие ретраи задания в него не входят; неустранённые ошибки сохраняются в errors.

Вход letopis status:

```json
{}
```

Согласованный выход:

```json
{
  "ok": true,
  "result": {
    "revision": "<Git tree OID опубликованных графа и FTS>",
    "reindex": null,
    "embedding_jobs": 3,
    "locks": [],
    "errors": []
  }
}
```

Мотивация: агент видит объём оставшейся фоновой работы без списка заданий, новых публичных ID или отдельной команды. Нулевое значение означает отсутствие активных заданий, а не само по себе полное векторное покрытие: неустранённая ошибка отражается в errors.

### Неприменённые правки в состоянии

Согласованная граница применения: после надёжного сохранения группы файлов финальная транзакция БД сохраняет необходимые служебные изменения, граф, FTS, ревизию корпуса и задания на embeddings, затем удаляет запись восстановления. Только после её надёжной фиксации apply возвращает успех; embeddings могут быть ещё не готовы. Наличие записи после сбоя означает необходимость полного отката. После полного отката запись удаляется, диагностика сохраняется независимо. Отдельное поле состояния записи не вводится. Физический аварийный протокол уточняется в [модели хранения](../../mechanics/storage-model.md).

Согласовано требование пользователя: status должен показывать, какие изменения не были применены. Информация о неприменённой атомарной правке сохраняется независимо от удаления записи восстановления. Полный откат означает, что группа не применена; незавершённое восстановление не означает уже выполненный полный откат. Ошибка обновления индекса после надёжного сохранения документов не меняет результат применения правки.

Согласованное представление: использовать существующий result.errors, без нового списка верхнего уровня. В details размещать hash и paths. Message объясняет причину и установленный исход всей группы. Код ошибки относится к фактической причине из согласованного каталога; новый код для каждого исхода здесь не вводится. До изменения канонических файлов в записи восстановления сохраняются hash, snapshot и paths. После отката сообщение использует сохранённые hash и paths и не зависит от возможности разобрать недописанный файл. Element_ids исключён из записи восстановления и диагностики отката. Хеш является отпечатком запроса, не уникальным ID каждого выполнения.

Вход status остаётся пустым объектом. Пример согласованного выхода после сбоя сохранения и успешно завершённого полного отката:

```json
{
  "ok": true,
  "result": {
    "revision": "<последний корректный индекс>",
    "reindex": null,
    "embedding_jobs": 0,
    "locks": [],
    "errors": [
      {
        "code": "internal_error",
        "message": "Правка прервана сбоем и полностью откатана; изменения не применены",
        "details": {
          "hash": "<хеш содержимого правки>",
          "paths": ["knowledge/design.md"]
        }
      }
    ]
  }
}
```

Согласовано: полный Markdown-патч в этом сообщении не возвращается и не требуется сохранять в БД ради диагностики. Формат code, message, details и поля hash, paths приняты. Физическая запись диагностики ещё проектируется. Согласовано удаление сообщений о завершённых неуспешных правках через letopis errors --clear по всему проекту, с сохранением активных ошибок. Автоматическое исчезновение ошибки только из-за успешного отката не принимается: восстановление согласованности файлов и выполнение исходного намерения агента — разные события. Чтение status и перезапуск по прежнему правилу не сбрасывают диагностику; такие сообщения снимаются явной командой letopis errors --clear после завершения неуспешной правки; активные ошибки этой командой не снимаются. Сохранённая диагностика не является кэшем исходных успешных ответов и не возобновляет бессрочную дедупликацию.

## Контракт errors

Статус: отдельная команда errors, флаг --clear и общая очистка сообщений о завершённых неуспешных правках согласованы. Status остаётся командой чтения; его result.errors и команда errors используют одни диагностические записи проекта.

### Просмотр

Команда: letopis errors. Вход через стандартный ввод:

```json
{}
```

Выход содержит список сообщений в result с уже согласованными code, message и details. Пример после завершённого полного отката:

```json
{
  "ok": true,
  "result": [
    {
      "code": "internal_error",
      "message": "Правка прервана и полностью откатана",
      "details": {
        "hash": "<хеш правки>",
        "paths": ["knowledge/design.md"]
      }
    }
  ]
}
```

### Очистка

Команда: letopis errors --clear. Вход:

```json
{}
```

Флаг очищает сохранённые сообщения о завершённых неуспешных правках по всему проекту. Хеши или новые поля JSON для выбора сообщений не передаются. Это общая очистка для всех агентов, работающих с памятью проекта. Активные ошибки подсистем, включая незавершённое восстановление и неустранённую ошибку индексирования, сохраняются до устранения соответствующей проблемы по прежним правилам. Код ошибки сам по себе не определяет, завершена ли проблема; состояние предоставляет её владелец.

После очистки result содержит оставшиеся сообщения. Пример, если активных ошибок нет:

```json
{
  "ok": true,
  "result": []
}
```

Сбой выполнения команды использует общий ответ ok: false и error. Успешный вызов возвращает один JSON в stdout и код завершения 0; ошибка исполнения — код 1. Чтение errors или status и перезапуск не очищают сообщения. Status сохраняет пустой вход и не получает clear_errors; действие задаётся только флагом отдельной команды errors.

Мотивация: агент получает весь список диагностических сообщений и может явно очистить обработанные сведения о завершённых неуспешных правках одной командой. Набор данных не дублируется, отдельный журнал ответов и адресация каждой ошибки не нужны. Физическое хранение диагностики и координация очистки с появлением новых сообщений ещё проектируются.

## Отмена

Статус: согласованы `SIGINT` для текущего вызова CLI и `letopis reindex --cancel` для текущей фоновой перестройки проекта, с сохранением последнего корректного индекса.

### 1. Прерывание выполняющегося вызова CLI

`SIGINT` в `search`, `traverse` и явном `reindex` обрабатывается как запрос отмены связанной работы через рабочий процесс. Для поиска и обхода отменяется свой запрос; для `reindex` — связанная с этим вызовом перестройка. Прерывание одного вызова не останавливает общий рабочий процесс и чужие независимые запросы. Если другие вызовы ждут ту же отменённую перестройку, они также получают исход отмены. Контракт отмены применения правки здесь не вводится.

Пример входа `letopis search` через стандартный ввод:

```json
{
  "query": "Как сохраняются знания?",
  "limit": 10
}
```

Во время выполнения этому процессу CLI передаётся `SIGINT`. JSON-выход после подтверждения отмены рабочим процессом:

```json
{
  "ok": false,
  "error": {
    "code": "cancelled",
    "message": "Запрос отменён",
    "details": {}
  }
}
```

`cancelled` обозначает исход отмены согласно общему каталогу ошибок. Если работа уже завершилась до принятия отмены, сохраняется её фактический результат. Принудительное уничтожение процесса не гарантирует доставку этого JSON-ответа; здесь проектируется обработанное прерывание. Агент использует имеющийся процесс CLI для адресации своего запроса; отдельный внешний ID запроса не требуется.

### 2. Отмена текущей фоновой перестройки проекта

Вызов `letopis reindex --cancel` адресует перестройку, активную на момент обработки запроса координатором, и ждёт её остановки. Действие относится к общему индексированию проекта. Если публикация уже завершилась либо активной перестройки нет, сохраняется текущая корректная версия; отмена не откатывает опубликованную версию. Новые задания, принятые после определения цели отмены, относятся к отдельной работе.

Вход через стандартный ввод:

```json
{}
```

Выход после завершения отмены:

```json
{
  "ok": true,
  "result": {
    "revision": "<ревизия последнего корректного индекса>"
  }
}
```

Если корректного индекса ещё нет, возвращается `revision: null`. Уже работающие поисковые запросы по опубликованной версии продолжаются. Вызовы, ожидающие отменённую перестройку, получают ответ отмены. Явно отменённое задание не перезапускается по правилу восстановления после сбоя. Отмена не устраняет ранее сохранённые ошибки подсистем; их согласованный жизненный цикл сохраняется.

Агент может остановить фоновую работу, у которой нет отдельного ожидающего CLI-вызова. Используется уже известная команда `reindex` и формат результата с ревизией; новые внешние ID заданий не требуются.

Оба способа отмены согласованы.

- Минимальная конфигурация адаптеров и запуска.

## Внешние вершины: сохранение идентичности

Статус: согласовано.

После удаления всех графовых ссылок на внешний источник он исключается из следующего опубликованного графа, но в первой версии бессрочно сохраняются в служебной БД соответствие адреса и диапазона его UUID. Прежняя история привязок доступна по известным Git-снимкам без отдельного учёта в БД. Если тот же адрес и диапазон снова используются, возвращается прежний UUID. Это отсутствие в текущей проекции, а не удаление идентичности с повторной выдачей ID другой сущности. Внешний файл не изменяется. Мотивация: структура индекса отражает текущие документы, а удаление и последующее возвращение ссылки не меняют идентичность источника. Дополнительная команда очистки не требуется.

Вход `letopis apply`; редактирование удаляет последнюю графовую ссылку на источник:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш исходного знания>",
      "markdown": "<!-- letopis: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"vertex\"} -->\nОписание хранилища без ссылки на прежний источник.\n<!-- /letopis -->\n"
    }
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

После успешной реиндексации внешний источник отсутствует в активной проекции. Повторное добавление ссылки на `src/storage.go#L10-L25` восстанавливает в графе тот же ID `fabd93e0-7f56-4c8d-a769-11f0bcaf7620`. Как обычно, поиск до публикации использует последнюю корректную версию индекса.

## Единое поле flags и недоступные хеши

Статус: оба решения согласованы. Формат `flags` заменяет прежние отдельные признаки во всех ссылках результатов `search` и `traverse`.

1. Ссылки результата используют один обязательный массив `flags`. Значения: `stale` — содержимое адресованного элемента изменилось относительно индекса; `source_changed` — хотя бы один источник знания отличается от подтверждённого состояния; `source_not_found` — хотя бы один источник знания или его фрагмент недоступен. Признаки могут сочетаться; повторов нет. Пустой список означает отсутствие обнаруженных причин, а не доказанную истинность знания. Для доступной внешней вершины, изменившейся после индексирования, возвращается только `stale`; причины перепроверки относятся к знаниям, связанным с ней. Недоступная внешняя вершина возвращается с `source_not_found`, а пока индекс ещё описывает существовавший источник, также с `stale`.

Мотивация: одна структура передаёт и признаки, и причины, сохраняет одновременные состояния и не дублирует булевый признак перепроверки списком причин. Согласованный фильтр `filters.needs_recheck` сохраняется: `true` означает наличие `source_changed` или `source_not_found`, `false` — отсутствие обоих; дополнительный фильтр флагов не вводится.

Вход `letopis search`:

```json
{
  "query": "Как устроено хранилище?",
  "limit": 5,
  "filters": {
    "needs_recheck": true
  }
}
```

Выход; изменились и сам документ знания после индексации, и его источник после подтверждения:

```json
{
  "ok": true,
  "result": [
    {
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "path": "knowledge/storage.md",
      "lines": [
        1,
        5
      ],
      "revision": "<снимок индекса>",
      "flags": [
        "stale",
        "source_changed"
      ]
    }
  ]
}
```

2. Для известной внешней вершины с сохранёнными ссылками возвращается успешный `inspect`, даже если файл источника исчез. `path` и диапазон сохраняются как адрес зарегистрированного источника; `hash` и `file_hash` равны `null`, поскольку текущие байты получить нельзя. Если файл существует, но диапазон недоступен, `hash` равен `null`, а `file_hash` содержит хеш существующего файла. Старые хеши не выдаются за актуальные. Общий снимок фиксирует состояние, включая отсутствие файла; строки внешней вершины в таком ответе обозначают адресованный диапазон, а не существующее содержимое. Неизвестный ID по-прежнему вызывает `not_found` для всего запроса. `inspect` разрешён по сохранённому в реестре ID внешнего источника без текущих ссылок; чтение не возвращает его в активный граф.

Мотивация: исчезновение файла не уничтожает известную графовую сущность; агент получает её адрес и видит недоступность по существующим полям, без нового флага или команды. Такие `null` не подходят для успешного подтверждения источников через `edit` со снимком.

Вход `letopis inspect`; источник всё ещё используется знанием, но его файл удалён:

```json
{
  "element_ids": [
    "fabd93e0-7f56-4c8d-a769-11f0bcaf7620"
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "snapshot": "<снимок текущего состояния>",
    "elements": {
      "fabd93e0-7f56-4c8d-a769-11f0bcaf7620": {
        "path": "src/storage.go",
        "lines": [
          10,
          25
        ],
        "hash": null,
        "file_hash": null
      }
    }
  }
}
```

## Недоступный источник в обходе и ожидание индексирования

Статус: оба решения согласованы.

1. При реиндексации сохраняются известная внешняя вершина и существующие ссылки на неё, если источник или диапазон недоступен. `traverse` возвращает её адрес с `source_not_found` в `flags`. Для внешней вершины этот признак обозначает недоступность самого адресованного источника; у знания — недоступность его зависимости. Отсутствие внешнего файла само по себе не блокирует публикацию корректных графа и FTS без ожидания embeddings по [D-71](../../decisions.md#D-71). Новая внешняя привязка по-прежнему требует доступного источника. После индексации состояния отсутствия возвращается только `source_not_found`; пока индекс ещё описывает существовавший источник, дополнительно возвращается `stale`. Если файл существует, но адресованный диапазон исчез, применяется то же правило. Мотивация: агент видит, какая ссылка требует исправления, а исчезновение исходного файла не блокирует индексирование остальных знаний. Используется существующий флаг, без нового статуса.

Вход `letopis traverse`:

```json
{
  "element_ids": [
    "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c"
  ],
  "mode": "relations",
  "direction": "outgoing",
  "edge_types": [
    "external"
  ],
  "depth": 1,
  "limit": 5
}
```

Выход после публикации индекса, уже фиксирующего отсутствие источника:

```json
{
  "ok": true,
  "result": {
    "elements": [
      {
        "element_id": "fabd93e0-7f56-4c8d-a769-11f0bcaf7620",
        "path": "src/storage.go",
        "lines": [
          10,
          25
        ],
        "revision": "<снимок индекса с отсутствующим источником>",
        "flags": [
          "source_not_found"
        ]
      }
    ]
  }
}
```

2. При явном `reindex` вызов присоединяется к уже выполняющемуся заданию, если оно работает с тем же согласованным Git-снимком и покрывает всю запрошенную область. Вызов ждёт публикации его результата и возвращает существующий `result.revision`; одинаковая перестройка не запускается повторно. Если снимок или область не подходят, выполняется обычное планирование задания для снимка явного вызова. Ожидающий вызов получает фактический успех, ошибку либо отмену задания. Совпадение пути без совпадения снимка недостаточно: новая правка не считается проиндексированной по старому заданию. Мотивация: агент может дождаться индексации своей правки существующей командой, а присоединение не запускает повторную перестройку графа/FTS; готовность embeddings не входит в ожидание по [D-71](../../decisions.md#D-71). Нового режима ожидания, параметра или идентификатора задания не требуется. Согласованные требования явной полной и выборочной перестройки сохраняются; совпадение снимка без покрытия области не позволяет подменить запрос другой работой.

Вход `letopis reindex`; фоновое задание уже индексирует тот же снимок и выбранный файл:

```json
{
  "paths": [
    "knowledge/storage.md"
  ]
}
```

Выход после успешной публикации этого задания:

```json
{
  "ok": true,
  "result": {
    "revision": "<ревизия опубликованного индекса>"
  }
}
```

## Inspect источника без ссылок и адрес Git-снимка

Статус: оба решения согласованы.

1. `inspect` разрешён по зарегистрированному ID внешнего источника даже после удаления всех графовых ссылок на него. Ответ показывает актуальное состояние адресованного файла или фрагмента в общем снимке. Недоступные хеши равны `null`, как согласовано ранее; прежнее содержимое и хеши не подставляются. Сам запрос не возвращает источник в активную графовую проекцию и не создаёт ребра. Неизвестный ID по-прежнему вызывает `not_found` для всего пакета. Мотивация: агент может использовать сохранённый ID для чтения или восстановления ссылки, а `inspect` не зависит от задержки удаления вершины из поискового индекса. Дополнительная команда для реестра источников не требуется.

Вход `letopis inspect`; текущих ссылок на источник нет, но ID сохранён в служебном реестре:

```json

  "element_ids": [

```

Выход, если файл и диапазон доступны:

```json
      "fabd93e0-7f56-4c8d-a769-11f0bcaf7620": {
        "path": "src/storage.go",
        "lines": [

```

2. `inspect.result.snapshot` представлен полным идентификатором объекта Git tree в Git-хранилище этого репозитория. Объект задаёт неизменяемое дерево файлов снимка; отдельный идентификатор letopis для адресации не вводится. Агент может читать файл средствами Git по форме `<tree_oid>:<path>`. Снимок сохраняет точные байты канонических документов и адресованных источников, включая незакоммиченные состояния; существующий индекс Git, рабочая ветка и пользовательские коммиты не изменяются. Алгоритм и формат OID задаёт Git-репозиторий; это не SHA-256 поля `hash`, и один не подменяет другой. Состав общего дерева согласован ниже: корпус и нужные источники. Способ построения, удержание объектов и отображение на исходные коммиты остаются предметом следующего проектирования. Согласованный тип `snapshot` — строка; другие поля ревизий автоматически не переопределяются. Мотивация: агент читает именно состояние, по которому получены хеши, стандартным инструментом и использует тот же адрес в `edit.snapshot`; дополнительный CLI для чтения текста не нужен.

## Состав и хранение Git-снимков

Статус: состав и бессрочное удержание используемых Git-снимков в первой версии согласованы. Git отвечает за хранение содержимого и объектов снимков; letopis через Git-адаптер создаёт и закрепляет нужные снимки и сохраняет OID и состояние операций в БД. Собственная система хранения версий текста в letopis не вводится. Индекс перестраивается, постоянная история его версий не хранится.

1. Общий снимок включает весь корпус знаний и целые доступные файлы внешних источников, на которые ссылаются текущие знания. Если `inspect` явно запрашивает зарегистрированный источник без текущих ссылок, его доступный файл также включается в возвращаемый снимок. Пути сохраняются относительно корня репозитория. Диапазон определяет хеш фрагмента, но в Git сохраняется файл целиком, чтобы агент мог читать его с исходной нумерацией строк и получить полный `file_hash`. Недоступные файлы отсутствуют в дереве, а их адреса остаются в служебном реестре. Посторонние файлы проекта и служебная БД не входят в это дерево; пользовательская рабочая копия и индекс Git не изменяются. Состав снимков для адресованного отката ограниченных правок и оптимизации построения ещё уточняется; предложение определяет общую базу чтения и индексирования. Мотивация: агент может читать документ и его источники из одного согласованного состояния, следуя существующим ссылкам. Ответ `inspect` по-прежнему содержит только запрошенные элементы, а не перечень всех файлов снимка.

Вход `letopis inspect`; знание ссылается на `src/storage.go#L10-L25`:

```json
{
  "element_ids": [
    "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c"
  ]
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "snapshot": "<OID дерева с корпусом и нужными источниками>",
    "elements": {
      "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c": {
        "path": "knowledge/storage.md",
        "lines": [
          1,
          5
        ],
        "hash": "<SHA-256 фрагмента>",
        "file_hash": "<SHA-256 файла>"
      }
    }
  }
}
```

Документ и целый файл его источника доступны в том же дереве по путям `knowledge/storage.md` и `src/storage.go`. Новые поля в запросе и ответе не вводятся.

2. В первой версии Git-снимки удерживаются бессрочно. Это касается снимков, выданные агенту через `inspect` либо сохранённые для операций, индексирования и истории источников. TTL, автоматическое освобождение этих снимков и команды продления не вводятся. Git tree и достижимое содержимое закрепляются служебными Git-ссылками в собственном пространстве `refs`; до выдачи снимка или изменения канонических файлов необходимые объекты и ссылки должны быть надёжно сохранены. Одного хранения OID в БД недостаточно для защиты Git-объектов от штатной очистки. Это проектируемая гарантия: механизм долговечности после потери питания и порядок обновления БД и refs требуют реализации и проверки. Временные внутренние объекты, не выданные и не нужные для истории или восстановления, данным правилом не удерживаются бессрочно. Мотивация: агент может продолжить работу по полученному снимку без дополнительных вызовов и параметров срока действия; история остаётся читаемой. Цена решения — рост дискового пространства. Удержание снимка не отменяет проверки `base_hash` и текущих источников.

Вход `letopis apply` спустя время после `inspect`; прочитанное знание и источники за это время не изменились:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш прочитанного знания>",
      "markdown": "<!-- letopis: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"vertex\"} -->\nПерепроверенное описание хранилища.\n[Код](src/storage.go#L10-L25 \"letopis:id=064f2964-77cc-41f0-87ac-d280c0ec59a7;type=external\").\n<!-- /letopis -->\n",
      "snapshot": "<ранее полученный OID дерева>"
    }
  ]
}
```

Выход после успешных обычных проверок:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

Снимок не истекает по времени. Изменившееся знание или источник по-прежнему вызывает `conflict`. Защита объектов, достижимых через `refs/*`, от штатной очистки описана в [документации git gc](https://git-scm.com/docs/git-gc); атомарный протокол letopis не следует из одного использования Git и ещё проектируется.

## Получение source_snapshot средствами Git

Статус: согласовано получение снимка агентом стандартными средствами Git и описание этого сценария в навыке агента. Команда letopis snapshot не вводится; inspect сохраняет запрос элементов по ID. Для create агент записывает полный tree OID в source_snapshot JSON-метаданных Markdown; для явной перепроверки через edit используется уже согласованный edit.snapshot.

Снимок должен существовать в Git-хранилище текущего проекта. Допустимы дерево существующего коммита и дерево нужных источников, созданное без коммита. Отдельная регистрация снимка в letopis не требуется. Правило состава снимка, возвращаемого inspect, этим не изменяется.

### Инструкция для навыка агента

Перед формулированием знания получи снимок и прочитай источники именно из него. Если код уже был прочитан из рабочей копии, сверь его с выбранным снимком. Не подставляй HEAD вместо снимка незакоммиченного состояния.

Для кода из текущего коммита, из корня репозитория:

```sh
snapshot=$(git rev-parse --verify 'HEAD^{tree}')
git show "${snapshot}:src/auth.rs"
```

Для незакоммиченного обычного файла src/auth.rs используй отдельный временный Git-индекс. Пример отдельного скрипта:

```sh
set -eu
snapshot_tmp_dir=$(mktemp -d)
trap 'rm -f "$snapshot_tmp_dir/index"; rmdir "$snapshot_tmp_dir"' EXIT
source_blob=$(git hash-object -w --no-filters -- src/auth.rs)
GIT_INDEX_FILE="$snapshot_tmp_dir/index" git read-tree --empty
GIT_INDEX_FILE="$snapshot_tmp_dir/index" git update-index --add --cacheinfo "100644,$source_blob,src/auth.rs"
snapshot=$(GIT_INDEX_FILE="$snapshot_tmp_dir/index" git write-tree)
printf '%s\n' "$snapshot"
git show "${snapshot}:src/auth.rs"
```

Для нескольких источников добавь каждый файл в тот же временный индекс перед write-tree. --no-filters сохраняет точные байты без преобразований атрибутами Git; режим 100644 в примере соответствует обычному неисполняемому файлу. Сохраняй пути относительно корня проекта. Коммит, пользовательский staging и рабочие файлы этим сценарием не меняются; новые объекты записываются в Git.

Полученный OID передай в source_snapshot создаваемого знания. Если между чтением и записью требуется новый снимок, проверь знание по его источникам перед заменой указателя. Пример описывает получение адреса версии, а не доказательство смысловой корректности знания.

### Проверка перед записью

При create с source_snapshot и при edit с snapshot letopis до изменения канонических файлов проверяет формат полного OID, наличие объекта в Git текущего проекта и его точный тип tree. Отсутствующий объект даёт not_found; неверный формат или существующий объект другого типа дают invalid_request. Весь apply отклоняется атомарно. Проверка входит в общий путь подготовки apply и apply --check; успешный check не отменяет повторную проверку перед сохранением.

Наличие tree не заменяет проверку адресованных источников: проверяются доступность нужных файлов и диапазонов в снимке по действующим правилам источников.

Согласовано: при create letopis сравнивает адресованные источники каждого нового знания с его source_snapshot. Для ссылки с диапазоном сравниваются точные байты указанного фрагмента, для ссылки на весь файл — байты всего файла. Если хотя бы один доступный источник отличается от снимка, весь apply отклоняется с conflict до изменения канонических документов. Несовпадение OID деревьев само по себе конфликтом не является: изменения вне адресованных источников и диапазонов не мешают записи. Это то же правило актуальности, которое уже действует для edit с snapshot. Недоступные файлы и диапазоны по-прежнему обрабатываются согласованными правилами validation_failed.

Вход: create передаёт source_snapshot S1 и ссылку external на src/auth.rs; в S1 срок сессии равен 24 часам, а в актуальном файле — 12. Выход: conflict, ни одна операция группы не применяется. Агент перечитывает актуальные источники, проверяет знание и подготавливает новую правку. Если ссылка адресует неизменившийся фрагмент, а изменения произошли за его пределами, конфликт только по этой причине не возникает.

letopis надёжно закрепляет принятые снимки служебными Git-ссылками до изменения канонических файлов, согласно общей гарантии удержания. Физический протокол долговечности ещё требует реализации и аварийной проверки.

Git-сценарий проверен 15 октября 2026 года в отдельном временном репозитории на Git 2.50.1: снимок коммита содержал значение 24, снимок незакоммиченного файла — 12; HEAD, рабочие файлы и байты пользовательского индекса при создании второго снимка сохранились. Проверено различение tree, commit, blob и отсутствующего объекта через git cat-file -t. Это проверка возможностей Git; реализация apply letopis не запускалась.

Основание Git-протокола: [rev-parse](https://git-scm.com/docs/git-rev-parse), [hash-object](https://git-scm.com/docs/git-hash-object), [update-index](https://git-scm.com/docs/git-update-index), [write-tree](https://git-scm.com/docs/git-write-tree).

## Чтение истории по известному Git-снимку

Согласовано: агент читает прошлое состояние знания по известному OID снимка корпуса и пути стандартными средствами Git. Из прежнего Markdown он получает прежние ссылки и source_snapshot для чтения источников. Отдельный учёт истории в БД и запрос списка прежних оснований по ID через CLI не вводятся. Бессрочное удержание необходимых снимков и текущие идентичности source сохраняются. Инструкция навыка использует тот же способ чтения <tree_oid>:<path>.

## Недоступный snapshot и ревизия источника

Статус: оба решения согласованы.

1. Весь `apply` отклоняется с `not_found`, если синтаксически допустимый полный OID из `source_snapshot` JSON-маркера в `create.markdown` либо `edit.snapshot` не существует в Git-хранилище текущего репозитория. Доступность snapshot проверяется при каждом новом самостоятельном вызове; старый успех по совпадению хеша не подставляется. Без содержимого снимка подтверждение источников не выполняется, текущие файлы вместо него не подставляются. Неверный формат OID либо существующий объект другого типа, не tree, вызывают `invalid_request`. Отсутствие файла источника внутри доступного tree не тождественно отсутствию самого snapshot и рассматривается правилами проверки источников. Мотивация: агент получает конкретную причину и может получить подходящий снимок средствами Git либо перечитать уже известный элемент через inspect; используются согласованные коды, новый тип ошибки или параметр не вводится.

Вход `letopis apply`; указанный tree OID отсутствует:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш прочитанного фрагмента>",
      "markdown": "<!-- letopis: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"vertex\"} -->\nПерепроверенное описание хранилища.\n[Код](src/storage.go#L10-L25 \"letopis:id=064f2964-77cc-41f0-87ac-d280c0ec59a7;type=external\").\n<!-- /letopis -->\n",
      "snapshot": "<OID отсутствующего Git tree>"
    }
  ]
}
```

Выход, без применения изменений:

```json
{
  "ok": false,
  "error": {
    "code": "not_found",
    "message": "Git-снимок не найден",
    "details": {
      "snapshot": "<OID отсутствующего Git tree>"
    }
  }
}
```

2. Согласовано: filters.source_revisions сравнивает содержимое адресованного источника в запрошенной Git-ревизии с его содержимым в source_snapshot знания. Для ссылки на фрагмент сравниваются точные байты того же пути и диапазона, для ссылки на весь файл — весь файл. Совпадение хотя бы одной ревизии в одной текущей привязке удовлетворяет фильтру; при заданном filters.sources адрес проверяется в той же привязке. Поиск по C2 находит знание с основанием из C1, если адресованные байты совпадают. Отдельный OID коммита в метаданных знания и БД не хранится; прежнее правило сохранения HEAD или tree OID как отдельной ревизии привязки заменено.

Вход letopis search; адресованный фрагмент в source_snapshot знания совпадает с тем же фрагментом в запрошенном коммите. Сам OID коммита в метаданных знания не сохраняется:

```json
{
  "query": "Как устроено хранилище?",
  "limit": 5,
  "filters": {
    "sources": [
      "src/storage.go"
    ],
    "source_revisions": [
      "<OID запрошенного коммита>"
    ]
  }
}
```

Выход:

```json
{
  "ok": true,
  "result": [
    {
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "path": "knowledge/storage.md",
      "lines": [
        1,
        5
      ],
      "revision": "<снимок индекса>",
      "flags": []
    }
  ]
}
```

В том же списке source_revisions агент может указать tree OID незакоммиченного состояния. Сравнивается содержимое адресованного источника, а не равенство OID. Адрес и проверка ревизии относятся к одной привязке; форма поискового результата не меняется.

## Определение проекта и корпуса

Статус: оба решения согласованы.

1. Корень проекта определяется как корень Git-рабочей копии, содержащей текущий каталог вызова CLI. Команды можно вызывать из любой её вложенной папки. Все пути запросов, Markdown-ссылок и результатов по-прежнему считаются от этого корня, а не от каталога запуска. Если рабочая копия не найдена, возвращается `not_found`; создание репозитория автоматически не выполняется. Дополнительное поле проекта в JSON и параметр корня не вводятся в первую версию. Мотивация: агент использует обычный рабочий каталог, а все вызовы внутри одной рабочей копии обращаются к одному процессу и служебному состоянию проекта. Поддержка нескольких worktrees остаётся вне первой версии.

Вход `letopis search`, вызванного из `<repo>/src/`:

```json
{
  "query": "Как устроено хранилище?",
  "limit": 5
}
```

Выход; путь по-прежнему от корня `<repo>`:

```json
{
  "ok": true,
  "result": [
    {
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "path": "knowledge/storage.md",
      "lines": [
        1,
        5
      ],
      "revision": "<снимок индекса>",
      "flags": []
    }
  ]
}
```

2. Корпус определяется по разметке: файлы `.md` и `.markdown` внутри рабочей копии с маркерами letopis вне блоков кода входят в область проверки и индексирования. Файлы могут лежать в разных папках; отдельный список или каталог корпуса не требуется. Обычные Markdown-документы без этих маркеров не входят в корпус, но могут быть внешними источниками. `.git` и собственная служебная директория letopis исключаются из обхода. Наличие неполного или некорректного маркера вне блока кода означает ошибку разметки, а не основание молча исключить файл. Примеры разметки внутри блоков кода не создают сущностей. Принадлежность элемента метавершине по-прежнему задаётся `includes`, расположение папок её не меняет. Мотивация: файл сам объявляет свои элементы; агент добавляет документ с разметкой обычной операцией, без изменения конфигурации или отдельной регистрации. Это предложение определяет файловую область корпуса, а не вводит неразмеченные знания.

Вход `letopis reindex`; `knowledge/storage.md` размечен, обычный `README.md` содержит только текст:

```json
{}
```

Выход после проверки и полной перестройки корпуса:

```json
{
  "ok": true,
  "result": {
    "revision": "<ревизия опубликованного индекса>"
  }
}
```

Элементы `knowledge/storage.md` входят в поисковый корпус. Сам текст `README.md` не индексируется; явная ссылка `external` на него по-прежнему создаёт внешнюю вершину по согласованным правилам. Публичные запрос и ответ `reindex` не меняются.

## Поисковый текст и повторное использование embeddings

Статус: оба решения согласованы. Это внутренние контракты конвейера; публичный CLI продолжает возвращать ссылки, а не текст или vectors.

1. Согласовано одно детерминированное поисковое представление собственного Markdown-фрагмента вершины или метавершины для текстового индекса и embeddings. Служебные блоки letopis и графовые метаданные убираются; от Markdown-ссылки остаётся подпись, содержимое назначения не подгружается. Представление включает собственный текст и примеры кода; вложенные и связанные элементы индексируются самостоятельно. Оригинальные байты полного Markdown продолжают определять `base_hash`, независимо от этого представления. Текст представления используется временно и не сохраняется в БД как копия документа; хранятся поисковые структуры и согласованные метаданные. Мотивация: оба вида поиска используют одно содержимое, изменение дочернего знания не требует заново вычислять вектор родителя, а случайные UUID и служебная разметка не занимают вход модели. Конкретные правила преобразования остальных Markdown-конструкций определяются единой реализацией и проверяются на корпусе; отдельный публичный формат текста не вводится.

Внутренний вход подготовки поискового текста:

```json
{
  "markdown": "<!-- letopis: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"metavertex\"} -->\nТранзакция сохраняется целиком.\n[Правила](knowledge/rules.md#9b016319-d499-4564-a74d-b3b13d129a6c \"letopis:id=064f2964-77cc-41f0-87ac-d280c0ec59a7;type=includes\").\n<!-- /letopis -->\n"
}
```

Внутренний выход:

```json
{
  "text": "Транзакция сохраняется целиком.\nПравила."
}
```

2. При перестройке embedding из доступного корректного индекса повторно используется, если совпадают SHA-256 подготовленного поискового текста и идентичность вычисления: адаптер, версия модели и параметры, влияющие на вектор. ID элемента и байтовый хеш его исходного Markdown не являются единственными ключами повторного использования. Изменение текста, модели или влияющих параметров требует нового вычисления. Повторное использование не подтверждает источники и не меняет правила `flags`. Постоянный архив прежних vectors или самостоятельная подсистема вечного кеша не вводятся: ненужные данные освобождаются вместе с индексами после завершения использующих их запросов. Для запросов поиска здесь не выбирается постоянный кеш. Мотивация: перенос элемента, изменение его ID, служебной разметки или адреса ссылки при прежней подписи не требует дорогого повторного вычисления неизменившегося поискового текста; смена модели не смешивает несовместимые векторы.

Внутренний вход порта embeddings; модель и влияющие параметры заданы выбранным адаптером:

```json
{
  "texts": [
    "Транзакция сохраняется целиком.\nПравила."
  ]
}
```

Внутренний выход, одинаковой формы при вычислении и повторном использовании:

```json
{
  "vectors": [
    [
      0.12,
      -0.34,
      0.56
    ]
  ]
}
```

Вектор из трёх чисел — иллюстрация формы, а не размерность выбранной модели. Порядок результатов соответствует порядку `texts`; фактическая размерность определяется конфигурацией модели. `cache_hit`, внешние ID кеша и новые поля CLI не вводятся. Замена модели требует подготовки согласованной новой версии индекса; детали закрепления конфигурации и направления запросов к соответствующему адаптеру уточняются в сводном дизайне.

## Текущий этап: модель хранения

Количество вопросов не ограничено; дизайн должен быть детальным при минимуме необходимых механизмов. Следующие решения и примеры относятся к [модели хранения](../../mechanics/storage-model.md). Поисковый текст и повторное использование embeddings согласованы; конкретные записи, ключи и физическое хранение уточняются в модели хранения.

## Представление графа в хранении

Метавершины и системный тип includes сохраняются в доменной модели. Хранение графовой проекции использует обычный направленный граф с наборами nodes и edges; включённость — тип ребра, отдельный массив членов внутри метавершины не хранится. Специализированный метаграфовый движок не требуется выбранными правилами. Отдельный исторический реестр UUID не требуется: проверяется уникальность текущих nodes и edges. Движком единой служебной БД выбран SQLite; физический DDL ещё проектируется. Детали записей и оставшиеся предложения описаны в [модели хранения](../../mechanics/storage-model.md).

## Нормализация адресов внешних источников

Согласовано: для разрешения и сравнения адресов внешних источников letopis удаляет компоненты `.` и сворачивает внутренние `..`, запрещая выход из корня Git. Номера строк записываются без ведущих нулей, регистр имён файлов сохраняется. Исходный Markdown не переписывается; хеш файла и фрагмента остаётся SHA-256 его точных байтов. Пример: `./src/../src/storage.go#L010-L025` разрешается по ключу `src/storage.go#L10-L25`. Вход и выход внутреннего преобразования приведены в [модели хранения](../../mechanics/storage-model.md); новых полей CLI это решение не вводит.

## Единые узлы источников в хранении

Согласовано: знания и источники хранятся в единой nodes. Поле kind имеет значения vertex, metavertex и source; source соответствует обычной вершине источника в доменной модели. Общее поле адреса uri заменяет path в модели хранения и представляет адрес описания знания или источника. ID и адреса известных источников сохраняются при реиндексировании и после удаления всех ссылок. Отдельная external_nodes не используется. Сетевое чтение, фиксация версий веб-страниц и соответствующие публичные поля ещё не определены. Подробности — в [модели хранения](../../mechanics/storage-model.md).

## Уточнение хеширования файлов и версий источников

Предварительно согласовано: file_hash вычисляется по всем байтам файла, пока SHA-256. Разметка файлов проектируется отдельным этапом; после её выбора правило может быть пересмотрено явным решением. Способ постоянного хранения или вычисления file_hash по запросу пока не выбран. Подтверждена зависимость знания от конкретной версии источника. Принято общее основание источников знания, описанное ниже. Независимое поле source_revision каждого ребра не принято; история читается по известным Git-снимкам, а фильтр по ревизии сравнивает содержимое источников без отдельного хранения OID коммита; правила описаны в [модели хранения](../../mechanics/storage-model.md).

## Общее основание источников знания

Согласовано: все источники одного знания относятся к одному общему Git-снимку. Обычный edit сохраняет основание, а edit с snapshot подтверждает все источники вместе по правилам следующего абзаца. Более раннее описание независимого обновления привязок этим правилом заменено. Текущее основание хранится в source_snapshot канонического Markdown и nodes. История читается по известным Git-снимкам без отдельного учёта в БД. Фильтр по ревизии сравнивает содержимое источника в запрошенной Git-ревизии и source_snapshot; отдельный OID коммита не хранится. Обсуждение продолжается по одному вопросу за раз.

При edit без snapshot с прежним набором источников сохраняется прежнее общее основание. Обновление текста знания не подтверждает источники заново. Edit с snapshot подтверждает все конечные источники по одному снимку после проверок. При добавлении или замене адреса источника snapshot обязателен; без него весь apply отклоняется с invalid_request. Удаление источника без добавления или замены других при edit без snapshot сохраняет прежнее основание оставшихся зависимостей. Сам snapshot по действующему контракту может быть любым доступным Git tree OID текущего репозитория; отдельная регистрация в letopis не требуется.

## Проверка упрощения и согласованности — 12 октября 2026

Принято: уникальность UUID проверяется среди текущих nodes и edges без проверки истории. Бессрочная дедупликация завершённых вызовов apply отменена; после потери ответа агент перечитывает состояние, новый вызов проходит обычные проверки. Хеш правки остаётся отпечатком исходного запроса, а не уникальным ID каждого выполнения. Атомарность, восстановление и история оснований знаний сохраняются. Запись восстановления удаляется после надёжного завершения правки или полного отката; прежние основания читаются по известным Git-снимкам без отдельного учёта истории в БД, а диагностика имеет собственные правила хранения. Подробности и открытые вопросы — в [аудите упрощения](../../appendix/simplification-audit.md).
