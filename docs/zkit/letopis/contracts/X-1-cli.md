## Layout
Машиночитаемый каталог всех входов, успешных ответов и общей ошибки: [X-1-cli.yaml](schemas/X-1-cli.yaml), JSON Schema 2020-12. Поле x-commands сопоставляет имя команды с input/success/error внутри $defs. Имя команды и флаги находятся в argv, в stdin — только описанный JSON без новой обёртки command. Примеры: [contracts-examples.json](../checks/contracts/contracts-examples.json). Каталог — дизайн, не реализация CLI.

Пустой stdin или stdin, содержащий только JSON-пробелы, равнозначен `{}`; при запуске с терминала stdin не читается и запрос считается пустым. Для нетерминального stdin ожидается первый байт не более 250 мс; если байт не пришёл, запрос считается пустым. После первого байта поток читается до EOF, чтобы принять полный JSON. Обязательные поля проверяются как обычно.

| inspect | element_ids / snapshot, elements | актуальные path/lines/hash знаний и source одного Git-снимка, без текста; неизвестный ID отклоняет пакет |
| search | query, limit, необязательный filters / список ссылок | гибридный поиск; до настройки и при сбое query embedding — FTS |
| traverse | element_ids, mode, direction, depth, limit; необязательные edge_types, edge_limit / elements и опциональный edges | relations/containment/both; стартовые элементы исключены, повторные достижения возвращаются один раз |
| index | необязательный paths / revision, published, files_updated, files_removed, invalid_files_updated | argv: без флагов инкрементально; --verify проверяет замыкания снимков; --full принудительно перепарсивает выбранные файлы и проверяет замыкания. paths ограничивает наблюдаемые владельцы и удаления, но проверка снимков остаётся глобальной; пустые paths охватывают весь корпус |

Уточнение 2026-10-29 ([D-105](../decisions.md#D-105)): search/traverse/inspect и check с непустым paths автоматически обновляют кэш из Markdown, проверяя корни/refs оснований и фактически адресованные объекты, без полного обхода source_snapshot. Полный check (paths отсутствует или пуст) выполняет batched-аудит всех оснований результирующей валидной проекции до SQL; `index --full` дополнительно перепарсивает весь корпус. Невалидный Markdown сохраняет last-valid основание; валидная замена/удаление убирает старое. Полный check сверяет проверенную revision с закреплённым read view; при публикации другой revision в промежутке возвращает internal_error с предложением retry. Повреждение несвязанных дочерних объектов выявляется полным check/`index --full`; успешное routine-чтение не удостоверяет весь снимок. Inspect отдельно полностью проверяет новый снимок захваченных bytes.

`init` принимает только пустой объект `{}` и до любых записей требует инициализированный Git work tree, не являющийся bare; подкаталог разрешается в Git-корень, вне work tree возвращается `invalid_request` без создания состояния. После Git-guard существующий config проверяется и валидируется до создания БД; затем открываются/проверяются схемы, конфигурация публикуется атомарно только при отсутствии, победитель гонки перечитывается и валидируется, а завершение каталога синхронизируется. Повторный и конкурентный вызовы сохраняют валидный config и логическое содержимое БД; повреждённое/несовместимое состояние не перезаписывается. Успех не индексирует корпус, не вызывает provider, не сбрасывает векторы и не запускает drain; частично завершённое состояние сохраняется для повторного вызова.

Пути относительны Git-корню. ID знания — путь или путь#якорь (KnowledgeId), ID source — нормализованный адрес (SourceId: path или path#Lstart-Lend), [D-91](../decisions.md#D-91)/[D-93](../decisions.md#D-93); UUID нет. ElementId в inspect/traverse принимает обе формы; путь обозначает либо элемент корпуса, либо source. Рёбра возвращаются тройками source/target/type без ID. Source без текущих ссылок отсутствует в графе: его адрес даёт not_found. Файл `.letopis/config.json` имеет вложенную схему Configuration с обязательной секцией `embedding_model` (`enabled`, `provider`, `model`, `parameters`, `max_retries`) и правится агентом или пользователем как файл. Сгенерированное значение: `enabled:false`, `provider:null`, `model:null`, `parameters:{}`, `max_retries:0`. Поддерживается только вложенная форма; старые плоские файлы отклоняются с диагностикой ручной миграции и не переписываются. Оба поля provider/model либо null (только при `enabled:false` и пустых parameters), либо заданы вместе; частичная конфигурация недопустима. Настроенные параметры локально проверяются и при `enabled:false`. Identity — SHA-256 JCS четырёх настроенных полей (`provider`, `model`, `parameters`, `max_retries`), без `enabled` и корневой обёртки, поэтому переформатирование файла или переключение `enabled` не сбрасывает векторы, а смена настроенных полей сбрасывает `.letopis/vectors.db` при следующем вызове команды, синхронизирующей embedding readiness (наблюдающий status — исключение). Сброс — одна транзакция записи vectors.db (BEGIN IMMEDIATE): повторная сверка identity, пересоздание vec1, очистка vector_keys и embed_failures, запись meta.config_identity; блокировки index.lock/embed.lock не берутся, drain перед сохранением вектора сверяет meta.config_identity и при несовпадении завершается. Валидный `enabled:false` не запускает inference/reset/drain, сохраняет векторы и попытки, даёт нулевые embedding-счётчики и скрывает сохранённые execution-ошибки. Невалидное содержимое остаётся видимой проблемой конфигурации; поиск работает через FTS. Служебная БД — пересоздаваемый кэш; её удаление не меняет контракт команд, следующий вызов обновляющей корпус команды выполняет reindex (status не пересобирает кэш), а векторы неизменных текстов из `.letopis/vectors.db` переиспользуются (D-92). SHA-256 представлен 64 строчными hex, snapshot — полный Git OID, revision — счётчик публикаций индекса (D-95); точный тип tree проверяется приложением. Источник ребра — элемент, содержащий ссылку.

## Help и version

Распознаются ровно три формы argv: `--help`, `<команда> --help` (init, check, inspect, search, traverse, index, status, config) и `--version`. Вывод — обычный текст в stdout, exit 0, stderr пуст; это осознанное исключение из правила «один JSON в stdout», потому что help не является результатом команды. `--help` перечисляет команды, правила ввода/вывода, коды ошибок и примеры; `<команда> --help` — поля JSON-входа, форму result и пример. `--version` печатает `letopis <версия>` из метаданных пакета. Формы распознаются до чтения stdin: репозиторий, конфигурация, сеть и сервисы не затрагиваются, поэтому работают вне Git-репозитория. Любой другой argv (пустой, `-h`, `-V`, `--help search`, `embed --help`, не-UTF-8) ведёт себя как прежде: `invalid_request`, exit 1. `embed --drain` ([D-94](../decisions.md#D-94)) в help не включается. Машинная схема [X-1-cli.yaml](schemas/X-1-cli.yaml) описывает init, config и остальные формы argv.

## Наблюдение status

Status читает последнюю опубликованную ревизию без refresh/reindex, schema bootstrap/repair, сброса vector identity, inference или запуска drain. Отсутствующий кэш или кэш без публикации даёт revision:null, нулевые embedding-счётчики и отсутствие проблем из кэша; config и блокировки наблюдаются независимо. Отсутствующие cache.db/vectors.db и служебный каталог не создаются; при опубликованном кэше и отсутствующем vectors.db все текущие хеши входят в backlog. Существующее недоступное или несовместимое хранилище — ошибка, а не пустой успех. Изменение файла отражается после публикации refresh другой командой.

Embedding-счётчики считают различные текущие knowledge search_hash: общие тексты учитываются один раз, source и осиротевшие vector/failure строки исключены. При совпадающей активной identity usable vector исключает хеш из обоих счётчиков; без вектора attempts ≥ 1+max_retries даёт failed, иначе backlog. Исчерпанные хеши выводятся в стабильном порядке. При отсутствующей/невалидной конфигурации или несовпадении её identity с закреплённой vector identity все текущие различные хеши считаются backlog, failed=0; сброса identity/попыток нет. Невалидный или нечитаемый config даёт безопасную проблему. Валидная disabled-конфигурация даёт embedding_backlog=0 и embedding_failed=0, не показывает исчерпанные попытки и query_error, но сохраняет их в vectors.db; после включения те же настройки снова показывают execution-проблемы. vec.query_error наблюдается при отсутствующей или enabled-конфигурации, не при disabled.

Revision, строки кэша, vector coverage, attempts и query_error читаются в одном read view. Атомарности между этим снимком, live config, Git-наблюдениями и блокировками нет; status не держит database writer.

В locks включаются только занятые kernel flock на существующих index.lock/embed.lock: проверка неблокирующая, свободный файл с прежним PID игнорируется, отсутствующие файлы и каталог не создаются. PID — записанное в файле положительное число, а не подтверждённая идентичность текущего владельца: при быстрой смене владельца может быть показан прежний корректный PID. Занятый lock с отсутствующим, нечитаемым или некорректным PID даёт безопасную ошибку наблюдения; status не записывает PID и не ждёт владельца.

## Timing and limits
Один JSON в stdout, без потоковых прогресс-сообщений; exit 0 для ok:true, 1 для ok:false, включая обработанную отмену. Ошибки имеют code/message/details. Status.problems перечисляет только текущие проблемы в том же формате Diagnostic; исправленная проблема исчезает без очистки, истории и lifecycle-флага нет ([D-95](../decisions.md#D-95)). Принудительное уничтожение процесса не обещает JSON-ответ. Числовые транспортные лимиты не добавляются; limit и edge_limit положительны, depth неотрицателен, пустые старты недопустимы. Фильтры и селекторы с пустыми списками эквивалентны отсутствующим, дубли обрабатываются один раз.

Каждый вызов search/traverse/inspect/check перед ответом обнаруживает изменённые файлы и публикует их валидные изменения в graph/FTS ([D-93](../decisions.md#D-93)). `index --full` ждёт graph/FTS. Векторы не ожидаются. Первый search при отсутствии индекса дожидается graph/FTS. До конфигурации модели работа через FTS разрешена. Прогретая секунда — цель, не отсечка; search не обрезается по времени. SIGINT отменяет свой процесс search/traverse/inspect/check/`index --full`, не чужие ([D-94](../decisions.md#D-94)); незавершённая перестройка не заменяет прежний кэш. Отмена обрабатывается (D-96): поток `signal-hook` принимает SIGINT, печатает единственный ответ ok:false/cancelled (once-guard на stdout: если результат уже напечатан, второй JSON не печатается) и завершает процесс с exit 1 в любой точке — SQL-шаг, ожидание flock, git-подпроцесс, HTTP. Незафиксированная транзакция SQLite откатывается как после сбоя (WAL), flock снимает ядро, оставленные git-объекты безвредны и чистятся как после сбоя; зафиксированная публикация остаётся. InterruptHandle не используется. У отсоединённого drain обработчика нет: сигнал завершает его по умолчанию, ответа нет, attempts в embed_failures сохранены. Отмены чужого процесса нет ([D-95](../decisions.md#D-95)).

Согласование ответа с кодом выхода подтверждено [TK-6](../checks/TK-6/review.md): если первым напечатан `ok:false/cancelled`, завершение всегда имеет exit 1; обычный путь, проигравший stdout once-guard, не может завершить процесс с exit 0. Если успешный JSON уже напечатан, последующий обработанный SIGINT может завершить процесс с exit 1 без второго JSON; завершённый до обработки сигнала вызов сохраняет exit 0. Проверка всего CLI при SQL/flock/git остаётся TK-29.

## Errors and retry
Каталог: invalid_request, not_found, validation_failed, embedding_failed, internal_error, cancelled; conflict исключён вместе с base_hash ([D-93](../decisions.md#D-93)). Все ошибки проходят общий JSON-формат. Ошибки разметки и целостности — validation_failed; отсутствующий запрошенный ID/допустимый Git OID — not_found. Неверный формат/тип snapshot — invalid_request. Подробные условия сохраняются в [контрактах](../contracts.md).

Команд записи корпуса нет: правки делает агент, check и индексация идемпотентны. Повтор `index --full` перестраивает граф/FTS заново; векторы неизменных текстов переиспользуются. В схеме x-idempotency у каждой команды указан явно.

При ошибке query embedding успешный FTS возвращает обычный search; последняя такая ошибка хранится одной строкой query_error в `.letopis/vectors.db` и видна в status.problems, пока следующий успешный embedding запроса её не удалит (D-62). Сбой запуска drain — предупреждение в необязательном поле warnings ответа любой команды; оно не сохраняется ([D-95](../decisions.md#D-95)). Ошибка фонового embedding не отменяет уже сохранённые документы и не меняет завершённый успех `index --full`. Публикации сериализуются flock на index.lock; читатели используют снимки SQLite. Текст документов/источников не возвращается через search/inspect/traverse; агент читает Git/Markdown самостоятельно.

## Реализованные search filters TK-22 — 2026-10-25

[Результаты проверки](../checks/TK-22/report.md): `needs_recheck`, `sources` и
`source_revisions` принимаются строгим CLI и применяются совместно по AND; внутри
списков OR, дубли не меняют ответ, пустые/отсутствующие списки не ограничивают.
`needs_recheck:true` требует любой текущий X-1 flag, `false` — ни одного; отсутствие
flags не подтверждает истинность/remote availability. Source — точный canonical URI;
whole-file и range различны. Revision — полный Git tree OID. При обоих списках
source identity и равенство адресованных bytes должны совпасть в одной binding.
Все requested revisions проверяются до inference и пустых candidate exits:
missing tree — not_found, wrong type/format — invalid_request, corruption — internal_error.
Eligible candidates ранжируются внутри полных FTS/vector каналов перед fusion/limit.
Query failure сохраняет эти же filters и обычный FTS success без query warning;
безопасная singleton query_error удаляется следующим успешным query при неизменной
config identity. Missing/bad config и несовместимая размерность дают filtered FTS.
Проверка storage/executor выполнена; status/problems UI остаётся TK-28.

## Runtime-проверки сверх JSON Schema
Приложение проверяет bytes/hash, доступность и тип объектов Git, границы строк end>=start, ссылки, уникальность якорей в файле, наличие created_at, includes DAG и принадлежность путей корню с учётом symlink. Schema не может доказать состояние файлов или аварийный протокол.

## Допущения до реализации
URI base_url включает API-префикс; его локальная проверка и построение запроса определены X-2. Состав status — по FR-32 и [D-95](../decisions.md#D-95), проверяется контрактными примерами. Алгоритм обхода, обнаружение изменений и блокировки — mechanics. Секреты не попадают в JSON или диагностику. Все приведённые примеры являются синтетическими примерами формы.

## Область согласованного чтения — 2026-10-19

Согласованное чтение нескольких документов выполняется по одному неизменяемому Git-снимку (существующий snapshot из inspect), [D-77](../decisions.md#D-77). Обычные чтения живых Markdown-файлов разрешены, но могут пересекать правки агентов и не получают межфайловой гарантии. Search/traverse сохраняют собственный согласованный снимок SQLite; он не распространяется автоматически на последующее чтение файлов. Протокол reader locks не вводится. CLI не возвращает содержимое документов; агент читает его самостоятельно. Состав JSON-ответов и перечень команд не меняются.

2026-10-19, [D-78](../decisions.md#D-78): max_retries обязателен в полном объекте конфигурации и его ответе; 0 означает только первую попытку, 3 — до четырёх попыток всего. Параметр не является частью HTTP-body провайдера. До настройки конфигурация остаётся null. Изменение любого настроенного поля, в том числе только этого, меняет identity и сбрасывает векторы и попытки; `enabled` и корневая обёртка в identity не входят ([D-95](../decisions.md#D-95), [D-104](../decisions.md#D-104)).

## Уточнение traverse TK-23 — 2026-10-26

`traverse` выполняет metadata-only BFS без query embedding, vector ranking и загрузки URL. Все старты валидируются до обхода; они исключены из результата, depth=0 возвращает пустой результат, includes занимает один шаг. Соседи обеих направлений объединяются по (тип, достигнутый ID, исходная тройка); incoming сохраняет ориентацию объявления. Node limit прекращает новые переходы сразу, edge_limit независимо ограничивает только реально рассмотренные рёбра, включая альтернативные пути и back edges; induced graph не строится. Строгий transport отклоняет неизвестные поля, malformed адреса и нецелые/отрицательные/переполненные числа до открытия storage.

## Index command — issue #94

`index` uses argv flags `--verify` and `--full` in either order; `--full` implies verification. Its stdin is `{}` or `{"paths":["letopis/architecture"]}` without a command wrapper. Nonempty paths select the named owner file or descendants at a directory boundary. Rows and removals outside the scope are untouched; valid unmatched selectors contribute nothing. An unchanged incremental corpus reports `published:false` and keeps its revision. Full mode always publishes and increments the revision, including for unchanged corpus. The `check.paths` input only filters findings and never scopes refresh. The former `reindex` command is removed; use `index --full`.
