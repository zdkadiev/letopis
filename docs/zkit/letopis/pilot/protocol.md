# P-1 — воспроизводимый протокол сравнительного пилота

Версия формата: **1**. Подготовлен в TK-5 на основании [NFR-8/FR-36](../requirements.md), [D-25](../decisions.md#D-25), [D-26](../decisions.md#D-26), [D-27](../decisions.md#D-27), [D-28](../decisions.md#D-28), [D-33](../decisions.md#D-33). Это методика и проверяемые формы, **не результат эксперимента и не доказательство пользы памяти**.

## 1. Вопрос, условия и границы

Сравнивается эффект самостоятельно накопленной межсессионной памяти целиком: один и тот же coding-агент выполняет одинаковые реальные связанные задачи Letopis в двух независимых условиях. `baseline` не переносит память между сессиями; `memory` начинает с пустого корпуса letopis и сохраняет созданные агентом знания. Обычные документы и исходники выбранного Git-снимка доступны обоим условиям. Сравнение с Markdown-заметками, Engram или другой системой памяти не проводится. Успешная работа этого checker не подтверждает выполнение NFR-8.

| Этап | Размер | Кто выбирает и запускает реальные задачи |
|---|---|---|
| `early` | 2 цепочки × 2 задачи × 2 условия = 8 записей | [TK-17](../roadmap/epics/EP-7-early-validation/tasks/TK-17-early-pilot.md) после TK-14/TK-16; решение G-1 |
| `final` | 3 цепочки × 3 задачи × 2 условия = 18 записей | [TK-30](../roadmap/epics/EP-5-final-pilot/tasks/TK-30-pilot-setup.md) выбирает; TK-31/TK-32 выполняют; TK-33 анализирует |

TK-5 не выбирает за будущий этап уже решённые задачи, не запускает агента/provider и не закрывает G-0: последний остаётся до TK-6. Подготовленный пример имеет `kind=demonstration`, синтетические задачи и фиктивные числа. Его прохождение проверяет только протокол. Реальные наблюдения используют `kind=pilot`, `real_tasks=true` и реальные источники evidence.

## 2. Что оператор фиксирует до запусков

Заполнить [study.json](templates/study.json), записать его SHA256 и сохранить неизменную версию у оператора. Пересмотр создаёт новый `study_id` и новую версию набора, а не подменяет условия после просмотра результатов. Шаблоны намеренно не готовы к запуску: `<fill>` и отсутствующие evidence должны быть заменены.

1. **Агент и бюджет.** Имя/версия harness, точный model/revision, параметры генерации, seed если поддерживается, common system/developer instructions, доступные tools, лимиты времени/ходов/контекста и правила retry. Нормализованный снимок общей конфигурации получает `agent.config_sha256`; этот же hash записывается в каждой сессии. Учесть делегирование: перечень `auxiliary_models` включает все вспомогательные модели, embedding/rerank. Основной agent/model/config в обоих условиях одинаков. Единственные разрешённые различия — подключение letopis, его навык и способ переноса его корпуса; обе инструкции сохраняются отдельно в `conditions.*.instruction`.
2. **Исходное состояние.** Для каждой цепочки — полный `base_commit` и `starting_code_sha256`. Последний — SHA256 канонического UTF-8 JSON-массива `[relative_path, sha256(bytes)]`, сортированного по POSIX-пути, с separators `(',', ':')` и завершающим LF. Учитываются все agent-visible файлы общего рабочего кода/документов/конфигурации; исключаются `.git`, экспериментальная память, логи и build outputs по заранее сохранённому одинаковому списку исключений. Состав/исключения и сам inventory приложить к preflight evidence. Hash нельзя выдавать за результат встроенного letopis API.
3. **Список задач.** Один и тот же замороженный текст каждой задачи, одинаковые входы и acceptance checks, общие правила оценки. `prompt` и `acceptance` имеют отдельные evidence refs. `check_ids` фиксируют полный набор проверок; `agreement_ids` — применимые договорённости. Оба условия получают одинаковый пользовательский prompt, не скрытый reviewer rubric или готовое решение.
4. **Порядок и вмешательства.** Заранее записать в selection/preflight evidence порядок цепочек и условий; по умолчанию автора — baseline первым в нечётной цепочке, memory первым в чётной. Это уменьшает односторонний эффект порядка, но не даёт статистической рандомизации. Одинаковые правила помощи оператора, сети и внешних данных; все подсказки/уточнения сохранять и тарифицировать. Не переносить знания или решения оператора из уже выполненного условия в другое.
5. **Полнота наблюдений.** Подготовить независимый inventory всех модельных запросов, raw usage, transcripts, correctness outputs, изменения code/memory inventory и операции памяти. Проверить, что harness действительно экспортирует нужные значения. Если экспорт недоступен, оставить `null` и отметить неполноту; не подставлять нули или оценки токенизатора вместо измерения.

`scoring_guide` — замороженные определения событий и нарушений с примерами из раздела 5. Reviewer fixtures/hidden checks держать вне agent-visible корня. Общие конфигурация/документы не включают готовый корпус Engram/letopis или решения будущих задач.

## 3. Подбор цепочек и защита от утечек

Кандидат — ещё не выполненная к моменту выбора реальная coding-задача Letopis с проверяемым результатом. В каждой следующей задаче должно быть объяснимо, какое исследование или договорённость из предыдущей работы может пригодиться; `reuse_from` содержит ID одной или нескольких предыдущих задач **той же** цепочки. Первая задача имеет пустой список. В `selection_rationale/selection_evidence` сохранить реальные issue/требования, мотивацию связи, rubric проверки и отсутствие доступного решения. Специально придуманные микрозадачи и synthetic RAM corpus не являются выборкой P-1.

Веток или Git worktrees одного checkout для изоляции эксперимента недостаточно: общий object store, refs, history и глобальная память могут раскрыть решения. Оператор готовит независимые копии только разрешённого стартового снимка и требуемых разрешённых Git-объектов, отдельные HOME/state/session directories и доступы. Не копировать `.engram`, накопленные `.agents`/memory files, историю данного разговора, прошлые session transcripts, Codex global memory, solutions или память другого условия. Build caches могут быть общими только при документированном отсутствии смыслового контекста и готовых решений в их содержимом; иначе изолировать их тоже.

Зафиксировать distinct `workspace_id`, `home_id`; memory store существует только у `memory`. Выключить все прочие механизмы межсессионной памяти, auto-resume, shared chat history и облачные knowledge stores. Ограничить видимость filesystem/tools так, чтобы агент не мог прочитать другое условие, операторские evidence и известные готовые решения. Проверить это до запуска попыткой прочитать заранее размещённые canary files через **те же инструменты и subprocess**, которыми пользуется агент. В `conditions.*.isolation` приложить config, allowlist, результаты probe и хеши доступного снимка. Разные строки ID — лишь метаданные, не proof sandbox.

Выбор автора для независимой единицы сравнения: **каждая цепочка начинает с пустой памяти**, затем внутри неё память продолжается только у `memory`. Между цепочками оба состояния создаются заново. Это не испытание обучения между разными цепочками. Новая сессия обязательна на каждой выполненной задаче, в обоих условиях; session IDs не повторяются во всём study.

## 4. Выполнение и формы записи

Для каждой пары цепочка/условие:

1. Проверить исходный code inventory и пустую память; начать новую сессию с замороженным prompt/config. В `memory` предоставить актуальную инструкцию навыка из [FR-36](../requirements.md), соответствующую испытываемому slice/full version: поиск ссылок, чтение исходных Markdown, формат/якоря/метаданные, обычные файловые правки агентом, `check` и исправление ссылок, работа с Git/source_snapshot. Не подменять отсутствующие CLI-команды mock-результатами. Минимальный навык slice поставляет TK-14; полный — соответствующий build. Baseline получает общие инструкции разработки без навыка накопления памяти.
2. Агент сам решает, что исследовать и сохранять. Корпус в memory не наполняется заранее дизайн-документами. Читать общие документы можно в обоих условиях. Сохранять, читать и проверять знания стоит токенов; они входят в полный расход.
3. Собрать исходный transcript, usage и correctness outputs. Снять code/memory inventory до и после. Code после задачи передаётся следующей задаче **своего** условия; патчи/корпус между условиями не копируются. Реализации могут различаться при одинаковых критериях корректности — это ограничение причинного вывода, которое отметить в отчёте.
4. Заполнить отдельную [session.json](templates/session.json) для каждого запланированного слота, включая ошибки. `correct` — все common checks true; `failed` — хотя бы один false; `incomplete` — false нет, но есть null. Не выполненную после провалившегося/незавершённого предшественника зависимую задачу записать `not_run` с причиной, `session_id=null`, всеми checks/agreements null, пустыми request inventory/research/profile и неизменным состоянием. Молча выкидывать задачу запрещено.
5. Начать следующую задачу новой сессией. `memory_before` равен `memory_after` предыдущей задачи; baseline всегда пуст. Даже если memory не записал полезного знания, оставить этот результат. Не заставлять post-hoc сохранить «правильный» факт ради пилота.

Memory snapshot имеет `items` (число канонических Markdown-файлов корпуса) и SHA256 inventory в том же формате, что code, без `.letopis` производных DB/lock/cache и без логов. Пустой корпус — hash UTF-8 `[]\n` (`37517e5f3dc66819f61f5a7bb8ace1921282415f10551d2defa5c3eb0985b570`; вычислить по правилу, не переписывать из примера). Checker вычисляет константу из этих байтов, сверяет первый пустой snapshot и непрерывность. Количество файлов не является количеством semantic fragments; оно не измеряет качество памяти.

Все refs evidence имеют `path`, `sha256`, `locator`: относительный путь внутри отдельного evidence root, SHA256 полного файла и точное место (строки/запрос/этап). Checker проверяет обычный файл, confinement и checksum, но **не доказывает смысл locator или правдивость аннотации**. Оператор сверяет место с исходным trace. Не добавлять секреты/ключи в публикуемые файлы; raw evidence с секретами хранить отдельно, публикуя пригодную для проверки отредактированную копию и её checksum. Эта инструкция не является security test.

## 5. Три метрики и корректность

**Повторные исследования.** Единица — самостоятельный эпизод поиска/чтения/вывода одного факта, полезного для задачи, с evidence в transcript. Общие `fact_id` кодирует оператор по замороженному rubric, не сообщает агентам. `first` — факт впервые установлен в этой цепочке/условии; `repeat` — агент повторно устанавливает уже установленный в предыдущей сессии факт; `revalidation` — целенаправленно перепроверяет прежний факт из-за возможной смены основания. Например, повторное выяснение того же владельца lock — repeat, проверка изменившегося кода владельца — revalidation. Повторный шаг в той же сессии не становится межсессионным repeat. `unresolved` означает неопределённую классификацию эпизода, в котором сам факт уже установлен и подтверждён evidence; этот fact_id входит в inventory для следующих сессий. Если неизвестно, был ли факт установлен, не добавлять его как установленный: сохранить сомнение в исходном trace/отчёте и завершить разметку до сравнения. `unresolved` сохраняет неоднозначность, не выдаётся за ноль. Показывать все четыре счётчика; основной repeat count неизвестен при unresolved. Семантическая классификация требует человека, а не простой суммы tool calls. Не считать каждое чтение документа отдельным исследованием.

**Договорённости.** До запуска задачи определить применимые `agreement_ids` и их смысл/источник в общем rubric. Для каждой возможности в обоих условиях записать `violated=true/false/null` и evidence. Показывать planned/assessed/not_run/unresolved и violations; rate = violations / assessed только при полном наблюдении выполненных возможностей и ненулевом denominator. Нельзя уменьшить число нарушений, не оценив сложные случаи. Договорённость, входящая в обязательную корректность, также проваливает acceptance check; stylistic agreement не подменяет функциональную проверку. Не добавлять удобные правила после просмотра результатов.

**Токены.** Сумма нормализованных input + output всех уникальных модельных запросов во всех попытках/ошибках/retries/delegation/compaction, включая поиск/переранжирование/embedding и работу агента с памятью. Для каждой сессии независимый `request_inventory.ids` сверяется с `requests[].id`; request IDs уникальны во всём study (при необходимости namespace provider/attempt/session). Закрытые внутренние вызовы не объявляются нулевыми: неизвестные input/output — `null`, итог total — `null`, отдельно известный subtotal и неизвестные request IDs. Результаты памяти, tool output, инструкции и summaries уже входят в prompt последующих LLM calls и **не прибавляются повторно** как оценка длины текста. Локальное файловое чтение/запись без модели не создаёт отдельный token charge.

`cached_input_tokens` — подмножество нормализованного input; `reasoning_output_tokens` — подмножество нормализованного output. Они показываются отдельно, не прибавляются второй раз. Если provider считает output без reasoning, exporter обязан сначала нормализовать сумму по raw usage и сохранить evidence. Если нормализация невозможна — output=null. Неизвестная разбивка cache/reasoning не делает известный общий input/output неизвестным. Итого и subtotal показываются по model и purpose (`agent`, `embedding`, `rerank`, `auxiliary`); сумма разных токенизаторов — только бухгалтерский raw count, не одинаковые единицы compute/цены. Анализ не придумывает процент улучшения или денежную стоимость.

**Корректность — отдельный gate.** `correctness_checks` показывает planned/assessed/not_run и unresolved_check_ids. Неоценённый check выполненной задачи остаётся пропуском даже при другом false check и outcome=failed: data_complete=false, провал также сохраняется в outcomes/correctness_preserved. Null checks заведомо невыполненного not_run считаются отдельно и не маскируют пропуски выполненной задачи. При одновременном провале и неполноте status=incomplete_data; correctness_preserved=false остаётся видимым. Полный positive вывод об экономии не допускается при failed/incomplete/not_run хотя бы в одном условии или при неполных метриках. Все такие слоты и их затраты остаются в таблице, отдельно перечислены пары задач с двумя correct outcomes. Checker не выбирает «победителя» по дешёвому провалу. Даже полностью корректный и полный малый sample даёт только descriptive данные; он не доказывает причинность, превосходство над иными системами памяти или статистическую значимость.

## 6. Профиль для P-2.7 и отчёт

`workload_profile` сохраняет реальные операции letopis/файлового редактора: `operation` search/read/create/edit/delete, фактический `uri`, UTF-8 `bytes`, время относительно начала сессии `timestamp_ms`, длительность `elapsed_ms`, `group_id` для совместной create/edit/delete правки и `error`, evidence. Это журнал наблюдений внешних операций, не новые команды/поля продукта. Неизвестные размеры/время — null. Code должен зафиксировать metadata/schema существующего slice, а не объявлять операции выполненными по тексту agent response. Snapshot памяти меняется только с записанной успешной create/edit/delete операцией. В baseline профиль пуст. По временам/группам и исходным rows TK-33 передаёт частоты/размеры/URI/группировку ресурсным задачам; synthetic demo не источник ресурсных входов.

Заполнить [report.md](templates/report.md): замороженный study/config/source, оба условия, все слоты, correctness, три критерия с denominators/unknowns, полный token ledger, утечки/вмешательства/retries, профиль и явные ограничения. Negative, mixed, incomplete и inconclusive результаты сохраняются равноправно. Решение G-1 или итоговая оценка остаётся у соответствующей roadmap-задачи/разработчика; нового обязательного процента нет.

## 7. Воспроизведение checker

Из Git-корня:

```sh
python3 -B tests/pilot_protocol/check.py \
  tests/pilot_protocol/examples/demonstration/study.json \
  tests/pilot_protocol/examples/demonstration/sessions \
  --evidence-root tests/pilot_protocol/examples/demonstration

python3 -B tests/pilot_protocol/run.py --evidence NEW_DIRECTORY
```

Зависимости: Python 3.11+, standard library. CLI читает study и все session JSON, проверяет evidence и печатает JSON в stdout; exit 0 — supplied records валидны, exit 2 — ошибка с field locator. CLI ничего не исправляет и не запускает агента. Дубликаты JSON keys и nonfinite числа отвергаются. Время операции — неотрицательное конечное число или null: целые проверяются без преобразования в float, верхняя граница времени форматом не вводится. Валидность не равна полноте: неизвестные usage/annotations остаются видимыми, outcome задачи не меняется ради красивого отчёта. Демонстрация всегда выдаёт status `demonstration_only`; реальные записи — `incomplete_data`, `correctness_not_preserved` или `descriptive_only`. Ни один status не равен «пилот выигран».

Локаторы с arbitrary text, quarantine/allowlist, agent identity и семантические оценки требуют операторской проверки. Checker не защищает от оператора, сфальсифицировавшего source logs/hash/attestation; не является ОС sandbox, model runner или доказательством correctness beyond supplied acceptance evidence. JSON/profile счётчики — выбранные форматы эксперимента, не публичный API Letopis. [README checker](../../../../tests/pilot_protocol/README.md) содержит точные примеры и ограничения.
