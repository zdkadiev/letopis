# letopis — модель хранения данных

Статус: начало детального проектирования хранения. Согласованные гарантии отделены от предлагаемых записей, ключей и физических механизмов. Согласованы единые `nodes` и `edges`, значение `nodes.kind = source` и общее поле адреса `uri`. Записи источников в `nodes` сохраняют идентичность при реиндексировании. Согласована уникальность UUID среди текущих nodes и edges без проверки истории; отдельное бессрочное резервирование удалённых ID исключено. Имена остальных наборов записей и их устройство обсуждаются. Выбраны Rust, rusqlite и vec1; SQLite является единой служебной БД первой версии. Физический DDL и реализация ещё проектируются; согласованные параметры SQLite описаны ниже.

Основания: [требования](../requirements.md), [доменная модель](../appendix/domain-model.md), [подсистемы](../architecture.md), [контракты](../contracts.md).

## Согласованное разделение данных

| Группа | Источник истины и место хранения | Жизненный цикл и восстановление |
|---|---|---|
| Канонические знания | Размеченные Markdown-файлы рабочей копии | Правки через CLI; версионирование содержимого в Git |
| Содержимое снимков | Объекты и служебные ссылки Git | Выданные и используемые снимки удерживаются бессрочно средствами Git |
| Графовая проекция | Производные записи в БД | Структура восстанавливается из документов; долговечные ID и адреса источников сохраняются в единой nodes |
| Текстовый индекс | Производная поисковая структура | Перестраивается; копии текста документов в БД не сохраняются |
| Embeddings и векторный индекс | Производные данные в БД/адаптере индекса | Вычисляются через очередь и могут отставать от графа/FTS; используются только совместимые с текущим поисковым текстом векторы |
| Идентичность внешних источников | Долговечное служебное состояние БД | Соответствие нормализованного uri и UUID хранится в nodes бессрочно, включая источники без ссылок |
| Подтверждённое основание знания | Source_snapshot в каноническом Markdown; его проекция в nodes, содержимое источников в Git | Один общий Git tree OID всех источников знания; явное подтверждение и история обязательны. Отсутствующее основание — NULL в nodes и опущенное поле в Markdown; история читается по известным Git-снимкам без учёта в БД; фильтр по ревизии сравнивает содержимое источника через Git без отдельного OID коммита |
| Выполнение и восстановление | Долговечный журнал БД и OID в Git | Незавершённая правка откатывается после сбоя; надёжно завершённая сохраняется. Запись восстановления удаляется после надёжного завершения правки или полного отката; бессрочный кэш успешных ответов не используется |
| Задания индексирования | Долговечное служебное состояние БД | Снимок, выбранная область, состояние и использованные ретраи; восстановление по тому же снимку |
| Локи и диагностика | Служебное состояние проекта | Локи для короткой фазы сохранения/восстановления; неустранённые ошибки переживают перезапуск |

Перестройка индекса не стирает идентичности источников, подтверждённые основания, удерживаемые Git-снимки и данные незавершённого восстановления. Текущее основание восстанавливается из канонического Markdown, прежние состояния читаются по известным Git-снимкам. Потеря всей служебной БД не равнозначна штатному reindex: автоматически назначенные UUID и время создания внешних вершин не восстанавливаются из одних текущих Markdown-файлов. План резервного копирования и восстановления служебного состояния требует отдельного проектирования.

Предыдущие опубликованные данные удерживаются только для использующих их запросов. Проверенные граф и FTS публикуются без ожидания всех embeddings; отсутствие актуальных векторов не блокирует FTS. Старый вектор не должен представлять изменившийся поисковый текст.

## Согласованные правила поисковых данных

Поиск использует одно детерминированное представление собственного текста вершины или метавершины: служебные блоки letopis и графовые метаданные удаляются, от ссылок остаются подписи, кодовые примеры сохраняются. Содержимое связанных и вложенных элементов не подгружается в этот текст. Он временно используется текстовым индексом и embedding-адаптером; копия текста документа в БД не сохраняется. `base_hash` по-прежнему вычисляется по полному исходному Markdown.

Embedding из доступного корректного индекса повторно используется при совпадении SHA-256 подготовленного поискового текста и идентичности адаптера, версии модели и влияющих на вектор параметров. Изменение текста или конфигурации требует вычисления. Ключ не ограничивается UUID или байтовым хешем исходного Markdown. Постоянный архив прежних векторов не вводится: ненужные данные освобождаются вместе с индексами после завершения читателей. Схема внутренних входа и выхода порта использует `texts` и соответствующий массив `vectors`; размерность задаёт модель. Физические записи и ключи ещё проектируются.

## Согласовано время создания узлов и рёбер

14 октября 2026 года принято требование времени создания узлов и рёбер. Для элементов с каноническим Markdown-представлением источник метки — соответствующий документ, а БД хранит её проекцию. Подтверждена постоянная дата рождения элемента. При редактировании и переносе существующего элемента с сохранением ID дата остаётся прежней; при восстановлении его описания из Git и при построении графа в новой БД значение читается из канонической разметки. Время запуска reindex не становится новым временем создания элемента. Метаданные в комментарии узла или title ссылки остаются частью согласованного хешируемого Markdown.

Автоматическое назначение времени создания выполняет letopis при первом успешном создании элемента. Агент передаёт create без даты; подготовленное значение сохраняется вместе с элементом в согласованной атомарной правке. Для размеченных элементов Markdown и БД получают одну метку, для внешнего источника первая регистрация фиксирует время только в nodes. При последующем редактировании, переносе и реиндексировании первоначальное время сохраняется; индексирование существующего размеченного описания читает его метку. Принято created_at INTEGER NOT NULL в nodes и edges: Unix timestamp в целых секундах с 1970-01-01 00:00:00 UTC. В JSON-маркере узла это число, в title канонической ссылки — created_at=SECONDS после id и type. Пример: 1791970200 соответствует 2026-10-14 09:30:00 UTC. Новым элементам метку назначает letopis; существующим размеченным элементам она копируется из канонического описания. SQL DEFAULT времени не задаётся: реиндексирование воспроизводит дату создания элемента. Единица измерения одна для Markdown и БД; поля часового пояса и формата не вводятся. Основание представления: [SQLite Date and Time Datatype](https://www.sqlite.org/datatype3.html#date_and_time_datatype).

Для kind = source принято исключение: время первой регистрации в графе хранится только в служебной БД, в существующей записи nodes вместе с UUID и URI. Исходный код и другие неразмеченные документы не изменяются CLI letopis. При повторной ссылке и реиндексировании сохраняются идентичность и прежнее время создания источника; после удаления всех ссылок метка остаётся в долговечной записи nodes. Отдельный документ или дополнительная таблица ради метки источника не вводится. Используется created_at INTEGER NOT NULL с Unix timestamp в секундах; назначение новой метки выполняет letopis. При потере всей БД первоначальные метки внешних источников требуют восстановления служебного состояния вместе с их UUID и URI; одни Markdown-документы не воспроизводят эти даты. Резервное копирование служебного состояния уже относится к отдельному этапу проектирования.

Общее подтверждённое основание знания принято хранить в source_snapshot канонического Markdown и проекции nodes; раздел ниже определяет его смысл. Created_at и source_snapshot имеют разные назначения: постоянная дата создания и подтверждённый снимок источников.

## Согласованная уникальность идентификаторов

Статус: принято 12 октября 2026 года. Проверяется уникальность UUID среди текущих nodes и edges, включая долговечные source без ссылок. История удалённых элементов для генерации и проверки UUID не просматривается.

UUID хранятся в SQLite как TEXT в каноническом строковом виде: нижний регистр, с дефисами. То же представление используется в Markdown и JSON CLI. Это относится к nodes.id, edges.id и ссылкам edges.source_id/target_id. Предложение бинарного хранения UUID отклонено как предварительная оптимизация. Правила идентичности, генерации и уникальности сохраняются. Для nodes приняты row_id INTEGER PRIMARY KEY AUTOINCREMENT и id TEXT NOT NULL UNIQUE; остальные физические ключи и ограничения уточняются отдельно.

Новый UUIDv4 генерирует letopis. Совпадение с занятым текущим ID требует другого UUID. Дублирующие объявления в каноническом корпусе отклоняются. Проверка не может опираться только на отстающую опубликованную поисковую проекцию; физическая межтабличная уникальность и конкурентный протокол ещё проектируются.

Отдельная identities и deleted-записи только ради резервирования удалённых ID не вводятся. Ранее обсуждавшиеся варианты заменены этим решением. Намеренного переиспользования освобождённых ID генератор не выполняет, но совпадение с забытым историческим UUID не проверяется. Перенос и восстановление той же сущности сохраняют ID. После потери ответа агент узнаёт ID уже сохранённых элементов из документов и актуальных метаданных.

Изменение политики UUID не отменяет историю оснований знаний и соответствие uri/UUID известных источников. Бессрочное хранение результатов для дедупликации отменено отдельным последующим решением. Отсутствие ссылок на source не является удалением его долговечной записи. Данные прежней индексной проекции удерживаются до завершения её читателей, независимо от политики UUID.

Мотивация: устойчивые ссылки и текущая целостность сохраняются без дополнительного исторического реестра и жизненного цикла tombstone. Пожизненное резервирование UUID больше не является гарантией первой версии.

## Согласовано: текстовое хранение SHA-256

Статус: принято пользователем. Значения SHA-256 в служебной БД хранятся как SQLite TEXT: 64 строчных шестнадцатеричных символа без префикса, в том же формате, который уже согласован для CLI. Правило распространяется на сохраняемые хеши файлов, элементов, правок и подготовленного поискового текста. Способы вычисления этих значений остаются согласованными ранее. Для недоступного источника сохраняется согласованный SQL NULL вместо хеша; новое правило доступности не вводится.

Вход: вычисленный SHA-256 канонического фрагмента. Выход хранения и чтения: одна и та же строка из 64 hex-символов в `nodes.hash` и JSON-ответе `inspect`; агент может использовать её как `base_hash` при следующей правке. Аналогичное представление применяется к хешам рёбер и остальным сохраняемым SHA-256.

Мотивация: единое представление в БД и CLI упрощает сопоставление значений, диагностику и преобразования на границах адаптеров. Выбор соответствует уже принятому текстовому хранению UUID и принципу простейшего корректного решения. Git OID сохраняет формат и алгоритм текущего Git-репозитория; формат SHA-256 letopis не переопределяет Git-идентификаторы.

### Согласовано: обязательность hash в nodes

Колонка nodes.hash хранится как TEXT со следующим ограничением:

```sql
hash TEXT
  CHECK (hash IS NOT NULL OR kind = 'source')
```

У vertex и metavertex хеш обязателен: letopis вычисляет SHA-256 полного канонического Markdown-фрагмента выбранного снимка. У недоступного внешнего source допускается SQL NULL; его UUID, адрес и связи сохраняются. Обязательность и допустимые значения kind закрепляются ранее согласованными NOT NULL и CHECK. Правила формирования и текстовое представление SHA-256 остаются прежними.

Вход: vertex или metavertex с вычисленным хешем. Выход: запись проходит это ограничение. Для этих видов hash = NULL вызывает ошибку ограничения SQLite. Недоступный source с hash = NULL допускается; корректный хеш доступного source также допускается. Ошибка при сохранении обрабатывается по согласованным правилам всей транзакции и восстановления.

Мотивация: узлы знаний имеют хеш для оптимистического контроля через base_hash; недоступность внешнего источника сохраняет его идентичность в графе. Ограничение использует существующие hash и kind и не добавляет новые поля или таблицы.

## Согласованная графовая проекция nodes и edges

Статус: сохранение метавершин/includes в доменной модели и представление хранения обычным графом nodes/edges согласованы. Исторический реестр identities не используется. Физические ключи nodes согласованы ниже; остальные ключи и индексы ещё проектируются.

Одна согласованная графовая проекция представляется наборами `nodes` и `edges`. Логическая модель не требует отдельной записи списка детей внутри метавершины. Системное ребро `includes` хранится в том же наборе рёбер; непосредственно включённые элементы выбираются по источнику и типу ребра.

### Логические записи nodes

| Поле | Смысл | Ограничение |
|---|---|---|
| `id` | Постоянный UUID узла | Уникален среди текущих nodes и edges; идентичность источника сохраняется независимо от перестройки и наличия ссылок |
| `kind` | `vertex`, `metavertex` или `source` | Вид хранения; source соответствует обычной вершине источника в домене |
| `uri` | Адрес описания или источника | Для знаний — путь с ID; для файлового источника — путь с необязательным диапазоном; модель допускает веб-адреса, их поведение ещё уточняется |
| `lines` | Начальная и конечная строки | Нумерация от 1, включительно; координаты снимка, для недоступного внешнего источника — его сохранённый адрес; для source без диапазона отсутствует |
| `hash` | SHA-256 полного фрагмента | Канонический фрагмент для знаний, адресованный фрагмент/файл для источника; для недоступного внешнего источника допускается `null` |
| `created_at` | Время создания | INTEGER NOT NULL, Unix timestamp в секундах; у source — время первой регистрации |
| `source_snapshot` | Общее подтверждённое основание знания | TEXT, полный Git tree OID; NULL при неустановленном основании и у source, в Markdown отсутствующее поле опускается |

`file_hash` относится к файлу и вычисляется для inspect по точным байтам общего Git-снимка, один раз на файл в рамках вызова. Постоянный кэш file_hash в БД не используется; согласованный порядок описан в разделе «Хеш файла по запросу». Это логические записи, а не окончательный физический DDL; согласованное представление диапазона двумя INTEGER-колонками описано ниже.

### Согласовано: ключи nodes и связь с поисковыми таблицами

Для nodes приняты следующие физические ключи:

```sql
row_id INTEGER PRIMARY KEY AUTOINCREMENT,
id     TEXT NOT NULL UNIQUE
```

Row_id — внутренний числовой ключ строки SQLite; UUID элемента хранится отдельно в id. Колонка row_id является явным псевдонимом встроенного rowid, но в nodes и SQL приложения используется согласованное имя row_id. SQLite назначает её автоматически при создании строки. AUTOINCREMENT не переиспользует автоматически номера ранее зафиксированных и затем удалённых строк сохраняемой таблицы; непрерывная последовательность без пропусков не требуется. Основание: [SQLite AUTOINCREMENT](https://www.sqlite.org/autoinc.html).

Для индексируемого знания используется равенство text_index.rowid = vector_index.rowid = nodes.row_id. Text_index и vector_index здесь — рабочие имена поисковых таблиц; их окончательный DDL ещё проектируется. Отсутствие вектора до обработки очереди допускается по согласованным правилам. UUID в Markdown, CLI, концах рёбер и embedding_jobs.node_id сохраняет прежний смысл; внутренний row_id не заменяет публичный ID. Проверка уникальности UUID среди текущих nodes и edges остаётся обязанностью общего валидатора и протокола записи: UNIQUE в nodes закрепляет только уникальность внутри этой таблицы.

Вход: создание знания с постоянным UUID U1. Выход хранения: SQLite назначает row_id = 42; записи FTS5 и готового вектора используют rowid = 42. Поиск получает числовой ключ, находит nodes.id = U1 и возвращает согласованные метаданные и ссылку. Если строка 42 удалена после COMMIT, автоматически создаваемая следующая строка не получает её номер.

Мотивация: одна существующая таблица связывает UUID со штатными числовыми ключами FTS5 и vec1, без отдельной таблицы соответствий. Явный INTEGER PRIMARY KEY сохраняет ключ при VACUUM. Полная схема nodes и порядок обновления поисковых строк уточняются отдельно; этим примером не подтверждается реализация будущей системы.

### Согласовано: UPSERT nodes по UUID

При сохранении подготовленной графовой проекции новые UUID вставляются в nodes, а существующие обновляются через ON CONFLICT(id) DO UPDATE. Ветвь обновления изменяет данные узла, сохраняя id и row_id; эти ключи не включаются в список SET. Решение применяется внутри согласованной транзакции apply или публикации результатов реиндексирования. Проверки разметки, оптимистических хешей и целостности до сохранения остаются обязательными: UPSERT не разрешает дублирующие объявления UUID в корпусе и не меняет правила create/edit CLI.

Схематичный пример обновления только поля hash, а не полный SQL для всех колонок nodes:

```sql
INSERT INTO nodes (id, hash)
VALUES (:id, :hash)
ON CONFLICT(id) DO UPDATE SET hash = excluded.hash;
```

В окончательном запросе вставки и обновления передаются необходимые поля подготовленной записи; полный DDL nodes ещё уточняется. Для source приложение сначала разрешает нормализованный uri в существующий UUID по согласованному правилу. Конфликт другого UUID по уникальному адресу источника не должен молча заменять его идентичность.

Вход: существующий UUID U1 с row_id = 42 и hash = h1; подготовленная запись U1 содержит hash = h2. Выход: та же строка с row_id = 42, id = U1 и hash = h2. Новый UUID получает автоматически назначенный row_id. Связи с FTS5 и vec1 используют прежний ключ существующего узла; актуальность текста и вектора обновляется по ранее согласованным правилам.

Мотивация: штатный UPSERT обновляет существующую строку без удаления и повторной вставки. Поэтому обновление nodes само по себе не вызывает каскадное удаление embedding_jobs, ссылающихся на UUID узла. Новая работа embeddings ставится отдельно по правилам очереди. Согласованный INSERT OR REPLACE в embedding_jobs сохраняется: там замена намеренно создаёт новый seq. Основание: [SQLite UPSERT](https://www.sqlite.org/lang_upsert.html), [SQLite REPLACE](https://www.sqlite.org/lang_conflict.html).

### Согласовано: уникальность адреса source в БД

Для nodes принят частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX nodes_source_uri
ON nodes(uri)
WHERE kind = 'source';
```

Индекс закрепляет правило: нормализованный uri соответствует одной текущей строке source. При разрешении повторной external-ссылки letopis находит и использует существующий узел источника с тем же адресом; новый UUID для того же источника не создаётся. SQL-ограничение отклоняет попытку сохранить вторую строку source с тем же uri. Для vertex и metavertex этот индекс дополнительной уникальности uri не вводит; правила их канонического описания сохраняются.

Вход: знания A и B содержат external-ссылки на src/auth.rs#L10-L20. Выход: в nodes одна строка source для нормализованного адреса и две связи к её UUID. Создание второй source-строки с другим UUID и тем же адресом вызывает ошибку ограничения SQLite; соответствующая операция обрабатывается по согласованным правилам транзакции и восстановления.

Мотивация: одна идентичность источника используется всеми знаниями, которые на него ссылаются. Правило выражено штатным индексом существующей таблицы без отдельной таблицы адресов или SQL-триггеров. Основание: [SQLite: unique partial indexes](https://www.sqlite.org/partialindex.html#unique_partial_indexes). Нормализация uri остаётся обязанностью приложения перед сравнением и сохранением; индекс сравнивает уже нормализованные значения.

### Согласовано: хранение вида узла

Статус: принято пользователем. Поле `nodes.kind` хранится как обязательный TEXT с тремя согласованными структурными значениями: `vertex`, `metavertex`, `source`. Используются штатные NOT NULL и CHECK:

```sql
kind TEXT NOT NULL
  CHECK (kind IN ('vertex', 'metavertex', 'source'))
```

Вход записи проекции: `kind = 'metavertex'`. Выход: это значение проходит проверку вида и сохраняется той же строкой; остальные ограничения записи остаются обязательными. `kind = 'unknown'` и SQL NULL отклоняются. При нарушении индексатор откатывает обновление и сохраняет последний корректный индекс. Доменная проверка разметки до сохранения документов сохраняется.

Мотивация: вид узла читается непосредственно из строки и соответствует согласованным именам доменной модели. Штатные ограничения закрепляют обязательность и допустимый набор значений в существующей таблице. Отдельный справочник видов и числовое кодирование не нужны. Это структурный вид элемента, а не смысловая метка знания или проектный тип ребра. Основание: [SQLite CHECK и NOT NULL](https://www.sqlite.org/lang_createtable.html#check_constraints).

### Согласовано: обязательный uri в nodes

Для всех видов узлов nodes принят один обязательный адрес:

```sql
uri TEXT NOT NULL
```

Для vertex и metavertex uri адресует канонический Markdown-фрагмент: путь от корня проекта со стабильным ID. Для source он содержит нормализованный адрес источника с необязательным диапазоном. Проверки формата адреса и нормализация выполняются приложением по согласованным правилам; NOT NULL закрепляет наличие адреса в БД.

Вход: источник src/auth.rs стал недоступен. Выход: его строка source сохраняет uri = src/auth.rs, UUID и связи; hash допускает NULL по принятому CHECK. Попытка сохранить любой вид узла с uri = NULL вызывает ошибку ограничения SQLite и обрабатывается по правилам соответствующей транзакции и восстановления.

Мотивация: поиск возвращает ссылки на знания, а перепроверка источников использует сохранённый адрес. Недоступность содержимого сохраняет этот адрес. Одна обязательная колонка обслуживает все виды узлов.

### Согласовано: хранение диапазона строк

Статус: принято пользователем. Имеющийся диапазон строк узла хранится в `nodes` двумя колонками SQLite INTEGER: `line_start` и `line_end`. Нумерация начинается с 1, обе границы включены, как уже согласовано в контракте. JSON-поле `lines` формируется из этих двух значений; отдельная запись массива в БД не требуется.

Вход индексатора: канонический фрагмент расположен на строках 12–24 выбранного Git-снимка. Выход хранения: `line_start = 12`, `line_end = 24`; выход CLI по-прежнему содержит `lines: [12, 24]`. Диапазон относится к соответствующему снимку и не заменяет стабильный ID элемента. Согласованное сохранение адресованного диапазона недоступного источника остаётся в силе; представление отсутствующего диапазона описано ниже, конкретный DDL ещё проектируется.

Мотивация: два скалярных значения прямо представляют начало и конец фрагмента, удобно читаются и проверяются средствами SQL. Агент получает прежний диапазон для точечного чтения документа. Новые публичные поля или команды не вводятся.

### Согласовано: источник без диапазона строк

Статус: принято пользователем. Для `kind = source`, адресующего файл целиком без указания строк, `line_start` и `line_end` оба равны SQL NULL. В JSON-метаданных `inspect` и ссылках `traverse` поле `lines` для такого источника опускается; `path` продолжает адресовать весь файл. SHA-256 вычисляется по всему файлу согласно уже согласованному правилу. Размеченные вершины и метавершины имеют обе границы своего канонического фрагмента.

Вход: ссылка типа `external` на `src/storage.rs` без `#L...`. Выход хранения: `kind = source`, `uri = 'src/storage.rs'`, `line_start = NULL`, `line_end = NULL`. Выход адреса в CLI: `path = 'src/storage.rs'`, поле `lines` отсутствует. Агент читает весь файл по указанному адресу и ревизии. Для адреса `src/storage.rs#L12-L24` сохраняются значения 12 и 24; исчезновение файла или недоступность этого диапазона не превращает адресованный фрагмент в ссылку на весь файл. Согласованные признаки недоступности и `null` для недоступных хешей сохраняются.

Мотивация: представление соответствует смыслу исходной ссылки. Отсутствие диапазона означает чтение всего файла, а заданные координаты сохраняют адрес конкретного фрагмента независимо от доступности содержимого. Агенту не требуется угадывать, какой из этих двух случаев подразумевался. Представление одной заполненной и одной пустой границы не допускается; конкретные ограничения DDL ещё уточняются.

### Согласовано: CHECK для границ диапазона

Статус: принято пользователем. В `nodes` добавляется одно ограничение CHECK: заполненный диапазон имеет обе границы, начало не меньше 1 и конец не меньше начала; две пустые границы допустимы только для `kind = source`. Соответствие диапазона адресу источника проверяется доменным валидатором. Это закрепляет уже согласованные правила, не меняя контракты CLI.

```sql
CHECK (
  (kind IS 'source' AND line_start IS NULL AND line_end IS NULL)
  OR
  (line_start IS NOT NULL AND line_end IS NOT NULL
   AND line_start >= 1 AND line_end >= line_start)
)
```

Вход записи проекции: `vertex` с границами `(12, 24)` или `source` с `(NULL, NULL)` — допустимы. `(24, 12)`, `(0, 12)`, `(12, NULL)` и `vertex` с `(NULL, NULL)` — недопустимы. Выход: допустимая запись сохраняется; нарушение вызывает ошибку SQLite, индексатор откатывает обновление и сохраняет последний корректный индекс. Предварительная доменная проверка до сохранения документов остаётся обязательной.

Мотивация: один штатный CHECK закрепляет корректность адресуемого диапазона в существующей таблице. Это помогает сохранять точные ссылки на фрагменты, которые получает агент. Явные `IS NULL` и `IS NOT NULL` учитывают семантику SQLite: результат NULL сам по себе не нарушает CHECK. Типы колонок и остальные ограничения уточняются в окончательном DDL. Основание: [SQLite CHECK constraints](https://www.sqlite.org/lang_createtable.html#check_constraints).

### Логические записи edges

| Поле | Смысл | Ограничение |
|---|---|---|
| `id` | UUID ребра | Уникален среди текущих nodes и edges; исторический реестр UUID не используется |
| `source_id` | UUID источника | Ссылка на запись nodes в той же проекции |
| `target_id` | UUID назначения | Ссылка на запись nodes в той же проекции, отличается от источника |
| `type` | Тип связи | Системные и проектные типы в согласованной грамматике |
| `hash` | SHA-256(JCS({source, markdown})) | Хеш вычисляется из канонической ссылки; полный Markdown в БД не сохраняется |
| `created_at` | Время создания ребра | INTEGER NOT NULL, Unix timestamp в секундах из канонического title |

Для обычных рёбер одна пара может иметь несколько записей, в том числе одного типа. Для `includes` разрешено только одно ребро на упорядоченную пару; его источник — метавершина. Циклическая включённость запрещена. Эти ограничения проверяются доменным валидатором; согласованные ограничения БД описаны ниже.

Метавершины разделяют общие элементы посредством разных рёбер `includes`, без копирования записи nodes. Внутренние рёбра фрагмента определяются правилом непосредственного вхождения обоих концов. Определение edges и UPSERT согласованы ниже; индексы для входящего/исходящего обхода и порядок синхронизации группы записей ещё проектируются.

Мотивация: агент получает обычные связи и включённость из одной согласованной структуры. Удаление или изменение `includes` не требует синхронизировать отдельный массив членства, а общий элемент остаётся одним узлом.

### Согласовано: определение edges

Принято сводное определение таблицы и частичного уникального индекса:

```sql
CREATE TABLE edges (
    id        TEXT NOT NULL PRIMARY KEY,
    source_id TEXT NOT NULL REFERENCES nodes(id),
    target_id TEXT NOT NULL REFERENCES nodes(id),
    type      TEXT NOT NULL,
    hash      TEXT NOT NULL,
    created_at INTEGER NOT NULL,

    CHECK (source_id <> target_id)
);

CREATE UNIQUE INDEX edges_includes
ON edges(source_id, target_id)
WHERE type = 'includes';
```

Оба конца обязательны и ссылаются на UUID в nodes; каскадное удаление не включается. Определение объединяет согласованные поля и ограничения. Уникальность UUID между nodes и edges, грамматику типов, допустимый источник includes и отсутствие циклической включённости проверяет общий доменный валидатор Rust.

Вход: подготовленное ребро между существующими узлами. Выход: строка edges, сохранённая через согласованный UPSERT. При нарушении ограничения вся соответствующая транзакция откатывается по правилам apply либо публикации реиндексации.

Мотивация: обычные связи, включённость и external-ссылки хранятся в одной таблице. Определение использует уже согласованные ограничения. Индексы для входящего и исходящего обхода и порядок синхронизации группы записей ещё уточняются; это не завершённая схема всей БД.

### Согласовано: первичный ключ edges

В edges принят первичный ключ по UUID ребра:

```sql
id TEXT NOT NULL PRIMARY KEY
```

ID хранится в прежнем каноническом строковом представлении UUID. PRIMARY KEY закрепляет уникальность внутри edges, NOT NULL — обязательность ID. Проверка уникальности UUID среди текущих nodes и edges остаётся в общем валидаторе и согласованном протоколе записи. Отдельная явная колонка row_id в edges не вводится: соответствие с FTS5 и vec1 относится к узлам nodes.

Вход: вставка ребра E1 с концами A → B. Выход: одна строка edges с id = E1. Вставка второй строки с таким же ID или NULL вызывает ошибку ограничения SQLite. Изменение концов существующего ребра сохраняет его ID по согласованному доменному правилу и выполняется через UPSERT, описанный ниже.

Мотивация: ребро адресуется одним имеющимся UUID. Простой первичный ключ обеспечивает обязательность и уникальность без дополнительного публичного или служебного идентификатора.

### Согласовано: UPSERT edges по UUID

При сохранении подготовленной графовой проекции новые рёбра вставляются в edges, существующие обновляются через ON CONFLICT(id) DO UPDATE. Обновление сохраняет id и записывает source_id, target_id, type, hash и created_at из подготовленной проекции. При обычном редактировании и переносе подготовленная ссылка сохраняет первоначальное время; при реиндексировании метка читается из канонического title. Используется тот же механизм UPSERT по публичному UUID, что и для nodes.

```sql
INSERT INTO edges (id, source_id, target_id, type, hash, created_at)
VALUES (:id, :source_id, :target_id, :type, :hash, :created_at)
ON CONFLICT(id) DO UPDATE SET
    source_id = excluded.source_id,
    target_id = excluded.target_id,
    type      = excluded.type,
    hash      = excluded.hash,
    created_at = excluded.created_at;
```

Это запрос сохранения одного подготовленного ребра внутри согласованной транзакции apply или публикации результатов реиндексирования. Он не описывает весь порядок синхронизации графа: удаление исчезнувших связей и порядок изменений при взаимосвязанных ограничениях обсуждаются отдельно. Проверки разметки, оптимистических хешей, уникальности UUID и целостности графа до изменения канонических документов остаются обязательными. Конфликт по другому ограничению не разрешается заменой постороннего ребра.

Вход: существующее ребро E1 связывает A → B; новая Markdown-ссылка с тем же ID связывает A → C и имеет новый hash. Выход: запись E1 обновлена, её ID сохранён. Если E1 отсутствует, вставляется новая запись при выполнении всех ограничений.

Мотивация: узлы и рёбра сохраняются единообразно. Обновление существующей связи не требует смены её ID или отдельного механизма замены записи. Основание: [SQLite UPSERT](https://www.sqlite.org/lang_upsert.html).

### Согласовано: обязательный hash в edges

Для edges принят обязательный хеш:

```sql
hash TEXT NOT NULL
```

letopis вычисляет SHA-256(JCS({source, markdown})) по UUID узла, содержащего ссылку, и Markdown самой ссылки. Прежнее текстовое представление SHA-256 сохраняется. Содержимое внешнего источника не требуется для этого вычисления: хеш ребра относится к объявленной связи, а хеш source-узла — к адресованному содержимому источника.

Вход: знание A содержит external-ссылку на src/auth.rs; файл источника стал недоступен. Выход: source-узел допускает hash = NULL по своему CHECK, а ребро сохраняет вычисленный хеш Markdown-ссылки. Попытка сохранить edges.hash = NULL вызывает ошибку ограничения SQLite, обрабатываемую по правилам соответствующей транзакции и восстановления.

Мотивация: каждое ребро имеет хеш для сравнения изменений при разборе документов. Недоступность содержимого источника отражается в source-узле, сохраняя описание самой связи.

### Согласовано: тип связи в edges

Для edges принято поле типа:

```sql
type TEXT NOT NULL
```

Имя типа берётся из поля title канонической Markdown-ссылки. Системные типы includes и external сохраняют согласованный смысл; проект может задавать другие имена в грамматике `[a-z][a-z0-9_]*` без предварительной регистрации. Справочник типов, таблица регистрации и конечный SQL-перечень допустимых имён не вводятся. Грамматику и системные правила проверяет общий доменный валидатор Rust; NOT NULL закрепляет обязательность поля в БД.

Вход: корректно размеченное ребро A → B с проектным типом supports. Выход: строка edges с type = 'supports'; отдельное создание типа не требуется. Supports здесь пример проектного имени, а не новый обязательный системный тип. Попытка сохранить type = NULL вызывает ошибку ограничения SQLite.

Мотивация: одно строковое поле описывает вид связи и позволяет агенту фильтровать обход по типам. Разные правила системных типов остаются в существующем валидаторе, без дополнительного справочника или механизма регистрации.

### Согласовано: внешние ключи для концов рёбер

Статус: принято пользователем. SQLite проверяет, что обязательные source_id и target_id каждого ребра ссылаются на существующие nodes той же графовой проекции. Используются стандартные FOREIGN KEY с включённым foreign_keys на каждом соединении. Автоматическое каскадное удаление не вводится: связи удаляются или переназначаются явно по уже согласованному правилу.

Вход построения: узлы A, B и ребро A → B из завершённого Git-снимка. Выход — допустимая запись согласованной проекции. Если передано ребро A → B, но узел B отсутствует, SQLite отклоняет запись; индексатор откатывает её транзакцию и сохраняет последний корректный индекс. Ошибка индексирования не откатывает ранее завершённую правку документов. FK дополняет согласованную предварительную валидацию графа.

Мотивация: обязательная связность записей обеспечивается штатным ограничением БД. Согласованный DDL использует REFERENCES nodes(id) для обоих концов без каскадного удаления. Порядок SQL-обновлений уточняется при проектировании транзакции. Основание: [SQLite Foreign Key Support](https://www.sqlite.org/foreignkeys.html).

### Согласовано: запрет одинаковых концов ребра в БД

Статус: принято пользователем. Доменный запрет закрепляется в БД. В `edges` добавляется стандартное ограничение `CHECK (source_id <> target_id)`. Оба конца обязательны по согласованной модели. Проверка разметки до сохранения документов сохраняется; ограничение БД закрепляет тот же инвариант для производной графовой проекции.

Вход индексатора: ребро A → A, где A обозначает один и тот же UUID. Выход: SQLite отклоняет запись; индексатор откатывает транзакцию обновления и сохраняет последний корректный индекс. Для A → B при разных концах это ограничение выполнено; остальные проверки по-прежнему обязательны. Ошибка обновления индекса не откатывает ранее завершённую правку документов.

Мотивация: согласованное правило выражается одним штатным ограничением таблицы, без дополнительных полей, таблиц или механизмов. Основание: [SQLite CHECK constraints](https://www.sqlite.org/lang_createtable.html#check_constraints).

### Согласовано: уникальность includes в БД

Статус: принято пользователем. Доменное правило закрепляется в БД. Для `edges` используется частичный уникальный индекс: пара `(source_id, target_id)` уникальна только среди рёбер `type = 'includes'` в одной графовой проекции. Обычные рёбра не подпадают под это ограничение; между той же парой разрешены несколько обычных рёбер, включая рёбра одного типа.

Вход индексатора: два ребра `includes` с разными ID и одинаковыми концами M → A. Выход: SQLite отклоняет вторую запись; индексатор откатывает обновление и сохраняет последний корректный индекс. Для двух обычных рёбер M → A это ограничение не нарушено. Проверка документов до сохранения по-прежнему выявляет дублирующую включённость; ограничение БД дополнительно закрепляет правило в производной проекции. Ошибка индексирования не откатывает ранее завершённую правку документов.

Мотивация: штатный механизм SQLite выражает согласованную уникальность включённости в существующей `edges`. Отдельная таблица членства не требуется. Это ограничение целостности; необходимость индексов для ускорения запросов рассматривается отдельно. Принят индекс edges_includes на (source_id, target_id) с условием WHERE type = 'includes'; его определение приведено выше. Основание: [SQLite Unique Partial Indexes](https://www.sqlite.org/partialindex.html#unique_partial_indexes).

### Согласовано: общая доменная проверка правил includes

Статус: принято пользователем. Эти два правила проверяет один общий доменный валидатор на Rust, используемый при проверке и применении правки и при индексировании Git-снимка. Для них SQL-триггеры не вводятся. Согласованные внешние ключи, CHECK и частичный уникальный индекс сохраняются.

Валидатор проверяет итоговый граф всей правки до изменения канонических файлов, учитывая существующие связи вне изменяемых документов. При индексировании он проверяет согласованный граф выбранного Git-снимка до публикации новой проекции. Источником `includes` может быть только метавершина; подграф рёбер `includes` не должен иметь циклов. Циклы обычных связей допустимы.

Вход: правка, после которой метавершины M и N включают друг друга — M → N и N → M, оба ребра типа `includes`. Выход `apply`: `validation_failed` с указанием связей, образующих цикл; вся правка отклоняется. При обнаружении той же ошибки в Git-снимке индексирование не публикует обновление и сохраняет последний корректный индекс с диагностикой. Аналогично отклоняется `includes` с источником, не являющимся метавершиной.

Мотивация: одна реализация правил даёт агенту согласованную диагностику при записи и реиндексировании. Проверка использует уже предусмотренный доменный валидатор и не требует отдельного механизма в БД. Правила относятся к структуре графа, а не к одному из способов её хранения.

Вход `letopis traverse`; метавершина содержит одну вершину:

```json
{
  "element_ids": [
    "b4655ec0-ddfb-4c13-ab83-dff053dbe399"
  ],
  "mode": "containment",
  "direction": "outgoing",
  "depth": 1,
  "limit": 10,
  "edge_limit": 10
}
```

Выход:

```json
{
  "ok": true,
  "result": {
    "elements": [
      {
        "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
        "path": "knowledge/rules.md",
        "lines": [
          1,
          6
        ],
        "revision": "<снимок индекса>",
        "flags": []
```

## Отклонено: отдельная external_nodes

Первоначальная отдельная таблица адресов источников заменена согласованной единой nodes с kind = source и uri. Её гарантия устойчивого соответствия адреса и UUID сохраняется; отдельная структура и дублирующее описание её полей удалены из актуального проекта.

## Согласованная единая nodes для знаний и источников

Статус: пользователь принял единую nodes, kind = source и uri. Отдельная external_nodes заменена этим решением. Отдельный исторический реестр UUID не используется; проверяется уникальность текущих nodes и edges.

Пользователь предложил хранить источники в общей nodes с дополнительным видом узла или признаком, учитывая будущие ссылки на веб-страницы. Различный жизненный цикл идентичности и поисковых данных требует правил сохранения, но сам по себе не требует отдельной таблицы источников. В текущем проекте приняты единые логические записи nodes.

Хранимый kind расширен значением source. Он обозначает обычную вершину внешнего источника в доменной модели, а не новую разновидность метаграфового элемента. В Markdown корпуса по-прежнему разрешены только vertex и metavertex; вершины источников создаёт letopis при разрешении external-ссылок. Источник и метавершина одновременно не требуются текущей моделью, поэтому отдельный признак происхождения пока не предлагается.

| Поле | Согласованный смысл | Ограничение |
|---|---|---|
| id | Постоянный UUID узла | Для источника сохраняется независимо от наличия ссылок и перестройки индекса |
| kind | vertex, metavertex или source | Вид записи хранения; source отображается на обычную вершину домена |
| uri | Адрес канонического описания либо источника | Используется вместо узкого path в хранении; для знаний — путь с ID фрагмента, для источника — путь с диапазоном или веб-адрес |

Производные hash и координаты фрагмента сохраняют свой смысл, но не составляют долговечную идентичность источника. Для source нормализованный uri должен однозначно определять UUID в рамках проекта; это условная уникальность по kind = source, а не требование уникальности любого адреса всех видов узлов. Физическое ограничение согласовано: частичный уникальный индекс nodes_source_uri по uri для kind = source. Изменение содержимого источника не меняет его UUID; другой адрес обозначает другой источник. Основание подтверждения относится к конкретному знанию: согласован один общий снимок всех его источников. История читается по известным Git-снимкам; отдельный учёт в БД не вводится.

Вход — ссылки в Markdown знания. Веб-ссылка иллюстрирует расширяемость адресной модели и пока не является принятым сценарием первой версии:

```markdown
[Реализация](src/storage.go#L10-L25 "letopis:id=tmp:001;type=external")
[Документация](https://example.org/docs#storage "letopis:id=tmp:002;type=external")
```

Результат разрешения — логические записи nodes; это иллюстрация хранения, а не новые поля публичного ответа apply:

```json
[
  {
    "id": "91e1798a-d1f4-43ba-817b-ad93c9c5ea86",
    "kind": "source",
    "uri": "src/storage.go#L10-L25"
  },
  {
    "id": "d047c32e-c620-4a91-a956-a697d71f3b77",
    "kind": "source",
    "uri": "https://example.org/docs#storage"
  }
]
```

Для собственного знания uri может иметь вид knowledge/rules.md#08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c; вид записи остаётся vertex или metavertex. ID связывает узлы и рёбра, адрес задаёт место чтения. Перенос знания меняет его адрес, сохраняя ID.

Основное условие единой таблицы: reindex не должен очищать соответствия ID и адресов источников, записанные в nodes. Известные источники без текущих ссылок сохраняются для inspect и последующего повторного использования ID. Они не становятся самостоятельными результатами поиска знаний. Наличие строки в nodes не заменяет проверку принадлежности согласованной поисковой проекции. Обновление индексных полей должно сохранять принятую атомарную публикацию и закрепление запросов за одной версией; физический способ обеспечения этих гарантий ещё не выбран.

URI-reference позволяет одинаковым адресным полем представить относительный путь и абсолютный веб-адрес. При этом нормализация и разрешение зависят от адресной схемы; файловые правила нельзя автоматически переносить на URL. Основание: [RFC 3986, относительные ссылки и нормализация](https://www.rfc-editor.org/rfc/rfc3986). Согласованная нормализация локальных адресов остаётся в силе. Правила веб-адресов, чтения страниц, фиксации их содержимого и перепроверки ещё не обсуждены; универсальное поле не включает автоматически сетевые операции в полностью локальную первую версию.

Мотивация: код и веб-документация представлены теми же узлами и рёбрами, агент использует обычные ссылки, а хранение не требует отдельного набора записей для каждого способа доступа к источнику. Одно значение kind = source также позволяет отличить доступные для редактирования знания от источников при валидации операций.

## Согласованная нормализация ключа адреса

Статус: пользователь принял нормализацию компонентов пути и номеров строк, сохранение регистра имени и неизменность исходного Markdown. Особенности кодирования адресов и альтернативных путей через символьные ссылки ещё требуют детализации.

Адрес нормализуется только для разрешения и сравнения источников: компоненты `.` удаляются, внутренние `..` сворачиваются без выхода из корня; номера строк записываются десятичными числами без ведущих нулей. Диапазон должен быть положительным и упорядоченным. Регистр имени сохраняется; дополнительная нормализация Unicode не вводится. Согласованные проверки выхода из корня через символьные ссылки сохраняются. Объединение различных адресов по физическому расположению файла этим решением не определяется.

Внутренний вход:

```json
{
  "uri": "./src/../src/storage.go#L010-L025"
}
```

Выход:

```json
{
  "uri": "src/storage.go#L10-L25"
}
```

Вход и выход показывают адрес после разбора Markdown-ссылки. Эти правила не вводят новые поля CLI и не меняют исходный Markdown: хеш фрагмента по-прежнему учитывает его точные байты. Каноническое кодирование специальных символов адреса относится к общей грамматике ссылок и не предполагает изменения имён файлов. Нормализация не исправляет недоступный файл или некорректный диапазон; такие случаи обрабатываются согласованными правилами валидации и перепроверки.

Мотивация: эквивалентные написания одного адреса не создают несколько внешних вершин. При этом агент сохраняет свой Markdown, а letopis не смешивает разные имена файлов или разные адресованные фрагменты.

## Согласовано: хеш файла по запросу

Статус: принято вычисление file_hash при inspect из общего Git-снимка без постоянного кэша в БД. Используется ранее выбранное хеширование всего файла, SHA-256 точных байтов. Пользователь оставил возможность пересмотра покрытия хеширования после отдельного этапа выбора разметки.

Согласовано: отдельная таблица files и копии file_hash в узлах ради постоянного кэша не вводятся. Для inspect хеш файла вычисляется по точным байтам общего Git-снимка, один раз на уникальный файл в рамках вызова. Для проверки base_hash при записи вычисляется хеш согласованного текущего состояния файла; прежний индекс не используется как доказательство совпадения. Хеш фрагмента в графовой проекции остаётся отдельным значением. Код и Markdown в БД не копируются.

Вход letopis inspect:

```json
{
  "element_ids": ["08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c"]
}
```

Выход соответствует принятому контракту; file_hash получен из файла в выданном снимке:

```json
{
  "ok": true,
  "result": {
    "snapshot": "<Git tree OID>",
    "elements": {
      "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c": {
        "path": "knowledge/rules.md",
        "lines": [1, 6],
        "hash": "<SHA-256 полного фрагмента>",
        "file_hash": "<SHA-256 всего файла>"
      }
    }
  }
}
```

Если несколько запрошенных элементов расположены в одном файле, рассчитанный file_hash используется для каждого ответа. Этот временный результат не вводит постоянный кэш. Для недоступного известного файлового источника сохраняются согласованные null-значения. Это решение относится к файловым источникам; поведение будущих веб-источников отдельно не определяет.

Мотивация: агент получает необходимые base_hash без дополнительного набора записей и синхронизации дубликатов. Цена — чтение и хеширование файла при соответствующем вызове; постоянный кэш можно обосновать позднее измерениями. Выбор механизма обнаружения изменений всего корпуса остаётся отдельным вопросом и этим решением не задаётся.

### Уточнение: хеш файла из хешей элементов

Пользователь предложил вычислять file_hash из хешей элементов. Такой составной хеш возможен, но не равен принятому SHA-256 байтов файла. Если использовать только хеши размеченных фрагментов, изменение заголовка, комментария, пробелов или другого содержимого вне этих фрагментов не изменит результат. Состав и порядок элементов также должны учитываться; нельзя брать хеш неупорядоченного множества. Полное покрытие каждого байта файла размеченными элементами ранее не требовалось.

Для полного контроля файла составной вариант должен учитывать и промежутки между элементами, что вводит дополнительную схему разбиения и хеширования. Во всех вариантах для проверки новой правки нужны актуальные данные: старые хеши из индекса не доказывают неизменность рабочей копии. Выигрыш составного варианта не установлен измерениями; при чтении и подготовке изменённого файла SHA-256 его байтов можно вычислять в том же проходе.

Пользователь предварительно выбрал хеширование всего файла. Условие покрывает любые его байты, включая содержимое вне описаний элементов. Разметка ещё не выбрана и проектируется отдельным этапом; после этого file_hash может быть пересмотрен явным решением. Составной хеш элементов сейчас не принят. Вычисление file_hash по запросу без постоянного кэша согласовано отдельным решением; это не следствие выбранного покрытия хеширования.

## Основание знаний и ревизии

Согласован один общий Git-снимок всех источников знания. Предложения хранить тройку verified.hash/revision/snapshot либо независимую source_revision на каждом external-ребре не приняты; их подробные схемы исключены из актуального проекта. Нельзя одновременно считать эти варианты выбранными и применять общее основание знания.

Содержимое прежнего источника доступно в Git по общему снимку и uri. Хеш можно вычислить по этому содержимому; необходимость постоянного кэша ещё не доказана. История читается по известным Git-снимкам. Для filters.source_revisions сравнивается содержимое адресованного источника из source_snapshot знания с тем же адресом в запрошенной Git-ревизии. При совпадении поиск по C2 находит знание, основанное на C1; отдельный OID коммита не хранится.

### Согласовано: source_snapshot в Markdown и nodes

Текущее подтверждённое основание знания хранится в поле source_snapshot JSON-метаданных его канонического Markdown-фрагмента. Значение — полный Git tree OID одного общего снимка всех источников знания. БД nodes хранит проекцию того же значения. Отдельный номер revision знания для этого основания не вводится. Принята колонка source_snapshot TEXT с NULL при отсутствии установленного основания и у source; правила описаны ниже.

При edit с snapshot letopis после проверки источников записывает переданный OID в source_snapshot канонического описания и его проекцию nodes в той же атомарной правке. При обычном edit без snapshot прежнее основание сохраняется. Добавление или замена источника требует явного snapshot по согласованному правилу. Реиндексирование читает source_snapshot из Markdown и сохраняет подтверждённое основание, даже если текущие источники уже изменились.

Source_snapshot входит в полный хеш Markdown-фрагмента узла. Изменение основания изменяет собственный hash узла; имеющийся base_hash защищает такую правку. Агент может прочитать сохранённый указатель непосредственно из документа после потери ответа CLI. Поисковое представление по прежнему правилу исключает служебные метаданные.

Актуальный текст знания адресуется снимком inspect или опубликованного графа/FTS в project.revision. Source_snapshot адресует подтверждённое содержимое источников знания. Эти указатели могут различаться: индекс построен по S2, а знание пока опирается на S1.

История оснований читается по известным Git-снимкам без отдельного учёта в БД. Filters.source_revisions сравнивает содержимое адресованных источников через Git; отдельный OID коммита в метаданных или БД не сохраняется. Восстанавливать исходный commit OID по tree не требуется. Принятый source_snapshot не устанавливает новый архив графовых проекций или постоянный кэш хешей прежних источников.

### Согласовано: отсутствие source_snapshot

В nodes принято:

```sql
source_snapshot TEXT
```

Если у знания основание ещё не установлено, source_snapshot отсутствует в каноническом Markdown, а в nodes равен NULL. У внешнего узла kind = source колонка также равна NULL: этот узел сам представляет источник, а не знание с подтверждённым основанием. У знания с установленным основанием сохраняется полный Git tree OID.

Удаление external-ссылок само по себе не обнуляет ранее установленное основание. Edit без snapshot сохраняет прежний source_snapshot, даже если удалены все ссылки; это не подтверждает новые источники автоматически. При create первый source_snapshot поступает из JSON-метаданных внутри create.markdown. После проверки снимка и адресуемых источников letopis сохраняет его в каноническом фрагменте и nodes в той же атомарной правке. Для нового знания с external-ссылками отсутствие снимка отклоняет всю правку; для знания без установленного основания и без внешних источников сохраняется правило NULL. Дополнительного поля create.snapshot нет.

Вход: создание договорённости без внешних источников и без установленного основания. Выход: в Markdown поле source_snapshot опущено; в nodes сохранён NULL. Отдельное значение-заглушка для отсутствующего OID не вводится.

Мотивация: единая nodes обслуживает знания и внешние источники с одним необязательным полем. Отсутствие значения отражается штатным NULL; в Markdown сохраняются только установленные метаданные.

### Согласовано: получение и проверка снимка источников

Агент получает source_snapshot стандартными средствами Git: использует дерево коммита либо создаёт дерево источников без коммита через временный индекс. Протокол включается в навык агента и описан в документе контрактов. Отдельная команда snapshot и реестр предварительной регистрации OID не вводятся.

Перед записью нового основания через create или edit letopis проверяет полный OID, наличие объекта в Git текущего проекта и его точный тип tree. Отсутствующий объект вызывает not_found; некорректный формат или другой тип — invalid_request. Проверка выполняется до изменения канонических файлов, вместе с проверками адресованных источников; ошибка отклоняет весь apply. Принятые снимки удерживаются служебными Git-ссылками по общему протоколу долговечности.

Согласовано: при create letopis сравнивает адресованные источники каждого нового знания с его source_snapshot. Для ссылки с диапазоном сравниваются точные байты указанного фрагмента, для ссылки на весь файл — байты всего файла. Если хотя бы один доступный источник отличается от снимка, весь apply отклоняется с conflict до изменения канонических документов. Несовпадение OID деревьев само по себе конфликтом не является: изменения вне адресованных источников и диапазонов не мешают записи. Это то же правило актуальности, которое уже действует для edit с snapshot. Недоступные файлы и диапазоны по-прежнему обрабатываются согласованными правилами validation_failed.

### Согласовано: обычная правка сохраняет основание источников

Статус: пользователь подтвердил сохранение прежнего основания при edit без snapshot. Правило применяется к обычной правке с прежними источниками; добавление или замена источника требует snapshot по следующему согласованному правилу.

Source_snapshot знания обозначает последний подтверждённый общий снимок его источников. Если edit меняет только Markdown и не передаёт snapshot, при неизменном наборе источников этот указатель сохраняется. Edit с snapshot после проверок обновляет основание всех источников знания целиком. Автоматическое реиндексирование не подтверждает новое основание.

Актуальный Markdown читается по snapshot ответа inspect либо снимку опубликованного графа/FTS; его состояние проверяется собственным hash. Source_snapshot из метаданных этого Markdown адресует подтверждённые источники знания. Значение может оставаться S1 после изменения самого текста и публикации индекса по S2.

Сценарий: основание знания — S1; код изменился и доступен в S2. Агент исправляет формулировку знания, сохраняя ссылки, без подтверждения источников. Вход apply:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш исходного фрагмента>",
      "markdown": "<полный новый Markdown-фрагмент с прежними source-ссылками>"
    }
  ]
}
```

Публичный выход остаётся согласованным:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>"
  }
}
```

После сохранения текущий Markdown доступен в новом Git-снимке, а source_snapshot в канонических метаданных и проекции nodes остаётся прежним:

```json
{
  "id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
  "source_snapshot": "<снимок S1>"
}
```

Мотивация: обычная правка формулировки не превращается в подтверждение изменившегося кода. Пометки о необходимости перепроверки сохраняют смысл. Правки с добавлением, удалением или переназначением external-ссылок требуют отдельного решения и данным предложением не покрываются. Возможность выбирать по прежней ревизии исходного коммита также остаётся открытой деталью общей модели.

### Согласовано: новый источник требует общего snapshot

Статус: пользователь подтвердил обязательность snapshot при добавлении или замене источника. У знания одно общее основание; независимая новая привязка к другой версии не создаётся.

Snapshot обязателен у edit, который добавляет новый адрес источника или заменяет адрес прежнего. Агент подтверждает знание по всем конечным источникам одного снимка. letopis проверяет доступность каждого адресованного фрагмента в снимке и соответствие его текущим байтам, затем меняет общее основание целиком. Изменение только подписи ссылки или иной графовой разметки без изменения адресов источников нового snapshot не требует. Удаление источника само по себе не добавляет новой зависимости и при edit без snapshot сохраняет основание остальных источников.

Сценарий: знание раньше ссылалось на src/storage.go, агент добавляет src/cache.go. Снимок S2 содержит оба файловых источника в состоянии, по которому агент подтверждает подготовленный текст. Вход apply:

```json
{
  "operations": [
    {
      "type": "edit",
      "element_id": "08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c",
      "base_hash": "<хеш исходного элемента>",
      "markdown": "<!-- letopis: {\"id\":\"08ff5c9e-d4c6-4f73-b0f4-58fd455c6c5c\",\"kind\":\"vertex\"} -->\nОписание хранилища и кэша.\n[Хранилище](src/storage.go#L10-L25 \"letopis:id=064f2964-77cc-41f0-87ac-d280c0ec59a7;type=external\")\n[Кэш](src/cache.go \"letopis:id=tmp:001;type=external\")\n<!-- /letopis -->\n",
      "snapshot": "<Git tree OID S2>"
    }
  ]
}
```

Выход при успешных проверках соответствует действующему apply:

```json
{
  "ok": true,
  "result": {
    "hash": "<хеш правки>",
    "ids": {
      "tmp:001": "07bd2df0-a311-479e-b21b-cd2728daf852"
    }
  }
}
```

Согласованные временные ID заменяются letopis; новые команды не вводятся. Source_snapshot знания в Markdown и nodes становится S2 для всех его источников. Без snapshot в таком сценарии возвращается invalid_request с объяснением необходимости общего основания, без применения изменений.

Уточнение действующего проектного контракта: edit.snapshot принимает полный OID любого доступного tree в Git-хранилище текущего репозитория, а не только выданные letopis снимки. not_found относится к отсутствию самого объекта в Git. Требование регистрации снимка в отдельном реестре ранее не принималось и не вводится. Получение снимка с новыми незакоммиченными источниками возложено на агента средствами Git через временный индекс; сценарий включается в навык агента и приведён в контракте. Обязательный коммит не требуется.

Мотивация: после правки у всего знания остаётся одно объяснимое основание. letopis не объединяет незаметно старую проверку одного источника и новую проверку другого. Прежний сценарий добавления новой привязки без snapshot заменён этим решением.

## Согласовано: история в известных Git-снимках

Для первой версии достаточно чтения известных Git-снимков стандартными средствами Git. Отдельный учёт истории оснований в БД не вводится: нет таблицы history или source_changes, цепочки прежних оснований либо индекса снимков по ID знания. CLI не получает отдельного запроса перечисления истории знания по ID.

Прежнее описание знания, его source_snapshot и ссылки external сохраняются в удерживаемом Git-снимке корпуса. Агент читает Markdown по известному OID снимка корпуса и пути, затем использует записанный в этом Markdown source_snapshot для чтения прежних источников. Снимок источников сам по себе не обязан содержать описание знания. Схематичный пример чтения:

```sh
git show '<knowledge_tree_oid>:knowledge/auth.md'
git show '<source_tree_oid>:src/auth.rs'
```

Бессрочное удержание необходимых Git-снимков служебными refs и отдельная операция пользовательского Git-коммита сохраняются. Известные tree OID позволяют читать прежнее содержимое без автоматического коммита после каждой правки; автоматическое перечисление всех прежних оснований по UUID не требуется. Порядок долговечной фиксации Git-объектов и refs остаётся частью физического протокола.

Текущий source_snapshot хранится в каноническом Markdown и проекции nodes. Долговечное соответствие uri и UUID известных узлов source, включая источники без текущих ссылок, сохраняется в БД по прежним правилам. Эти текущие идентичности не становятся журналом истории. Удаление записи восстановления после завершения операции не освобождает удерживаемые Git-снимки.

Решение заменяет прежние требования к служебным записям истории привязок в БД. Фильтр по Git-ревизии сохраняется с выбранной семантикой сравнения содержимого адресованных источников. Отдельный OID коммита и новая таблица привязок для этого не вводятся.

## Согласовано: область изменения канонических документов

letopis изменяет только специально размеченные Markdown-документы корпуса. При существующем пути принадлежность корпусу определяется по исходному каноническому состоянию: разметка letopis должна присутствовать до правки. Обычные документы без разметки, исходный код и другие внешние источники доступны для чтения по прежним правилам, но не являются целями записи letopis. Переданный base_hash и разметка нового содержимого не разрешают изменение существующего файла вне корпуса.

Нарушение этой границы отклоняет всю атомарную группу без изменения документов; тот же контроль действует при проверке без сохранения. Снимок для отката относится к разрешённым изменениям корпуса, а не создаёт право записи вне него. Ранее согласованное создание нового файла через create сохраняется: по отсутствующему пути создаётся сразу размеченный Markdown-документ после общей проверки. Служебные записи БД и удерживаемые Git-снимки сохраняют ранее согласованные роли; это ограничение области изменения пользовательских файлов.

## Согласовано: фиксация правки и очередь embeddings

Статус: принято пользователем. Обычная правка синхронно сохраняет файлы, граф и FTS; вычисление embeddings выполняется через долговечную очередь. Требование ждать все embeddings перед публикацией снято. Граф остаётся производной структурой, восстанавливаемой из Markdown.

### Запись документов через apply

До изменения канонических файлов надёжно сохраняются Git-снимок прежнего состояния и запись восстановления. Правка проверяется по актуальным хешам и общим правилам целостности; изменения графа и FTS подготавливаются для затронутых элементов и необходимых зависимостей.

После надёжного сохранения группы файлов финальная транзакция SQLite фиксирует необходимые служебные данные, назначенные идентичности и подтверждённые основания (прежние основания остаются в Git по D-11/D-14), изменения nodes/edges и FTS5, ревизию корпуса и задания на embeddings. В той же транзакции удаляется запись восстановления. Только после её надёжной фиксации apply возвращает прежние hash и, при создании, ids. Документы и их прежние байты остаются в Markdown и Git; в БД нет копий текста.

Если актуальный вектор уже существует и соответствует подготовленному поисковому тексту и конфигурации модели, он переиспользуется. Новый или изменившийся поисковый текст требует задания на embeddings; несовместимый старый вектор не участвует в поиске. Физический способ исключения и очистки такого вектора ещё проектируется.

Сбой до финальной фиксации требует полного отката файлов и относящихся к правке служебных изменений. Сбой после неё не откатывает правку даже при потере ответа; агент перечитывает состояние. Удаление записи восстановления остаётся маркером завершения. Общая атомарность файлов и БД обеспечивается прикладным протоколом, а не автоматически одной транзакцией SQLite. Порядок надёжной записи файлов, каталогов, Git-объектов и БД ещё проектируется и требует аварийной проверки.

### Асинхронное вычисление embeddings

Исполнитель использует неизменяемый Git-снимок задания и согласованное поисковое представление только затронутых элементов. Вычисление выполняется вне транзакции записи. Готовый вектор используется только при соответствии текущему подготовленному тексту, адаптеру, модели и влияющим параметрам. Выполнение старого задания не должно возвращать граф или FTS к прежнему снимку.

Готовый применимый вектор и удаление обработанного задания фиксируются одной транзакцией SQLite. Устаревший элемент пропускается без ошибки; сохранившаяся запись именно этого задания удаляется в транзакции обработки результата. Исполнитель читает текущую строку задания и вычисляет embedding вне транзакции БД; в новой короткой транзакции записи проверяет существование исходного seq перед сохранением применимого вектора и удалением строки. При отмене исходная строка удаляется, а диагностика сохраняется в errors. Соответствие поисковому тексту и конфигурации модели остаётся обязательным; согласована одна активная конфигурация в служебных метаданных и её транзакционная смена с заменой очереди; физическое хранение ещё проектируется. Новое задание для того же элемента заменяет старое в очереди. Если запись старого задания уже заменена, завершение его вычисления не изменяет и не удаляет новую запись. Согласовано: одна строка embedding_jobs относится к одной вершине или метавершине; обязательный node_id уникален через UNIQUE(node_id). Новая работа заменяет только строку того же элемента. Новые запросы видят добавленные векторы; текущие запросы сохраняют свой снимок чтения БД.

Ошибка или отмена вычисления embeddings не откатывает документы, граф или FTS. Поиск использует FTS при отсутствии актуального вектора. Status показывает число заданий на embeddings и диагностику отдельно от неприменённых правок. Ограниченные ретраи, восстановление прерванного задания по его снимку и явный reindex с ожиданием graph/FTS и постановки заданий по D-71 сохраняются. Согласовано поле status.result.embedding_jobs: число заданий, ожидающих выполнения, выполняющихся или ожидающих разрешённого ретрая. Завершённые, отменённые и исчерпавшие ретраи задания не учитываются; неустранённые ошибки остаются в errors. Ноль не гарантирует полного векторного покрытия при наличии таких ошибок.

Для первоначального построения и изменений через Git граф/FTS также проходят общую проверку и транзакционную публикацию, а embeddings могут появляться позднее. При ошибке подготовки или публикации графа/FTS сохраняется их последняя корректная версия. Первый поиск ждёт корректных графа/FTS, но не всех embeddings. Правила конкурентного явного reindex и внешних Git-изменений ещё проектируются.

Для чтения операций letopis требуется согласованное представление документов и метаданных; произвольное чтение нескольких файлов во время замены не даёт общей атомарности чтения. По D-77 согласованное чтение нескольких документов выполняется по одному Git-снимку, ordinary live reads не имеют этой гарантии. Протокол фиксации — MC-2.

### Согласовано: закрепление индекса транзакцией чтения SQLite

Статус: принято пользователем. Один search или traverse выполняет все чтения в одной транзакции SQLite на выделенном соединении. Первое чтение закрепляет опубликованное состояние графа, FTS и доступных актуальных векторов. Векторное покрытие может быть неполным; запрос не ждёт его заполнения. Соединение не выполняет параллельных операций других запросов. Транзакция заканчивается при завершении или отмене; устройство пула ещё выбирается.

Вход сценария: запрос A уже прочитал ревизию R1; индексатор атомарно публикует согласованную ревизию R2; запрос Б начинает чтение после этой публикации. Выход: A до завершения использует R1, Б использует R2. Один запрос не смешивает проекции этих ревизий. SQLite в принятом WAL-режиме удерживает необходимое состояние для активного читателя. Это относится к данным индекса; ссылки результата по-прежнему ведут к текущим документам с указанием индексированной ревизии и согласованными признаками устаревания.

Мотивация: стандартная изоляция SQLite обеспечивает согласованное чтение для агента. Приложение задаёт границы одной транзакции и не поддерживает отдельный счётчик читателей ради удержания снимка БД. Подготовка данных и конкретный порядок SQL-обновлений ещё проектируются; граф/FTS и готовые векторы публикуются отдельными согласованными транзакциями, описанными ниже. Корректность совместного снимка графа, FTS5 и выбранного vec1 необходимо проверить при реализации, включая откат и отмену. Исследовательская проверка vec1 с прежним читателем не является проверкой всего продукта.

Ограничение: длительная транзакция чтения может задерживать полное checkpoint WAL. Завершение и отмена запроса должны освобождать транзакцию; политика checkpoint и обработка ошибок SQLite проектируются отдельно. Основания: [SQLite isolation](https://www.sqlite.org/isolation.html), [SQLite WAL](https://www.sqlite.org/wal.html).

### Согласовано: транзакционные публикации графа/FTS и векторов

Финальная транзакция обычного apply обновляет граф, FTS5, необходимое служебное состояние, ревизию корпуса и очередь embeddings и удаляет запись восстановления. Новые читатели видят изменения всей группы после COMMIT; уже выполняющиеся запросы удерживают прежний снимок SQLite. Фоновый исполнитель не публикует повторно старые граф и FTS.

Отдельная транзакция сохраняет готовый применимый вектор и удаляет именно обработанную строку embedding_jobs. Вычисление модели выполняется до её открытия. Добавление вектора не является новой ревизией файлов: revision по-прежнему адресует снимок опубликованных графа и FTS. При ошибке до COMMIT откатываются изменения этой транзакции; ранее завершённые публикации сохраняются. Отмена не отменяет уже завершённый COMMIT.

Вход: apply изменил элемент A и опубликовал его новый текст в графе/FTS, актуального вектора нет. Выход: поиск уже находит A через FTS; задание вычисляет embedding по своему снимку. После проверки применимости результат становится доступен векторному поиску. Ошибка задания оставляет доступным FTS и отражается в диагностике.

При сбое на границе финального COMMIT правки восстановление использует запись восстановления: оставшаяся запись требует отката, её удаление означает завершение. Для транзакции вектора SQLite сохраняет либо прежнее состояние с заданием, либо готовый вектор с удалённым обработанным заданием. Устаревший элемент пропускается, а сохранившаяся запись именно этого задания удаляется в транзакции обработки результата. Заменённая запись не восстанавливается завершением старого вычисления; конкретный DDL ещё проектируется.

Мотивация: одна транзакция связывает сохранение графа/FTS с долговечной постановкой работы; вторая связывает результат вычисления с завершением задания. Нет окна успешной правки без задания на необходимый вектор. Атомарность файлов, графа и FTS и аварийные переходы нужно проверить в продуктовой реализации. Основания: [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [SQLite isolation](https://www.sqlite.org/isolation.html).

## Согласовано: срок жизни записи восстановления

Запись восстановления существует только для незавершённой правки. Она надёжно сохраняется до первого изменения канонических файлов и удаляется либо в финальной транзакции успешной записи, либо после надёжно завершённого полного отката. Бессрочная дедупликация завершённых вызовов отменена; первоначальный JSON-ответ не требуется хранить для отдельного повторного вызова.

Очистка не удаляет историю оснований, идентичности источников, необходимые задания индексирования, диагностику и удерживаемые Git-снимки. Эти данные имеют собственные правила хранения; запись восстановления не должна оставаться их единственным владельцем. После полного отката сведения о неприменённой правке сохраняются независимо от удаляемой записи.

Согласовано: до первого изменения канонических файлов запись восстановления надёжно сохраняет hash, snapshot и paths. Снимок и пути задают полный откат, а hash и paths используются в диагностике неприменённой правки. Element_ids не сохраняется ни в записи восстановления, ни в диагностике отката. Разбор недописанного файла для формирования сообщения не требуется. Полный текст патча и документов в БД ради этого не сохраняется.

Логический вид записи ниже не определяет полный физический набор колонок или первичный ключ. Хеш является отпечатком содержимого правки, а не уникальным идентификатором всех выполнений. Snapshot здесь адресует состояние до правки; состав снимка ещё уточняется.

```json
{
  "hash": "<хеш содержимого правки>",
  "snapshot": "<Git tree OID состояния до правки>",
  "paths": ["knowledge/design.md"]
}
```

После надёжного завершения или полного отката запись отсутствует:

```json
null
```

### Согласовано: хранение paths в записи восстановления

Список paths хранится JSON-массивом строк в одной колонке SQLite типа TEXT:

```sql
paths TEXT
```

Например, значение колонки для правки двух файлов:

```json
["knowledge/design.md", "knowledge/api.md"]
```

Пути остаются относительно корня репозитория. Восстановитель читает весь массив из записи восстановления и использует его вместе с snapshot для отката всей группы. Отдельная таблица путей не вводится. Вход и выход CLI не меняются: это физическое представление уже согласованного списка paths.

Мотивация: список сохраняется и читается целиком вместе с одной записью восстановления. Одного поля достаточно для этого сценария; дополнительные строки и связи между таблицами не нужны.

## Согласовано: удаление записи как маркер завершения

Статус: принято пользователем. Наличие записи восстановления означает незавершённую правку. Отдельные состояния pending/committed и отдельная очистка завершённых записей не вводятся; прежнее предложение двух состояний заменено этим решением. Внешние вход и выход apply не меняются.

Логический порядок:

1. Надёжно сохранить Git-снимок состояния до правки и запись восстановления в БД до изменения канонических файлов.
2. Сохранить всю группу файлов и обеспечить долговечность записанного содержимого и необходимых изменений каталогов.
3. Одной финальной транзакцией БД сохранить необходимые служебные изменения, текущие подтверждённые основания, назначенные идентичности, граф, FTS, ревизию корпуса и задания на embeddings; удалить запись восстановления.
4. После надёжной фиксации вернуть успех. Граф и FTS уже доступны; embeddings вычисляются асинхронно через очередь.

Совпадение файлов с желаемым содержимым само по себе не означает завершения. Сбой после сохранения файлов, но до надёжной фиксации финальной транзакции оставляет запись восстановления: требуется полный откат. Сбой после финальной транзакции не откатывает правку, даже если агент не получил ответ. После потери ответа агент перечитывает актуальные документы и метаданные.

| Вход восстановителя после сбоя | Действие и результат |
|---|---|
| Запись восстановления существует | Откатить всю группу по сохранённому снимку; надёжно завершить восстановление, сохранить диагностику неприменённой правки и удалить запись |
| Записи нет | По этой записи восстанавливать нечего; отсутствие записи само по себе не сообщает агенту, был ли прежний вызов успешен или уже откатан |

Согласовано: восстановитель определяет незавершённую правку по оставшейся записи журнала и восстанавливает её файлы по прежнему Git-снимку. Корректная разметка текущего повреждённого или недописанного файла не является предпосылкой отката. Область восстановления задаётся записью правки, проверенной до начала изменения документов; это не разрешает запись в посторонние файлы. Для существовавшего документа прежнее содержимое восстанавливается целиком, без попытки угадать по текущему тексту, какая часть была записана. Для документа, созданного незавершённой правкой, отсутствие пути в прежнем снимке означает удаление созданного файла.

Если прервался сам откат, запись остаётся; следующий запуск повторяет восстановление. Ошибка отката также сохраняет запись и диагностику, а поиск и новые правки ждут завершения восстановления. Удаление после отката не происходит до надёжного восстановления всех затронутых файлов.

Мотивация: финальная транзакция одновременно фиксирует служебные результаты и удаляет маркер незавершённости. Дополнительное поле состояния и отдельная очистка после успеха не требуются. Логическая граница принята; физический порядок долговечной записи Git-объектов и refs, файлов и каталогов, настройки БД и аварийные проверки после потери питания ещё проектируются. Состав снимка отката и физический ключ записи ещё не выбраны. Этот дизайн не подтверждает готовность реализации.

## Согласовано: диагностика неприменённых правок

Сообщение о неприменённой атомарной правке хранится независимо от записи восстановления и попадает в существующий result.errors команды status. Согласован общий формат code, message, details: message объясняет причину и исход всей группы, details содержит hash правки и paths файлов. Хеш остаётся отпечатком содержимого, а не уникальным ID всех выполнений. Код ошибки выбирается из существующего каталога по фактической причине.

При аварийном восстановлении hash и paths для диагностики берутся из заранее сохранённой записи восстановления; разбор повреждённого файла не требуется. Диагностика переживает очистку записи восстановления и перезапуск. Полный Markdown-патч или исходный JSON-запрос не требуется хранить в БД только ради этого сообщения. Ошибка индексирования после завершения apply остаётся отдельным событием и не означает отката документов. Успешный откат также не доказывает исполнения исходного намерения агента и сам не очищает сообщение о неприменённой правке.

Согласована отдельная команда letopis errors для чтения того же набора сообщений. Флаг --clear очищает сообщения о завершённых неуспешных правках по всему проекту; активные ошибки сохраняются до устранения проблемы. Вход остаётся {}, результат — список оставшихся сообщений. Новые поля JSON и селекторы хешей не вводятся. Status остаётся командой чтения.

Публичные вход и выход приведены в контрактах status и errors. Физические ключи и записи диагностики, отображение ещё не назначенных ID и координация очистки с новыми ошибками ещё проектируются. Классификацию активной ошибки и сообщения о завершённой неуспешной правке предоставляет владеющая ими подсистема, а не разбор текста message.

## Согласовано: одна активная embedding-конфигурация проекта

Отдельная таблица embedding_config в служебной SQLite-БД проекта хранит одну активную embedding-конфигурацию: provider, модель и параметры, влияющие на вектор. Её используют индексирование и поиск через согласованный общий порт embeddings. Полная копия конфигурации в каждом embedding_jobs не требуется: смена активной конфигурации заменяет всю работу для прежней модели. Таблица embedding_config и её базовый DDL согласованы пользователем; добавлена отдельная колонка provider. Provider обозначает поставщика модели или обслуживающую её платформу; колонка adapter исключена, реализация порта выбирается в Rust по provider. Конкретные параметры адаптеров уточняются. Отдельный публичный ID конфигурации не вводится. Для project согласованы id = 1 и revision — Git tree OID снимка опубликованных графа и FTS; embedding_config принадлежит этому проекту через общую БД, без отдельной колонки project_id.

Исполнитель получает queued-строку и активную конфигурацию согласованным чтением одного состояния SQLite. Чтение заканчивается до вычисления модели. В памяти сохраняются исходный seq, uri, snapshot и соответствующая конфигурация с доступом к адаптеру, который её обслуживает. Это не добавляет транзакцию записи на весь период вычисления и не позволяет сочетать новое задание с настройками прежней модели.

Поисковый запрос закрепляет конфигурацию вместе со своим снимком чтения индекса и использует совместимый адаптер для вектора запроса. Уже выполняющийся запрос сохраняет доступ к соответствующему адаптеру до завершения; обновление глобального runtime само по себе не подменяет закреплённую модель. Постоянная история прежних конфигураций не вводится. Способ управления ресурсами адаптеров и проверки расхода памяти ещё проектируется.

Смена активной embedding-конфигурации имеет одну транзакционную границу SQLite:

1. Обновить активную конфигурацию в служебных метаданных.
2. Очистить прежние векторные данные и строки прежней очереди embeddings. Таблица embedding_jobs и её счётчик AUTOINCREMENT сохраняются; номера прежней работы не переиспользуются.
3. Поставить новую queued-работу для вершин и метавершин опубликованного графа; внешние узлы источников не индексируются векторно. Задания получают новые seq через согласованные INSERT OR REPLACE и AUTOINCREMENT. Их snapshot и uri адресуют снимок опубликованных графа/FTS, а не произвольное ещё не проверенное состояние рабочей копии.

Граф и FTS сохраняют свою опубликованную проекцию; их revision по-прежнему обозначает Git-снимок корпуса. После COMMIT новые запросы используют новую конфигурацию, FTS и готовые совместимые векторы. Завершение прежнего вычисления проверяет старый seq: заменённой строки нет, результат отбрасывается. Ошибка транзакции сохраняет прежние метаданные, векторы и очередь. Новая конфигурация не подтверждает исправление прежних ошибок сама по себе: диагностика сохраняет согласованный жизненный цикл errors.

Вход: проект переключает активную embedding-модель A на B, пока выполняется работа A и опубликованы граф/FTS по S1. Выход после COMMIT: граф/FTS остаются по S1; для знаний поставлены новые задания B по S1 с новыми seq. Поиск продолжает работать через FTS и постепенно получает векторы B. Результат прежнего задания A не публикуется; запрос, начавшийся до переключения, сохраняет свой снимок и совместимый адаптер.

Мотивация: один общий источник настроек обслуживает поиск, вычисление и восстановление после перезапуска. Замена очереди сохраняет достаточность уже выбранной проверки seq для прежних вычислений. Физическая очистка и перенастройка vec1, включая смену размерности, ещё проектируются и не подтверждены существующей Rust-пробой; принят логический протокол, а не готовая реализация переключения.

### Согласовано: колонки embedding_config и отдельная таблица project

Пользователь принял embedding_config с колонками id, provider, model и parameters; внутренний ключ id = 1. Отдельная колонка adapter исключена. В таблице сохраняется одна активная конфигурация проекта; публичный идентификатор конфигурации не вводится.

Согласованный DDL после исключения adapter:

```sql
CREATE TABLE embedding_config (
    id         INTEGER PRIMARY KEY CHECK (id = 1),
    provider   TEXT NOT NULL,
    model      TEXT NOT NULL,
    parameters TEXT NOT NULL DEFAULT '{}'
        CHECK (json_valid(parameters) AND json_type(parameters) = 'object'),
    max_retries INTEGER NOT NULL CHECK (max_retries >= 0)
);
```

Parameters содержит JSON-объект с дополнительными настройками выбранного провайдера и модели; по умолчанию это {}. Согласованный CHECK проверяет корректность JSON и тип object, не ограничивая ключи параметрами OpenAI. Конкретные имена и смысл настроек определяет адаптер провайдера; общий SQL-перечень ключей не вводится. Функции описаны в [официальной документации SQLite](https://www.sqlite.org/json1.html). Знание и его Markdown в эту строку не копируются. Исполнитель и поиск получают настройки из одной активной строки в согласованном снимке чтения SQLite. Обновление строки при смене влияющей на векторы конфигурации входит в уже согласованную транзакцию очистки векторов и замены очереди. Provider обозначает поставщика модели или обслуживающую её платформу. Формат идентичности модели ещё уточняется.

Provider выбирает поставщика или платформу, например OpenAI или Ollama; model задаёт выбранную модель. Adapter — внутренняя реализация порта, переводящая вызов texts → vectors в протокол выбранного провайдера или локальное вычисление. Согласовано выбирать её в коде по provider; в embedding_config отдельная колонка adapter не хранится. Обязательный локальный режим сохраняется.

### Согласовано: project(id, revision)

Таблица project хранит общее состояние проекта знаний текущего Git-репозитория. В первой версии одна служебная SQLite-БД обслуживает один проект. Внутренний ключ id = 1 ограничивает таблицу одной строкой; сам CHECK не создаёт эту строку. Публичный UUID проекта и сохранённые имя или путь корня не требуются: корень определяется по Git.

```sql
CREATE TABLE project (
    id       INTEGER PRIMARY KEY CHECK (id = 1),
    revision TEXT
);
```

Revision содержит Git tree OID снимка, по которому опубликованы граф и FTS. До первой успешной публикации значение NULL. При apply оно обновляется в финальной транзакции SQLite вместе с графом, FTS и заданиями embeddings; при реиндексировании — в транзакции публикации соответствующего снимка. Сохранение отдельных векторов не меняет revision: embeddings могут отставать по согласованным правилам очереди.

Status читает revision для сообщения агенту о состоянии индекса. Search получает её в своей транзакции чтения вместе с индексом. При смене embedding-модели новые задания строятся по этому опубликованному снимку, а не по произвольному текущему состоянию рабочей копии. История снимков остаётся в Git; project хранит только указатель на текущую публикацию.

Вход: первая успешная публикация графа и FTS по снимку S1, затем apply по S2. Выход: после первой публикации project содержит id = 1, revision = S1; после финального COMMIT правки — revision = S2. Последующая обработка embeddings по S2 оставляет revision = S2.

Мотивация: один указатель связывает состояние CLI, поиск и создание заданий с согласованным снимком корпуса без отдельной истории версий индекса в БД. Embedding_config принадлежит проекту через общую SQLite-БД: одна БД обслуживает один проект, в каждой из этих таблиц по одной активной строке с id = 1. Колонка project_id и внешний ключ между ними не вводятся. Поиск читает ревизию project и настройки embedding_config в одной транзакции чтения SQLite. Это сохраняет согласованность чтения без дублирования принадлежности проекту. Предложение общей строки project_state с JSON всей конфигурации не принято и не является физической схемой.

## Согласовано: основа очереди заданий индексирования

Статус: пользователь принял основу очереди — таблицу в служебной БД, одного исполнителя и обработку в порядке постановки. Ниже приведён логический каркас записи для дальнейшей детализации. Это внутреннее хранение проекта, а не новый формат CLI. Движком служебной БД выбран SQLite; DDL, окончательный набор полей и оставшиеся правила ещё проектируются.

Одна существующая таблица embedding_jobs используется для долговечной работы на embeddings; второй механизм очереди не вводится. Один исполнитель берёт задания в порядке постановки. Поиск и CLI выполняются тем же локальным процессом. Задание читает свой неизменяемый Git-снимок; новые правки обновляют граф/FTS и ставят необходимую работу для следующих снимков. Согласованы одна строка на вершину или метавершину и обязательный node_id с UNIQUE(node_id). Групповая правка сохраняет несколько строк в одной транзакции. Селекторы paths и element_ids остаются входом CLI reindex и не обозначают пакет внутри одной строки очереди. Остальные поля и физическая схема ещё проектируются.

### Согласовано: внешний ключ задания на узел

Поле embedding_jobs.node_id обязательно, уникально и ссылается на nodes.id с ON DELETE CASCADE. Удаление строки узла удаляет его строку очереди в той же транзакции. Уже выполняющееся вычисление не сохраняет результат для удалённого узла и не восстанавливает исчезнувшее задание. Ранее согласованное включение foreign_keys на каждом SQLite-соединении относится и к этому ограничению.

Фрагмент ограничения для окончательного DDL:

```sql
FOREIGN KEY (node_id)
  REFERENCES nodes(id) ON DELETE CASCADE
```

Вход: групповая правка полностью удаляет вершину A после исправления входящих ссылок; для A есть строка очереди. Выход: узел A и его задание отсутствуют после COMMIT. При откате транзакции сохраняются обе строки; результат выполняющегося вычисления проверяется перед сохранением по обычным правилам.

Задание является служебной работой для конкретного узла. Входящие графовые рёбра по-прежнему требуют явного исправления в правке и используют согласованные внешние ключи без каскадного удаления. Перенос с прежним ID сохраняет идентичность узла; смена адреса не требует удаления самой строки nodes. Порядок SQL-обновлений итоговой проекции ещё проектируется.

Мотивация: штатное ограничение БД удаляет ненужную работу вместе с её узлом и не допускает задания для отсутствующего node_id. Основание: [SQLite foreign key actions](https://www.sqlite.org/foreignkeys.html#fk_actions).

### Согласовано: адрес элемента в снимке задания

В embedding_jobs хранится uri TEXT NOT NULL: значение nodes.uri на момент постановки работы. Используется прежний формат адреса знания — путь от корня Git-проекта и стабильный ID. Поле snapshot адресует неизменяемый Git tree; uri адресует нужный фрагмент внутри него. Текущий nodes.uri не подменяет сохранённый адрес задания после переноса файла.

Вход: работа A поставлена по S1 с uri knowledge/old.md#A; затем элемент с прежним ID перенесён в knowledge/new.md без изменения поискового текста. Выход: исполнитель читает knowledge/old.md из S1 и выделяет A по ID, после вычисления проверяет применимость результата к текущему элементу. Исходный адрес и снимок выполняющейся работы не изменяются.

Мотивация: один сохранённый адрес позволяет читать точный вход задания после перемещения элемента, используя ту же грамматику, что и nodes.uri. Поиск по всему корпусу для разрешения адреса не нужен; диапазоны текущих строк не подменяют координаты прежнего снимка. В БД хранится ссылка, а текст остаётся в Git. Порядок чтения и разбор Markdown ещё проектируются.

### Согласовано: seq и проверка результата вычисления

Каждое новое задание получает новый seq, включая замену задания того же node_id. Номер прежней работы не переиспользуется для новой. Повторная попытка существующего задания относится к той же работе; новый seq требуется именно при постановке нового задания. UNIQUE(node_id) по-прежнему оставляет в очереди только одну текущую строку для узла. Согласовано seq INTEGER PRIMARY KEY AUTOINCREMENT: SQLite автоматически назначает номер при вставке нового задания; приложение не задаёт его вручную и не сбрасывает служебный счётчик. Номера надёжно сохранённых заданий не переиспользуются после удаления строк. Пропуски в последовательности допустимы; непрерывная нумерация не требуется. Согласован оператор INSERT OR REPLACE для постановки и замены; его порядок описан ниже. Основание: [SQLite AUTOINCREMENT](https://www.sqlite.org/autoinc.html).

Согласованный фрагмент DDL:

```sql
seq INTEGER PRIMARY KEY AUTOINCREMENT
```

Порядок обработки, согласованный пользователем:

1. Прочитать текущую строку задания и сохранить её seq и данные входа, включая uri и snapshot. Завершить чтение до вычисления; отдельная дополнительная проверка перед вычислением не требуется.
2. Вычислить embedding вне транзакции БД по неизменяемому входному снимку.
3. Открыть новую короткую транзакцию записи. Проверить, что строка с исходным seq существует; при отмене она удаляется. Если строка существует, сохранить применимый вектор и удалить именно её в той же транзакции. Если строки нет из-за замены, удаления или отмены, отбросить прежний результат, не изменяя вектор и новую работу.

Вход: исполнитель прочитал работу узла A с seq=10; во время вычисления новая правка заменила её работой seq=11. Выход: завершение seq=10 не сохраняет прежний вектор и не удаляет seq=11. Если замены не было и задание не отменено, после COMMIT вектор сохранён, а строка seq=10 удалена.

Мотивация: модель не удерживает транзакцию записи во время вычисления; проверка принадлежности работы, сохранение вектора и удаление задания имеют одну точку фиксации. Новый seq отличает замену без дополнительного хеша для этой проверки. Конфигурация модели фиксируется общими служебными метаданными проекта; её смена заменяет очередь с новыми seq. Требование совместимости модели с текущим поисковым индексом сохраняется, физическое кодирование ещё проектируется.

### Согласовано: постановка задания через INSERT OR REPLACE

letopis ставит новое задание оператором INSERT OR REPLACE в таблицу embedding_jobs. Приложение передаёт данные новой работы и не указывает seq: SQLite назначает его через AUTOINCREMENT. При конфликте UNIQUE(node_id) прежняя строка того же узла удаляется, а новая вставляется с новым seq. Постановка после CLI-правки входит в уже согласованную финальную транзакцию apply вместе с графом и FTS; отдельная точка фиксации очереди не вводится. Для других причин индексирования используются те же правила постановки.

Вход: для узла A существует работа seq=10 по снимку S1; завершённая правка требует вычисления по S2. Выход после COMMIT: для A остаётся одна новая строка по S2 с новым seq и данными новой работы; строки других узлов сохраняются. Исполнитель прежнего задания не проходит проверку существования исходного seq и не изменяет новый вектор или новую строку. Если финальная транзакция откатилась, прежняя строка сохраняется, а новая работа не становится видимой исполнителю.

Мотивация: один SQL-оператор покрывает создание и замену по существующему ограничению UNIQUE(node_id). Не нужны предварительная проверка наличия строки и отдельные ветви постановки. Основание: [SQLite REPLACE](https://www.sqlite.org/lang_conflict.html). Окончательный набор колонок и начальное состояние строки ещё проектируются; согласованный оператор не фиксирует пока не выбранный полный DDL.

### Согласовано: два состояния очереди и выполнение в памяти

Поле embedding_jobs.state имеет два согласованных значения: queued и failed. Queued означает незавершённую работу, которая ожидает вычисления, выполняется или ожидает разрешённого ретрая. Failed означает исчерпание ретраев: строка сохраняется и пропускается исполнителем. Состояния running, done и cancelled в БД не хранятся; успешно обработанная, устаревшая незаменённая или отменённая строка удаляется по уже согласованным правилам. Физический тип колонки, ограничения и значения по умолчанию ещё проектируются.

Единственный исполнитель проекта выбирает queued-задание и хранит сведения о текущем вычислении в памяти рабочего процесса, включая исходный seq. Чтение строки и начало вычисления не меняют её state на running. Рабочий процесс предоставляет текущий прогресс для status; согласованный счётчик embedding_jobs включает queued-строки, включая вычисляемую и ожидающие разрешённого ретрая, и исключает failed.

При сбое процесса вычисляемая работа остаётся queued, если её строка не была заменена или удалена. Новый исполнитель может снова обработать её по сохранённым uri, snapshot и счётчику retries. Отдельное восстановление перехода running → queued не требуется. После успеха вектор и удаление строки фиксируются вместе; при исчерпании ретраев сохраняется failed. Порядок учёта новой попытки и физическое восстановление этого счётчика ещё уточняются.

Вход: исполнитель прочитал seq=10 и завершился до сохранения вектора. Выход: в БД остаётся queued-строка; после перезапуска она доступна для обработки по своему прежнему Git-снимку. Строки failed не выбираются, удалённая отменённая работа не восстанавливается.

Мотивация: присутствие queued-строки уже сохраняет незавершённую работу, а один исполнитель знает, что вычисляет прямо сейчас. БД хранит признаки, необходимые для продолжения или остановки, без отдельного долговечного состояния текущего выполнения. Публичные CLI-контракты и правила диагностики сохраняются.

Пример содержимого очереди: первое задание выполняется по снимку S1, второе ждёт обработки более позднего S2. В БД обе строки имеют queued; сведения о текущем выполнении seq=1 находятся в памяти рабочего процесса. Ниже показан логический массив строк таблицы, не ответ status:

```json
    "state": "queued",
    "attempts": 1
```

## Согласовано: режим WAL и долговечная фиксация SQLite

Статус: принято пользователем. Выбран WAL с synchronous=FULL, fullfsync на macOS и SQLite 3.51.3 или новее. Это внутренняя конфигурация, без новых команд и параметров CLI.

Выбран WAL с synchronous=FULL: WAL позволяет чтению и записи БД выполняться одновременно, сохраняя одного писателя. FULL синхронизирует WAL при каждом коммите и обеспечивает долговечность завершённых транзакций БД после потери питания при корректной работе нижележащих механизмов хранения. Основания: [SQLite WAL](https://www.sqlite.org/wal.html) и [PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous).

Внутренние настройки открытия служебной БД:

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
```

На macOS согласован дополнительно fullfsync=ON, чтобы SQLite использовала F_FULLFSYNC. При таком fullfsync отдельный checkpoint_fullfsync не требуется. На Linux этот механизм отсутствует; применяется синхронизация соответствующего VFS. Основание: [PRAGMA fullfsync](https://www.sqlite.org/pragma.html#pragma_fullfsync).

```sql
PRAGMA fullfsync = ON;
```

Режим БД проверяется после открытия; параметры синхронизации применяются к соединениям, выполняющим запись. Драйвером выбран rusqlite; реализация настройки соединений ещё проектируется. Для первой версии требуется SQLite 3.51.3 или новее с исправлением WAL-reset. Основание: [SQLite WAL: исправление WAL-reset](https://www.sqlite.org/wal.html).

Это внутренний WAL SQLite для данных БД. Принятый прикладной журнал восстановления и Git-снимок по-прежнему обеспечивают откат Markdown-файлов; WAL SQLite их не заменяет. Удаление прикладной записи восстановления остаётся частью финальной транзакции после надёжного сохранения документов. Embeddings и подготовка файлов выполняются вне длительной транзакции записи SQLite.

Мотивация: поиск может читать опубликованные данные во время коротких служебных записей, а надёжно завершённая финальная транзакция не должна исчезать после потери питания. Цена FULL и fullfsync — дополнительная синхронизация на коммит; её задержку нужно измерить. Полный порядок долговечной записи Git, файлов, каталогов и БД, обслуживание checkpoint и проверка аварийных сценариев ещё проектируются. Согласованный профиль не подтверждает готовность реализации.

## Согласовано: FTS5 без копии текста

Статус: принято пользователем. FTS5 в режиме contentless-delete выбран как текстовая часть уже согласованного гибридного поиска внутри единой SQLite-БД; CLI-контракт search сохраняется.

Выбран FTS5 в режиме contentless-delete внутри той же SQLite-БД. Contentless хранит структуру поискового индекса без полной копии входного текста; contentless-delete поддерживает DELETE, INSERT OR REPLACE и полную замену индексируемых колонок при UPDATE. Чтение текстовой колонки возвращает NULL. Основание: [FTS5: contentless и contentless-delete](https://www.sqlite.org/fts5.html).

Пример DDL для одной индексируемой колонки; имя таблицы и физическая связь с публикуемыми данными ещё уточняются:

```sql
CREATE VIRTUAL TABLE text_index USING fts5(
    text,
    content = '',
    contentless_delete = 1
);
```

Вход индексирования: nodes.row_id, записываемый как rowid строки FTS5, и согласованный подготовленный поисковый текст Markdown-фрагмента. Текст передаётся FTS5 для построения индекса; его полная копия в колонке text не сохраняется. Вход текстового поиска — подготовленное выражение запроса; выход — совпавшие rowid, сопоставляемые с постоянными ID узлов для гибридной выдачи. Сами документы агент читает по ссылкам согласно прежнему контракту.

Решение использует выбранный SQLite и стандартный модуль FTS5; поставляемая сборка должна включать этот модуль. Служебная разметка, метаданные ссылок и текст включённых дочерних элементов обрабатываются по ранее принятому правилу подготовки текста. Индексируются знания vertex/metavertex; внешние source сами не становятся текстовыми результатами.

Мотивация: единый движок обслуживает служебные данные и текстовую поисковую структуру, сохраняя границу хранения без копий документов. Связь rowid/UUID согласована через nodes.row_id и nodes.id. Окончательный DDL FTS5, токенизация и подготовка выражения MATCH, ранжирование, выборочная перестройка и обслуживание поисковых таблиц ещё проектируются. Этот пример не подтверждает измеренное качество или скорость поиска.

## Согласовано: Rust, rusqlite и vec1

Статус: принято пользователем. Язык реализации первой версии — Rust; доступ к единой служебной SQLite-БД — через rusqlite; векторный поиск — через нативное расширение vec1. FTS5 contentless-delete остаётся текстовой частью гибридного поиска. Выбор сохраняет DDD и hexagonal, согласованные CLI-контракты, общую БД и асинхронное вычисление embeddings при синхронной фиксации графа и FTS.

Режим vec1, метрика, конкретные версии зависимостей, способ включения расширения в поставку, организация соединений и локальный embedding-адаптер уточняются отдельно. Векторное расширение хранит и ищет готовые векторы; вычисление embeddings остаётся обязанностью прежнего сменного адаптера. Профиль SQLite 3.51.3+, WAL, synchronous=FULL и fullfsync на macOS остаётся обязательным.

Основание выбора и результаты временной проверки описаны в [исследовании Rust](../research/R-2-rust-sqlite.md); [Go-исследование](../research/R-1-go-sqlite.md) сохраняется как сравнение альтернатив. Исследовательские замеры не подтверждают нагрузочные и аварийные гарантии полного letopis.

## Предложение: режим flat для vec1

Статус: vec1 уже выбран; точный режим flat и косинусная метрика остаются предложением для первого прототипа. Окончательная настройка зависит от измерения поиска и памяти на корпусе проекта.

Предлагается использовать выбранный vec1 в режиме flat с косинусным расстоянием. Flat выполняет точный поиск по всем векторам, сохраняя их в упакованных массивах; обучение ANN-модели для этого режима не требуется. Режимы none/flat и настройка distance описаны в [руководстве vec1](https://www.sqlite.org/vec1doc.html).

Vec1 реализован в portable C без внешних зависимостей. На дату проверки актуальный релиз — 0.8. Для прототипа фиксируется проверяемый релиз расширения; он должен быть включён в поставку локального приложения и проверен с выбранной SQLite 3.51.3+ на macOS/Linux. Основание: [описание и сборка vec1](https://www.sqlite.org/vec1.html). Расширение не заменяет модуль получения embeddings.

Пример создания таблицы векторов; окончательные имена и связь с публикацией ещё уточняются:

```sql
CREATE VIRTUAL TABLE vector_index USING vec1(vector);
```

После загрузки векторов настройка режима:

```sql
INSERT INTO vector_index(cmd, arg)
VALUES('rebuild', '{"index":"flat","distance":"cos"}');
```

Вход индексирования — векторы от согласованного embedding-порта и связь строк с узлами знаний. Вход векторного поиска — embedding запроса, фильтры и лимит; выход — ближайшие узлы для объединения с FTS5-результатами. Публичный search продолжает возвращать ссылки без текста и оценок; новый режим CLI не вводится.

Мотивация первого прототипа: получить точный базовый результат и проверить требования по скорости и памяти с минимальным набором настроек. Время полного поиска растёт с количеством и размерностью векторов; из десятков тысяч документов может получиться существенно больше векторов. Само наличие flat не подтверждает одну секунду или работу в бюджете ноутбука с 4 ГБ памяти.

Если точный вариант не выполняет критерии, требуется сравнение с ANN по задержке, памяти и качеству результатов; vec1 поддерживает ANN, но это потребует отдельного решения о конфигурации и обслуживании. Нельзя объявлять flat окончательным механизмом только на основании его простоты. Метрика, формат и ключи векторов, выполнение принятых фильтров до лимита, выборочное обновление и совместная публикация ещё проверяются и проектируются. Продуктовый прототип letopis здесь не реализован.

Выполнена отдельная [проверка Go-драйверов и векторных расширений](../research/R-1-go-sqlite.md): нативный vec1 0.8 с mattn и встроенный vec1 0.7 с ncruces прошли основные проверки регистрации, отката, WAL-снимка и отмены; исследована альтернативная интеграция sqlite-vec с modernc. Go и эти драйверы остаются исследованными альтернативами; для реализации выбран Rust с rusqlite. Замеры 50 000 синтетических векторов не подтверждают ресурсные и временные требования полного letopis.

В [Rust-проверке](../research/R-2-rust-sqlite.md) rusqlite 0.40.2, встроенная SQLite 3.53.2 и нативный vec1 0.8 прошли проверки FTS5, отката, WAL-снимка, фильтров и отмены. Эти версии являются проверенной исследовательской базой, а не автоматически закреплёнными версиями продуктовой поставки. Рекомендуется минимальная обвязка rusqlite без ORM и обязательного async-слоя. Сопоставимый порядок времени векторного поиска не доказывает преимущества одного языка для всего letopis.

## Последовательность дальнейшего детального проектирования

1. Единые nodes/edges, сохранение идентичности источников и физическая уникальность текущих UUID.
2. Координаты, актуальные и подтверждённые хеши, фильтрация по ревизиям источников. История по известным Git-снимкам согласована.
3. Журнал восстановления: состав данных полного отката и физический порядок долговечной фиксации; наличие записи и её удаление в финальной транзакции как маркер завершения согласованы. Диагностика и история имеют отдельные правила.
4. Задания, используемая конфигурация, локи, диагностика и восстановление владельца.
5. Текстовый и векторный индексы, совместимость модели и данные embeddings.
6. Публикация, закрепление читателями, удаление ненужных производных данных.
7. Физические схемы SQLite и индексы доступа, транзакционные границы портов, миграции схемы и резервное копирование служебного состояния; движок SQLite уже выбран.
8. Проверка инвариантов, аварийных сценариев и ресурсных ограничений на прототипе.

Порядок может уточняться при обнаружении зависимости или противоречия; количество вопросов не ограничено.

## Открытые вопросы согласованности для аудита

- Вопрос бессрочной дедупликации закрыт: она отменена, после потери ответа агент перечитывает состояние. Хеш исходного JSON остаётся отпечатком содержимого, а не уникальным ключом каждого нового выполнения. Срок жизни записи восстановления согласован: удаление после надёжного завершения правки или полного отката. Удаление записи восстановления в финальной транзакции БД принято как маркер завершения без отдельного поля состояния. Физический аварийный протокол ещё проектируется.
- Для отката требуется сохранить прежнее содержимое всех затронутых размеченных Markdown-документов корпуса. Изменение существующего неразмеченного файла не допускается: весь запрос отклоняется до записи. Точный состав снимка восстановления ещё уточняется; откат не разрешает запись в посторонние документы. Ранее согласованный create по отсутствующему пути создаёт сразу размеченный документ после общей проверки.
- Точный порядок Git-объектов, служебных refs, файла журнала БД, замен файлов и результата операции должен выдерживать потерю питания. Одно применение Git или транзакции БД не описывает весь протокол.
- Текущий source_snapshot знания восстанавливается из канонического Markdown. История оснований читается по известным удерживаемым Git-снимкам. Соответствия uri/UUID источников и данные восстановления требуют сохранного служебного состояния БД. Для полной потери БД ещё не определены резервное копирование и восстановление.
- Старая графовая проекция не является достаточным основанием для проверки новой записи: документы и источники могли измениться после её публикации. Нужен точный контракт доступа к текущему каноническому состоянию.

Эти пункты фиксируют незавершённые вопросы проекта, а не обнаруженные дефекты реализованного letopis.

## Метаграф и обычный граф: анализ представления

Статус: пользователь подтвердил сохранение метавершин и includes в доменной модели и обычный граф nodes/edges в хранении. Исторический реестр идентификаторов не используется; движком выбран SQLite, физический DDL ещё проектируется.

Текущая модель letopis содержит вершины, метавершины и направленные бинарные рёбра; метарёбра исключены. По этим определениям она точно представляется типизированным направленным мультиграфом: вершины и метавершины — узлы с `kind`, а включённость — системное ребро `includes`. Для метавершины непосредственный состав определяется исходящими includes; внутренние рёбра выбираются по непосредственному вхождению обоих концов. Отдельного физического примитива вложенного графа для этого не требуется.

Обычная модель property graph предоставляет узлы, их свойства и типы связей; представление составных сущностей через связи описано в [официальных понятиях Neo4j](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/). Это подтверждение возможностей представления, а не выбор Neo4j для letopis. Точная представимость нашей модели — вывод из её собственных согласованных правил.

Дополнительная польза метавершин относится к предметной семантике: составное понятие имеет собственные ID и описание; агент может сначала прочитать его, затем раскрыть нужные части; общий элемент включается в несколько контекстов без копирования. Связь с компонентом в целом имеет отдельный смысл от связи с отдельным его решением. Эти возможности сохраняются в обычном графе, если у него есть те же узлы-группы, связи includes и правила обхода.

Стоимость этой семантики — проверка разрешённых источников includes, уникальности включения пары и отсутствия циклов, различение непосредственного и транзитивного состава. Она не доказывает повышение recall или экономию токенов и не заменяет проверку актуальности знаний. Сокращение лишнего контекста следует измерять на задачах агентов.

Согласовано: составные сущности и включённость сохраняются в доменной модели, хранение использует обычную графовую проекцию. Специализированный метаграфовый движок не обоснован текущими требованиями. При отказе от использования составных сущностей их предметную семантику следует пересмотреть отдельным решением пользователя.
