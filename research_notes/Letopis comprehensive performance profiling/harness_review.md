## Blocking integrity findings

1. `profile.py:33,73-98,325-338,422-461`: The main baseline is a new sparse generator at 0/100/1k/10k with one internal edge per node and no source links, not the authoritative seed-65 canonical 60/1k/10k, 2,000-byte, five-edge mixed source/relationship baseline. Even optional canonical 100k uses seed 20261117 and bypasses the independent validator and returned corpus manifest. This materially changes measured I/O and graph behavior, not merely a label. Generate and independently validate the required canonical scales with seed 65; keep sparse variants separately identified.
2. `profile.py:121-145,159-166,745-810`: `summarize` groups solely by case ID, combining all appended campaigns and all executable hashes into one median/throughput, including explicitly reduced repeats and potentially different builds. The audit never rejects mixed identities or checks requested versus actual repeats; early `break` or `return` at lines 167-185 records at most one skip and leaves planned samples and all later cases unaccounted. Partition results by campaign, executable/build, fixture/config and stage; explicitly record planned, attempted, censored and missing work, and audit mismatches before reporting.
3. `profile.py:188-228,241-267`: `timeout = min(timeout, 10)` kills the sampler and product after ten seconds rather than capturing a ten-second window with separate cleanup time. Timeout makes the row invalid even if a partial profile exists; expensive operations cannot produce valid bounded-window evidence. Use the existing `tests/performance/window.py` mechanism with a separate sampler/cleanup timeout, identify and filter the product PID, and label the resulting capture censored and non-baseline.
4. `profile.py:250-267,814-821,850-863`: A valid gzip and non-null stacks produce a successful profile without verifying executable identity, matching dSYM/debug identifiers, resolved symbols, or product PID. Stack summarization is called without `pid_filter`, potentially attributing other sampled processes to Letopis. Archive and verify build metadata and matching binary/symbol identity; identify the product process and report unresolved or wrong-process stacks as unavailable, not hotspot evidence.
5. `profile.py:73-118,121-140,173-185`: `validate` is optional and its results are not checked by `measure`/`profile`; fixture hashes are recorded at creation but never checked before copying, and setup only compares projected aggregate counts. Input edits or incorrect graph/search semantics can become successful baseline rows. Require passing validation for the exact immutable fixture, case and binary identity before measurement; independently verify fixture hashes and meaningful case semantics, including the actual vector-only canary.
6. `profile.py:167,191-193,939-940`: The 2 GiB guard counts only scratch, before copying, not growing evidence/profile streams; no live 1 GiB RSS watchdog exists. One setup/copy or measured command can exceed either specified ceiling before the next check. Implement bounded live owned-process RSS enforcement and account for scratch **and evidence**, including in-progress growth; retain cleanup/censor evidence on limit breach.

## Additional correctness risks

- `profile.py:628-629`: The drain oracle equates HTTP request count with queued hashes. OpenAI requests can batch multiple indexed inputs, so valid batched drains would fail despite complete vector coverage. Verify item/index coverage and vector keys instead of assuming one request per hash.
- `profile.py:784-810`: `throughput_success_per_second` excludes failed/censored call durations. Its label discloses that fact, but it is not campaign throughput and should not be reported as overall throughput. Provide attempted elapsed-time accounting or omit the throughput claim.
- `profile.py:255-267`: Profile validation catches `OSError`/`ValueError` but not malformed profile `KeyError`, `TypeError`, or `EOFError` from later parsing/symbol processing. The outer catch then replaces the completed measurement with a setup failure and loses its metrics from the JSONL row. Preserve the raw command record and classify profile processing errors separately.
- `profile.py:297-301,931-936`: Reacquiring the lease uses blocking `LOCK_EX` without a deadline. An unexpected lock holder can hang setup beyond the stage budget; use bounded nonblocking acquisition and report ownership/cleanup failure.
- `profile.py:463-484`: Real-repository export filters only the first path component and extension, not nested generated/evidence/secret paths. Tracked sensitive text or generated content under `docs`, `src`, `skills`, or `letopis` can be copied into evidence. Apply explicit component/path exclusions and secret-safe allowlisting before reading or copying.
