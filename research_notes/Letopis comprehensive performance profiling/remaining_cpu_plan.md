## Aggregate capture design

Implement a private sequential wrapper under the new evidence directory. It launches exact private executable with `subprocess` and a fresh stdin pipe per child, records every child PID, argv, fixture identity, exit, output hash and validation outcome; records must cover all intended children, not merely the sampler's final exit. No shell-shared input descriptor: every JSON child gets the complete independent request and EOF. Configure finite run counts (initially a few dozen; at most 100 for repeat-safe cases) and cap per-child and aggregate time. Preserve detailed receipts and all failures. A failed child makes the aggregate invalid; no unnoticed partial-success attribution.

Profile the wrapper's descendant tree only if actual samply behavior captures its children; verify this in bounded runtime validation. Use 1 kHz initially; **10 kHz only for a separately labeled diagnostic aggregate if the initial short capture is inadequate and budget permits**, with a strict finite attempt count. Target at least 100 usable product stack observations per aggregate, not 100 per invocation; if unavailable or below threshold, report insufficient, not zero cost. The report must name rate, child count, fixture state and aggregate nature. No aggregate sampler duration, CPU, or RSS is per-call latency, per-call memory, or a primary baseline.

For each captured profile, retain raw gzip, sidecar and hashes. Validate executable library path/code ID, sidecar UUID, private executable hash, and matching symbol artifact; record every successfully started target PID and reconcile it with per-child receipts and sampled thread PIDs. Filter wrapper, mock server, Git and setup out. Handle PID reuse by refusing ambiguous mappings rather than merging unrelated processes. PID-filtered `threadCPUDelta` is the denominator; deduplicate function names per stack, sum weights across verified product PIDs, and require a positive-weight resolved `letopis::` function in the actual product library. Report all target PIDs, sampled versus unsampled, total CPU and usable stacks; inclusive functions overlap and cannot be summed. Do not treat wrapper stacks or an unrelated positive CPU total as Letopis attribution.
