# Letopis implementation hot-path hypotheses

## 1. What runs for every command, including startup and background completion?

### Takeaway

This is read-only implementation research, not a profiling result. Refresh, service composition, diagnostics and background readiness can cost more than the named operation; a small search/traversal/inspect result does not imply a small command. No compilation, installation, product commands, benchmarks, provider requests or measurements were performed.

Scope update from coordinator: **samply and “Local only (Recommended)” are user-approved**, and the user selected “Proceed autonomously.” Use deterministic localhost embeddings through the OpenAI-compatible protocol, satisfying the initial assignment's OpenAI-only constraint. No real provider API calls, real credentials or paid traffic. macOS `sample` is fallback only if samply is blocked. No agent delegation.

#### Startup and finish costs to retain in whole-command accounting

- Foreground `index/check/search/traverse/inspect` eagerly builds a separate embedding executor **before** its command-specific service. That opens one vector writer plus cache reader/writer; command-specific composition opens another database group. For search/traverse, the background executor and query executor are separate service/storage instances. Thus repeated SQLite initialization within one invocation is a concrete code path, not assumed connection pooling. [commands](../../src/commands.rs#L63-L82), [search/traverse/inspect composition](../../src/commands.rs#L139-L181), [executor](../../src/lib.rs#L609-L626), [DB opens](../../src/lib.rs#L834-L857).
- Each confined writable DB group bootstraps schemas, prepares native vector representation, attaches the other DB and opens reader connection. Already-flat preparation still compares model bytes against a newly created in-memory reference DB. Non-flat state adds an atomic native rebuild; separate it from normal warm startup. [open_confined_databases](../../src/lib.rs#L834-L857), [bootstrap_vectors/vector_index_prepare/is_flat_index](../../src/storage/schema.rs#L30-L104).
- Database operations use synchronous WAL/FULL, plus fullfsync on macOS. Acquisition has bounded contention retry; transaction end commits synchronously. Database writers and index/embed locks are distinct waits. [configure_database](../../src/storage/connection.rs#L195-L224), [contention policy](../../src/storage/connection.rs#L19-L75), [transaction acquisition/finalization](../../src/storage/transaction.rs#L86-L180).
- `finish_foreground` invokes `start_if_needed` **before response encoding/output**. It does readiness, work selection, embed-lock probe/release and possibly process spawn. Config readiness can reset vector state, even when the named command does not infer a query. [finish](../../src/cli/response.rs#L111-L119), [background](../../src/service/background_runner.rs#L36-L54), [availability/readiness](../../src/service/embedding.rs#L74-L146).
- Spawned drain uses same executable with `embed --drain`, `setsid`, null stdin/stdout/stderr; parent drops child handle without waiting. Child acquires its own lock. Concurrent launchers may spawn losing children after a successful advisory probe. Parent latency excludes drain completion; child CPU/RSS need explicit separate attribution. [composition](../../src/lib.rs#L642-L656), [process_spawn](../../src/process/detached.rs#L32-L55), [drain acquisition](../../src/service/embedding.rs#L149-L165).
- CLI input can impose 250 ms first-byte polling when a pipe stays open without bytes; after first byte it reads to EOF. Feed finite input/closed stdin so harness behavior is not mistaken for algorithm latency. Output encodes to bytes, then `write_all`/flush; response volume and downstream backpressure can matter. [ProcessInput::read](../../src/process/input.rs#L34-L55), [ResponseWriter](../../src/cli/response.rs#L75-L99), [response_encode](../../src/cli/output.rs#L156-L239).

### Inferences

- **H1 — startup floor:** tiny/no-op commands may spend substantial CPU in repository discovery, multiple SQLite opens/schema validation/native model preparation, not their named algorithm. Confirm with samply launch captures including process start, comparing help/config/status/no-op index/search depth-zero traverse; refute if these stacks contribute little CPU and unprofiled startup wall time stays negligible. Symbols may be inlined; absence of exact Rust frame alone does not refute.
- **H2 — latency vs CPU divergence:** lock contention, fullfsync, spawn, pipe poll and writes may dominate wall but not on-CPU samples. Confirm with retained blocked/wait stacks or allowed wall-stack fallback plus ordinary wall/user/system CPU and explicit workload state; do not diagnose waits from CPU-share percentages alone.
- **User-approved provider isolation:** run deterministic localhost **OpenAI-compatible** `/embeddings`, use fixture-only dummy `OPENAI_API_KEY` because current adapter requires a nonempty printable key, never read/forward real credentials. Set explicit localhost `base_url`; return indexed finite float vectors of chosen dimension. Adapter and ureq/JSON/SQL work would be measured, **real model compute, internet latency and paid-provider behavior would not**. `openai_vectors_compute` and `build_authorization` establish protocol/key requirement. No provider request was made during this research. [adapter](../../src/embedding/provider.rs#L242-L270), [X-2](../../docs/zkit/letopis/contracts/X-2-embeddings.md#L6-L23).

### Gaps

- Current measured startup shares, lock waits, end-to-end command latency, allocation attribution and process-tree memory are unknown. Read-only research cannot establish them.
- Provider scope is resolved: user approved deterministic localhost embeddings and autonomous continuation. Real-provider performance remains deliberately outside scope.

## 2. Which algorithms could scale badly, and what sampling would confirm or refute them?

### Takeaway

Prioritize filesystem/provenance, publication graph reconciliation, whole-corpus inspection and full-K native vector work. These are **candidate hotspots inferred from code**, not measured bottlenecks on current revision.

### Cited Findings

#### Refresh and publication

- `DocumentRefreshService::get_file_state` reads all file rows into a BTreeMap plus distinct source snapshots. `detect_changes` builds candidate set and stats candidates; same-stat non-racy files skip reading, changed/racy files capture and SHA-256 bytes. First preliminary scan may be repeated under index lock. A no-op corpus with source snapshots still enters lock/retention path. [refresh/detection](../../src/service/document_refresher.rs#L170-L346), [discovery](../../src/service/utils.rs#L85-L210).
- Git discovery loads/expands index, collects tracked path bytes, performs root worktree walk collecting untracked entries, then filters ignores. Application-level scoped path selection occurs after raw listing, so scoped index does not guarantee scoped directory-walk cost. Non-Markdown repository population and ignore policy are independent workload axes. [Git enumeration](../../src/git/repository.rs#L779-L836), [selection](../../src/service/utils.rs#L85-L184).
- Any actual publication loads all nodes/edges into `EffectiveGraph`, even for small update/path scope. Changed bytes are captured/hashed for detection, preflight, and preparation; changed marked files are parsed in both `prepare_basis` and `prepare_file`. The final preparation and source reconciliation run inside write transaction. [prepare_publication](../../src/service/document_refresher.rs#L426-L464), [preflight](../../src/service/document_refresher.rs#L538-L609), [prepare_file](../../src/service/document_refresher.rs#L670-L717), [write unit](../../src/service/document_refresher.rs#L349-L405), [global graph load](../../src/service/document_refresher.rs#L884-L898).
- `EffectiveGraph::apply` scans retained edges for every prepared owner and uses linear `prepared.cleared.contains`. `get_file_ids_by_path` scans all knowledge IDs per changed file. `collect_source_references` loops edges, and for each source target uses `knowledge.keys().any` for identity conflict. `publish_edges` scans global edges, writing only changed owners. These concrete nested scans are candidates for change-count × total-graph amplification. [apply/IDs/reference accounting](../../src/service/document_refresher.rs#L947-L1006), [edge publication](../../src/service/document_refresher.rs#L804-L810).
- Source reconciliation groups touched addresses by file for one current capture, but computes `select_bytes`/hash separately per address. SQL writes remain per row. Commit reconciles unresolved edges through storage helpers, requiring examination separately from parse cost. [source publication](../../src/service/document_refresher.rs#L731-L787), [cache edge resolution](../../src/storage/cache.rs#L1148-L1188), [cache advance_revision](../../src/storage/cache.rs#L162-L190), [FTS replacement](../../src/storage/cache.rs#L320-L361).

#### Git reads, hashing and provenance

- `blob_get_by_tree_oid_and_path` verifies root, walks each path component by reading a tree and locating entry, then reads addressed blob. `ObjectReader::object_verify_by_oid` uses uncached local ODB decode and independently rehashes full object body in chunks. Addressed reads return cloned owned bytes; reusable decode capacity above 4 MiB is released. 4 MiB is retained-buffer threshold, **not peak-memory or input-size bound**. [path reads](../../src/git/repository.rs#L391-L432), [reader](../../src/git/reader.rs#L148-L244).
- Successful tree structural-validation identities are memoized up to 4096 per invocation, **not tree bytes or object checksum results**. Exact type/hash verification occurs before reuse. Wide tree bodies, deep paths, packed/delta vs loose objects and SHA-1 vs SHA-256 remain workload axes. [reader](../../src/git/reader.rs#L148-L163), [X-3 boundary](../../docs/zkit/letopis/contracts/X-3-git.md#L21-L41).
- Strong tree sync audits full closure with pending/visited object identities and reads/hashes all reachable blobs/trees; each audit has its own visited map. Distinct roots sharing objects can still repeat closure work across audits. Inspect, whole `check`, and verified/full index expose this path; root-only retention is not equivalent. [closure traversal](../../src/git/repository.rs#L578-L633), [snapshot sync](../../src/service/provenance.rs#L119-L148), [Git durability writes](../../src/git/durability.rs#L63-L184), [contract](../../docs/zkit/letopis/contracts/X-3-git.md#L21-L41).
- Batch provenance groups historical sources by `(TreeOid, RepoPath)`, locates requested line boundaries once and hashes exact borrowed ranges. Admission is at most 4096 roots+exact results and 1 MiB address strings; overflow selects whole-call sequential fallback, not truncation. Successful grouping releases blob before fresh live capture. Every local binding still captures live file anew; line selection can rescan its bytes. [batch API/group hash](../../src/service/provenance.rs#L79-L88), [hashes](../../src/service/provenance.rs#L167-L248), [plan/cache/fallback](../../src/service/provenance.rs#L279-L427), [source range selection](../../src/domain/source.rs#L98-L213), [contract](../../docs/zkit/letopis/contracts/I-4-sources.md#L97-L133).
- Search/traverse invoke singleton `observe_sources`, not cross-candidate batch grouping. `compare_revision` verifies requested/basis roots and independently reads/hashes addressed source on both trees; search has bounded per-invocation revision-comparison reuse. [provenance](../../src/service/provenance.rs#L72-L115), [search comparisons](../../src/service/search.rs#L460-L498), [search singleton](../../src/service/search.rs#L168-L185), [traverse singleton](../../src/service/traversal.rs#L261-L273).

#### Markdown and inspect

- Parser materializes all pulldown-cmark offset events even before deciding file is unmarked. It collects layout/headings/metadata, hashes element bytes and renders/hash search text. `search_text_render` scans complete event stream per element, checking metadata ranges; `element_bounds_calculate` scans headings per element, and `edges_collect` searches element list for each inline link. Many elements/headings/links per large file may cause superlinear work despite monotonic line cursor improvement. [parse](../../src/markdown/parser.rs#L45-L78), [layout/bounds](../../src/markdown/parser.rs#L200-L272), [edges](../../src/markdown/parser.rs#L332-L371), [render](../../src/markdown/parser.rs#L546-L574), [syntax contract](../../docs/zkit/letopis/contracts/X-4-markdown.md#L5-L24).
- Inspect loops all discovered candidate files regardless requested count, parses/writes marked blobs, gathers all declared sources, assembles intermediate/final trees and performs final closure sync. File payloads are released per capture; metadata/path/source maps accumulate. Cold object-store insertion adds staged write/verification/fsync/no-clobber publication, whereas repeated identical blobs may reuse durable existing objects. [inspect](../../src/service/inspection.rs#L41-L169), [Git writes](../../src/git/repository.rs#L695-L722), [durability](../../src/git/durability.rs#L63-L184).

#### Search / SQLite / vector dimensions

- Rust candidates are bounded to union of L FTS and L vector knowledge rows, L ≤100; metadata, eligibility and RRF operate inside this pool with no refill. **Not** full-corpus Rust ranking. Fresh file read+hash still happens per candidate. Successful last-file Markdown reuse is limited to 256 KiB input, 1024 elements and 256 KiB ID/path content; oversized files bypass reuse and are reparsed for each candidate. [search](../../src/service/search.rs#L104-L191), [reuse](../../src/service/search.rs#L253-L323), [contract](../../docs/zkit/letopis/contracts/X-1-cli.md#L126-L137).
- FTS SQL matches, joins nodes, computes BM25, sorts score/URI, applies LIMIT; result bound does not bound posting-list or sort work. Compare rare/common tokens and absent/non-token queries. [FTS](../../src/storage/cache.rs#L549-L591), [token construction](../../src/service/search.rs#L513-L523).
- Vector query counts **all vector keys**, passes that as native `K`, then joins native result to current nodes and applies distance/URI sort and SQL L. Exact flat/cos native work can scale with total retained vectors × dimension, including stale/orphan keys, even though only L rows reach Rust. This is not ANN or `K=L`. [nearest/count](../../src/storage/vector.rs#L673-L695), [SQL](../../src/storage/vector.rs#L698-L752), [D-108](../../docs/zkit/letopis/decisions.md#L2355-L2359).
- Query embedding occurs while a cache read view is pinned, outside any service-owned write unit; completion updates singleton query_error in a short separate guarded vector transaction. Long mock delays can expose long-reader/WAL interaction, not real provider performance. [search scope](../../src/service/search.rs#L117-L150), [query diagnostics](../../src/service/embedding.rs#L484-L526), [scope contract](../../docs/zkit/letopis/contracts/I-8-read-view.md#L18-L26).

#### Graph traversal and diagnostics

- BFS retains compact start/discovery IDs, visited set, selected elements and optional bounded edge map, with ≤two neighbor pages of 32. It stops new discovery at node limit; edge_limit only caps stored edges, not neighbor work. Dense cyclic graphs/duplicate alternatives may require many examined edges to discover few new nodes. No generic O(total graph) traversal load is implied by BFS itself. [BFS](../../src/service/graph.rs#L64-L149), [pages](../../src/service/graph.rs#L217-L261), [keyset SQL](../../src/storage/cache.rs#L1403-L1466).
- Traversal hydration freshly captures/parses owner file per returned knowledge link, observes all its outgoing external bindings pagewise, and does not use search's last-file parser reuse. Lots of result elements in one large file or large external fanout can dominate bounded BFS. [hydration](../../src/service/traversal.rs#L70-L110), [bindings](../../src/service/traversal.rs#L193-L273).
- Check/status diagnostics read whole node/edge/file collections, build knowledge BTreeSet, compute dangling targets and includes SCCs, then filter paths. Source diagnostics perform another nodes_get and edges_get, build owner→source map, then observe batches of 256 selected knowledge nodes. Status is not cheap metadata-only monitoring. [graph diagnostics](../../src/service/graph_diagnostics.rs#L38-L74), [source diagnostics](../../src/service/utils.rs#L288-L359), [SCC](../../src/domain/validation.rs#L55-L209), [status](../../src/service/status.rs#L63-L89).
- Enabled status counts distinct current hashes, verifies native vector coverage, gets/decodes all current uncovered failure rows before filtering attempt threshold, then constructs diagnostics. These SQL/collection costs scale independently of returned clean status size; disabled mode skips embedding counters but not graph/source diagnostics. [status counters](../../src/service/status.rs#L177-L235), [storage coverage/failures](../../src/storage/vector.rs#L923-L1053).

#### Embedding/drain

- Drain selects one eligible work item with anti-exists vector/failure checks and URI ordering, rereads/parses owner file, reserves attempt durably, calls provider with **one text**, then stores vector in another guarded transaction. After successful work it resets cursor to beginning; selected skips accumulate in per-drain BTreeSet. Increasing coverage and repeated sections in one owner may amplify selection/reparse work. [loop/preparation](../../src/service/embedding.rs#L257-L332), [reserve/compute/publish](../../src/service/embedding.rs#L335-L481), [selection SQL](../../src/storage/vector.rs#L844-L891).
- Failures consume durable attempts and can sleep one second between retries; completed drain prunes unreferenced vectors/failures. Mock success, retry/exhaustion, stale-file skip, shared search_hash reuse, config reset and already-running lock are distinct paths. [retry delay](../../src/service/embedding.rs#L15), [failure lifecycle](../../src/service/embedding.rs#L380-L442), [prune](../../src/storage/vector.rs#L218-L261).
- Vector dimension affects mock JSON size, float decoding/validation, f32→bytes encoding, native distance work and storage writes. Current native dimension policy is 2–4096; choose dimensions through accepted configuration/protocol, not arbitrary benchmark-only product changes. [dimension constants](../../src/storage/vector.rs#L22-L24), [vector serialization](../../src/storage/vector.rs#L653-L684), [provider decoding](../../src/embedding/provider.rs#L327-L402).

### Inferences

Each hypothesis requires fresh ordinary wall/CPU/RSS results plus separately retained samply stacks. Inclusive stack categories overlap; never add them. Vary one axis at a time while validating IDs/counts/revision/config/vector coverage.

Preserve process RSS timelines/high-water and distinguish allocator/native SQLite work, decoded Git buffers, accumulated metadata/graph maps, encoded response bytes, foreground vs detached children, and deterministic localhost mock-server RSS. A stable logical cache bound does not imply bounded whole-command RSS. ### Gaps

- None of H1–H14 has been measured in this task. Source asymptotics do not establish dominant runtime on practical corpora.
- Sampling may inline/merge Rust functions or under-sample short commands; use frozen binary + symbols, startup coverage and adequate repeat evidence. A no-sample function is not zero-call proof.
- Proposed matrix should separate no-index bootstrap, initialized no-op outside racy window, racy unchanged files, one-file/bulk changes, deletions/invalid files, scoped/full/verified modes; lexical/no-vector/partial/full-vector hybrid, source filters/range changes; graph chains/stars/cycles/high degree; shared/distinct source groups and fallback boundaries; drain success/retry/exhaustion/reset/busy/skip. These are research recommendations, not measurements or authorization to run them.

## 3. What historical evidence exists, and how must its limits be preserved?
