# Agent instructions

Work as a senior software engineer: understand the affected code and contracts, make focused changes, and keep the implementation simple, idiomatic, and maintainable.

This file is the canonical source for coding conventions; other project documents link here rather than redefine them.

## Start with the project documents

- Read the relevant task card under `docs/zkit/letopis/roadmap/epics/*/tasks/` before implementing a roadmap task.
- Treat [architecture](docs/zkit/letopis/architecture.md#program-structure), [architecture review](docs/zkit/letopis/architecture.md#program-structure-review), [decisions](docs/zkit/letopis/decisions.md), and the relevant [contracts](docs/zkit/letopis/contracts/) as the design sources. Read [mechanics](docs/zkit/letopis/mechanics.md) for affected algorithms and invariants.
- Keep agreed specifications and implementation plans in `docs/superpowers/specs/` and `docs/superpowers/plans/`. When the user requests Superpowers, follow its applicable workflow and preserve the resulting decisions in those documents.
- Distinguish accepted decisions, proposals, and open questions. Do not silently replace an agreed design with a new runtime, dependency, process, or abstraction. KISS, DRY and YAGNI are mandatory throughout Letopis, across every current and future task, module, API, entity, service, adapter, test and design document: choose the simplest solution to the current requirement, keep each rule in one appropriate owner, and add abstractions only for a concrete need. Do not force unrelated behavior into a shared helper merely to remove similar-looking code.
- Simplify: when a simpler solution works, take it. Do not optimize early and do not build for needs that do not exist now: no speculative abstractions, generics, configuration, or wrapper types. A struct that only bundles another struct's constructor arguments is such a wrapper; expose the fields or pass the arguments directly instead. Apply SOLID to real component boundaries, not to every type.

## Hexagonal architecture and physical modules

The directory structure must reflect responsibilities and dependency boundaries:

- `src/domain/`: pure entities, values, and rules; no filesystem, process, Git, SQL, HTTP, or CLI orchestration.
- `src/service/`: application-owned traits and concrete application services. Define all application-owned traits directly in `service/mod.rs`; collect public shared service data/value/request/response types in `service/types.rs` and all service errors, diagnostics, failure records and result aliases in `service/error.rs`; keep each concrete service struct and its implementations in a separate responsibility-named file, with unit tests in a sibling `*_test.rs` file. Only concrete service implementation files, the central `mod.rs`/`types.rs`/`error.rs` contracts, and a private `utils.rs` for helpers shared by services belong directly in `src/service/`. Helpers used by only one service stay private in that service file; do not create a service just to wrap helpers. Keep `src/service/` flat: production helpers are ordinary private items in their owning service file, unit tests live in sibling `*_test.rs` files. Production code precedes tests. Services depend on domain types and their interfaces, not concrete technology implementations.
- `src/git/`, `src/storage/`, `src/embedding/`, `src/markdown/`, `src/filesystem/`, and `src/process/`: separate responsibility-named modules, introduced when their tasks implement them. Concrete structs implement the application-owned traits. These modules do not orchestrate one another.
- `src/cli/`: argument parsing (`input.rs`), help text (`help.rs`), typed results and the shared background step (`response.rs`), and output formatting (`output.rs`). It does not construct services or adapters or access the environment; the shared background step may call the injected application interface. Business rules belong to services/domain.
- `src/lib.rs`: composition root with actual constructor calls wiring adapters into services through interfaces, plus the public `wire_*`/`open_*` constructors. Module declarations and reexports alone are not composition.
- `src/commands.rs`: per-command wiring. `run_request` selects the command from a typed `Request`, builds the services that command needs through the `lib.rs` constructors, calls the service, and finishes with `cli::finish_foreground` (or builds the response directly for status, drain and help).
- `src/main.rs`: thin CLI entry point using the assembly from `lib.rs`.

Use `trait` for component interfaces and concrete `struct`/`impl` for implementations. Do not introduce `ports/`, `adapters/`, or `contracts/` directory layers. A module's `mod.rs` defines its interface, declares children, and explicitly reexports the necessary types. Put each concrete implementation's struct, inherent methods, and trait implementations together in its own file, for example `git/repository.rs` or `storage/cache.rs`; keep implementation bodies out of `mod.rs`. Keep every application-owned trait declaration in `service/mod.rs`, including storage and transaction interfaces; do not split them into private trait files. Shared public service types and their pure validation stay together in `service/types.rs`; service failures and error-result aliases stay in `service/error.rs`. Both modules are public and explicitly reexported from `service/mod.rs`. Domain types and technology-private errors remain in their own layers. Keep implementation details private and expose only the necessary API. Add modules with real functionality; do not scaffold future subsystems or trivial forwarding services. These rules describe the implemented layout; historical TK-9 plans retain the migration steps and paths of their captured revision.

Declare production modules in separate files with `mod name;`. Do not create a separate module or file for a function or struct used from only one place: keep it in the file that uses it and preserve the caller-abstraction order there. Inline `mod name { ... }` blocks are not used. Each source file has at most one test file. Unit tests for a module live in a sibling `<module>_test.rs` file declared at the end of that module's file with `#[cfg(test)] #[path = "<module>_test.rs"] mod tests;`, so tests stay children of the module they test and keep private-item access; keep test helpers after the tests in that file. When one file previously had several test modules, merge them as nested modules in that single test file.

Shared `src/utils.rs` and private module-local `utils.rs` are allowed for useful helpers; see [code reading order](#code-reading-order) for when to extract them. Keep domain rules and technology-specific behavior in their owners; utilities must not bypass module boundaries.

Keep the DDD boundary explicit: entities and value objects own domain data, local invariants and pure behavior; they have no storage, filesystem, Git, HTTP, service or injected infrastructure dependencies. Application services own use-case orchestration and dependencies through small application-owned interfaces. Algorithms that incrementally load graph data belong to a service such as `GraphService`, while `Graph` remains dependency-free domain data. Avoid pass-through services, factories and extra interface layers that add no responsibility.

### Infrastructure component boundaries

- Each cohesive infrastructure responsibility has one main concrete implementation struct implementing its required application-owned traits. Retain separate structs for genuinely independent owners, such as `CacheStorage` and `VectorStorage`, or for actual resource guards, values and algorithm state; do not add structs solely to bundle constructor arguments or forward calls.
- A component's interfaces, types, errors and policies use its own concepts. Git owns repositories, worktrees, indexes, ignore rules, objects and references; services/composition own Markdown-candidate selection and application-specific private-path inclusion. Markdown owns the project's X-4 Markdown syntax and its parsed values; it does not orchestrate Git, filesystem, storage or providers. Embedding owns provider/model/vector/HTTP protocol behavior. Process owns generic processes, signals and I/O; consumers choose application commands. CLI owns request, command and output representation and calls injected services.
- A trait method may delegate to a same-named private free function outside `impl` when that keeps the implementation clear. Pass `self` or the required resource handles directly, keep the struct and its trait implementations together in their owning file, and place helper functions according to the code-reading and utility rules. This does not add a proxy component, move application orchestration into an infrastructure component, or change the receiver rule for services' injected collaborators.

### Cache storage

- The `.letopis/` databases are a rebuildable cache, not user data. Do not add schema migrations, legacy-format conversion or other backward-compatibility paths for changes to the storage schema or behavior: after such a change the user recreates the cache from the existing knowledge files. Keep only the validation and failure behavior the current task explicitly requires for invalid or incompatible state.

### Filesystem boundary

- The filesystem component and its interfaces speak only in file/filesystem terms: files, directories, paths, bytes, metadata, permissions, identities, symlinks and locks. Database, cache, vector, embedding, configuration, knowledge and command roles do not belong in filesystem interface names, methods, parameters, return types or errors. A database file is an ordinary file at this boundary.
- Keep application-specific filenames, file roles, content interpretation and policies with their consumers or composition; SQLite connections, schemas, transactions, WAL and attachments belong to storage. Expose generic file operations rather than `get_config`, `get_database_exists`, `lock_embed` or role-specific interfaces such as `EmbeddingFiles`, `StatusFiles` and `InitFiles`. Filesystem failures use file-specific errors; consumers map them to their own errors. Fallible I/O must preserve permission, unsafe-path and other I/O failures as typed file errors rather than silently treating them as absence. A filesystem predicate may return `bool`, `Result<bool, FileError>` (or `FileResult<bool>`) or another appropriate type according to the operation's contract.
- Prefer one concrete `LocalFileSystem` implementing the required file-related interfaces. Do not add a filesystem component or wrapper such as `DatabasePaths` for each consumer or file role. Private values and RAII guards are appropriate only for real per-operation observations, owned resources or lifetimes. Preserve confinement, no-follow checks, file/directory identities, replacement detection, alias checks and lock ownership while simplifying; do not retain stale observations as permanent component state.

## Naming

A name must state what the value is or what the operation does, readable on its own. Keep one name for one concept, never use a plural noun for one object (`files` for one filesystem, `storage` for one database), and never reuse one word for two different kinds of value in the same scope. Prefer standard programming and computer-science terms over invented or domain metaphors.

- Name each value for what it contains, using its origin only as a qualifier. Use `source_hash` for the hash of addressed source bytes, `knowledge_hash` for the hash of knowledge text, `snapshot` for a Git tree, `current` for working-copy data, `source_address` for a source address and `line_range` for a line range. Do not substitute vague or invented labels such as `historical` or `selector` for these concepts. Apply this consistently to types, functions, parameters, variables and comments.

### Types, modules and files

- Name types by responsibility or technology (`CacheDatabase`, `CacheStorage`, `GitSnapshots`, `GitRepository`), without `Port`/`Adapter` suffixes.
- Every concrete application service struct is named with the `Service` suffix (`CheckService`, `SearchService`); the traits it implements keep role names (`Checker`, `Searcher`).
- Name source files after the one responsibility they own, using standard programming and computer-science terms. A file name must be unambiguous on its own: name the concrete concept the file implements, never a vague role (`utils`, `common`, `helpers`, `misc`, `manager`, `processing`) and never the abstract result of the work. `utils.rs` is the agreed exception, and only for helpers shared within its own scope.

### Functions and methods

- Compose function and method names from a verb and the entity it operates on. The basic verbs are `create`, `build`, `update`, `delete`, `get`, `sync`, `upsert` and `verify`; when none of them states the operation, use another standard verb. Do not invent a verb or a domain metaphor (`ref_update_by_oid`, not `snapshot_pin_by_oid`). Keep `validate_*` for input/schema validation, `is_*` for predicates, `map_*` for mappings, and established constructor/conversion forms such as `new`, `new_with_cause`, `as_str`, `to_hex` and `into_inner`.
- Name a function for the concrete operation it performs, using standard programming and computer-science terms. Do not name it after the abstract result or quality of the operation: write `loose_object_sync_by_oid` (the function synchronizes an object file and its directories) rather than `object_confirm_durable` (`durable` is the outcome, not the action). The same applies to comments: state the operation (`Synchronizes the object file and its parent directories to disk`), not the quality it produces.
- Except for infrastructure component operations and their application-owned trait methods governed by the infrastructure rules below in this section, name custom functions and methods with verbs or verb forms describing their action: `get_entries`, `build_command`, `verify_object`, `get_kind`, `is_empty`, `has_exact_ref`. Use `get_` for custom accessors rather than bare nouns. Keep established Rust constructor/conversion forms (`new`, `new_with_cause`, `as_str`, `to_hex`, `into_inner`) and names required by external or standard-library traits (`fmt`, `source`, `drop`). Application-owned traits and their implementations follow these conventions and must be renamed together. Apply the rule to test helpers; test names describe the behavior being verified. Name verification operations `verify_*` (`verify_object`, `verify_basis`, `verify_discovery_unchanged`); keep `validate_*` for input/schema validation and `is_*` for predicates.
- Except for infrastructure component operations and their application-owned trait methods governed by the infrastructure rules below in this section, use `get_<entity>` for retrieving data from a database, filesystem, external service or in-memory value. Do not introduce synonyms such as `read_`, `fetch_`, `load_` or `list_` for the same retrieval operation. This applies to single values and collections; names required by external APIs or external/standard-library traits remain unchanged.
- Except for infrastructure component operations and their application-owned trait methods governed by the infrastructure rules below in this section, name filtered retrieval methods as `get_<entity>_by_<filter>`, joining multiple filters with `_and_`, for example `get_edge_by_source_id_and_target_id(...)`. Retrieval methods without filters do not need `_by_`.
- Name infrastructure component operations, their application-owned trait methods and the private functions implementing them `<entity>_<action>_by_<filter>_and_<filter>`, using entities from the component's own context and omitting `_by_` when there is no filter. For example, use `file_get_by_path`, `tree_verify_by_oid`, `file_parse` and `process_spawn`. Preserve constructor/conversion forms and names required by external traits. Application-service use-case methods keep their responsibility-based names; storage transaction scopes and multi-statement operations retain the explicit exceptions below.
- Name storage SQL query functions and their application-owned trait methods `<table>_<action>_by_<filter>_and_<filter>`, using the exact schema table and column names and the actions `save`, `get`, `delete`, `upsert`, or `update` (for example, `edges_get_by_source_id`, not `edges_get_by_source`). Omit `_by_` when there is no filter. Each query function performs one database action; do not combine actions in one name or function, such as `get_or_insert`. Keep related actions inside the same transaction when atomicity requires it. This table-first rule applies to individual SQL queries and their storage trait methods; transaction scopes and multi-statement operations keep responsibility-based names.
- Name filesystem operations and their application-owned trait methods `<entity>_<action>_by_<filter>_and_<filter>`, following the same entity/action/filter order as storage queries. Use filesystem entities such as `file`, `directory`, `symlink` and `lock`, for example `file_get_by_path`, `file_get_metadata_by_path`, `file_delete_by_path`, `directory_create_by_path`, `symlink_get_by_path` and `lock_acquire_by_path`. Omit the filter suffix when there is no filter. Do not substitute a consumer's database, embedding or command terminology for those entities. Traits and their implementations use the same names; names required by external or standard-library traits remain unchanged.
- Name filesystem predicates `<entity>_is_<condition>`, including the generic file-presence predicate `file_is_exist(...)`, regardless of whether the file contains a database, configuration or other content; do not introduce role-specific existence methods.
- Name a type-mapping function `map_<source>_to_<target>` after its concrete source and target types, for example `map_file_error_to_storage_error`. When several distinct mappings share one source/target pair, name each by the classification it applies (`map_constraint_error_to_storage_error`) or consolidate them into one function; do not use an open-ended `map_embedding_error_to_command_error`, `map_match` or `map_file_error_to_embedding_error` that hides either side.
- An error builder with no input is allowed when it is passed as the function value of `ok_or_else`, because that call supplies the missing input: name it `build_<classification>_error`.
- Name storage closure scopes `with_read_tx`, `with_write_tx` and `with_status_read_tx`. Callbacks take no transaction argument; operations use the injected storage owner. External API names remain unchanged.

### Values and fields

- Name map variables, parameters and fields `<values>_by_<key>` so the name states both the stored values and their key, for example `line_byte_ranges_by_line_number` or `nodes_by_id`. Join composite key names with `_and_`, for example `hashes_by_tree_and_source`. Apply this rule to new and touched map names.
- Name every boolean value with the `is_` prefix, reading as the fact it asserts: predicates and functions returning `bool` (`is_ready`, `is_same_identity`), and variables, parameters and fields that hold a boolean (`is_eligible`, `is_missing`). Exceptions: an infrastructure predicate keeps its `<entity>_is_<condition>` form (`file_is_exist`, `ref_lock_is_busy`); persisted schema column names and serialized wire fields keep their exact names; boolean parameters read as the fact they assert (`is_eligible`, `is_missing`) unless they mirror a persisted column or a serialized wire field; and an operation that reports success as part of a side effect keeps its verb name (`lock_try_acquire`).
- Name every variable, parameter and field consistently with its type: use the type's own words in `snake_case` instead of a synonym that could describe something else — `filesystem` for a `LocalFileSystem`, `file_reader` for a `FileReader`, `file_writer` for a `FileWriter`, `cache` for a `CacheDatabase`, `vector_database` for a `VectorDatabase`. A trait-object parameter may use the shorter role name (`provider`) only when no other value in the same scope could be confused with it.
- Prefer descriptive variable and parameter names based on their type and role, in the style of JetBrains IDE name suggestions; use idiomatic Rust `snake_case` and retain exact schema column names where applicable. Name paths by their actual role, for example `start_path` for the command invocation path, `root` for the discovered worktree root, and `service_directory` for the managed `.letopis` directory. Prefer parameter names that state the contract role (`path`, `root`, `start_path`, `entries`, `deadline`) over generic names (`value`, `data`, `input`, `arg`) or type echoes.
- Use database schema names for columns and corresponding parameters; do not invent synonyms. Parameters that are not columns, such as attempt limits, cursors and search expressions, should describe their actual role.
- Name mutex fields and shared mutex handles with the `_mutex` suffix, such as `completion_mutex`. Name the acquired guard for the state it protects. Apply this rule to new and touched fields.
- Replace meaningful repeated domain/protocol literals with clearly named constants near their owning module; use SCREAMING_SNAKE_CASE. Do not replace literals mechanically or collect unrelated constants in a global bag.

## Rust conventions

- Follow the pinned toolchain in `rust-toolchain.toml` and lint policy in `Cargo.toml`; [development guide](docs/development.md) explains the checks.
- Import types with `use` instead of repeating long `crate::...` paths at call sites. Write enum variants through the imported type, for example `SnapshotErrorKind::InternalError`. Prefer explicit imports over wildcard imports.
- Every function performs exactly one action. Do not combine validation with construction or retrieval: a `validate_*`/`verify_*` function returns `()` and takes the value it checks, while parsing, construction and returning the value stay with the caller. The same applies to any function whose name promises one action but also builds and returns a value.
- Keep functions and methods focused: aim for about 40 lines, with 60 lines as the upper limit. Split longer implementations into cohesive named helpers, not arbitrary wrappers or compressed formatting. Apply the same rule to tests and test helpers.
- Use ownership and borrowing deliberately; add cloning, shared ownership, locks, or dynamic dispatch only for an actual need.
- Prefer unique ownership and explicit borrows; use `Rc`/`Arc` only when shared ownership is required.
- Keep dispatch simple and deliberate. Use concrete types for domain data and implementations; use traits for required component boundaries. Add generics only when type variation, reuse, or a scoped associated type requires them and they keep the API clear. Prefer object-safe `dyn Trait` fields for service dependencies when a generic parameter only selects an injected implementation; do not propagate generic parameter lists through services and public signatures solely for dependency injection. Retain generics for concrete needs such as associated lock types. Choose borrowed or owned access according to the actual lifetime, without adding a Box, Arc, factory or wrapper unnecessarily. CacheDatabase and VectorDatabase use generic closure methods and require concrete type parameters; share the same owner through Rc when collaborating services must join a scope. Do not introduce boxed transaction interfaces or storage GAT. Preserve required lifetimes and necessary generics for lock capabilities or remaining non-object-safe interfaces, without extra forwarding layers. Do not mechanically replace existing generics or mandate static/dynamic dispatch everywhere.
- Do not use `unwrap`/`expect` in production code; return a typed `Result`. `expect` is allowed only for an invariant guaranteed by construction; mark it `#[expect(clippy::expect_used, reason = "...")]` and state the invariant in the reason. Tests may use both. A detected programming bug is a panic, an expected failure is an error.
- Use `match`, `if let` or `let ... else` instead of `is_some()`/`is_ok()` followed by `unwrap()`.
- Every public type implements `Debug`.
- Model finite alternatives with enums and expected failures with typed `Result`. Document public APIs as described in [readability and documentation](#readability-and-documentation). Preserve useful internal error causes while keeping public diagnostics free of secrets and raw knowledge/provider/subprocess payloads.
- Do not create a function solely to return a fixed response with no input, even when the construction is repeated; construct the value at the call site. Repeated message text may be a named constant. An error-mapping function that takes one error and returns another is allowed and is reused at every matching call site. This does not prohibit trait-required constructors or builders that perform meaningful work.
- In `.map` and `.map_err` chains, use a named mapper function instead of an inline closure so the chain stays readable: `...map_err(map_file_error_to_storage_error)?`. Name each mapper `map_<source>_to_<target>` and reuse it at every matching call site.
- Compose ordinary storage queries with SeaQuery and typed table/column identifiers; execute through rusqlite using bound values from the private storage/query.rs helper. Keep builder types inside storage. Raw SQL is reserved for schemas, SQLite introspection/PRAGMAs/native probes, and specialized FTS5/vec1 search or native commands; format substantial SQL across readable lines. Never interpolate user values or render them into SQL with to_string.
- Write newly authored executable SQL keywords in lowercase, including schemas, queries and test fixtures. Preserve string literals and bound values; keep ordinary queries composed with SeaQuery. Preserve captured historical evidence and compatibility fixtures, including intentionally uppercase legacy SQL.
- Inject service collaborators through construction and access them through `self.dependency`. Internal helpers that use collaborators are receiver methods, not functions that receive and forward those dependencies. Use private operation-scoped receivers only for meaningful orchestration. Keep domain data dependency-free and shared free helpers data-only. Storage operations require an active closure scope on their injected owner. Same-instance nested scopes join; a caught nested error or failed write makes the outer scope rollback-only. Only the outer owner finalizes. CacheStorage and VectorStorage are separate transaction boundaries; provider HTTP stays outside service-owned write scopes. Filesystem path policy belongs to filesystem and composition, not storage. Enforce explicit entry requirements for use cases that cannot safely join: drain requires inactive owners; query inference permits a cache read with an inactive vector owner. Incompatible inherited scopes become rollback-only before provider calls.
- Keep I/O synchronous according to the design; do not add an async runtime without an agreed requirement. Product Git operations belong in `src/git/` and use the pinned local Rust library in process; no Git CLI fallback, executable helper, filter, lazy fetch, or shell substitute. Git CLI remains available for author workflows, fixtures, and independent test oracles.
- Standard Clippy checks and the explicitly selected pedantic checks in `Cargo.toml` are enabled; see the development guide for each rule and its purpose. `dbg!`, `todo!`, and `unimplemented!` are denied. Do not enable all of `restriction`, `pedantic`, or `nursery` indiscriminately. Fix the underlying finding rather than adding a blanket allowance; any exception must be narrow and explain its reason, written as `#[expect(lint, reason = "...")]` rather than `#[allow]`, so the exception fails the build when it is no longer needed. Public fallible APIs document `# Errors`, and public APIs that can panic document `# Panics`.

## Code reading order

Code reads top to bottom, from abstract to concrete. Apply these rules to new and touched code only; do not reorder untouched code just to conform.

- Within owned implementation code in a file, define a caller above the functions and methods it calls. Test calls into production APIs are exempt; tests remain last. Recursive cycles cannot satisfy a strict order: keep their entry point first and related helpers together. Type and constant definitions are not calls and may be referenced from above.
- Group by level of abstraction: orchestration and abstract calls first, then intermediate steps, then low-level details. Keep methods of the same level adjacent.
- Separate top-level `struct`, `enum`, `impl`, `trait` and `fn` items, and methods directly inside an `impl`/`trait`, with exactly one blank line. Do not run declarations together.
- In centralized `service/types.rs`, preserve caller-before-callee order across value parsers: a higher-level parser's private helper may precede the lower-level value type's `impl` it invokes. Keep each type's implementation together and its fields private.
- Within an `impl`, public methods come first and private helpers last, in the order they are first called. A public method that calls another public method stays above it.
- A trait implementation declares its methods in the same order as the trait declares them; the trait order is canonical for every implementation.
- Within a file, order items as constants, types, `impl` blocks with the public API, trait implementations, then private free functions. Trait implementations such as `Display` stay next to their type. The `#[cfg(test)] #[path = "..."] mod tests;` declaration for the sibling test file comes after the production items in the module's own file.
- Place a helper by its consumers: one file keeps it as a private function at the bottom of that file; several files of one module share the module-local `utils.rs`; several modules share `src/utils.rs`. Extract only when there are at least two consumers. Do not create a dedicated module or file for a helper used from a single place; keep it private in that consumer's file. `utils.rs` files follow the same top-to-bottom order.

## Readability and documentation

Apply these rules to new and touched code only.

- Prefer early exits: `let Some(x) = value else { return ... };` and `?` over nested `match` and `if let`. Keep nesting to two levels.
- Use newtypes and enums instead of bare primitives: `SnapshotId(String)` rather than `String`. Replace ambiguous boolean arguments with explicit enum variants so call sites show their intent.
- Use newtypes for distinct domain types; aliases do not enforce type boundaries.
- Prefer named structs over tuples; reserve tuple structs for single-field newtypes.
- Group more than four use-case parameters into a request struct; consider one for four parameters when it improves clarity. Do not create a struct solely to bundle constructor arguments.
- Do not use `&mut` parameters as output: a function returns its result instead of filling an argument (`fn count(..) -> Counts`, then merge at the caller). `&mut self` for state the type owns is fine. Allowed exceptions: signatures fixed by a trait or external API (`fmt`, `Read`/`Write` streams, `rusqlite::Connection` transactions) and handles that are the resource itself, not a result container. Apply to new and touched code only.
- Use iterator chains while they read well (three or four steps); split longer chains into named steps instead of a manual loop or one long expression.
- Write explicit types in signatures; do not use `impl Trait` where it hides meaning.
- Keep files focused on one responsibility, roughly 500-2000 lines; split a file that grows far beyond that. The central service contract files `service/mod.rs`, `service/types.rs` and `service/error.rs` are explicit exceptions: keep their interfaces, shared values and errors together respectively. Service implementation files with private helpers are also an agreed exception to the file-length recommendation; keep their ownership rather than creating service subdirectories. The same file-length exception applies to `src/cli/response.rs` and the implementation files in the flat `src/git/` directory. Unit tests live in sibling `*_test.rs` files and do not count toward the implementation file length.
- Implementation comments explain why, not what: required for `unsafe`, platform workarounds, and non-obvious invariants. Do not narrate the body line by line or repeat the method name. API documentation and test phase markers follow their respective rules below.
- Spell out abbreviations in new or changed comments, including documentation and test phase descriptions. Keep referenced identifiers spelled exactly as declared.
- Document every `pub` item and interface method (including traits reexported by `service/mod.rs`) and every private method whose purpose is not clear from its name and signature. Private trivial accessors and obvious one-liners need no comment.
- A method comment starts with one sentence saying what it does, then states the contract: preconditions, what is returned, side effects, and guarantees such as atomicity or idempotence, plus `# Errors` and `# Panics` where they apply.
- Document the returned value of every commented public function or method in a `# Returns` section. State the value directly without repeating `Returns`: write `The current revision`, not `Returns the current revision`. A method returning `()` needs no `# Returns` section.
- Write method and function comments in plain words: no invented terms or jargon. Use standard programming and computer-science terms, and do not introduce extra domain vocabulary when a common term states the operation (`synchronize`, not `make durable`). The first sentence names exactly the one action the function performs, in the simplest verb that fits (`Returns the current revision`, `Writes the generated configuration`, `Rejects unsafe paths`). State the same contract in the same plain wording.
- Document every parameter of a commented method in a `# Arguments` section: one bullet per parameter naming it and describing its role, meaning, and any required invariant. This applies to constructors and trait-mandated signatures as well; the exception is the trivial private one-liners above.
- Document a trait's contract on the trait itself: what every implementation must guarantee, not only the current one. Trait methods define the API contract and need the clearest comments in the code: one plain action, every input, the returned value, every state change, and every failure stated explicitly. An `impl` comment covers only what is specific to that implementation, such as SQLite or Git behavior.
- Update a comment in the same commit that changes the behavior it describes.

## Verification

Run commands from the repository root; from elsewhere use `make -C <path> <target>`. Dependencies are locked and offline: if they have not been prepared, run `cargo fetch --locked` first. Checks never download dependencies or rewrite files; apply formatting with `make fmt`. `make check` and `make verify` print one `ok` line on success and the full output of the failed step on failure, which keeps logs small; `V=1` (for example `make check V=1`) shows every command's output.

| Command | Runs | Use |
| --- | --- | --- |
| `make check` | `cargo fmt --check`, `cargo check` (all targets), Clippy with `-D warnings`, root tests | Required for every product Rust change. |
| `make verify` | `make check`, strict Rustdoc (`RUSTDOCFLAGS='-D warnings'`), root tests in the release profile | Before claiming completion of a task that changes Rust source, Rust API documentation, or dependencies. |
| `python3 -B tests/storage/run.py --platform host\|linux --evidence <new directory>` | Schema parity, runner tests, native SQLite/vec1 capabilities, copied standalone executable and its linkage | When storage, native stack, build, or vendored inputs change. Evidence goes to a new directory, never over existing evidence. |

### Review and reporting

- A test must not assert its own ground truth: do not compute the expected value with the code under test or repeat the implementation in the assertion. Use independent literals or an independent oracle.
- A `TODO` names an issue (`// TODO(#123): ...`); otherwise fix it now or record it in the task card.
- Mutation-check the tests you write: after a test passes, temporarily break the code it covers by hand (flip a condition, change a returned value, remove a call) and confirm the test fails, then restore the code. A test that still passes does not verify that behavior; strengthen it. No tooling is required; do not leave mutations in the tree.
- New or modified unit and integration tests must use fully described Given, When, Then phases; untouched active tests remain a retrofit backlog, not evidence of repository-wide compliance. Structure each test as Given, When, Then: prepare inputs/fixtures, execute the behavior, then check results. Mark the phases with explicit `// Given`, `// When`, `// Then` comments in Rust and `# Given`, `# When`, `# Then` in Python. Repeat phases for genuinely sequential scenarios; use a combined `When / Then` comment when an assertion directly executes the behavior. Follow each marker with a short colon-separated comment of at most two sentences saying what this phase sets up, does or expects, e.g. `// Given: a repository with one stale link`, `// When: the check runs`, `// Then: exactly one finding is reported`. Keep helpers private and scenario assertions visible.
- Test meaningful behavior and failure paths for behavioral changes. Import-only or documentation-only edits do not need new behavioral tests.
- Before claiming completion, verify the actual changed tree. Report exact commands/results and any unrun checks or platform limits.
- Review physical files, visibility, trait implementations, import direction, and `lib.rs` wiring; a passing linter alone does not establish architectural compliance.
- Root checks do not execute historical proof harnesses with their own manifests. Run the relevant harness or platform runner when the change requires it; do not imply unrelated suites were rerun.
- Preserve historical evidence against its captured revision. Store new evidence separately and update the relevant task/spec/plan with findings, decisions, and limits. For Markdown-only edits, check affected links and consistency. Changes to Rust source, Rust API documentation or dependencies require `make verify`.

## Workspace and memory

- Inspect the current branch/worktree and dirty files first. Preserve user edits and unrelated work; do not stash, reset, overwrite, or clean them away.
- Keep changes in the intended task worktree. Commit only the intended paths. Merge, push, publish, and update GitHub issues when authorized by the user; preserve authorization already given in the conversation.
- Use the Letopis skill in `skills/letopis/` for repository knowledge.
- For preparing or publishing a Letopis release, use [letopis-release](skills/letopis-release/SKILL.md); its release content requires explicit user approval before publication.
